# 에이전트와 스킬 사용 안내

상태: 사용자 요청 반영 / 검토일: 2026-10-27 / 적용 범위: travel_APP의 기획·개발·검증 작업

이 문서는 누가 일을 맡고, 어떻게 결과를 확인하는지 설명합니다. 기존 프로젝트 규칙은 [AGENTS.md](../../AGENTS.md)를 따릅니다.

## 기획은 어떤 순서로 하나요?

항상 큰 단위부터 정하고 작은 단위로 내려갑니다. 문서도 같은 순서로 설명합니다.

1. **서비스 목적:** 누구의 어떤 불편을 해결할지 정합니다.
2. **전체 사용자 흐름:** 사용자가 처음 들어와 목적을 이루기까지의 길을 그립니다.
3. **기능 범위와 우선순위:** 그 길에 필요한 기능과 먼저 만들 것을 정합니다.
4. **페이지별 역할과 이동:** 각 화면이 하는 일과 다음에 갈 화면을 정합니다.
5. **세부 동작:** 버튼을 누르면 생기는 일, 필요한 데이터, 실패했을 때의 처리를 정합니다.
6. **개발과 검증:** 만들 작업을 나누고 어떤 결과가 나와야 완료인지 정합니다.

예를 들어 ‘여행 계획을 쉽게 만든다’는 목적을 먼저 정합니다. 그다음 ‘여행 만들기 → 날짜 정하기 → 일정 넣기’ 흐름을 정하고, 마지막에 날짜 선택 화면의 버튼과 오류 안내를 구체화합니다. 이 예시는 기획 순서를 설명하며 앱의 새 정책을 확정하는 내용은 아닙니다.

각 세부 기능이 어느 상위 목적과 흐름에 필요한지 설명합니다. 상위 방향이 미정이면 가정과 결정할 사항을 먼저 적고 관련 세부 사항을 확정으로 표시하지 않습니다. 이미 정한 큰 방향은 확인해 이어갑니다. 작은 수정도 전체 흐름에서 어디에 해당하고 무엇에 영향을 주는지 먼저 확인합니다.

## 누가 무엇을 하나요?

| 담당자      | 하는 일                                                                    | 끝낼 때 전달할 내용                 |
| ----------- | -------------------------------------------------------------------------- | ----------------------------------- |
| 주 에이전트 | 사용자 요구를 정리하고 기획합니다. 요청받은 개발과 실제 검사를 진행합니다. | 바뀐 내용, 검사 결과, 남은 문제     |
| 분석 담당   | 문서와 코드를 읽고 공식 자료를 조사합니다.                                 | 확인한 사실, 출처, 아직 모르는 부분 |
| 검토 담당   | 빠진 조건과 오류 상황을 찾습니다.                                          | 문제의 영향, 고칠 기준, 필요한 검사 |

간단한 작업은 주 에이전트가 맡습니다. 나눠 조사할 필요가 있을 때만 분석·검토 담당을 부릅니다. 동시에 일하는 인원은 주 에이전트를 포함해 최대 3명입니다.

분석·검토 담당은 파일을 바꾸거나 테스트를 실행하지 않습니다. 따라서 검토 의견만으로 앱이 정상 작동한다고 결론 내리지 않습니다. 실제 조작과 검사는 주 에이전트의 책임입니다.

## 읽기 전용은 무엇을 뜻하나요?

현재 역할 지시는 파일을 수정하지 말라는 약속입니다. 파일 쓰기 권한을 별도로 없애는 장치는 아닙니다. 권한 요청 기능을 꺼도 이미 가진 쓰기 권한은 남을 수 있습니다. 실제 쓰기를 막아야 하는 조사에서는 부모 세션부터 읽기 전용 환경을 사용합니다.

역할 파일이 부모의 권한을 별도로 바꾸지 못한다는 점은 [공식 에이전트 문서](https://learn.chatgpt.com/docs/agent-configuration/subagents)를 기준으로 확인했습니다. 설정 변경 뒤에는 문법 검사와 새 세션의 실제 반영 여부를 구분해 보고합니다.

## 문서는 어떻게 쉽게 쓰나요?

화면마다 아래 질문에 차례대로 답합니다.

1. 이 화면은 왜 필요한가요?
2. 사용자는 무엇을 누르거나 입력하나요?
3. 그러면 앱이 무엇을 보여주나요?
4. 실패하면 사용자는 무엇을 하면 되나요?

예를 들어 여행 저장 기능은 이렇게 설명합니다.

> 여행 이름과 날짜를 입력한 뒤 ‘저장’을 누릅니다. 저장이 끝나면 내 여행 목록에 새 여행이 보입니다. 저장에 실패해도 입력한 이름과 날짜는 그대로 남습니다. 사용자는 내용을 다시 쓰지 않고 ‘다시 저장’을 누르면 됩니다.

이 문장은 설명 방식의 예시이며 현재 구현이 검증됐다는 뜻은 아닙니다. 실제 기능 문서에는 구현된 동작과 확정된 정책을 적습니다. 어려운 용어는 처음 나올 때 뜻을 설명합니다. 서버 주소나 데이터 항목 같은 개발 정보는 뒤쪽 표나 부록에 정확히 남깁니다. 쉬운 말로 바꾸면서 조건과 예외를 빼지 않습니다.

## 스킬은 언제 쓰나요?

스킬은 담당자가 참고하는 작업 설명서입니다. 설치된 스킬을 모두 실행할 필요는 없습니다.

| 작업           | 사용할 스킬과 기준                                                                             |
| -------------- | ---------------------------------------------------------------------------------------------- |
| 코드 작성      | `global-work-rules`와 AGENTS.md 3절. 함수는 한 가지 책임을 맡고 필요한 이유에만 주석을 씁니다. |
| 한글 작성      | `humanize-korean`으로 표현을 점검하고 위 질문으로 내용이 쉬운지 확인합니다.                    |
| Word 문서      | `documents`로 문서를 만들고 실제 페이지를 확인합니다.                                          |
| UI 설계·수정   | `ui-ux-pro-max`를 참고하되 현행 디자인 문서를 우선합니다.                                      |
| 앱 설치 아이콘 | `icon-generator`를 사용합니다. 화면 안의 아이콘은 기존 UI 체계를 따릅니다.                     |

여행 앱에만 필요한 규칙은 이 프로젝트에서 관리합니다. 공용 스킬에 여행 앱의 고유 정책을 넣지 않습니다. 디자인 기준은 기존 공통규격 문서에서만 관리합니다.

## 실제로 작동하는지는 어떻게 확인하나요?

자동 검사는 코드의 오류를 찾는 데 도움이 됩니다. 화면을 직접 눌러 확인하는 검사와 실기기 검사는 따로 기록합니다. 아래 양식을 해당 작업의 검수 보고에 복사합니다. 증거 파일은 `outputs/`에 두고 다른 환경에서도 이해할 수 있도록 결과를 보고서에 요약합니다.

| 항목              | 기록할 내용                                                                              |
| ----------------- | ---------------------------------------------------------------------------------------- |
| 검사 ID·대상 버전 | 검사 이름, 커밋 또는 작업 버전과 미커밋 변경 범위                                        |
| 검사 종류·환경    | 자동 검사 / 실제 웹 조작 / 실기기, 기기·브라우저·앱 버전, 서버 환경, 가짜 응답 사용 여부 |
| 사전 조건         | 로그인 여부, 필요한 여행 상태. 계정 비밀번호 등 비밀 값은 제외                           |
| 조작 순서         | 사용자가 실제로 누르고 입력한 순서                                                       |
| 기대 결과         | 무엇이 보여야 하고 무엇이 저장돼야 하는지                                                |
| 실제 결과         | 관찰한 화면과 저장·재조회 결과                                                           |
| 판정              | 통과 / 실패 / 미검증 / 해당 없음                                                         |
| 증거·후속 조치    | 로그·화면 위치, 미검증 또는 해당 없음의 이유, 남은 검사와 담당                           |

저장을 바꿨다면 목록에 나타나는 것만 보고 끝내지 않습니다. 화면을 나갔다 돌아와 다시 조회해 같은 내용이 남는지도 확인합니다. 실패 시 입력 유지와 재시도는 해당 기능의 정책에 맞춰 확인합니다. 가짜 응답으로 통과한 검사를 실제 서버 저장 성공으로 보고하지 않습니다.

실기기나 계정이 없어 검사하지 못했다면 ‘미검증’으로 씁니다. 코드가 없으면 미구현 사실을 적고 완료로 표시하지 않습니다. 검사에서 기대 결과와 다른 동작이 나오면 ‘실패’입니다. ‘해당 없음’은 검사 자체가 이번 변경에 적용되지 않을 때만 씁니다.

## 재검토는 몇 번 하나요?

처음 검토한 뒤 같은 문제는 최대 2회 다시 검토합니다. 주 에이전트가 아래 기록을 맡습니다. 설정 파일이 횟수를 자동으로 세지는 않습니다.

| 쟁점 ID   | 대상·버전   | 검토 단계                    | 바뀐 내용 또는 새 근거 | 결과·남은 문제        | 검토자·날짜      |
| --------- | ----------- | ---------------------------- | ---------------------- | --------------------- | ---------------- |
| 작성할 ID | 파일과 버전 | 최초 0 / 재검토 1 / 재검토 2 | 재검토하는 이유        | 결론, 영향, 다음 행동 | 담당 역할과 날짜 |

검토를 맡길 때 이 기록도 함께 전달합니다. 변경이나 새 근거가 없으면 반복하지 않습니다. 같은 문제의 파일명·담당자·버전이 달라져도 횟수를 초기화하지 않습니다. 새로운 문제는 기존 문제와 무엇이 다른지 적습니다.

두 번째 재검토에도 문제가 남으면 사용자에게 근거·영향·선택지를 설명합니다. 다만 이 제한을 이유로 수정 후 필요한 테스트를 생략해서는 안 됩니다. 의견을 다시 검토하는 횟수와 실제 테스트 실행은 구분합니다.

## 완료 보고에는 무엇을 쓰나요?

바뀐 파일과 이유, 실행한 검사와 결과, 실행하지 못한 검사와 이유, 남은 문제를 씁니다. ‘스킬 설치’, ‘지침 읽기’, ‘도구 실행’, ‘결과 확인’은 서로 다른 단계입니다. 수행한 단계까지만 완료로 보고합니다.
