## 원인과 수정

### OCR

이전 503의 세부 원인은 당시 로그로 확정할 수 없습니다. 같은 합성 영수증을 현행 코드로 직접 인식했을 때 실제 공급자는 성공했고 38.7초가 걸렸습니다. 기존 서버 제한 45초·앱 제한 55초에 여유가 적었습니다. 이를 공급자 장애나 시간 초과로 확정하지 않습니다.

서버는 60초, 새 앱 소스는 75초로 맞추고 모델 추론 강도를 low로 명시했습니다. 설정 누락·시간 초과·공급자 실패·빈 출력·잘린 출력·JSON 오류·초안 계약 오류를 내부 단계로 구분합니다. 사용자에게는 기존 OCR_UNAVAILABLE 응답을 유지하며, 원본·키·공급자 오류 원문은 로그에 남기지 않습니다. 코드 펜스 주변 공백을 허용하되 금액·통화·날짜·품목을 추정하거나 잘못된 값을 자동 보정하지 않습니다.

실제 staging에서는 인식 결과1200엔·품목2개, 같은 원본 캐시, 확인 전 기록 미생성, 확인 저장 후1500엔으로 수정, 같은 영수증·경비 ID 재조회가 통과했습니다. 마지막 신규 인식은 약8초였습니다. 속도 개선의 원인을 설정 변경만으로 단정하거나 이후 응답 시간을 보장하지 않습니다.

별도 OCR 계정이나 Vision 키는 필요하지 않습니다. 현재 Cloudflare AI 바인딩의 실제 성공을 확인했습니다. 계정의 이용량·결제 한도는 계속 관리해야 합니다.

### 항공 조회

실패 원인은 두 가지였습니다.

- 로컬에 등록한 KAC 키와 달리, 배포 서버에는 KAC_FLIGHT_SERVICE_KEY와 FLIGHT_LOOKUP_LIMITER가 없었습니다. 기존 로컬 키의 실제 조회 성공을 확인한 뒤 staging Secret으로 등록하고 사용자별 분당6회 제한을 연결했습니다. 새 공공데이터 계정이나 키 재발급은 필요하지 않습니다.
- 설정 연결 뒤에도503이 남았습니다. 현재 사용 중인 workerd에서 redirect:error가 TypeError를 내며 외부 호출 전에 중단되는 것을 A/B 검사로 재현했습니다. Node fetch 모의 검사만으로는 발견되지 않았습니다. redirect:manual로 바꾸고3xx 응답은 따라가지 않고 거부합니다. 임의 주소로 키를 재전송하지 않습니다.

staging의 실제 인증 요청에서 RS901 김포06:00→제주07:15를 세 차례 정상 반환했습니다. 제공되지 않는 도착 시각·터미널을 추정해 채우지 않습니다. 이번 성공은 당일 국내 지원 구간의 증거이며 해외 출발·인천 국제선·과거/먼 미래의 모든 편을 지원한다는 뜻은 아닙니다. 제공 범위는 [기존 실제 조회 분석](<../../03. 개발/01. API계약/항공편_실제데이터분석.md>)을 따릅니다.

기본 npm run test:cloud에도 새 KAC 전송 회귀를 포함했습니다. 배포 후 바뀐 API 후보 파일은 이 검사 명령을 담은 package.json뿐이며, 서버 실행 소스는 최종 staging 버전과 일치합니다. 배포 당시 API 해시는6e78a6b0a63cf075586c5ea89ce98423942d8197442050272d2b0ef84682115b로 별도 보관했습니다.
