## 판정 기준

- **정상 동작:** 해당 행의 핵심 행동을 실제 앱 웹 화면 또는 실제 로컬 서버·DB로 실행한 통과 근거가 있다. 통제 응답을 쓴 검사는 이를 명시한다. 모든 입력 조합·실기기·운영 환경의 정상까지 보증하지 않는다.
- **미구현:** 필요한 진입·처리 연결이 없음을 코드와 화면에서 확인했다.
- **오류:** 기대 동작과 다른 결과를 실행해 재현했다. 동일 원인이 여러 행에 걸치면 영향 항목은 각각 표시하되 개발 작업은 한 건으로 묶는다.
- **미검증:** 구현은 있지만 핵심 동작 또는 행에 포함된 필수 플랫폼·외부 연동·예외의 실행 근거가 부족하다. 고장으로 단정하지 않는다. 일부 통과 결과도 함께 남긴다.

복합 행은 알려진 오류를 우선한다. 웹에서 대신할 수 없는 촬영·Play 업데이트·실제 Google 인증·OS 공유가 핵심이면 미검증으로 둔다. 카탈로그에 없던 세부 기능을 별도 행으로 추가해 78개 합계를 바꾸지 않는다. 관련 공백은 추가 결정 목록으로 관리한다.

오류 4행 중 Page04_01·Page12_02·Common02는 **같은 G01 복귀 결함**이다. Page09_23은 **G03 공유 거절 후 복사 대안 부족**이다. 재현 원인은 2건이다. 미구현 Page02_06은 G02 비밀번호 복구다. G04 앱 직접 열기와 L01 기기 여행 이전은 복합 행의 관련 공백으로 별도 계획한다.

## 우선순위와 개발 작업

이 문서의 P1·P2는 이번 보완 작업의 순위이며 기존 영수증 MVP의 P0 범위를 재정의하지 않는다. 현재 근거로 데이터 손실·권한 유출을 새로 확정한 P0 결함은 없다. 이후 재현되면 즉시 P0으로 올리고 다른 작업보다 먼저 처리한다. 미검증을 낮은 중요도로 간주하지 않는다. 계정·파일·권한 관련 검증은 출시 전에 끝내야 한다.

## 실행 순서와 인계

1. **재현 기준 고정:** G01·G03 재현과 G02 부재를 그대로 보존한다. 각 작업은 영향을 받는 Page ID와 성공/실패 조건을 연결한다. V3·V7·V8의 부족한 실행 근거를 확보하고 실패가 있을 때만 수정 범위를 늘린다.
2. **즉시 수정:** F1과 F3은 앱 내부에서 완결되는 수정으로 먼저 처리한다. F2는 발송·세션 정책 결정을 병행한 뒤 앱·서버를 연결한다. 대기 중인 외부 설정 때문에 F1·F3을 중단하지 않는다.
3. **기능별 회귀:** 수정된 실패 시나리오와 정상 경로를 함께 검사한다. 변경 유형에 맞는 인증·API·헤더/이탈 테스트 및 `npm run check`를 통과시킨다. 모델·DB 변경이 있으면 객체사전·API 계약·마이그레이션 순서도 갱신한다.
4. **외부·실기기 인수:** V1·V2·V4·V5·V6을 승인된 테스트 환경에서 실행한다. 접근 조건이 없으면 미검증 상태와 필요한 조건을 남긴다. 검사할 수 없다는 이유로 정상으로 전환하지 않는다.
5. **범위 확장 판단:** D1~D3은 결정 전 구현 완료 일정에 넣지 않는다. 채택 시 별도 수용 기준과 작업을 만들고 현재 지원 범위를 바꾸는 문서도 함께 갱신한다.
6. **최종 인계:** 이 78행의 판정을 실행 로그·빌드 식별자·기기·환경·남은 차이와 함께 갱신한다. 하나의 원인으로 여러 행을 정상 전환할 때도 각 경로 회귀가 있어야 한다. 사용자가 실제 화면과 미검증 항목을 확인한 뒤 출시 여부를 결정한다.

담당은 개인 이름 대신 PD·앱·서버/데이터·QA 역할로 정의했다. 일정은 외부 계정·기기·발송 정책과 구현 규모를 확인한 뒤 산정하며 근거 없는 완료 날짜를 약속하지 않는다. 에이전트는 주 담당 포함 최대 3명, 분석·검토는 읽기 전용으로 운영한다. 이번 대조는 역할별 최초 1회이며 불필요한 반복 검토는 하지 않았다.
