1. 실제 Google 로그인·복귀
실제 staging 웹의 Google 버튼으로 Google 계정 선택 화면까지 이동했다. 서버 인증 준비는 200, 인증 시작은 accounts.google.com으로 302이며 S256 PKCE를 사용했다. Google 계정은 로그아웃 상태여서 사용자가 직접 로그인·동의를 진행하도록 화면을 열어 두었다. 비밀번호·인증번호를 요청하거나 대신 입력하지 않았다.
이 결과는 Google 사용자 로그인 완료, 인증 코드 교환 성공, 로그인 뒤 원래 여행 복귀를 검증했다는 뜻이 아니다. 신규 회원 온보딩 이후 복귀, 기존 회원 복귀, 실제 Android 복귀도 아직 남는다.
처음 클릭했을 때 앱의 공통 실패 안내가 한 차례 나타났다. 당시 원문 오류를 기록하는 경로가 없었다. 인증 준비·서버 시작을 별도로 확인한 뒤 원문 없는 단계 진단을 추가하고 웹을 다시 반영했다. 이후 앱 버튼으로 Google 계정 선택 화면에 진입했다. 최초 실패 원인은 확정하지 않았으며 진단 추가만으로 원인 수정이 끝났다고 표시하지 않는다.
oauthSteps.ts는 return/nonce/proof/session/prepare/open 단계와 허용한 오류 종류만 기록한다. 메시지·스택·URL·토큰·검증자·인증 코드는 기록하지 않는다. 외부 입력이 오류 이름에 들어가도 그대로 출력하지 않는다. 동기·비동기 실패와 정상 반환에 대한 2개 회귀 검사를 추가했다. 기존 버튼·제목·문구·레이아웃은 바꾸지 않았다.
실제 서버에서 인증 시작 주소 재사용은 401, 취소 시 복귀는 허용 웹의 /auth/callback?error=cancelled로만 302다. 취소 응답에 인증 코드나 회원 세션을 넣지 않았다. 실제 Google 인증을 성공한 것으로 가장하는 가짜 코드는 사용하지 않았다.

2. 외부 요청 우회
apps/api/test/maps-share-security.test.ts: 실제 API 라우트·인증 미들웨어를 통과하는 4개 검사 묶음. IP 숫자/16진 표기, IPv6, 메타데이터 주소, localhost, 사용자 정보, 호스트 혼동, 포트, 경로, 비 HTTPS, 악성 redirect를 검사했다.
tests/cloud/mapsShareSecurity.test.mjs: 실제 Worker·운영 마이그레이션·D1 회원 인증을 사용하는 3개 검사 묶음. 외부 응답만 격리했으며 내부망에는 실제 요청하지 않았다. 무인증·잘못된 주소는 외부 요청 0건, 악성 단축 링크는 허용 Google 호스트에 첫 HEAD 한 번만 보내고 중단했다. 회원 Authorization·Cookie·Google 키는 외부 요청에 없었다. 정상 Google 공유 후보 반환도 확인했다.
서버는 단축 링크마다 목적지를 다시 검사하고 manual redirect·최대 4회·전체 10초 신호를 적용한다. Google 지도 본문을 임의로 가져오지 않는다. 첫 주소가 허용됐다는 이유로 이후 임의 호스트를 신뢰하지 않는다. 공급자 실패의 원문도 응답에 포함되지 않았다.
실제 staging에서는 검수 회원으로 잘못된 주소 9종 422, 정상 직접 지도 후보 200, 무인증 가져오기 401을 확인했다. Google 시작·취소까지 포함해 결과 레코드 13개가 통과했다. 이 수치를 HTTP 총 요청 수로 사용하지 않는다. 검수 세션은 종료했으며 새 여행·공개 글·실사용자 원본을 만들거나 수정하지 않았다.
초기 검사 2건은 /../ 경로가 URL 파서에서 유효한 Google 단축 경로로 정규화되는 상황을 차단 대상으로 잘못 가정해 실패했다. 내부망 우회가 아니었고 Google 호스트·4회 제한은 유지됐다. 검수 입력을 실제 허용 규칙에 맞게 고친 뒤 재실행했다. 서버 검증을 약화하거나 이 실패를 취약점 수정으로 집계하지 않았다.
장소 ID·사진 이름은 고정 공급자 주소에 검증 후 연결하며, 사진 표시 링크도 별도의 Google 호스트 검사를 거친다. 이 검수는 임의 서버 요청 경계에 관한 것으로 모든 입력 공격·비용 악용·외부 공급자 침해까지 통과했다는 뜻은 아니다.

3. 키·검수 자격 증명 검사
공식 Gitleaks 8.30.1 Windows 실행 파일을 공식 릴리스에서 받아 게시된 SHA-256과 대조했다. 검출기는 이 PC에서 실행했고 소스나 키를 외부 검사 서비스로 전송하지 않았다. 기본 규칙에 Stitch AQ 형식 규칙을 추가하고 합성 표식으로 실제 검출도 확인했다.
현재 Git 추적·추가 대상 텍스트 783개 파일, 전체 Git 참조 이력 52개 커밋, 웹 후보 산출물을 검사했다. 검출 원문은 메모리에서만 처리하고 파일·행·규칙·커밋만 남겼다. 현재 소스·문서 검출 5건과 Git 이력 검출 1건은 배포 버전 UUID·디자인 토큰 내용 해시·격리 Worker의 합성 테스트 Secret으로 확인했다. 실제 서비스 자격 증명으로 판정한 항목은 없었다. Git 이력을 다시 쓰거나 파일을 임의 삭제하지 않았다.
웹 후보에서는 검출 0건이다. 실제 staging의 실행 청크 2개는 후보 SHA-256과 모두 일치했다. 로컬에서 확인할 수 있는 비공개 항공 서비스 키와 QA 비밀번호도 값 자체를 메모리에서 대조했으며 현재 소스·후보 공개 파일과 일치하지 않았다. 서버 Secret 원문 전체를 열람했다는 뜻은 아니다.
QA 계정 파일·.env.release·웹 임시 산출물은 Git 제외를 확인했다. /outputs/·환경 파일·서명 파일은 기존 .easignore에서도 제외된다. Android 패키지는 만들지 않았으므로 최종 APK/AAB의 비밀 미포함 판정은 별도다.
발견한 배포 검사 보완점: 기존 hasUnsafeReleaseValues는 일부 서버 변수 이름과 sb_secret 형식만 검사해, 변수 이름을 지운 Stitch 키·PEM 개인 키 원문을 놓칠 수 있었다. 합성 입력으로 먼저 실패를 확인한 뒤 원문 형식도 차단하도록 보완했다. 검사 결과에 값을 출력하지 않으며 일반 공개 설정은 그대로 허용한다.
개발 도구 키 관리 권고: 사용자는 해당 키가 Stitch MCP용이라고 명확히 했다. 앱 소스·웹 배포에서 이 키가 발견된 사실은 없고, 이번 작업에서 앱·웹·API에 넣지도 않았다. 앞서 교체를 권고한 이유는 채팅에 원문이 남았기 때문이며 배포에 넣어서가 아니다. 채팅 입력만으로 인터넷 공개나 제3자 악용이 확인됐다고 단정하지 않는다. MCP 설정의 키 관리·필요 시 교체는 별도로 관리하며, 미교체 자체를 앱 배포 P0 차단 사유로 사용한 이전 판정은 정정한다. 키 원문은 다시 기록하지 않는다.
