기존 수정은 보존했다. 앱 코드·DB·인증 정책은 변경하지 않았다. 운영 배포는 하지 않았다.
‘클라이언트 피드백’은 최종 사용자가 겪을 불편을 뜻한다. 예상 반응은 사용성 가설이며 실제 고객 인터뷰 인용이 아니다.

1. 평가 결론과 서비스 목적

사용자가 남긴 ‘어플리케이션으로의 기능은 0점’은 현재 만족도에 관한 평가다. 이번 조사에서 이를 정량 품질 점수로 바꾸지는 않았다. 로그인, 초안, 저장 재시도, 계정별 데이터 보호 코드는 있다. 그러나 사용자가 그 기능을 찾아 같은 조건으로 실행하고 저장 결과를 확인하는 과정에는 끊기는 지점이 있다.

후속 사용자 피드백에 따라 가장 먼저 해결할 범위는 계획 생성 → 세부 일정 추가 → 일정 저장의 전체 흐름이다. 페이지별 정책과 핵심 기능이 같은 기준으로 연결되는지 평가한다. 로그인은 이 흐름의 입력 보존·복귀에 필요한 범위부터 확인한다. 일정 저장 후 다른 날짜가 보이는 위험과 날짜가 있는 초안의 잘못된 이동도 함께 확인한다. 상세한 우선순위와 공통 기준은 17절을 따른다.

서비스 목적은 여행 계획을 만들고 실제 방문과 지출을 여행에 연결해 남기는 것이다. 영수증의 음식·상품 품목도 해당 방문에 연결한다. 계획과 실제 기록은 구분한다. OCR로 글자를 읽은 결과나 영수증 한 장만으로 본인 방문·원본 진위를 보장하지 않는다.

전체 흐름은 시작 방법 선택 → 로그인 또는 기본 입력 체험 → 여행 날짜·나라·선택 도시 → 선택 항공편 확인 → 여행 저장 → DAY별 일정 추가 → 저장한 날짜에서 결과 확인이다. 여행 중·여행 후에는 여행 선택 → 영수증 등록 → 상호·결제 시각·통화·총액·품목 확인 → 기존 방문 연결 또는 새 실제 방문 생성 → 저장 결과 확인으로 이어진다.

여기서 ‘여행 만들기’는 여러 날짜와 일정을 담는 여행을 만드는 일이다. ‘일정 추가’는 그 여행의 특정 DAY에 식사·숙소·관광·이동 등을 한 건 넣는 일이다. ‘등록’은 입력을 서버에 저장하고 다시 조회해 확인하는 일이다. 공개 게시와는 구분한다.

2. 확인한 범위와 증거의 한계

코드·문서: 요청한 다섯 흐름을 모두 읽고 대조했다. 현재 홈은 PlanningStartScreen이다. 이전 HomeScreen의 추천 배치를 현행 홈 문제로 취급하지 않았다.
실제 웹 조작: 새 웹 빌드를 127.0.0.1:8873에서 열었다. 390px에서 시작·로그인·이메일 로그인·회원가입 폼·여행 만들기를 조작했다. 외부 계정 생성이나 로그인 제출은 하지 않았다. 기본 빌드 설정에서 Google 버튼이 이용 불가 상태로 표시되는 것을 관찰했지만 서비스 전체의 Google 장애로 판정하지 않았다.
자동 검사: npm run test:auth, 301개 통과. 순수 로직·테스트 응답을 포함한 검사이며 실제 인증 서버·DB 인수를 대신하지 않는다.
실제 회원 로그인, 이메일 발송, 서버 여행 저장·재조회, 로그인한 MY, OS 알림 수신, Android/iOS 설치본과 카메라는 미검증이다. 테스트 계정과 설치본을 이용한 후속 인수 검사가 필요하다.
실기기 글자 200%·키보드·TalkBack/VoiceOver·안전 영역도 미검증이다. 코드의 규격 대조와 실제 기기 동작을 구분했다.

화면 목적: 내 여행을 이어가거나 새 여행을 만들고 영수증을 정리할 여행을 고른다.

12. 우선순위와 개발 인계

P0는 이번에 재현한 장애의 등급이 아니라 출시 전 반드시 통과할 인수 기준이다. 테스트 계정으로 로그인 → 여행 생성 → 일정 저장 → 재진입·서버 재조회를 끝까지 확인하기 전에는 사용 가능한 핵심 흐름으로 승인하지 않는다.
P1은 목적 달성·정보 신뢰·접근성에 직접 영향을 주는 수정이다. AUTH-01~04, HOME-01~02, PLAN-01~03, PROFILE-01, SET-01~03을 먼저 처리한다. AUTH-04는 정책 결정, PLAN-02와 HOME-02는 실제 재현 검사를 먼저 붙인다.
P2는 입력 부담·탐색·표현 개선이다. AUTH-05~07, HOME-03, PLAN-04~06, PROFILE-02, SET-04를 다음으로 진행한다. 전면 재디자인이나 새 커뮤니티 기능 추가는 이번 개선 범위에 넣지 않는다.

작업 묶음 A — 첫 진입과 복구
인증 담당이 시작 화면 이메일 경로, 게스트 문구, 비밀번호 복구·이메일 확인 정책을 맡는다. 기존 인증 복귀 계약과 공개 경로 허용 목록을 유지한다. 인수는 첫 진입·가입·취소·실패 후 원래 작업 복귀다.
작업 묶음 B — 계획 생성과 저장 신뢰
여행 담당이 진행 조건 공통화, 검색 통합, 자동 제목 구분, 초안 분류, 임의 사진·공항 제거, 저장 후 DAY 복귀를 맡는다. 새 테이블은 전제로 하지 않는다. 공개 응답과 내부 모델의 변경 필요성을 먼저 확인하고 바뀌면 DB_객체사전을 함께 갱신한다.
작업 묶음 C — 개인정보와 설정
프로필·알림 담당이 생일 수정·삭제, 설정 진입, 예약 언어·상태, 실제 버전을 맡는다. 사용자별 비공개 필드와 계정 변경 후 응답 보호를 유지한다.

단계별 통과 기준
1차: 첫 진입·잘못된 진행·거짓 표시를 고치고 핵심 왕복 흐름을 실제 서버에서 통과한다.
2차: 작은 화면·큰 글꼴·입력 오류·저장 실패·응답 유실·로그인 취소를 검사한다. 실제 저장과 화면 상태가 일치해야 한다.
3차: 프로필·언어·알림·권한을 실기기에서 확인하고 기존 4개 GNB·헤더·뒤로가기 회귀를 통과한다.
일정과 비용 추정은 담당자·서버·테스트 계정 조건 확인 후 정한다. 근거 없는 완료 날짜를 제시하지 않는다.

성공 지표 제안 — 현재 측정값 없음
첫 실행에서 자기 계정으로 들어가는 성공률, 여행 생성 시작 대비 첫 일정 저장·재조회 완료율, 로그인 후 원래 입력 복원율, 저장 응답 유실 뒤 중복 생성 건수, 저장 실패 뒤 입력 보존율을 측정한다. 시작 이벤트·성공 이벤트·중단 구간을 구분하고 비밀번호·영수증 원문·개인 메모를 계측 데이터에 넣지 않는다. 첫 릴리스에서는 아래 인수 시나리오 전부 통과를 기준으로 삼는다.

17. 후속 피드백 — 핵심 플로우의 정책·기능 일치가 최우선

반영일: 2026-11-02 / 상태: 평가 우선순위 반영, 구현 변경 없음.
사용자는 페이지별 정책과 핵심 기능이 맞지 않는 점을 가장 큰 문제로 지적했다. 특히 계획 생성 → 세부 일정 추가 → 일정 저장이 제대로 이어지지 않는다고 평가했다. 이 절이 앞선 개별 화면의 수정 순서보다 우선한다. 18쪽 프레젠테이션은 최초 평가 자료로 보존한다.

평가 단위
개별 화면에 기능이 있는지보다 사용자가 여행 하나를 만들고 세부 일정 한 건을 저장한 뒤 다시 확인할 수 있는지를 먼저 판단한다. 이 왕복이 통과하기 전에는 핵심 기능을 사용 가능한 상태로 승인하지 않는다. 앞선 평가가 결함을 화면별로 흩어 놓은 점을 보완한다.

현재 확정 정책을 단계마다 적용할 기준

1. 기본 정보 입력: 로그인 전에도 입력한다. 입력 중인 값을 저장 완료로 표시하지 않는다. 나라·유효한 출발일과 도착일을 정식 생성 조건으로 삼는다. 도시·제목·항공편은 선택이다. 위·아래 다음은 같은 조건을 사용한다.
2. 로그인과 복귀: 서버 저장 전에 정식 회원 여부를 확인한다. 로그인·회원 설정 뒤 같은 작성 내용과 목적지로 돌아온다. 로그인 성공만으로 생성·저장 성공을 표시하지 않는다. 로그인 전 어느 단계까지 입력할지는 화면·컨트롤러·안내가 같은 정책을 따르게 한다.
3. 작성 중 초안: 날짜를 정하지 못한 입력은 정식 로그인 후 서버 초안으로 저장한다. 날짜가 있어도 정식 생성 전이면 초안이다. 초안 ID로 정식 여행의 세부 일정·비용 화면을 열지 않는다.
4. 여행 생성: 정식 여행 ID와 기간에 맞는 DAY를 서버가 생성한다. 성공을 확인한 ID로 상세를 연다. 초안을 전환했다면 같은 내용을 두 여행처럼 표시하지 않는다. 이 완료는 여행 기본 틀 생성이며 세부 일정 등록 완료와 구분한다.
5. 세부 일정 추가: 실제 여행 ID와 선택한 DAY에 연결한다. 다른 DAY로 바꿨다면 그 DAY가 저장 대상이다. 공개용 설명·사진·영수증 같은 선택 기능은 기본 일정 등록을 막지 않는다.
6. 일정 저장: 해당 일정의 서버 저장 성공을 확인하고 저장한 DAY와 행으로 돌아온다. 화면 재진입·서버 재조회에서도 같은 내용이 한 건 남아야 한다. 응답 유실은 같은 요청으로 재시도하고, 저장 성공 후 조회 실패는 재저장이 아닌 재조회로 복구한다.

현재 확인한 불일치
PLAN-01은 같은 입력을 상단과 하단 다음이 다르게 처리하는 웹 재현 사례다. PLAN-02는 폼의 저장 DAY가 바뀌어도 일반 일정 성공 후 화면의 선택 DAY를 바꾸는 처리가 없는 코드상 위험이다. HOME-02는 초안을 정식 여행의 행동에 연결할 수 있는 코드상 위험이다. 세 항목을 서로 떨어진 UI 문제로 취급하지 않고 같은 여행의 상태·식별자·저장 결과가 이어지는지 확인하는 검사로 묶는다. 뒤의 두 항목은 실제 서버·화면 재현이 남아 있다.

저장 단위의 구분
현재 구현에서 서버 초안 저장, 여행 생성, 세부 일정 한 건 저장은 별도 요청이다. 사용자가 말한 ‘일정 저장’을 이 중 어느 동작으로 안내하는지 화면 문구와 완료 상태를 맞춰야 한다. 세부 일정을 여러 건 작성한 뒤 전체 계획을 한 번에 확정하는 방식은 별도 정책 변경이다. 이번 피드백만으로 그 방식을 승인된 저장 계약으로 가정하지 않는다.

다음 수정의 순서와 완료 기준
먼저 이 여섯 단계의 필수값·작성 상태·로그인 경계·저장 대상·다음 화면·실패 복구를 공통 계약으로 정리한다. 다음으로 UI의 잠금 조건, 폼 검증, 요청 변환, 서버 검증, 저장 후 이동을 같은 계약과 대조한다. 차이가 확인된 부분을 수정하고 하나의 연속 검사로 확인한다. 앱 코드는 이번 후속 평가에서 수정하지 않았다.
인수 시나리오는 ‘도시 없이 나라·날짜 입력 → 로그인 왕복과 입력 보존 → 항공편 없이 정식 여행 생성 → DAY 2에 일정 추가 → 저장한 DAY의 행 확인 → 다른 화면 방문 → 서버 재조회 → 동일 일정 한 건 확인’이다. 여기에 저장 실패·응답 유실·충돌·연속 누르기를 추가한다. 날짜 미정 초안은 별도 분기로 저장·재조회·이어쓰기·정식 전환을 확인한다. 실제 비운영 서버를 사용하는 검사와 응답을 통제한 자동 검사는 구분한다.
프로필·설정·장식 UI 개선은 이 흐름을 회복한 뒤 진행한다. 기존의 중복 방지·입력 유지·계정 보호는 보존한다.
