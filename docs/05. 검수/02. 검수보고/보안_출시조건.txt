1. 판단과 기준
최종 보안 검수는 다른 회원의 여행에 접근할 수 없는지, 선택하지 않은 기록이 공개되지 않는지, 외부 API 호출을 악용할 수 없는지부터 확인한다.
웹·API는 OWASP ASVS 5.0.0의 적용 가능한 Level 2 요구사항을 검수표에 매핑한다. API Security Top 10 2023을 공격 시나리오 분류에 사용한다. 모바일은 MASVS와 MASTG의 저장·인증·통신·플랫폼·개인정보 항목을 적용한다. 표준 전체 인증을 받았다고 표시하지 않는다.
현재는 코드·웹·API 검수까지 준비한다. Android 빌드는 하지 않는다. 실제 최종 Android 배포본의 패키지·서명·기기 저장소 검수는 빌드 승인을 받은 뒤 별도 통과해야 한다.

3. 시험 환경과 증거
staging의 검수 전용 회원과 여행만 사용한다. 실사용자 여행·사진·영수증은 시험 대상에서 제외한다.
A: 여행 소유 회원 / B: 편집 동행 회원 / C: 조회 동행 회원 / D: 해당 여행에 참여하지 않은 회원 / G: 게스트 / N: 익명.
추가 상태: 동행에서 제거된 B, 초대 철회·만료, 탈퇴 유예, 계정 삭제 기한 경과, 로그아웃·계정 전환.
소유자만 여행 관리·초대·멤버 관리·공개 명령을 실행하는 현재 서버 계약을 기준으로 대조한다. 편집 동행자는 허용된 일정·기록을 수정하며 조회 동행자는 쓰기를 할 수 없어야 한다.
각 사례에 사례 ID, 우선순위, 대상 URL/명령, 주체·역할, 사전 상태, 입력 변형, 기대 결과, 실제 상태 코드, 응답 필드, 전후 버전·건수, 재현 순서, 담당자, 증거 파일을 남긴다.
요청·응답 증거에서 비밀번호·토큰·인증 헤더·서명 URL·실제 영수증·API 키는 제거한다. 허용되지 않은 요청은 오류 상태뿐 아니라 저장·공개·업로드·공급자 호출도 일어나지 않았음을 확인한다.
실서비스 대량 요청이나 비용 발생 스트레스 테스트는 실행하지 않는다. 제한 경계와 날짜·만료 경합은 격리된 DB·가짜 시계·통제된 공급자 응답으로 먼저 재현한다. 외부 서비스 실검수는 최소 호출로 확인한다.

4. 우선순위와 합격 조건
P0: 타인 정보 접근, 계정 탈취, 권한 상승, 비공개 정보 공개, 서버 비밀 유출, 임의 서버 요청 등 즉시 출시를 막는 문제.
P1: 악용 가능한 사용량 제한 우회, 저장·업로드 검증 우회, 세션 잔류, 개인정보 잔류 등 피해가 발생하는 문제. 공개 출시 전 해결하고 재검증한다.
P2: 피해 경로가 확인되지 않은 강화 권고와 운영 개선. 담당자·완료 기한·위험 수용 사유를 기록한다.
심각도는 재현 가능성·노출 범위·데이터 민감도·예상 피해를 함께 보고 확정한다. 도구의 등급만으로 출시 여부를 정하지 않는다.

S01. 여행·기록 권한 [P0]
tripId/dayId/scheduleId/mediaId/receiptId/postId를 검수 계정 사이에서 바꿔 조회·수정·삭제·업로드·OCR·공개 요청을 보낸다. 요청 본문의 userId/ownerId/role을 바꿔 권한을 얻지 못해야 한다.
D/N은 비공개 원본을 읽거나 바꾸지 못한다. C의 쓰기와 B의 소유자 전용 명령이 서버에서 차단된다. 다른 여행의 DAY·사진·영수증을 끼워 넣어도 연결되지 않는다. 제거된 동행의 이전 세션·파일 URL도 현재 권한에 맞게 차단된다.
검증 위치: apps/api/src/infrastructure/storage/cloudStore.ts, cloudRpc.ts, workspace.ts, packages/validation/src/workspaceModel.ts.

S02. 로그인·게스트·세션 [P0]
없는/변조된/만료된 토큰, 로그아웃한 토큰, 다른 계정으로 전환한 직후의 늦은 응답을 검사한다. 인증 실패 이후 서버 데이터나 이전 회원 캐시가 새 계정에 표시되면 실패다.
게스트 연결은 인증 서버가 확인한 게스트와 회원 사이에서만 이뤄져야 한다. 임의 게스트 ID로 기록을 가져오지 못하고 연결 후 이전 게스트 토큰의 권한을 확인한다.
Google OAuth는 state·검증자·일회용 코드·만료·재사용·허용 복귀 경로·외부 URL 우회·다른 앱의 복귀 가로채기를 검사한다. 표시 이름이나 이메일만으로 기존 계정을 탈취·연결할 수 없어야 한다.
검증 위치: cloudAuth.ts, guestLink.ts, socialHandoff.ts, socialProviders.ts, apps/mobile/src/services/cloudAuth.ts, features/auth/.

S03. 공개 정보와 공개 중단 [P0]
개인 메모·예약번호·동행 개인 정보·영수증 원본/상세 품목·비선택 사진·비선택 일정이 공개 JSON, 사진 URL, 미리보기, HTML, 오류, 로그에 없어야 한다.
공개된 여행만 익명으로 읽힌다. 공개 중단·사진 선택 해제·재공개 뒤 이전 URL과 기존 서명 URL을 재요청해 서버가 새 공개 범위를 적용하는지 확인한다. 이미 외부에서 내려받은 사본까지 회수할 수 있다고 안내하지 않는다.
브라우저·CDN·서비스 캐시에 개인 응답이 공용 저장되지 않아야 한다. 다른 계정으로 같은 경로를 열어 앞선 회원의 응답이 재사용되지 않는지 확인한다.
검증 위치: workspaceModel.ts 공개 투영, cloudMedia.ts, placePhotos.ts, app.ts, 웹 공개 화면.

S04. 사진·영수증 업로드 [P0/P1]
위장 MIME/확장자, 잘린 JPG/PNG, 정상 헤더에 잘못된 본문, 과도한 픽셀 수, 크기 초과, 다른 회원 업로드 경로, 기존 파일 덮어쓰기, 등록하지 않은 파일 참조를 검사한다.
파일 선두 시그니처만 맞는다고 정상 이미지로 통과했다고 판단하지 않는다. 서버가 허용 형식과 실제 디코딩 결과·크기·이미지 치수를 안전하게 검증하는지 확인한다.
현재 imagePreparation.ts는 4MiB 이하 파일을 원본 바이트로 전달하는 경로가 있다. GPS·기기·촬영자 EXIF를 넣은 소유 검수 사진을 업로드한 뒤 공개 다운로드 파일에서 제거되는지 확인한다. 제거 전까지 공개 사진 개인정보 검수를 합격 처리하지 않는다.
공개 사진은 필요한 메타정보만 남기고, 영수증은 비공개 원본과 공개 갤러리가 섞이지 않아야 한다. 클라이언트 처리를 거치지 않은 직접 API 업로드도 같은 기준으로 검사한다.

S05. 입력·링크·외부 요청 [P0/P1]
제목·DAY 소개·장소 팁·닉네임·공유 소개·OCR 결과의 HTML/스크립트·제어문자·SQL 문자열·최대 길이·잘못된 JSON을 검사한다. 스크립트 실행, SQL 동작 변경, 서버 내부 오류 노출이 없어야 한다.
지도 단축 링크의 매 단계 목적지 검증을 확인한다. localhost·사설 IP·클라우드 메타데이터·유사 Google 도메인·인증 정보가 포함된 URL·중첩 리다이렉트가 임의 fetch로 이어지지 않아야 한다.
공격용 내부 주소는 외부 실서버를 호출하지 않는 통제된 fetch 테스트로 검증한다. 운영 중인 외부 호스트를 공격 대상으로 삼지 않는다.

S06. 사용량·비용 악용 [P1]
로그인·가입·게스트 생성·지도 검색/상세/사진·항공편·OCR·업로드·초대에 대해 회원/IP/여행/기간별 제한과 전체 상한을 대조한다. 게스트 재발급·여러 계정·동시 Worker 요청으로 전체 한도를 우회하지 못해야 한다.
거절 요청·재시도·같은 영수증 재확인·공개 사진 반복 조회가 공급자 호출이나 중복 요금을 어떻게 만드는지 확인한다. 제한 저장소 장애·설정 누락 시 유료 요청이 무제한으로 진행되면 실패다.
Google Cloud 사용량 제한·결제 경고와 앱 서버 제한을 함께 확인한다. 예산 알림을 자동 과금 차단으로 취급하지 않는다. 운영 한도는 예상 이용량과 공급자 요금표에 맞춰 별도로 확정한다.

S07. 저장 무결성·경합 [P1]
같은 중복 방지 키/다른 본문, 다른 회원의 키, 오래된 버전, 다른 여행 버전, 동시에 같은 영수증 확정, 저장 중 권한 제거·공개 중단을 시험한다.
허용된 명령만 한 번 저장되고 잘못된 요청은 롤백돼야 한다. 여행 버전·일정·비용·영수증·파일 참조 사이에 일부만 확정된 상태가 남지 않아야 한다. 성공 응답 없이 임의로 재시도해 중복 저장되지 않아야 한다.

S08. 탈퇴·복구·보존 [P0/P1]
탈퇴 유예 직후 기존 세션·파일 접근이 차단되고 새 로그인에서만 90일 이내 복구된다. 90일 경계의 복구/정리 경합을 가짜 시계와 격리 DB로 검증한다. 실제 검수 계정에 영구 삭제를 실행하는 것은 별도 승인 범위다.
계정의 이메일·인증·프로필 삭제와 여행 보존을 분리한다. 계정과 분리한 사진·영수증·자유 입력문에도 개인정보가 남을 수 있으므로 계정 분리만으로 완전 익명화됐다고 표시하지 않는다. 보존 범위·접근 권한·공개 상태·예약 정리 작업·실패 재시도까지 확인한다.
동행자에게 소유자를 자동 이전하지 않는 사용자 결정과 기존 동행의 허용 권한을 유지한다.

S09. 웹·키·배포 환경 [P0/P1]
웹 토큰은 현재 localStorage, 네이티브 토큰은 SecureStore 경로를 사용한다. 웹은 XSS 발생 시 토큰 노출 위험을 우선 평가하고, HttpOnly 쿠키/BFF 등 대안의 필요성을 결정한다. 저장 방식을 바꾸면 CSRF·CORS·네이티브 로그인·로그아웃까지 함께 재검증한다.
웹의 CSP·프레임 삽입 방지·nosniff·Referrer-Policy·HTTPS·허용 Origin을 실제 응답으로 검사한다. 앱과 직접 API 요청에서도 인증·객체 권한을 재검사해야 한다. CORS만으로 비회원 접근을 막았다고 판단하지 않는다.
소스·Git 이력·환경 파일·웹 JS·소스맵·배포 압축물·로그·검수 산출물에서 비밀과 검수 계정 정보를 검사한다. 결과에는 값 대신 위치와 종류만 기록한다. 기존 QA 자격 증명 파일이 공개 폴더·Git·Android 산출물에 포함되지 않아야 한다.
Google Android 지도 키는 패키지명·Play 앱 서명 인증서와 API 제한, 웹 키는 허용 도메인·API 제한, 서버 키는 서버 Secret과 필요한 API 범위로 나눠 확인한다. 클라이언트 지도 키의 표시 자체와 서버 비밀 유출은 구분한다.
Stitch 키는 개발용 MCP 설정에서 관리하고 앱·웹·API 배포에는 포함하지 않는다. 이전 대화의 원문 입력에 따른 교체 권고는 개발 도구 키 관리 항목으로 별도 기록한다. 앱 배포 포함이나 서비스 영향이 확인되지 않은 상태에서 미교체만으로 앱 출시를 차단하지 않는다. 키 원문을 다시 기록하지 않는다.
Cloudflare 운영/검수 DB·R2·인증 Origin 분리, 최소 권한 토큰, 백업·복원, 관리자 접근, 민감 정보 없는 경보·감사 기록을 확인한다. DB 직접 검수 권한 부족은 실제 관리자 설정 검수 완료 전까지 미확인으로 남긴다.

S10. 의존성·Android 최종 산출물 [P0/P1]
잠금 파일 기준 의존성 목록과 알려진 취약점을 검사한다. npm audit 등 결과는 런타임 도달 가능성·악용 조건을 검토하고 자동 강제 업데이트로 UI/기능을 깨뜨리지 않는다.
이후 빌드를 승인받으면 동일 커밋·설정의 최종 AAB/Play 설치본에 MobSF 등 정적 검사와 MASVS/MASTG 기기 검수를 수행한다. 디버그 설정·평문 통신·내보낸 컴포넌트·백업·딥링크·불필요 권한·로그·캐시·토큰 저장·계정 전환을 확인한다. 소스 검사 통과를 패키지 검사 통과로 대신하지 않는다.
HTTPS 인증서 검증은 유지한다. 인증서 고정이나 Play Integrity 같은 추가 장치는 위협과 운영 복구 비용을 평가한 뒤 도입하며, 서버 권한 검사를 대신하게 하지 않는다.

5. 실행 순서와 담당
1단계: 클라이언트·서버 담당이 API/명령/역할/민감 데이터 목록을 맞추고, 위 사례를 적용 가능한 ASVS/MASVS 요구사항과 연결한다. 누락·제외 항목에는 이유를 남긴다.
2단계: 서버 담당이 S01~S03·S05·S07의 자동 반례 테스트, 클라이언트 담당이 S02·S03·S04·S09의 세션/공개/파일/웹 저장 검증을 먼저 수행한다.
3단계: 운영 담당이 S06·S08·S09의 실제 제한·Secret·DB/R2 권한·정리 작업·경보·복원을 확인한다. staging에서 회원 간 실제 API 검수를 최소 요청으로 실행한다.
4단계: 발견 사항을 수정하고 해당 재현 테스트와 npm run check·관련 기능/클라우드/릴리스 테스트를 통과시킨다. 바뀐 서버·웹을 반영한 뒤 같은 반례를 다시 확인한다.
5단계: Android 빌드 승인 후 S10을 최종 Play 설치본에서 수행한다. 공개 출시 전에는 구현 담당과 별도의 보안 검토자가 P0/P1 증거와 주요 권한·정보 노출 경로를 재검토한다.

6. 출시 합격 기준과 보고
필수 적용 사례 전체가 통과하고 재현 가능한 미해결 P0/P1이 0건이어야 한다. 필수 항목의 미실행·권한 부족·판정 불가를 통과로 계산하지 않는다.
차단된 요청에서 데이터 변경·외부 유료 호출·파일 유출이 없다는 증거를 남긴다. 공개 데이터는 허용 목록으로 비교하고 비공개 금지 필드는 부재를 검증한다.
수정한 취약점은 재현 테스트를 회귀 검사에 남긴다. 범위·코드/배포 식별자·환경·테스트 계정 역할·발견/수정/재검증·남은 위험·최종 검토자를 보고서에 기록한다.
2026-10-19 계획 작성 시점 판단: 기능 저장·재조회·공유 검수는 확인됐으나 최종 보안 출시 승인은 하지 않았다. 당시 작업은 계획 문서 작성과 코드/기존 증거 확인이며 공격 테스트·서버 배포·Android 빌드는 실행하지 않았다. 2026-10-20 실제 검수·수정 결과와 남은 범위는 SECURITY_P0_REVIEW.txt에 별도로 기록했다.
