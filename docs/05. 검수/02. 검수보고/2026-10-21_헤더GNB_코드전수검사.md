> 2026-10-22 경로 정리 안내: 이 문서는 작성 당시의 코드 검사 기록입니다. 현재 없는 두 파일의 위치는 링크 대신 파일명으로 보존했습니다. 현행 헤더·GNB 규격과 이후 수정 결과를 함께 확인합니다.
> 이 문서는 수정 전 검사 기록이다. 후속 조치와 재검증은 [헤더·GNB 규격 고정 보완](2026-10-21_헤더GNB_규격보호검수.md)에서 확인한다.

GNB의 페이지별 중복 구현은 발견하지 못했다. 현재 GNB는 루트에서 한 번만 표시하며, 일반 화면은 공통 헤더를 사용한다. 다만 **임의 헤더 교체, 페이지의 헤더 외곽 스타일, 규격값 분산과 예전 코드가 남아 있어 공통 규격을 구조적으로 강제하는 작업은 미완료**다.

## 우선 보완 항목

P1은 페이지 작업 전에 규격 우회 경로를 막을 항목이고, P2는 규격값·잔재·예외 상태를 정리할 항목이다. 아래7개는 현재 UI 오류와 향후 변경 위험을 구분한 검수 항목이며, 모두 화면이 잘못 표시된다는 뜻은 아니다.

### F01 P1 임의 헤더를 전달할 수 있는 인터페이스

[communityFeedTypes.ts:10](../../../apps/mobile/src/features/workspace/communityFeedTypes.ts)의 `header?: ReactNode`와 [CommunityScreenView.tsx:28](../../../apps/mobile/src/features/workspace/CommunityScreenView.tsx)의 `props.header || <ScreenHeader ...>`가 전체 헤더 교체를 허용한다. 현재 전달자는 공개 발자국의 HomeHeader 1곳으로, 승인된 브랜드형이다. 임의 헤더가 실제로 전달되는 사례는 없지만 다른 페이지가 자체 제목·버튼·스타일을 통째로 넣어도 이 계약은 거부하지 않는다.

공통 규격이 정한 유형만 선택하도록 바꾸고, 실제 헤더 조립은 공통 컴포넌트가 맡아야 한다. 제목·행동·복귀·잠금 상태만 페이지에서 연결한다.

[ScreenTitle.tsx:6](../../../apps/mobile/src/components/ScreenTitle.tsx)도 일반 TextProps의 `style`을 받는다. 크기·색·굵기는 마지막 공통 스타일이 덮어쓰지만 `fontFamily`는 공통 스타일에 고정하지 않아 호출자가 글꼴을 바꿀 수 있다. 현재5개 호출 위치에는 그런 사용이 없고, 전달된 스타일은 배치용이다. 허용할 배치 속성과 보호할 글자 속성을 타입·렌더링 계약으로 구분해야 한다.

### F02 P1 공개 발자국의 페이지 전용 헤더 외곽 스타일

[PublicFootprintsScreen.tsx:28](../../../apps/mobile/src/features/workspace/PublicFootprintsScreen.tsx)는 HomeHeader를 페이지의 `s.header` View로 감싼다. 기존 발자국 시안의 브랜드형 승인은 FOOTPRINTS_PUBLIC_FEED_SPEC.md에 있다. 현재 승인된 모양을 공통 유형에 정의하고 페이지 외곽 스타일 의존을 없애야 새 규칙대로 관리할 수 있다. 이번 검사에서는 구분선을 삭제하거나 모양을 변경하지 않았다.

### F03 P2 헤더 규격값과 스타일 원본 분산

`HomeHeader.tsx:6`가 페이지용 [homeStyles.ts:17](../../../apps/mobile/src/features/workspace/homeStyles.ts)에서 브랜드 헤더 스타일을 가져온다. 최소 높이56·최대 너비640·좌우20·상하6·간격8이 별도 숫자로 남아 있다. 브랜드 글자24/34는 공통 토큰을 참조한다. 현재 값은 규격에 맞지만 홈 본문 스타일 작업이 공통 브랜드 헤더에도 영향을 줄 수 있다.

[ScreenHeader.tsx:65](../../../apps/mobile/src/components/ScreenHeader.tsx)의 간격 8, [GlobalNavigation.tsx:179](../../../apps/mobile/src/components/GlobalNavigation.tsx)의 라벨 13/20·600과 초점선 2도 공통 컴포넌트 내부의 별도 수치다. 페이지별 위반은 아니며 현재 규격과 일치한다. 브랜드 헤더 스타일을 공통 소유로 분리하고 공통 수치의 참조 원본을 정리하면 규격 변경의 적용 범위가 명확해진다.

### F06 P1 금지된 새 구현을 소스 단계에서 차단하는 검사 부재

AGENTS.md에 금지 규칙은 있지만 check-code-boundaries.mjs에는 헤더·GNB의 소유 파일, 임의 스타일 주입, 페이지별 메뉴 복제를 차단하는 규칙이 없다. 이번에도 기존 코드 경계 검사는386개 파일에서0건으로 통과했다.

기존 화면 회귀 검사는 있다. CI·웹 배포·내부 테스트 빌드 워크플로는 `test:workspace:web`를 실행하며, 이 명령은 workspace.spec.ts의 헤더·GNB 검사도 포함한다. 별도 `test:headers:web`도 제공한다. 따라서 CI에 헤더 검사가 전혀 없다는 판정은 하지 않는다.

다만 헤더 테스트의 대상 화면은 수동 목록이다. 새 라우트를 추가해도 검사 대상에 자동 등록되지는 않는다. 공통 요소의 사용 위치·유형·허용 속성을 검사하는 정적 규칙과, 라우트 목록에 대한 헤더 정책 누락 검사가 필요하다. 테스트를 새 복제 구현의 모양에 맞춰 바꾸는 것도 규격 변경으로 관리해야 한다.

근거: package.json의 check/test:headers:web, scripts/check-code-boundaries.mjs, scripts/verify-workspace-web.mjs, playwright.workspace.config.ts, tests/web/workspace.spec.ts:11785·11880, .github/workflows/ci.yml:26·40 및 deploy-web.yml·play-internal.yml의 테스트 단계.

## 규격 위반으로 집계하지 않은 코드

- HomeHeader는 홈과 공개 발자국에서 재사용하는 승인된 브랜드형이며 페이지별 복제2개가 아니다.
- ScreenHeader의 inset=false는 나라·도시 선택과 프로필 시트에서 부모의20 여백을 중복하지 않기 위한 사용이다. 부모 여백을 대조했다.
- MyTripsControls의 우측 View는 공통 간격 토큰과 HeaderAction2개만 묶는다.
- FlightTicketEditorView의 완료, TripPlanningFlowView의 다음은 공통 Action의 size=header·quiet를 사용한다.
- WorkspaceSections의 본문 여행명은 승인 H04의 ScreenTitle이며 중복 상단바가 아니다.
- HomeExplore·HomeGuide·HomeRecommendation의 header, 항공 카드의 header, 이메일 입력의 formHeader는 본문 섹션·카드·폼 제목이다.
- 캐러셀·달력의 chevron-back, 카드 더보기 아이콘20, 여행 내부 섹션 탐색은 상단 뒤로가기나 앱 GNB와 기능이 다르다.
