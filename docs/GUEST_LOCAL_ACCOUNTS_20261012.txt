TripPrint 기기별 게스트 및 닉네임 고유성 구현 보고
기준일: 2026-10-12 (한국 시간)

1. 확정한 정책과 가능한 닉네임 수

- 게스트는 Google 인증 없이 사용하는 기기별 계정이다.
- 닉네임 형식은 Quest- 뒤에 A~Z와 0~9를 조합한 여섯 자리다. 예: Quest-A1B2C3.
- 자리마다 36가지이므로 총 36^6 = 2,176,782,336개다. 고정 접두사는 경우의 수에 영향을 주지 않는다.
- 이는 가능한 이름 수다. 회원이 같은 형식의 이름을 사용하거나 이미 발급한 이름은 제외하므로 실제 남은 수는 더 작다.
- 게스트·이메일·Google 회원 전체에서 닉네임을 중복 발급하지 않는다. 앞뒤 공백과 ASCII 영문 대소문자 차이도 중복으로 취급한다.
- 실제 계정 식별자는 UUID다. 닉네임은 로그인 비밀번호나 다른 기기의 기록 복원 수단이 아니다.

2. 구현한 저장 및 이용 흐름

- 최초 게스트 시작: 인터넷을 통해 실제 D1 user 행과 서명된 익명 세션을 발급하고, 고유 닉네임을 기기에 보관한다.
  가짜 사용자나 Google 계정을 만들지 않는다. DB의 isAnonymous=1로 회원 관리 시 구분한다.
- 이후 같은 기기 시작: 보관한 UUID와 프로필로 로컬 여행을 연다. 유효한 서버 세션이 없어도 기기 여행 저장·편집은 가능하다.
- DB 저장 범위: 계정 식별자, 닉네임, 익명 여부, 생성·갱신 시각 및 기존 인증 세션 정보.
- 기기 저장 범위: 여행·DAY·항공편·일정·비용·준비물·다이어리의 원본 데이터, 사진과 영수증.
  게스트의 여행 생성·변경·사진 저장을 원격 trips/checklists/files API로 보내지 않는다.
- Android/iOS는 앱 문서 파일, 웹은 해당 브라우저 localStorage에 여행을 보관한다.
  사진은 네이티브 앱 문서 파일 또는 웹 data URI로 보관하며 재실행 뒤에도 사용할 수 있다.
- 저장은 계정별 직렬화, 동일 요청 재시도 방지, 변경 버전 검사와 소유 UUID 검사를 거친다.
  웹에서는 지원되는 navigator.locks로 탭 사이의 쓰기도 직렬화한다.
  읽기·쓰기 실패를 성공으로 표시하거나 기존 문서를 빈 여행으로 덮어쓰지 않는다.
- 게스트 영수증은 기기 사진을 선택하고 사용자가 내용을 직접 입력·확정한다. 서버 자동 인식을 위해 업로드하지 않는다.
- 공개 커뮤니티 조회는 가능하다. 커뮤니티 게시·초대·동행 공유는 회원 가입이 필요하다.
- 장소 검색·프로필 수정·신고/차단처럼 서버를 사용하는 기능은 인터넷과 유효한 서버 세션이 필요하다.
  기기에 저장된 프로필만으로 서버 인증을 우회하지 않는다.
- 회원 전환 시 기존 기기 여행을 자동 업로드하지 않는다. 로그아웃 후 같은 기기에서 게스트를 다시 선택하면 기존 기록을 이어간다.
- Android allowBackup=false로 다른 기기로 게스트 여행이 자동 복원되지 않도록 설정했다.
  앱 삭제·저장 공간 초기화 시 기기 기록을 잃을 수 있음을 시작 화면에 안내한다.

3. 닉네임 고유성과 기존 DB 변경

- 신규 게스트는 Web Crypto 난수와 거절 표본 추출로 여섯 문자를 동일 확률로 생성한다.
- 기존 이름과 충돌하면 제한 횟수 안에서 다시 생성한다. 동시 발급의 최종 중복 차단은 DB UNIQUE INDEX가 보장한다.
- 이메일 가입과 프로필 변경은 이미 사용 중인 닉네임을 거부하고 다시 입력할 수 있는 안내를 제공한다.
- 소셜 초기 이름이 중복되면 프로필 설정 전에 고유한 임시 이름을 발급한다.
- 0006_unique_nicknames.sql은 user(lower(trim(name)))에 고유 인덱스를 생성한다.
- 기존 중복 이름은 생성 순서상 첫 계정이 유지하고 나머지는 UUID 접미사로 구분한다.
  기존 이름의 앞뒤 공백을 정리하고 게시물 작성자 및 여행 멤버의 표시 이름도 반영한다.
  기존 여행 버전을 1 증가시켜 적용 전 화면에서 저장하면 버전 충돌을 감지한다.
  기존 게스트의 이름을 일괄 Quest 여섯 자리로 바꾸는 작업은 아니다. 새 발급부터 이 형식을 사용한다.
- 신규 테이블은 만들지 않았다. 상세 컬럼·타입·제약·로컬 객체는 docs/DB_DICTIONARY.txt에 기록했다.

4. 이번 추가 변경 파일

서버:

- apps/api/src/cloudAuth.ts: 익명·이메일·소셜 생성 시 이름 정책 적용.
- apps/api/src/cloudProfiles.ts: 변경 전 검사와 DB 동시 충돌 처리.
- apps/api/src/errors.ts: 닉네임 충돌 및 공통 여행 규칙 오류 응답.
- apps/api/migrations/0006_unique_nicknames.sql: 중복 정리, 고유 인덱스, 기존 표시 이름 및 여행 버전 갱신.
- apps/api/src/cloudModel.ts: 공통 여행 규칙의 기존 서버 진입점 유지.

6. 배포 및 실기기에서 남은 확인

- 이 작업에서 원격 D1 변경·Worker/웹 배포·커밋/푸시·AAB 생성·Play 업로드는 실행하지 않았다.
- 새 버전 배포 전에 0006 마이그레이션과 새 Worker를 함께 반영해야 한다. 로컬 통합 검증은 원격 적용을 의미하지 않는다.
- 최신 앱으로 새 설치, 업데이트, 사진 권한, 실제 촬영·재실행, 비행기 모드 편집, 앱 삭제 후 기록 범위를 확인한다.
- 회원 가입과 게스트 전환에서 서로의 여행이 섞이지 않는지 확인한다.
- Android Hermes 번들은 JS·자산 생성 검증이며 설치 가능한 APK/AAB 또는 실기기 저장 검증을 대체하지 않는다.
- Google 계정 저장 목록 직접 동기화, 이메일 확인·비밀번호 복구·회원 탈퇴는 앞선 준비 보고의 미완료 항목으로 남는다.

최종 확인: 로컬 구현·코드 검사·146개 자동 테스트·Android Hermes 번들 검증 완료. 원격 적용과 최신 AAB의 Play 출시 및 실기기 인수는 남아 있다.
