점검일: 2026-10-12 / Windows 로컬 작업 디렉터리 기준

1. 최종 판정
자동 코드·기능 검사는 통과했다. Windows 네이티브 컴파일과 Android Studio Sync는 실패했다.
현재 위치에서 Run 버튼 빌드 및 Play 배포 준비 완료로 판정하지 않는다.
staging에는 새 여행지 API와 이번 웹 후보가 아직 적용되지 않았다.

동일 검사 코드를 변경하지 않고 정상 권한 환경에서 재실행하여 각각 30개 / 11개 통과를 확인했다.
실패를 무시하거나 테스트 조건을 완화하지 않았다.

3. Android 환경 및 실제 실패 원인
- 네이티브 프로젝트: apps/mobile/android. 저장소 루트의 android 폴더가 아니다.
- Android 앱 식별자: com.tripprint.app / versionName 0.1.0 / 로컬 versionCode 1.
- Gradle 9.3.1 / Microsoft JDK 21.0.8 / SDK API 36 / Build Tools 36.0.0.
- NDK 27.1.12297006 / CMake 3.22.1 설치 확인.
- 생성 manifest: allowBackup=false, travelapp 딥링크, 기본 Activity, text/plain 공유 인텐트 확인.
- 기존 :app:tasks 성공은 작업 등록 확인이다. APK 컴파일 성공을 뜻하지 않는다.
- Android Studio 실제 Sync: 12분 23초 후 실패. react-native-worklets C++ PCH 컴파일에서
  한글 경로가 잘못 인코딩되어 WorkletsPCH.h를 열지 못했다.
- android.overridePathCheck=true는 AGP 사전 검사만 우회한다. 위 C++ 오류를 해결하지 못한다.
- 이전 assembleDebug는 의존성 다운로드에서 장시간 대기했다. 스레드 덤프를 확인한 뒤
  이번 작업이 시작한 CLI 빌드 프로세스만 중단했다. APK 생성은 확인되지 않았다.
- T: 가상 드라이브로 원본을 연결해 C++ 모듈을 재검증했다.
  첫 검사 2분 22초 실패, 자동 연결 캐시를 백업하고 재생성한 검사도 53초 후 같은 오류로 실패했다.
  앱 루트는 T:로 바뀌었지만 Expo 자동 연결의 의존성 경로가 실제 J: 한글 경로로 돌아갔다.
  따라서 이 프로젝트에서는 subst만으로 해결됐다고 안내하지 않는다.
- 실험 생성 캐시는 .release에 보관하고 원래 자동 연결 캐시를 복원했다. T: 매핑도 해제했다.
- Android Studio의 TripPrint.app Run 설정 파일은 존재하나, Sync 실패로 실제 모듈 연결은 미검증이다.
- 설치 가능한 APK/AAB, 에뮬레이터 앱 실행, Android 성능: 이번 점검에서 성공 증거 없음.

다음 Windows 빌드 조치:
원본 미커밋 변경을 보존한 영문·공백 없는 실제 경로의 별도 체크아웃/복사본에서
의존성을 새로 설치하고 Expo prebuild 및 Gradle assembleDebug를 검증해야 한다.
예: J:/travel_APP 또는 C:/src/travel_APP. 가상 드라이브나 원본을 가리키는 junction만으로 대체하지 않는다.
원본 작업 디렉터리는 이동하지 않았다. 새 경로를 마련한 후 Android Studio에서 해당 apps/mobile/android를 연다.
JDK 21과 SDK 경로를 연결하고 Sync 성공 → TripPrint 앱 모듈 선택 → 기기 선택 → Run 순으로 검증한다.
개발용 debug 실행에는 .env.mvp 공개 설정을 사용하는 Metro가 필요하다.
현재 이전 Metro 프로세스는 CI 모드로 시작되어 reload가 비활성화되어 있다. 개발 시 CI 없이 재시작한다.
Play용 빌드는 기존 GitHub Linux Gradle 경로를 사용할 수 있으나 현재 미커밋 소스를 반영한 새 실행이 필요하다.

5. Play 내부 테스트 전 남은 항목
차단 / 확인 필요:
1) 로컬 Windows 네이티브 경로 문제 해결 및 실제 APK 시작 검증.
2) 새 API·0006 migration·동일 웹 후보 staging 적용 후 추천 API와 게스트 닉네임 발급 검증.
3) 현재 소스를 반영한 AAB 빌드, 기존 Play 업로드 키 서명, Play 최고값보다 큰 versionCode 확인.
   로컬 versionCode=1을 그대로 기존 Play 업데이트에 제출하지 않는다.
4) 내부 테스터 설치, Google 가입·재로그인, 게스트 오프라인 기록, 영수증 촬영,
   커뮤니티 게시·다른 계정 조회·철회 및 비공개 접근 거부 검증.
5) 동일 설치 빌드의 콜드 시작·프레임·메모리 등 Android 성능 측정.
