# 계정 이행·삭제 서버 정책

계정 입력은 Google 인증으로 받은 정보만 사용한다. 기기에서 시작한 게스트 여행은 서버 회원과 구분한다. 이 문서는 계정 DB·API의 적용 방법과 기존 자료·삭제 요청의 처리 범위를 정한다. 화면 배치와 입력창을 바꾸는 작업은 포함하지 않는다.

## 1. 계정과 저장 정보

| 대상               | 서버 기준                                                | 저장·사용 목적                                    |
| ------------------ | -------------------------------------------------------- | ------------------------------------------------- |
| Google 회원        | `account.providerId='google'` 연결이 있는 내부 `user.id` | 같은 회원의 여행·권한·로그인 연결                 |
| 현재 게스트        | 서버 회원을 만들지 않는 기기 이용 모드                   | 기기 여행 보관. 로컬 UUID는 서버 인증 자격이 아님 |
| 기존 비Google 계정 | 이행이 끝나지 않은 기존 자료                             | 기존 ID·여행 접근 유지. Google 회원 수에는 제외   |

Google `sub`는 로그인 연결 키다. 이메일은 본인 계정 안내용 비공개 값이며, 같은 이메일이라는 이유로 계정을 합치지 않는다. 신규 이름은 `여행자`, 사진은 NULL이다. 닉네임·소개·여행 스타일·성별·생일·프로필 사진의 추가 입력은 받지 않는다. Google 공급자 토큰·scope·만료 시각은 로그인 검증 중에만 사용하고 `account`에 남기지 않는다. 세션 IP·User-Agent도 새로 저장하지 않는다.

앱 로그인 세션은 Google 토큰과 별개다. 기존 7일 만료·1일 갱신 설정을 유지한다. 인증 공격 제한에는 요청 IP를 사용할 수 있으며, `rateLimit`의 1분 제한 창이 지난 행은 시간별 정리에서 삭제한다. 이는 이용 통계나 회원 프로필에 사용하지 않는다.

## 2. 기존 자료 이행

| 현재 자료                                      | 처리                                                                                    |
| ---------------------------------------------- | --------------------------------------------------------------------------------------- |
| Google 회원 ID·sub·비공개 이메일·여행 소유권   | 유지. 새 회원 ID로 옮기거나 여행 날짜를 바꾸지 않음                                     |
| 이메일·Kakao·Naver·서버 익명 기존 자료         | 자동 삭제·자동 병합하지 않음. 기존 접근 권한 유지                                       |
| 이메일 신규 가입·서버 익명 신규 가입           | HTTP 경로 차단. 신규 외부 가입은 Google만 허용                                          |
| 기존 이메일 로그인                             | Google 연결 전에는 유지. 연결 직후 기존 비밀번호 해시 제거                              |
| 기존 Kakao·Naver 로그인                        | 기존 연결 계정만 허용. 신규 가입 요청으로 우회할 수 없음                                |
| Google 명시 연결                               | 기존 계정에 로그인한 뒤 10분 이내에 같은 이메일의 Google 인증을 명시 요청. 기존 ID 유지 |
| 추가 프로필과 사진·완료 응답 사본              | `account_data_cleanup`에 기존 ID를 넣고 재시도 가능한 서버 작업으로 정리                |
| 여행·공개본·가져오기 사본의 옛 이름            | 기본 표시명으로 갱신. 여행 버전을 올려 오래된 화면의 덮어쓰기 차단                      |
| 기존 저장 요청 키·입력 해시·여행 가져오기 매핑 | 유지. 재시도로 여행이 다시 생성되지 않도록 보존                                         |

신규 수집을 먼저 닫는다. 정리 작업은 프로필 R2 파일을 삭제한 후 D1의 프로필·사진 메타데이터·프로필 제출 사본을 지운다. R2 저장 뒤 DB 기록에 실패했던 사진도 `profiles/<userId>/` 경로에서 찾는다. 한 계정의 정리가 실패하면 작업 행을 남기고 다른 계정의 정리는 계속한다.

`profiles` 등 호환 테이블과 인증 SDK의 nullable 컬럼은 당장 DROP하지 않는다. 실행 중인 구버전 코드와 외래키를 확인한 뒤 별도로 제거한다. 표가 남아 있다는 이유로 신규 개인정보 수집을 허용하지 않는다.

## 3. 신규 계정 삭제

정책 식별자는 `account-delete-v1`이다. 복구 유예를 새로 두지 않는다. 삭제 요청은 본인 세션과 생성 후 10분 이내의 최근 인증을 요구한다. 서버에 `userId`를 보내 삭제 대상을 고를 수 없다.

1. `GET /api/v1/account/deletion-preview`로 삭제·탈퇴·소유권 이전 대상을 확인한다.
2. 다른 참여자가 있는 본인 소유 여행은 `409 OWNERSHIP_TRANSFER_REQUIRED`로 거부한다. 다른 사람의 자료를 함께 삭제하거나 소유자를 임의 선정하지 않는다.
3. 기존 참여자를 새 소유자로 명시하고 현재 여행 버전으로 소유권 이전을 요청한다. 소유자 본인의 최근 인증이 필요하다. 이전 소유자는 편집자로 남는다.
4. `DELETE /api/v1/account`에 `{ "confirm": true, "policyVersion": "account-delete-v1" }`를 보낸다.
5. 서버는 삭제 작업 생성·전체 세션 폐기·본인 소유 여행 초대 철회를 같은 DB 처리에서 확정한다. 이전에 발급한 본인 비공개 파일 주소도 삭제 상태를 확인해 거부한다. 응답 `202 pending`은 접수이며 삭제 완료가 아니다.
6. 시간별 예약 실행이 파일·사본을 정리하고 마지막에 실제 `user` 행을 삭제한다. 실패하면 로그인 차단과 작업 행을 유지한 채 재시도한다. 자동 로그인으로 삭제를 취소하지 않는다.

공유 소유 여부는 작업 생성 SQL에서도 확인한다. DB 트리거는 삭제 접수 뒤 새 세션·여행·초대 수락·업로드·가져오기·OCR 결과가 뒤늦게 저장되는 것을 막는다. 이전 요청의 파일 저장이 늦게 끝나면 업로더뿐 아니라 대상 여행·소유자 상태를 확인하고 영속 정리 작업으로 넘긴다.

공유 여행에 삭제 대상 구성원의 참조가 남아 있으면 해당 참조 정리가 끝날 때까지 저장을 제한한다. 남은 참여자의 조회 권한은 유지한다. 앱 연결 단계에서 처리 중 안내와 재시도를 별도로 검수한다.

## 4. 삭제 범위

| 자료                                               | 신규 삭제 정책                                                                             |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 본인만 참여하는 소유 여행                          | 여행·일정·비용·영수증·초대·공개 사본·원본 파일 삭제                                        |
| 다른 사람이 소유한 공유 여행                       | 본인 구성원 표시·권한 제거. 다른 참여자의 일정·공동 기록 유지                              |
| 공유 여행의 본인 업로드                            | 원본·미디어 참조·해당 영수증·품목·연결 비용·OCR 사본 삭제. 사진 미보관 영수증도 포함       |
| 다른 소유자의 공개본                               | 삭제 사진을 선택 공개했거나 삭제 비용을 공개 요약에 포함한 경우 철회. 무관한 공개본은 유지 |
| 본인이 작성한 공개본·신고·차단                     | 삭제                                                                                       |
| 계정·인증 연결·세션·추가 프로필·초안·가져오기 자료 | 삭제. FK가 없는 자료와 비CASCADE 참조도 별도 정리                                          |
| 이미 소비한 초대의 본인 참조                       | `used_by=NULL`. `used_at`은 유지해 초대 재사용 방지                                        |
| 회원 이용 원본                                     | `usage_events.member_id` FK로 삭제. 구 90일 파기 작업도 원본을 명시 삭제                   |
| 식별자 없는 일별 통계                              | 개인 원본과 분리. 개인 ID·이메일을 넣지 않음                                               |
| 기기 게스트 원본·내보낸 파일·다른 사람이 받은 사본 | 서버가 원격 삭제하지 못함. 서버 계정 삭제가 기기 전체 삭제를 뜻하지 않음                   |

공유 일정·메모에는 작성자별 원문 이력이 없다. 본인 계정 삭제가 다른 사람이 소유한 공유 여행의 모든 공동 텍스트를 삭제한다는 뜻은 아니다. 삭제 대상으로 지정할 수 있는 근거와 공동 기록의 범위를 구분한다.

파일 정리가 실패하면 계정 DB를 먼저 지워 경로를 잃지 않는다. 늦은 파일 저장 직후 DB까지 중단된 경우에는 예약 실행이 파일의 서버 소유자·여행·가져오기 작업을 대조해 고아 파일을 다시 정리한다. 정상 파일과 복원 차단 표식은 보존한다. D1 최종 삭제는 원자 배치로 처리한다. 일부 DB 삭제만 성공한 상태를 완료로 응답하지 않는다. 한 작업은 5분 선점으로 중복 실행을 제한하고, 실패 시 선점을 풀어 다음 실행에서 재개한다. 이 5분은 복구 유예나 자료 보관 기간이 아니다.

## 5. 기존 90일 요청과 API 호환

유지보수는 진행 위치를 DB에 저장한다. 고아 파일은 한 호출에서 100개를 묶어 D1 3회로 대조한다. 회원 삭제는 공유 여행 2개·R2 목록 1000개까지 처리하고 남은 위치에서 재개한다. 추가 개인정보 정리도 계정 1개·사진 목록 1페이지씩 처리한다. 한 종류가 실패해 다른 종류의 정리를 계속 막지 않도록 삭제·개인정보 정리·구 요청 파기·영수증 정리를 번갈아 선택한다. 자료량에 따라 여러 예약 실행이 필요하다.

예약 실행은 무료 요금제의 호출 한도도 고려해 검증한다. 검사에서는 batch 안의 SQL까지 개별 계산해 50회보다 보수적인 예산을 적용했다. 실제 플랫폼의 batch 계산 방식과 한도는 [Cloudflare D1 공식 문서](https://developers.cloudflare.com/d1/platform/limits/)를 따른다. 확인일은 2026-11-06이다.

이미 저장된 `account_retirements`의 기산일·기한·상태를 유지한다. 유예 안의 본인 재로그인 복원과 기한 뒤 파기는 기존 계약을 따른다. 이 경로는 여행을 남기는 이전 정책이므로 신규 실제 삭제와 구분한다.

신규 `POST /api/v1/account/retirement`는 `410 RETIREMENT_POLICY_REPLACED`로 닫는다. 추가 프로필 입력 경로도 `410 PROFILE_INPUT_RETIRED`다. `/api/auth/delete-user`, `/delete-anonymous-user` 등 직접 삭제 우회 경로는 열지 않는다.

현재 앱의 예전 탈퇴 버튼·90일 안내와 새 삭제 API 연결은 별도 앱 작업이 필요하다. 서버 작업만으로 앱의 계정 삭제 흐름까지 완료했다고 표시하지 않는다. 비밀번호를 잊은 기존 이메일 계정의 복구 수단도 별도 결정·연결 대상이다.

## 6. 백업 복원과 삭제 표식

활성 DB와 R2 원본 삭제는 과거 백업의 개별 행을 즉시 지우는 작업과 다르다. DB에서 지운 계정이 백업 복원으로 되살아나지 않도록 R2 비공개 `account-deletions/<userId>.json`을 DB 최종 삭제 전에 남긴다. 내부 UUID·작업 UUID·정책 버전·요청 시각만 보관하며 이메일·sub·이름·사진·여행 내용은 넣지 않는다. 일반 미디어 API로 읽을 수 없다.

복원 시에는 공개 접속을 닫고 복원 DB에 최신 마이그레이션을 적용한다. 현재 R2 삭제 표식은 과거 백업으로 덮어쓰지 않는다. 새 복원 작업을 시작할 때 `account_storage_sweep.restore_cursor`를 빈 문자열로 초기화한다. 내부 함수 `restoreAccountDeletionBlocks`를 별도 호출마다 최대 10개씩 실행해 삭제 계정의 작업과 세션 차단을 복원한다. 진행 위치는 DB에 남으며 반환값 `complete=true`까지 다시 호출해야 한다. 복원본에 공유 소유 관계가 달라져 있으면 자동 파일 삭제를 거부하고 소유권부터 대조한다. 이를 확인하기 전 복원 DB를 서비스에 연결하지 않는다.

표식은 해당 계정이 포함된 복원 가능한 백업·내보내기 사본이 남아 있는 동안 보관한다. 운영자가 그 사본이 없음을 확인한 뒤 표식을 정리한다. 현재 운영 백업 기간을 조사하지 않았으므로 임의의 삭제 일수를 확정하지 않는다. R2까지 과거 상태로 함께 복원하는 경우에는 현재 삭제 표식을 별도로 보존·대조해야 한다.

## 7. 적용 순서와 복구

1. 대상 환경·Worker 버전·D1 백업·R2 접근 범위를 기록하고 정리 작업이 실행되지 않는 격리 사본을 준비한다.
2. 개인정보 값 대신 계정 종류별 건수·Google 중복 연결 건수·고아 참조·공유 소유 여행 건수를 조사한다. 한 계정에 Google 연결이 둘이면 자동 합치지 않고 이행을 중단한다.
3. `0013`까지의 기존 적용 상태를 확인한 뒤 `0014_account_lifecycle.sql`, `0015_account_deletion_guards.sql`을 순서대로 적용한다.
4. 새 서버를 배포하고 Google 인증·기존 로그인·자료 재조회·직접 입력 차단·삭제 접수·실패 재시도를 검수한다. 추가 통계 수집 경로는 아직 열지 않는다.
5. 정리 작업을 실행하고 계정 ID·여행 ID·소유권·저장 요청 키 보존, 개인정보 사본·R2 원본 제거를 확인한다.

추가 스키마만 적용한 단계에서는 기존 행을 병합하거나 지우지 않는다. 새 Worker 적용이 실패하면 정리 실행을 중단하고 추가 구조를 유지한 채 원인을 확인한다. 실제 개인정보 정리·계정 삭제 후에는 옛 개인정보를 일반 롤백으로 복원하지 않는다. 운영 이행·정리·배포는 대상 환경이 포함된 실행 승인 범위에서 수행한다.

## 8. API와 완료 범위

| 경로                                                | 역할                                                        |
| --------------------------------------------------- | ----------------------------------------------------------- |

| `GET /api/v1/profile`                               | 구 앱 조회 호환. 추가 입력 완료를 요구하지 않는 기본 표시값 |
| `POST /api/auth/link-social`                        | 최근 본인 세션에서 Google 명시 연결                         |
| `GET /api/v1/account/deletion-preview`              | 삭제 범위·소유권 이전 필요 목록                             |
| `POST /api/v1/account/owned-trips/:tripId/transfer` | `{newOwnerId,version}`로 기존 참여자에게 소유권 이전        |
| `DELETE /api/v1/account`                            | 명시 확인·정책 버전·최근 인증을 갖춘 본인 삭제 접수         |

이 정책의 구현·검증 상태는 [계정 데이터관리 검수](<../04. 검증/계정_데이터관리_검수.md>)에 기록한다. 로컬 격리 D1·R2 검사, 실제 Google 제공자 로그인, 운영 이행·배포를 각각 구분한다.
