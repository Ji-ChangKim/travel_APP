# 핵심 사용자 사이클 검수

## 현재 판정과 확정한 범위

앱의 기본 화면 이동은 로컬 실제 서버 검수를 통과했다. 게스트 서버 저장과 실제 Google·장소·영수증·공유를 잇는 전체 여행 사이클은 아직 완료하지 않았다. 기본 구조의 변경·캡처·검증 근거는 [앱 기본 구조 구현 검수](앱기본구조_구현검수.md)에서 확인한다.

사용자와 확정한 기준은 다음과 같다.

- 게스트: 실행 → 게스트 시작 → 기본 프로필 표시 → 여행 생성 → 계획·기록 추가 → **게스트 프로필로 서버 DB 저장 → 재조회**. 커뮤니티 공유는 게스트 완료 기준에서 제외한다.
- 일반 회원: 실행 → Google 로그인 → 기본 프로필 표시 → 여행 생성 → 계획 추가 → 커뮤니티 공유 → 공개 결과 재조회.
- 두 경로 모두 추가 프로필 입력은 요구하지 않는다.
- 지금은 앱 기본 구조를 우선하고 여행 제작·일정 편집은 이후에 진행한다.

기준 버전은 `main`의 `d92abb9cfd640fd84a8aa5eb3aeceaec99ad7eb0`와 현재 변경 파일이다. 검수 환경은 Windows·Node.js 22.17.0·npm 11.5.2·Chrome·격리 Worker/D1/R2다. 운영 데이터·실제 개인정보·실제 계정으로 공개·삭제 검수를 수행하지 않았다.

판정은 통과·실패·미검증·해당 없음으로 구분한다. 코드 존재, 자동 검사, 실제 화면 조작, 실제 공급자 연결을 서로 구분한다. 기기 캐시에 남은 화면은 서버 저장 성공으로 세지 않는다.

## 남은 쟁점

### GUEST-01 게스트 서버 저장

필수 새 기능이다. 현재 여행·계획·사진은 기기 저장소에만 보관하며 서버의 게스트 소유 여행 생성·재조회는 미구현이다. Google 로그인 없이 서버가 검증할 게스트 자격과 소유권을 마련해야 한다. 앱이 보낸 UUID만으로 권한을 주지 않는다.

기존 기기 기록을 보존하고 서버 저장·중복 요청·세션 복원·재조회를 연결한다. DB·도메인 계약이 바뀌면 DB 사전을 갱신한다. 기기 조회를 서버 조회로 대체 보고하지 않는다. 기존 기기 전용 계정 정책 문서도 이 구현 단계에서 함께 갱신한다.

### RECEIPT-01 장소만 남기기

`ReceiptReviewView.tsx`는 장소만 남길 때 금액을 `'0'`으로 바꾸지만 `formCommands.ts`는 계속 `receipt.confirm`을 만든다. 공통 검증은 양수 금액만 허용한다. 실제 제품의 변환·검증 함수에서 `input.amount` 오류를 확인했다.

지출을 만들지 않는 별도 저장 분기가 필요하다. 0원 지출을 허용하는 것만으로 해결하지 않는다. 통과 기준은 장소 1개·새 지출 0개·같은 재조회 결과이며, 원본 보관·정리를 함께 확인한다.

### PLACE-01 게스트 Google 검색

기기 게스트의 Google 검색은 실제 서버 세션이 없어 오류로 끝난다. 직접 입력 저장은 가능하다. 서버 게스트 작업에서 검색 접근·사용량 제한을 정하고 실제 결과 선택·저장을 검수한다. 회원 전용으로 유지한다면 이용 조건과 로그인 복귀를 먼저 연결한다.

### RECEIPT-02 일정 작성 중 영수증 진입

`forms.ts`는 새 일정에도 UUID를 만든다. `ScheduleEditorView.tsx`는 폼 ID가 없을 때만 영수증 촬영·사진 버튼을 표시하므로 신규 장소 작성 화면에서도 버튼이 없다. 여행 상세 하단의 별도 영수증 진입은 존재한다. 신규 여부 판단과 지원할 진입 경로를 여행 페이지 작업에서 맞춘다.

### RECEIPT-03 DAY와 결제 날짜

영수증 확인 화면에서 DAY를 고르면 `transactionDate`가 해당 DAY 날짜로 바뀐다. 실제 결제일을 수정하는 일과 방문 일정을 배치하는 일을 구분해야 한다. 여행 범위 밖 결제일·현지 자정·여행 후 일괄 등록을 실제 촬영 자료로 검수한다.

## 해결한 기본 구조 연결

- AUTH-01: 기본 프로필의 생일·성별 생략을 앱이 받아들이도록 고치고 추가 입력 관문을 제거했다. 실제 로컬 회원이 홈·MY로 들어가고 재로그인하는 검수를 통과했다. 실제 Google 공급자 인증 통과를 뜻하지 않는다.
- DOC-01: [앱·서버 API 계약](<../01. API계약/앱서버_API계약.md>)을 실제 `/api/v1`, `/receipts/ocr`, `/files` 및 새 계정 경로에 맞췄다.
- I18N-01: 누락된 고정 문구 번역을 보완했다. 인증 단위 검사 356개 통과.

Google 403·429·500을 빈 결과로 바꾼다는 초기 후보는 실제 제품 함수 검사에서 모두 503 오류로 처리돼 결함에서 제외했다. `shared/http/readBounded.ts`가 HTTP 성공 여부를 검사한다. 실제 Google 검색 성공 검수와는 별개다.

## 버튼 검수 절차

1. 화면·이용 방식·권한·상태별로 버튼을 등록한다. 시작·로그인·홈·커뮤니티·MY뿐 아니라 여행 제작·장소·영수증·공개 확인의 후속 검수를 구분한다.
2. 버튼마다 정상·빈 상태·오류·저장 중 조건과 기대 이동·저장 결과를 적는다. 비활성 조건과 연속 누르기를 확인한다.
3. 취소·닫기·뒤로가기는 저장 없이 원래 화면·입력으로 돌아가야 한다. 처리 중에는 중복 요청·이탈로 자료가 손상되지 않아야 한다.
4. 저장 직후 표시 → 화면 이탈·재진입 → 새 조회를 확인한다. 삭제는 새 조회에서도 제거돼야 하며 연결된 비용·영수증·사진 영향을 확인한다.
5. 실패 뒤 재시도·다른 사진·직접 입력·돌아가기 중 실제 제공하는 복구 행동을 조작한다.

기록 필드는 `화면·상태 / 이용 방식·권한 / 버튼 / 조작 / 기대 결과 / 실제 결과 / 판정 / 증거`다. 버튼 목록을 수집한 것만으로 모두 눌러 검수한 것으로 세지 않는다. 기본 구조 밖 여행·영수증·공유 버튼 전수 검수는 남아 있다.

회원과 게스트의 실제 서버 저장은 HTTP 응답·재조회·검수 DB 값을 대조한다. 같은 요청 재시도는 같은 키를 쓰며 버전 충돌은 최신 자료를 확인한 뒤 처리한다. 미인증·보기 전용·다른 여행 권한·오프라인·서버 오류는 기능에 필요한 항목을 골라 검사한다. 운영 자료로 삭제·공개 게시를 시험하지 않는다.

## 검증과 검토 기록

현재 기본 구조의 명령·결과·캡처·검토 차수는 [구현 검수](앱기본구조_구현검수.md)에 기록했다. 전체 API 검사 174개와 기본 구조 UI 6개는 로컬 실제 저장소 검수다. 외부 Google·실기기 촬영·실제 OCR·전체 여행 공개 사이클은 미검증이다.

영수증·검색의 제품 함수 재현 자료는 `outputs/functional-audit/contract-results.json`, 새 기본 구조의 실제 요청·캡처는 `outputs/app-shell/ui-results.json`과 PNG다. 로컬 출력 폴더는 Git 제외 대상이므로 다른 담당자에게 이 문서와 재현 조건을 함께 전달한다.

CYCLE-01·CYCLE-02·RECEIPT-01·SHARE-01은 최초 검토 0회로 조사했다. 기본 구조의 계정 수정은 SHELL-AUTH-01 재검토 1회에서 읽기 전용 검토를 마쳤다. 영수증·여행 페이지는 새 변경이 없어 추가 재검토를 요청하지 않았다. 실제 조작과 검사는 주 에이전트가 수행했다. 비밀 값·실제 개인정보는 기록하지 않는다.

후속 순서는 실제 Google·실기기 인수, 게스트 서버 저장·재조회, 여행 제작과 Google 장소·영수증·회원 공유 검수다. 영수증 추출·저장 성공을 본인 방문·영수증 진위 인증으로 표현하지 않는다.
