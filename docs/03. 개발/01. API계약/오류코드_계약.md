# TripPrint 에러 코드 정의서

- 문서 버전: 1.0
- 작성일: 2026-10-13
- 대상: `apps/mobile`의 APP/WEB 및 `apps/api`의 현행 API
- 목적: 내부 테스트에서 페이지·발생 상황·통신 여부·원인·복구 방법을 동일한 기준으로 판단한다.
- 상태: **현행 오류 목록 + 신규 표시/진단 규약**. `TP-...` 표시 코드와 공통 오류 변환기는 아직 앱에 구현되지 않았다. 아래 사용자 문구는 적용 기준이며 현재 화면 문구와 전부 일치하지 않는다.
- 관련 문서: [핵심 흐름 안정화 및 실기기 인수](<../../00. 문서안내/개발검수_현재상태.txt>), [API 제안 계약](API_기본계약.md), [DB·도메인 명세](<../02. 데이터정의/DB_객체사전.txt>)

## 1. 기본 원칙

1. **에러 코드, HTTP 상태, 발생 페이지, 실제 원인을 따로 기록한다.** HTTP 409만으로 동행 충돌을 판단하지 않는다.
2. **서버에 연결하지 못한 것과 서버가 거절한 것을 구분한다.** HTTP 응답을 받았다면 서버 또는 중계 계층의 응답이다. 응답을 못 받았다면 저장 성공 여부가 불명확할 수 있다.
3. **앱 버전 오류와 여행 데이터 수정 충돌은 다르다.** 앱 업데이트는 호환되지 않는 형식이 확인된 경우에만 안내한다.
4. **게스트 여행은 기기 저장이다.** 게스트 처리기가 API와 비슷한 코드·상태를 반환해도 원격 서버 통신 오류로 분류하지 않는다. 공개 여행지·커뮤니티 등 온라인 기능은 게스트도 통신한다.
5. 오류 화면은 무엇을 하지 못했는지와 다음 행동을 먼저 안내한다. 코드·추적 번호는 보조 정보로 표시한다.
6. 실패를 빈 목록·가짜 로그인·가짜 저장 성공으로 바꾸지 않는다. 원본 여행·사진·작성 내용을 임의 삭제하지 않는다.
7. 이번 문서 작성은 오류 규약 정의다. 신규 코드 적용, 로그 수집, DB 변경, 배포 완료를 의미하지 않는다.

## 2. 오류 분류와 판정 근거

| 분류  | 의미                                       | 서버 통신 여부·판정 근거                                         | 대표 상황                                                           |
| ----- | ------------------------------------------ | ---------------------------------------------------------------- | ------------------------------------------------------------------- |
| `NET` | 연결 또는 응답 대기 실패                   | 원격 요청을 시작했으나 유효 HTTP 응답을 확보하지 못함            | 오프라인, 연결 종료, DNS/TLS/CORS 등으로 fetch 실패, 제한 시간 초과 |
| `SRV` | 서비스 실패 또는 응답 계약 오류            | 원격 HTTP 5xx, 제공 불가 코드, 성공 응답의 JSON/필수 구조 불일치 | API 500/503, HTML 오류 응답, 잘못된 배포 응답                       |
| `AUT` | 로그인·인증·계정 일치 오류                 | 서버 확인 또는 기기 내 인증 흐름 검증                            | 로그인 필요, 확인된 만료, 잘못된 로그인 콜백, 처리 중 계정 변경     |
| `PER` | 이용 권한 제한                             | 서버 권한 검사 또는 게스트 기능 제한                             | 읽기 전용 멤버의 수정, 게스트의 회원 기능 접근                      |
| `VAL` | 입력·파일 형식 오류                        | 요청 전 기기 검증 또는 서버 400/422                              | 필수값·날짜·금액 오류, 닉네임 중복, 잘못된 공유 링크                |
| `VER` | 호환성 또는 요청 버전 정보 오류            | 명시적인 형식 검사나 `VERSION_REQUIRED`                          | 지원하지 않는 시작 계약/기기 문서 버전, If-Match 누락               |
| `CON` | 동시 수정·요청 재사용 충돌                 | 명시적인 API/게스트 오류 코드                                    | `VERSION_CONFLICT`, 중복키의 본문 불일치·만료                       |
| `BIZ` | 여행 상태·대상 존재·초대 상태 제한         | 서버 또는 게스트 업무 규칙                                       | 보관 여행 수정, 대상 삭제, 초대 만료·철회                           |
| `DEV` | 기기 저장·운영체제 작업 실패               | 기기 파일, localStorage, SecureStore, 외부 앱 실행 결과          | 저장 공간 부족, 사진 처리 실패, 지도/스토어 실행 실패               |
| `LIM` | 크기·요청 횟수 제한                        | 기기 제한 검사 또는 HTTP 413/429                                 | 업로드 용량 초과, 영수증 스캔 횟수 초과                             |
| `MED` | 사진·영수증 작업 실패                      | 작업 단계는 확인했으나 더 구체적인 원인이 없음                   | 사진 업로드/표시 실패, 영수증 인식 실패                             |
| `APP` | 미분류 앱 오류 또는 저장 후 후속 조회 실패 | 안전한 대체 처리에 사용                                          | 알 수 없는 예외, 저장 성공 뒤 목록 갱신 실패                        |

**판정 제한:** fetch 실패만으로 Wi-Fi, DNS, TLS, CORS 중 어느 것이 원인인지 확정하지 않는다. 일반 `TypeError` 전체를 네트워크 오류로 취급하지 않고, 실제 원격 요청 경계에서 발생했는지 확인한다. JSON/Zod 오류도 검증 대상이 사용자 입력인지 서버 응답인지 기기 문서인지에 따라 분류가 달라진다.

원격 HTTP 응답이 없는 실패의 `httpStatus`는 `null`이다. 0·500을 임의로 넣지 않는다. 게스트 처리기의 상태 숫자는 `localStatus`로 구분하고 원격 `httpStatus`로 기록하지 않는다.

## 3. 에러 코드 표시 규약

### 3.1 형식

표시 코드 형식은 **`TP-{PAGE}-{CATEGORY}-{NNN}`**으로 정한다. 예: `TP-TRIP-CON-001`.

- `TP`: 서비스 식별자. 내부 패키지명 WHEREGO와 분리한다.
- `PAGE`: 아래 페이지/기능 식별자. `/trips/실제UUID`처럼 개인정보나 리소스 ID를 포함하지 않는다.
- `CATEGORY`: 2절의 원인 분류.
- `NNN`: 4절의 공통 상황 번호. 같은 CATEGORY 안에서 의미를 고정하고 폐기 코드도 재사용하지 않는다.
- 서버의 기존 `VERSION_CONFLICT` 등은 **원인 코드 `sourceCode`**로 보존한다. 신규 TP 코드로 서버 응답을 변경하지 않는다.
- 일정·사진처럼 하나의 상세 페이지에 여러 작업이 있을 때는 해당 기능 식별자를 쓴다. 예: 사진 다운로드는 `TP-PHOTO-MED-002`, 비용 저장은 `TP-COST-NET-002`.
- 서버·인증 공급자의 원문 메시지나 임의 코드를 그대로 표시 코드로 사용하지 않는다. 등록되지 않은 오류는 해당 페이지의 `APP-001`로 변환한다.

| PAGE    | 페이지/기능              | 현행 진입 위치                    |
| ------- | ------------------------ | --------------------------------- |
| `BOOT`  | 시작·복원·업데이트       | `/`                               |
| `SIGN`  | 이메일·소셜 로그인/가입  | `/login`, 이메일 입력 화면        |

| `TRIP`  | 여행 상세·기간·상태      | `/trips/[id]`                     |
| `PLAN`  | 일정·장소 검색·지도      | 여행 상세 일정 입력               |

### 3.2 표시 위치·문구·접근성

| 상황                          | 표시 방식                     | 안내 및 행동                                                          |
| ----------------------------- | ----------------------------- | --------------------------------------------------------------------- |
| 필드 입력 오류                | 해당 입력 바로 아래           | 잘못된 항목과 수정 방법. 여러 오류는 첫 오류로 이동하며 입력을 유지   |
| 조회 전체 실패                | 해당 페이지 오류 영역         | 불러오지 못한 대상 + `다시 불러오기` + 가능한 복귀 경로               |
| 일부 카드·사진 실패           | 해당 카드/사진 영역           | 정상 페이지는 계속 사용. 실패 영역만 재시도                           |
| 저장 거절·응답 유실           | 작성 폼 안의 지속 오류 영역   | 입력을 유지하고 상황에 맞는 `다시 저장하기` 또는 `최신 내용 불러오기` |
| 로그인 만료 확인              | 해당 작업 안내 후 로그인 진입 | 재로그인 안내. 다른 계정으로 이전 요청을 자동 재전송하지 않음         |
| 필수 호환성 오류              | 시작/해당 기능의 차단 화면    | 업데이트 안내. 확인되지 않은 호환성을 캐시로 우회하지 않음            |
| 선택 업데이트                 | 안내 카드                     | `Google Play에서 업데이트` / `현재 버전으로 시작`. 오류 코드 없음     |
| 취소·알림 거절·조회 결과 없음 | 일반 안내·빈 상태             | 정상 사용자 선택으로 처리. 장애 코드/장애 집계 없음                   |

화면 예시(신규 규약):

```text
다른 동행이 내용을 변경했어요.
작성한 내용은 유지돼요. 최신 내용을 확인한 뒤 다시 저장해 주세요.
[최신 내용 불러오기]
오류 코드 TP-PLAN-CON-001
요청 번호 <실제 응답의 requestId가 있을 때만 표시>
```

문구 다음 줄에 작은 보조 글씨로 `오류 코드 ...`를 표시한다. 입력 오류는 보조 코드가 폼 전체를 반복해서 채우지 않도록 오류 영역에 한 번만 표시한다. 사용자가 복사할 수 있는 오류 정보에는 코드·발생 시각·안전한 추적 번호만 포함한다. 원문 링크·토큰·사진·입력 본문은 포함하지 않는다. 복사 버튼은 실제 복사 기능이 구현된 뒤 표시한다.

색상만으로 실패를 구분하지 않는다. 오류 텍스트에 접근성 알림을 제공하고 스크린리더가 문구와 행동을 읽을 수 있게 한다. 중요한 저장 오류는 자동으로 사라지는 토스트만으로 전달하지 않는다. 재시도 중 버튼을 잠그고 완료 후 다시 사용할 수 있게 한다.

개발 용어인 DB·API·세션·공급자 설정, 원문 예외·SQL·스택·HTTP 응답 HTML은 사용자 문구에 표시하지 않는다. 현재 문구를 유지할 때도 실제로 보존된 정보에만 “유지돼요/보관되어 있어요”라고 안내한다. 화면 안의 임시 입력 유지가 앱 종료 후 영구 복원을 의미하지 않는다.

### 3.3 변환 우선순위와 정보가 없는 응답

1. 발생 페이지·작업 단계·실제 통신 경계를 먼저 확인한다. 입력 검증/기기 문서/서버 응답의 파싱 오류를 같은 오류로 묶지 않는다.
2. 알려진 `sourceCode`와 HTTP/로컬 상태의 조합이 일치하면 5절 대응표를 적용한다. 예를 들어 NICKNAME_TAKEN + 409는 VAL-002다.
3. 응답 코드와 상태가 모순되면 계약 이상으로 진단하고 원문 메시지를 신뢰하지 않는다. 잘못된 응답만으로 만료·저장 거절·저장 성공을 확정하지 않는다.
4. 원인 코드가 없으면 아래 HTTP 보조 기준을 적용한다. 공통 API가 아닌 인증/파일 경로는 해당 경로의 계약을 우선한다.
5. HTTP 응답이 없으면 요청 경계에서 확인된 연결 실패/시간 초과만 NET으로 분류한다. 그 외에는 확인된 기기·사진 단계 오류 또는 APP-001로 처리한다.

| 실제 HTTP만 확인된 경우 | 보조 표시 기준                                              | 주의 사항                                                                  |
| ----------------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------- |
| 400 / 422               | VAL-001                                                     | 원문 HTML/메시지를 필드 안내로 사용하지 않음                               |
| 401                     | AUT-001                                                     | 인증을 다시 확인해야 함. 구체적인 만료 근거가 있는 경우만 AUT-002로 세분화 |
| 403                     | PER-001                                                     | 게스트 회원 기능 제한은 확인된 로컬 MEMBERSHIP_REQUIRED로 구분             |
| 404                     | BIZ-002                                                     | 특정 데이터 삭제를 확정하지 않음. 잘못된 API 경로/배포 문제도 조사         |
| 409                     | APP-001 + 결과 확인 안내                                    | sourceCode 없이 CON-001로 단정하거나 자동 새 키를 생성하지 않음            |
| 410                     | INV 작업의 초대 만료 계약이 확인되면 BIZ-003, 그 외 APP-001 | 모든 410을 초대 오류로 해석하지 않음                                       |
| 413                     | LIM-001                                                     | 해당 경로의 요청/파일 한도 안내                                            |
| 428                     | 해당 여행 쓰기 계약이면 VER-003, 그 외 APP-001              | 스토어 앱 버전 오류로 해석하지 않음                                        |
| 429                     | LIM-002                                                     | Retry-After가 실제 제공되고 유효할 때만 대기 시간 표시                     |
| 500~599                 | SRV-001                                                     | 503만으로 설정 누락·OCR 실패를 특정하지 않음                               |
| 그 외 실패 상태         | APP-001                                                     | 확인 가능한 상태만 진단에 보존                                             |

화면 영향도는 코드와 별도로 판단한다. `blocking`은 시작 호환성·필수 인증·전체 조회처럼 다음 진행을 막는 오류, `action`은 현재 저장/검색 실패, `partial`은 일부 카드·사진·선택 알림 실패다. 정상적인 취소·빈 목록·선택 업데이트는 오류 영향도를 부여하지 않는다. 사진 한 장의 오류로 앱 전체를 차단하지 않는다.

### 5.1 현행 응답 형식과 예외

공통 `renderError`를 통과한 오류는 다음 형식이다. 예시 번호는 설명용이며 실제 진단에 사용하지 않는다.

```json
{
  "error": {
    "code": "VERSION_CONFLICT",
    "message": "요청을 처리할 수 없습니다."
  },
  "meta": { "requestId": "실제 요청에 부여된 UUID" }
}
```

- `fieldErrors`는 실제 ZodError에서 얻을 수 있을 때만 추가된다. 모든 422에 존재하지 않으며 화면 문구는 허용한 필드·안전한 문구로 변환한다.
- `currentVersion`, `retryAfter`, `displayCode`는 현행 공통 오류 응답의 보장 필드가 아니다. API 제안 계약의 예시와 혼동하지 않는다.
- `/api/auth/*`는 Better Auth 자체 응답을 반환한다. 공통 오류 envelope와 requestId가 항상 있다고 가정하지 않는다.
- 중계 계층의 HTML/빈 응답, 미등록 경로의 기본 404, 파일·이미지 응답은 별도 형식일 수 있다. HTTP 상태가 확인되면 보존하고 원문 HTML을 표시하지 않는다.
- Foundation 클라이언트는 실패 응답이 JSON이 아니어도 HTTP 상태를 보존하며 `payload=null`로 전달한다. 성공 응답의 JSON/구조 오류는 별도 계약 실패다.
- 공개 시작·여행지·커뮤니티 클라이언트와 일부 인증/업로드 처리는 현재 오류를 일반 Error 문구로 바꿔 HTTP/원인 코드가 소실될 수 있다. 문구만 보고 구체적인 서버 코드나 원인을 복원하지 않는다.

| `unknown`   | 전송 뒤 연결 종료·시간 초과·5xx·성공 응답 해석 실패 등 | 같은 경로·본문·계정·Idempotency-Key로 결과 재확인. 새 키 자동 생성 금지 |
| `confirmed` | 실제 쓰기 성공 응답/동일 요청 성공 재생을 확인         | 후속 조회 실패는 APP-002. 조회만 재시도                                 |

이 상태는 **신규 진단 규약**이며 새로 구현된 상태 필드가 아니다. 저장 결과 불명확은 원인 분류와 별개다. 예: `TP-COST-NET-002` + `unknown`.

### 7.2 반드시 지킬 처리 순서

1. 계정·입력·권한·기기 파일을 검증한다. 확인된 입력 오류는 해당 필드에 표시한다.
2. 쓰기 시작 시 본문·계정·경로·요청 키를 확정하고 중복 클릭을 차단한다. 자동 쓰기 재시도는 하지 않는다.
3. 실패 시 입력과 확정 요청을 보존한다. 401은 재인증, 403은 권한, 409는 sourceCode로 분기한다.
4. `VERSION_CONFLICT`라면 최신 내용을 읽고 사용자에게 변경 검토를 맡긴다. 최신 조회도 실패하면 초안/기존 요청을 잃지 않고 조회 재시도를 제공한다.
5. 최신 내용을 반영해 새로운 저장을 승인한 때에만 새 버전·새 요청 키를 만든다. 자동 덮어쓰기는 하지 않는다.
6. 네트워크/시간 초과처럼 결과가 불명확하면 확정했던 동일 요청으로 재확인한다. 사진 업로드를 매번 반복하거나 비용/여행을 새로 생성하지 않는다.
7. 키 만료·본문 불일치는 저장 결과 대조를 우선한다. 무조건 새 키로 재시도하면 중복 저장할 수 있다.
8. 작업 중 계정이 변경되면 이전 계정의 응답으로 화면을 이동하거나 현재 계정 요청으로 바꾸지 않는다.
9. 원본 삭제·후속 목록 갱신 등 부수 작업만 실패하면 완료된 저장 사실을 유지한다.

조회 재시도는 동일 계정의 읽기 작업에만 적용한다. 자동 재시도를 추가할 경우 횟수 제한·지연을 두고 인증/권한/입력/호환성/업무 제한은 자동 반복하지 않는다. 취소된 조회·이전 검색의 늦은 응답은 사용자 오류로 알리지 않는다. 타임아웃과 사용자의 취소를 이름이 `AbortError`라는 이유만으로 동일하게 처리하지 않는다.

현행 참고: Foundation 요청은 기본 15초, 시작 공통 정보·Play 확인은 8초, 공개 여행지 조회는 30초다. 모든 외부 작업이 동일한 제한 시간을 갖거나 같은 예외 형식을 반환한다고 가정하지 않는다.

원문 URL 대신 `/api/v1/trips/:tripId/commands` 같은 허용된 경로 템플릿만 남긴다. 서버 requestId는 요청마다 달라질 수 있으며, 동일 쓰기를 구분하는 Idempotency-Key와 다른 개념이다. 수집 전송처·보존 기간·열람 권한은 로그 기능 구현 시 별도 결정한다. 현재 자동 수집이 된다고 안내하지 않는다.
