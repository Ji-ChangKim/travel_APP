# 웹 페이지 개발 폴더와 Git 운영 계획

웹은 기존 `travel_APP` 저장소의 `apps/web`에서 개발한다. 앱·웹·API를 한 저장소에 두고 회원·여행·영수증의 모델과 API 계약을 함께 관리한다. 페이지별 작업은 짧게 유지하는 기능 브랜치로 나누고 검사를 마친 뒤 `main`에 합치는 방향을 권장한다.

이 문서는 적용한 개발 기반과 후속 페이지·공통 UI·배포 계획을 구분한다. [저장소 아키텍처](저장소_아키텍처규격.md), [웹사이트 전체 계획](<../../01. 서비스기획/03. 작업계획/웹사이트_초기구성_계획서.md>), [홈페이지 화면 계획](<../../02. 디자인/01. 화면설계/웹홈페이지_화면계획.md>)을 연결한다. 0.0.1에서는 `codex/prepare-0.0.1` 브랜치에 Next.js 실행·검사 환경을 구성한다. 현재 실행 방법은 [웹 개발 실행 안내](<../03. 개발환경/웹_개발실행_안내.md>)를 따른다. 커밋·푸시·원격 설정·운영 배포는 별도 범위다.

Android·WEB 1.0.0의 최종 범위·구조 장단점·개발 단계는 [정식 출시 계획](<../../01. 서비스기획/03. 작업계획/앱웹_정식출시_계획서.md>)을 따른다. iOS는 후속 출시다. 이 문서의 브랜치는 단계 구현을 위한 작업 단위이며 실제 제품의 버전과 별개다.

## 2. Git 저장소와 브랜치

앱과 웹의 저장소를 분리하지 않는다. 공유 계약 변경을 같은 변경 묶음에서 검토하고, 어떤 웹·API·앱 조합을 검증했는지 같은 커밋으로 추적한다. 배포 시점은 클라이언트별로 다를 수 있으므로 설치된 구버전 앱과의 API 호환성도 유지한다.

| 브랜치안               | 용도                                | 유지 방식                              |
| ---------------------- | ----------------------------------- | -------------------------------------- |
| `main`                 | 검사를 통과한 통합 기준             | 직접 기능 작업·강제 덮어쓰기 금지 권장 |
| `codex/web-foundation` | 웹 실행·타입·빌드·검사·공통 UI 연결 | 기반 검증을 마치면 병합·정리           |
| `codex/web-home`       | 홈의 로그인 전·후 화면과 상태       | 관련 문서·홈 검사까지 한 작업으로 병합 |
| `codex/web-auth`       | 공통 계정·쿠키·인증 복귀            | 앱 인증 회귀 포함                      |
| `codex/web-planner`    | 일정·지도·장소 편집                 | 공유 계약과 앱 읽기 호환 검증          |
| `codex/web-receipts`   | 영수증 업로드·확인·연결             | 중복·비용·삭제·재조회 검증             |
| `codex/web-community`  | 공개 일정 열람·공개·가져오기        | 공개 정보·철회·권한 검증               |

페이지마다 영구 브랜치를 만들지 않는다. 같은 페이지라도 독립된 수정은 새 작업 브랜치로 처리한다. 초기에는 상시 `develop`·`web` 브랜치를 추가하지 않고, 검수 환경은 배포 대상과 커밋으로 구분한다.

작업 순서는 **현행 문서·미커밋 변경 확인 → main 기준 작업 브랜치 → 구현·문서·검사 → 변경 검토 요청(PR) → 검사·화면 근거 확인 → main 병합 → 검수 환경 확인 → 승인 범위의 운영 배포**다. 현재 남은 기획 문서는 구현 변경과 구분해 반영 범위를 확인한다. 임의 stash·reset·일괄 stage로 다른 변경을 섞거나 지우지 않는다.

PR에는 관련 화면·기능 ID, 변경 파일, 공통 계약 영향, 실제 캡처, 실행 검사, 미검증 항목을 적는다. 기획·화면·관련 검사·문서 변경은 함께 검토하되 관계없는 정리와 의존성 교체는 넣지 않는다. 처음에는 작업 단위의 squash 병합을 권장하며 결과 커밋도 프로젝트의 `타이틀 : 설명` 형식을 따른다.

커밋 예시는 `feat: 웹 홈 로그인 전후 화면 구성 : 회원 상태별 대표 여행과 생성·공개 일정 이동을 연결하고 빈 화면·오류 복귀를 추가`다. 빌드 결과·검수 이미지·실제 키·로컬 설정은 커밋하지 않는다. 커밋·푸시 시 같은 날짜의 일일 보고서에 결과와 미검증 범위를 누적한다.

`main`에는 PR·필수 검사·검토 해결·강제 push 금지 등의 보호를 적용하는 방향을 권장한다. 리뷰 인원 조건은 실제 담당자 수와 GitHub 제공 범위에 맞춘다. 혼자 작업하는데 충족할 수 없는 필수 승인 인원을 설정하지 않는다. 이는 설정 제안이며 원격에 적용한 상태가 아니다. [GitHub 브랜치 보호](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

## 3. 최상위 개발 폴더

```text
travel_APP/
├─ apps/
│  ├─ mobile/       기존 Expo 앱과 앱의 웹 실행
│  ├─ web/          별도 웹사이트
│  └─ api/          공통 인증·여행·영수증·커뮤니티 API
├─ packages/
│  ├─ domain/       공통 데이터 모델·업무 규칙
│  ├─ validation/   공통 입력·응답·명령 검증
│  ├─ api-client/   공통 통신·오류·저장 요청
│  └─ ui/           도입 후보: 앱·웹 공통 표현과 탐색 구성요소
├─ tests/
│  ├─ web/          웹 화면·상태·이동 검사
│  └─ config/       화면별 Playwright 설정
├─ scripts/         기존 역할별 도구 폴더
├─ docs/            기획·화면·API·DB·검수 기준
├─ outputs/         로컬 캡처·로그·검수 결과, Git 제외
├─ package.json
└─ package-lock.json
```

`packages/ui`는 아직 없는 도입 후보이며 폴더를 미리 비워 만들지 않는다. `apps/web`도 필요한 기능부터 추가한다. 새로운 저장소, 별도 웹 회원 DB, 독립된 디자인 토큰 폴더를 만들지 않는다. Android 산출물의 기존 외부 경로는 유지하며 웹 작업 때문에 이동하지 않는다.

## 4. 웹 내부 페이지 구조

웹의 기본 후보는 **Next.js App Router + TypeScript**다. 공개 일정의 페이지별 주소·검색 노출과 회원 작업 화면을 한 프로젝트에서 관리하려는 선택이다. 다음 구조는 해당 후보를 선택했을 때의 설계이며 프레임워크 설치·최종 확정을 뜻하지 않는다. 실제 실행 환경·공통 UI·인증을 검증한 뒤 버전을 고정한다. [Next.js 페이지 구조](https://nextjs.org/docs/app/getting-started/project-structure)

```text
apps/web/
├─ src/
│  ├─ app/
│  │  ├─ layout.tsx
│  │  ├─ page.tsx                         / 소개 랜딩
│  │  ├─ (member)/home/page.tsx             /home 서비스 홈 계획
│  │  ├─ (auth)/login/page.tsx             /login
│  │  ├─ (public)/footprints/page.tsx      /footprints
│  │  ├─ (public)/community/[postId]/page.tsx
│  │  └─ (member)/
│  │     ├─ plans/page.tsx                 /plans
│  │     ├─ new-trip/page.tsx              /new-trip
│  │     ├─ trips/[tripId]/page.tsx
│  │     └─ my/page.tsx                    /my
│  ├─ features/
│  │  ├─ home/
│  │  │  ├─ ui/
│  │  │  │  ├─ HomePage.tsx
│  │  │  │  ├─ VisitorHomeView.tsx
│  │  │  │  └─ MemberHomeView.tsx
│  │  │  ├─ model/homePresentation.ts
│  │  │  ├─ manager/useHomeController.ts
│  │  │  └─ styles/homeStyles.ts
│  │  ├─ auth/
│  │  ├─ trip-planning/
│  │  ├─ receipts/
│  │  └─ community/
│  ├─ shared/
│  │  ├─ navigation/routeMap.ts
│  │  ├─ config/
│  │  └─ errors/
│  └─ server/
│     ├─ session/
│     └─ proxy/
├─ public/
├─ package.json
├─ tsconfig.json
└─ .env.example
```

소개 랜딩은 `/`, 서비스 홈은 `/home`으로 나눈다. 서비스 홈 한 주소에서 로그인 상태에 따라 `VisitorHomeView`와 `MemberHomeView`를 선택하는 계획이다. 이번 구현은 랜딩·공통 모듈이며 서비스 홈은 설계까지다. 두 route group에 각각 같은 홈 주소를 만들지 않는다. `Visitor`는 비로그인 표시 상태이며 게스트 계정을 뜻하지 않는다. `(member)`라는 폴더 이름이 접근 제어를 해 주는 것은 아니므로 서버와 API에서도 권한을 확인한다.

`page.tsx`는 주소·초기 진입·메타데이터·페이지 조립을 맡는다. 표시 컴포넌트 `ui`에는 직접 통신·비용 계산·서버 명령 생성을 넣지 않는다. `model`은 상태 분류, `manager`는 조회·행동 연결, `styles`는 표현을 맡는다. 모든 버튼의 목적지는 `routeMap.ts`와 기능별 이동 규칙으로 관리한다. 공개·회원 페이지에서 같은 경로를 서로 다르게 해석하지 않는다.

`server`는 브라우저 세션 검증과 공통 API 전달처럼 웹 서버에서만 실행할 책임을 둔다. DB에 직접 연결하거나 API의 여행 권한·저장 규칙을 복제하지 않는다. 서버 전용 모듈이 브라우저 묶음에 포함되지 않는지 검사한다.

폴더는 소문자 kebab-case, 모듈은 camelCase, React 컴포넌트는 PascalCase를 따른다. `page.tsx`·`layout.tsx`·괄호 그룹·대괄호 경로는 프레임워크 규약의 예외다. 실제로 필요한 페이지에만 로딩·오류·없는 페이지 처리를 추가한다.

## 5. 공통 UI와 코드 공유

업무 모델·입력 검증·금액 규칙·API 요청은 기존 `packages`를 재사용한다. `apps/web`이 `apps/mobile/src`를 광범위하게 직접 참조하거나 앱 코드 전체를 복사하지 않게 한다.

현재 `HomeHeader` 등에는 Expo Router 의존성이 있으므로 Next.js에 그대로 가져온다고 작동을 보장할 수 없다. 기반 작업에서 화면 표현과 플랫폼 이동을 분리하는 범위를 검증한다. 필요하면 기존 이름과 규격을 유지하는 공통 표현을 `packages/ui`에 두고, 앱·웹의 이동 처리는 얇은 연결 계층에서 제공한다. 플랫폼별 출력 코드가 필요해도 규격·공통 속성·검수는 하나로 관리한다.

공통 `ScreenHeader`, `HeaderAction`, `HomeHeader`, `GlobalNavigation`을 페이지마다 다시 만들지 않는다. UI 분리를 하더라도 모양·치수·색상·글꼴·4탭 정책은 변경하지 않으며 앱의 기존 진입점이 새 공통 표현을 사용하도록 연결한다. 토큰은 현행 `design-tokens.json`을 기준으로 공급하고 다른 색상·치수의 사본을 만들지 않는다.

공통 UI 추출은 홈페이지 작업에 숨겨 섞지 않고 기반 변경으로 검토한다. 추출 전후 실제 앱·웹 화면과 헤더·뒤로가기·이탈 보호를 검사한다. 실행 호환과 공통 규격을 확인하기 전에는 Next.js 기반을 확정하거나 홈페이지 UI 구현 완료로 보고하지 않는다.

## 6. 로컬·검수·운영 환경

| 환경 | 웹·앱 연결                        | 데이터 기준            | 용도                                     |
| ---- | --------------------------------- | ---------------------- | ---------------------------------------- |
| 로컬 | 개발 웹과 개발 앱 → 같은 로컬 API | 격리된 로컬 DB·파일    | 페이지 개발·상태·저장·실패 재현          |
| 검수 | 검수 웹과 검수 앱 → 같은 검수 API | 같은 검수 D1·비공개 R2 | 실제 계정·지도·영수증·교차 저장 확인     |
| 운영 | 운영 웹과 배포 앱 → 운영 API      | 운영용 D1·R2 별도 연결 | 사용자 서비스. 승인한 배포 범위에서 실행 |

동일 환경의 앱·웹은 같은 핵심 DB를 사용한다. 로컬·검수·운영 DB까지 하나로 합친다는 뜻은 아니다. 개발 웹이 운영 API에 조용히 연결되는 기본값을 만들지 않는다. 페이지 주소를 바꾼다고 데이터 환경까지 바뀌지 않도록 배포 설정에서 명시한다.

현재 Windows·PowerShell·기존 경로를 우선 유지한다. Linux CI와 실제 웹 실행 환경에서도 빌드를 확인한다. 처음부터 Docker·WSL·새 패키지 관리자를 필수로 추가하지 않는다. 필요한 호환 문제를 확인한 경우에만 별도 도입한다.

루트에서 기존 잠금 파일로 `npm ci`를 실행하는 운영을 유지한다. 공통 잠금 파일 하나를 쓰고 앱별 독립 잠금 파일은 추가하지 않는다. 새로운 Next.js·React·배포 실행 계층의 요구사항이 현행 Node·React와 맞는지 먼저 확인한다. 다른 버전이 필요하면 앱 호환·CI·잠금 파일을 함께 검토한 뒤 변경한다.

| 실행 항목           | 현재                                                            | 도입안                         |
| ------------------- | --------------------------------------------------------------- | ------------------------------ |
| 앱 실행·웹 미리보기 | `npm run start`, `npm run mobile:web`                           | 유지                           |
| API 개발            | `npm run api:dev`                                               | 유지                           |
| 별도 웹 개발        | `npm run web:dev`                                               | 홈페이지·실제 인증 연결        |
| 별도 웹 빌드        | `npm run web:build`, `web:start`                                | 배포 실행 계층 검증            |
| 별도 웹 검수        | `web:typecheck`, `web:lint`, `test:web:dev`, `test:web:runtime` | 홈·계정·이동·공통 UI 검수 추가 |

표의 웹 명령은 0.0.1에 연결한다. 기존 `npm run web`과 `build:web`의 대상은 Expo 앱으로 유지한다. 독립 웹의 기본 포트는 3000이며 자동 HTTP 검사는 빈 임시 포트를 사용한다. API·Expo 포트는 기존 설정을 따른다. 빌드와 개발 서버는 동시에 실행하지 않는다.

환경 값은 승인된 로컬 설정·비밀 저장소에서만 사용한다. `apps/web/.env.example`에는 항목명과 안전한 예시만 기록하고 실제 값은 제외한다. 서버 비밀을 브라우저 공개 변수에 넣지 않는다. 환경별 OAuth 복귀 주소와 웹·API 출처를 명시하고, 단순히 이름이 다른 환경 파일만 만든 것으로 격리가 됐다고 판단하지 않는다.

## 7. 타입·빌드·자동 검사 연결

앱·웹의 tsconfig를 실행 환경에 맞게 분리한다. 루트 Expo 검사에서 웹을 제외하는 대신 웹 전용 타입 생성·검사를 루트 `typecheck`에 필수로 연결한다. 공통 패키지는 기존 검사로 확인한다. ESLint도 같은 방식으로 분리하고 루트에서 모두 실행한다.

0.0.1 코드 경계 검사는 직접 import·문자열 동적 import·실행 재내보내기를 다룬다. 중간 모듈·계산된 경로까지 추적하지 않는다. 실제 서버 전용 기능을 넣기 전에 `server-only` 표식 또는 의존성 추적과 빌드 실패 검증을 추가한다. 공통 UI와 탐색 경계 확장은 0.1 선행 작업이며 아직 완료로 판단하지 않는다.

CI에는 별도 웹의 실제 타입 검사·빌드·페이지 이동 검사를 추가한다. 기존 API·인증·앱 검사는 유지한다. 공통 패키지·헤더·저장 계약이 바뀌면 앱과 웹 양쪽을 검사한다. 이후 경로별 검사 최적화가 필요해도 보호 브랜치의 필수 검사 결과가 빠지지 않게 구성한다.

현재 코드 경계 검사 대상에 `apps/web/src`를 추가하고 UI의 직접 저장·비밀 모듈 참조·공통 계층 역의존을 검사한다. 새 패키지·tsx·생성 파일을 다룰 때 저장소 구조 검사·ESLint·Prettier·자원 검사·빌드 제외도 함께 갱신한다. `.next`와 최종 선택한 실행 계층의 빌드 산출물·생성 타입·로컬 검수 결과가 Git에 들어가지 않게 한다.

탐색 경계 검사도 함께 확장한다. 현재 `check-navigation-boundaries.mjs`는 모바일 소스와 Expo 타입 설정을 기준으로 해석하므로, 웹별 타입·경로 해석과 `packages/ui`를 거친 실제 공통 헤더·GNB 의존성 추적을 추가한다. 새 웹의 가짜 헤더·로컬 스타일 덮어쓰기·중복 GNB·페이지 탐색 정책 누락은 실패하고 승인한 공통 UI 연결은 통과하는 검사 사례를 둔다. 기존 모바일의 단일 헤더·GNB 규칙과 회귀 검사는 유지한다. 검사 명령이 통과했다는 사실만으로 새 경로까지 검사했다고 판단하지 않는다.

| 변경             | 필요한 검증                                                        |
| ---------------- | ------------------------------------------------------------------ |
| 문서만           | `npm run check:docs`와 변경 문서 서식                              |
| 웹 코드·설정     | `npm run check` + 별도 웹 실제 타입·빌드                           |
| 로그인·쿠키·복귀 | 위 검사 + `npm run test:auth`, 실제 Google·다중 계정               |
| 도메인·API·DB    | 위 검사 + `npm run test:foundation`, 앱·웹 저장·재조회             |
| 공통 UI·탐색     | 위 검사 + `npm run test:headers:web`, 뒤로가기·이탈 보호·실제 캡처 |
| 배포 설정        | `npm run test:release`, 릴리스 설정·산출물·대상 환경 검증          |

통과한 CI와 실제 화면 검수를 구분한다. 홈의 H01~H16처럼 기능 수용 기준을 페이지 작업에 연결하고, 캡처·로그는 `outputs/`에 보관한다.

## 8. 페이지별 관리 방식

페이지를 추가할 때 **주소·접근 권한·화면 문서·구현 경로·이동 목적·검사·배포 버전**을 연결한다. 기획·구현·자동 검사·실제 검수·배포는 각각 표시하며 하나의 완료 체크로 합치지 않는다. 초기에는 저장소 문서 표와 PR로 관리하고 별도 페이지 관리 시스템은 만들지 않는다.

| 페이지           | 주소                            | 기능 폴더안              | 현재 기획 수준                       | 구현·실제 검수                   |
| ---------------- | ------------------------------- | ------------------------ | ------------------------------------ | -------------------------------- |
| 홈               | `/`                             | `features/home`          | 별도 상세 계획·H01~H16 있음          | 독립 웹 미구현·미검증            |
| 로그인           | `/login`                        | `features/auth`          | 기존 정책과 웹 게스트 금지·복귀 계획 | 웹 세션 연결 검증 필요           |
| 내 여행          | `/plans`                        | `features/trip-planning` | 전체 계획에 역할·권한 정의           | 웹 상세 설계·구현 필요           |
| 여행 만들기·편집 | `/new-trip`, `/trips/:id`       | `features/trip-planning` | 앱 계약 재사용·지도 확장 계획        | 실제 웹 지도·공통 계약 검증 필요 |
| 영수증           | 여행 안의 영역·확인 화면        | `features/receipts`      | 기존 제약·보완·수용 기준 정의        | 웹 업로드·확정 검증 필요         |
| 커뮤니티         | `/footprints`, `/community/:id` | `features/community`     | 선택 공개·가져오기·철회 계획         | 별도 웹 미구현·미검증            |

홈을 예로 들면 화면 문서는 [홈페이지 화면 계획](<../../02. 디자인/01. 화면설계/웹홈페이지_화면계획.md>), 진입은 `app/home/page.tsx` 계획, 기능은 `features/home`, 검수는 H01~H16으로 연결한다. 배포한 뒤에는 해당 커밋·검수 URL·실행 환경을 기록한다. PR 미리보기가 준비되기 전에는 실제 미리보기 URL을 만들어 적지 않는다.

## 9. 미리보기와 배포

작업 중 로컬 미리보기 → PR 코드·자동 검사 → 검수 환경의 실제 앱·웹 확인 → 운영 반영 순서로 간다. PR별 외부 미리보기는 실행 기반과 권한·비용을 준비한 뒤 추가하는 후보다. 미리보기에서 운영 DB·비밀·파일을 사용하지 않고 PR 코드가 공용 검수 DB에 자동 마이그레이션을 실행하지 않게 한다.

실제 Google 로그인은 등록한 고정 검수 복귀 주소에서 확인한다. 무작위 PR 주소에 자동으로 로그인이 된다고 가정하거나 OAuth 허용 범위를 넓게 열지 않는다. 해당 미리보기에서 인증을 실행하지 못했다면 공개 화면 검수와 실제 로그인 검수를 구분한다.

현재 배포는 Expo 웹의 정적 결과를 Pages에 올린다. Next.js의 서버 렌더링·쿠키 중계가 필요한 웹을 이 경로에 그대로 넣지 않는다. 별도 웹은 Workers의 Next.js 실행 경로를 우선 검증한다. 확인일인 2026-11-10의 공식 안내는 vinext를 기본 경로로 소개하지만 베타라고 명시한다. 실행 계층은 공통 UI·인증·파일 업로드·빌드 호환을 확인한 뒤 선택한다. 정적 내보내기만 쓰는 경우와 서버 기능이 필요한 경우의 배포를 구분한다. [Cloudflare Next.js 안내](https://developers.cloudflare.com/workers/framework-guides/web-apps/nextjs/)

기존 앱 웹 배포는 전환 검수까지 보존한다. 새 웹 배포 작업은 대상·빌드 명령·산출물·런타임·인증 주소를 별도로 명시하고, API·기존 앱 웹을 바꿀 필요가 없으면 불필요하게 함께 배포하지 않는다. 다만 서버 계약 변경이 있으면 호환 순서·DB 적용·백업·복구를 함께 준비한다.

main 병합을 운영 배포와 동일하게 취급하지 않는다. 검증한 커밋과 환경을 지정해 배포한다. 문제 발생 시 이전 검증 산출물 또는 되돌리는 새 커밋을 사용하고 DB 변경은 별도 복구 절차를 따른다. DB를 되돌리지 않고 화면만 과거 버전으로 바꾸어도 되는지 확인한다.

이번 계획서의 완료 범위는 저장소·폴더·브랜치·페이지 추적·환경·검사·배포 흐름을 제안한 것이다. 실제 Git 보호 설정, Next.js·공통 UI·타입 설정, 새 세션·실행 계층, CI·미리보기·배포는 아직 적용·검증하지 않았다.
