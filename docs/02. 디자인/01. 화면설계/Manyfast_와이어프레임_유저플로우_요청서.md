# TripPrint 와이어프레임과 유저 플로우 제작 요청서

Manyfast에서 TripPrint의 전체 화면 구조와 사용자 이동 흐름을 설계할 때 사용하는 프로젝트 설명서입니다. 여행을 처음 만드는 순간부터 실제 방문과 지출을 기록하고, 필요한 부분만 공유하는 과정까지 연결해 주세요.

와이어프레임은 화면의 정보와 행동을 배치한 구조도이고, 유저 플로우는 사용자의 선택에 따라 화면이 어떻게 이어지는지 보여주는 흐름도입니다. 이번 요청의 결과물은 이 두 가지와 화면별 설명입니다. 앱 구현, 배포, 새로운 인증 정책 확정은 포함하지 않습니다.

F01~F09와 화면 목록은 현행 기획이 요구하는 설계 범위입니다. 실제 앱에 있는 기능을 그대로 재현하는 자료와는 차이가 있습니다. 코드에서 확인한 제약은 10절에 함께 적었습니다. 차이가 있는 부분은 와이어프레임에 `결정 필요` 주석을 붙여 주세요.

## 1 서비스 목적과 사용자 문제

**TripPrint는 여행 계획과 실제 여행 기록을 한 여행 안에서 관리하는 서비스입니다.** 사용자는 목적지와 기간으로 계획을 시작하고, 여행 중이나 여행 후에 영수증과 사진으로 다녀온 장소와 지출을 정리합니다. 함께 가는 사람과 일정을 편집하거나, 직접 고른 일정만 공개할 수 있습니다.

해결하려는 문제는 다음과 같습니다.

| 사용자 상황        | 겪는 문제                                          | 설계가 도와야 할 일                                                    |
| ------------------ | -------------------------------------------------- | ---------------------------------------------------------------------- |
| 여행을 준비할 때   | 날짜가 미정이거나 세부 계획이 없어 시작하기 어렵다 | 목적지와 날짜 또는 예정 일수만으로 여행을 만들고 DAY별 계획을 시작한다 |
| 여행 중일 때       | 계획과 실제 방문이 달라지고 영수증이 흩어진다      | 기존 계획을 유지하면서 실제 방문과 지출을 빠르게 남긴다                |
| 여행을 마친 뒤     | 어디서 무엇을 샀는지 다시 정리하기 어렵다          | 영수증의 상호·결제 시각·음식과 상품 품목을 확인하고 방문에 연결한다    |
| 동행자와 준비할 때 | 여러 곳에 나뉜 일정을 주고받아야 한다              | 같은 여행을 함께 보거나 권한에 따라 편집한다                           |
| 여행을 공유할 때   | 영수증이나 사적인 메모까지 공개될까 걱정된다       | 공개될 정보만 미리 보고 선택한다                                       |

대상은 여행을 준비하는 개인과 동행 그룹, 여행 중 바로 기록하는 사람, 여행 후 영수증을 모아 정리하는 사람입니다. 특정 연령이나 여행 숙련도를 전제로 하지 마세요.

지원 대상으로 문서에 정의된 환경은 Android, iOS, 모바일·데스크톱 웹입니다. 설계는 모바일을 먼저 완성하고 넓은 웹 화면에서의 확장 방식을 덧붙여 주세요. 플랫폼 정의와 실제 배포·실기기 검증 여부는 구분합니다.

## 2 먼저 이해할 핵심 개념

| 개념           | 뜻                                               | 화면에서 구분할 점                                 |
| -------------- | ------------------------------------------------ | -------------------------------------------------- |
| 여행           | 목적지·기간·일정·기록을 묶는 단위                | 다른 여행의 영수증이나 지출이 섞이지 않아야 한다   |
| DAY            | 여행의 첫날부터 세는 일차                        | 날짜 미정일 때도 DAY 1부터 계획할 수 있다          |
| 계획 일정      | 앞으로 방문하려고 추가한 장소와 시간             | 실제 다녀온 것으로 자동 표시하지 않는다            |
| 실제 방문 기록 | 여행 중·후에 사용자가 남긴 방문 정보             | 원래 계획을 자동으로 덮어쓰지 않는다               |
| 영수증 기록    | 이미지에서 읽은 결제 정보와 사용자가 확인한 내용 | 글자 추출과 저장 완료, 방문 여부를 구분한다        |
| 메뉴·구매 품목 | 영수증에 적힌 음식이나 상품                      | 앱의 탐색 메뉴와 구분해 설명한다                   |
| 가계부         | 여행의 예상 비용과 실제 지출을 보는 곳           | 통화·예상/실제·중복 합산 여부를 구분한다           |
| 발자국         | 사용자가 선택해 공개한 여행 일정 피드            | 개인 기록 전체를 공개하는 기능으로 표현하지 않는다 |

OCR은 사진 속 글자를 읽는 기능입니다. **OCR 결과, 사용자 확인, 구매 증빙, 실제 방문 인증은 각각 다른 의미입니다.** 영수증만으로 본인이 방문했거나 영수증 원본이 진짜라고 보장하지 않습니다. 와이어프레임에는 `영수증 기록`, `확인 후 저장`처럼 근거에 맞는 표현을 쓰고, `방문 인증 완료`, `진짜 여행자 인증` 배지를 임의로 만들지 마세요.

## 3 설계 범위와 제작 순서

전체 구조를 먼저 정리한 뒤 핵심 흐름, 개별 화면, 오류 상태 순서로 구체화해 주세요. 아래 우선순위는 이번 설계의 제작 순서이며, 제품의 출시 범위를 새로 정하는 기준은 아닙니다.

| 순서 | 범위               | 완료해야 할 연결                                             |
| ---- | ------------------ | ------------------------------------------------------------ |
| 1    | 전체 구조와 진입   | 시작 → 둘러보기/로그인 → 홈 → 네 개 루트 탭                  |
| 2    | 여행 계획          | 홈/내 여행 → 목적지·기간 → 여행 일정 → 장소·항공편 추가      |
| 3    | 영수증과 실제 기록 | 여행 선택 → 이미지 등록 → 내용 확인 → 방문 연결 → 저장 결과  |
| 4    | 동행과 공개        | 초대·수락·권한 분기, 공개 선택·미리보기·철회, 공개 일정 담기 |
| 5    | 계정과 보조 작업   | 프로필, 언어·글자 크기, 준비물·멤버 관리와 오류 복구         |

예약·결제 중개, 숙소 판매, 광고·구독 요금제, AI 자동 완성 여행, 영수증 진위 판정, 포인트·리워드, 새 소셜 기능은 이번 범위에 추가하지 마세요. 기존 로고와 하루 캐릭터도 유지합니다.

## 4 사용자 모드와 권한

| 모드 또는 역할 | 설계에서 허용할 행동                                 | 제한과 안내                                                                           |
| -------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 게스트         | 이 기기에서 여행 계획과 기록을 시작한다              | 기기 안의 기록임을 쉬운 말로 알린다. 동기화·동행 초대·공개에는 로그인 흐름을 연결한다 |
| 회원           | 프로필을 마치고 자신의 여행을 동기화한다             | 로그인 전 입력과 원래 하려던 행동으로 돌아간다                                        |
| 여행 소유자    | 여행 관리, 멤버·권한 관리, 여행 삭제, 공개 여부 결정 | 삭제·공개·철회 전 결과와 범위를 확인한다                                              |
| 편집자         | 공유받은 여행의 일정·항공편·영수증·준비물을 편집한다 | 소유자 전용 관리 행동은 구분한다                                                      |
| 열람자         | 공유받은 여행을 읽는다                               | 편집 버튼을 실행 가능한 것처럼 보여주지 않는다                                        |
| 공개 여행 독자 | 공개된 일정만 보고 자신의 여행으로 담는다            | 원본 영수증·비공개 메모·품목·동행자 정보에 접근하지 않는다                            |

원본 영수증을 동행자에게 어디까지 보여줄지, 편집자가 다른 사람의 영수증을 수정·삭제할 수 있는지는 별도 확인 항목입니다. 단순히 같은 여행의 멤버라는 이유로 모든 원본을 볼 수 있다고 설계하지 마세요.

현재 영수증 확인 UI에는 원본 보관 시 나와 여행 친구가 볼 수 있다는 안내가 있습니다. 이는 일반 공개와 구분해야 하며, 역할별 실제 접근 권한을 추가로 확인해야 합니다. 원본 보관 여부는 내용 확인과 별도의 선택으로 표시합니다.

## 5 전체 화면 구조와 공통 탐색

공통 규격의 루트 탭은 **홈 → 내 여행 → 발자국 → 내 정보** 네 개입니다. 루트 탭 화면에는 하단 GNB를 표시합니다. GNB는 앱 전체를 이동하는 하단 메뉴입니다.

여행 만들기, 여행 상세 작업 공간, 로그인·프로필 설정, 영수증 확인, 공개 여행 상세에는 GNB를 숨깁니다. 여행 안의 `일정·지도·가계부`는 해당 여행에서만 쓰는 내부 탐색이며 루트 GNB와 구분합니다. 준비물·멤버 관리의 진입점을 별도로 제공하되, 루트 탭을 늘리지 마세요.

```text
시작
├─ 먼저 둘러보기 → 홈
└─ 로그인 → 필요하면 프로필·약관 → 원래 목적지 또는 홈

홈 / 내 여행 / 발자국 / 내 정보
├─ 홈·내 여행 → 여행 만들기 → 여행 상세
│  ├─ 일정 → DAY 선택 → 장소·항공편·영수증 추가
│  ├─ 지도 → 같은 여행의 위치 확인
│  ├─ 가계부 → 지출·영수증 확인
│  └─ 보조 관리 → 준비물·동행자·공개 설정
├─ 발자국 → 공개 여행 상세 → 내 여행으로 담기 → 생성된 여행
└─ 내 정보 → 프로필·언어·글자 크기·계정 관리

초대 링크 → 초대 확인 → 필요하면 로그인·프로필 → 수락 → 초대받은 여행
```

시작 화면은 헤더와 GNB를 모두 생략합니다. 홈에는 브랜드 헤더를 사용하고, 나머지 루트 탭에는 뒤로가기 없는 화면 제목을 둡니다. 하위 화면에는 뒤로가기와 제목을 제공합니다. 로그인 중계 화면을 거쳤더라도 뒤로가기는 사용자가 시작한 작업 맥락으로 이어져야 합니다.

### 문서와 코드의 경로 차이

| 화면 역할 | 현행 기획 문서의 이름과 경로 | 코드에서 확인된 루트 탐색 |
| --------- | ---------------------------- | ------------------------- |
| 홈        | 홈 `/`                       | 홈 `/`                    |
| 여행 목록 | 내 여행 `/trips`             | 내 여행 `/plans`          |
| 공개 피드 | 발자국 `/footprints`         | 커뮤니티 `/footprints`    |
| 계정      | 내 정보 `/account`           | MY `/my`                  |

와이어프레임의 화면 역할은 공통 규격의 네 탭으로 정리하고, 개발 연결 주석에는 실제 경로를 병기해 주세요. 이름·경로를 통일하기 위한 앱 변경은 별도 결정 사항입니다. 이 차이를 해결하려고 새로운 탭을 추가하거나 두 개의 계정 탭을 만들지 마세요.

## 6 핵심 유저 플로우

각 흐름에는 시작 조건, 사용자 행동, 앱이 보여주는 결과, 취소·실패 시 돌아갈 곳을 표시해 주세요. 성공 경로와 오류 경로를 서로 다른 선이나 라벨로 구분합니다.

### F01 시작과 로그인

앱 시작 → 둘러보기 또는 로그인 → 첫 회원은 프로필·필수 약관 → 원래 목적지 또는 홈으로 이동합니다. 로그인 취소 시 재시도와 이전 화면 복귀를 제공합니다. 게스트의 기록을 가져오는 과정이 실패해도 기기의 원본을 지우지 않습니다.

닉네임은 필수입니다. 앞뒤 공백 제거와 문자 정규화 후 한글 완성형·영문·숫자 2~10자를 허용하고 중복은 허용합니다. 입력 중인 한글을 강제로 자르지 않습니다. 소개·여행 스타일은 선택 항목입니다. 소개글의 공통 길이 제한은 확인 전까지 임의로 적지 마세요.

### F02 목적지와 기간으로 여행 만들기

홈 또는 내 여행의 새 여행 행동 → 나라·도시 선택 → 날짜 지정 또는 일정 미정 → `다음` → 생성된 여행 일정으로 이동합니다. 홈의 도시 카드에서 시작했다면 목적지를 미리 채웁니다.

기능 문서의 설계 기준은 날짜 지정 시 당일치기부터 최대 90일, 일정 미정 시 기본 3일·선택 범위 1~15일입니다. 목적지와 기간 방식이 정해져야 다음 버튼을 활성화하고, 미정 여행의 날짜를 나중에 정할 때는 기존 DAY별 장소를 유지하도록 정의합니다. **현재 생성 코드는 날짜를 요구하며 최대 30일이고, 기간 적용 시 바로 생성합니다.** 일정 미정과 별도 다음 버튼은 기존 기능으로 표시하지 말고 설계 검토 대상으로 구분해 주세요.

이 단계에서는 항공편·상세 장소·영수증을 필수로 묻지 않습니다. 생성 실패 시 선택을 유지하고 재시도합니다. 로그인 때문에 화면을 벗어났다면 목적지·기간을 복원합니다.

### F03 DAY별 일정 채우기

여행 상세 → DAY 선택 → 장소 검색 → 장소 선택 → 시간·메모·예상 비용 확인 → 선택 DAY에 반영합니다. 여행 도시를 기준으로 장소를 찾고, 동명이점은 이름·주소·위치로 구분합니다. 검색 결과가 없거나 조회에 실패했을 때의 안내와 재시도를 포함합니다.

항공편은 편명과 탑승일로 조회하거나 직접 입력합니다. 저장 후 해당 탑승일의 DAY에서 확인합니다. 순서 변경은 길게 누르기만 요구하지 말고, 접근 가능한 대체 조작도 설계 검토 항목으로 제시해 주세요.

### F04 여행 중 영수증 등록

현재 여행 또는 영수증 진입점 → 대상 여행 확인 → 카메라/앨범 → 분석 중 → 추출 내용 확인·수정 → 기존 방문에 연결 또는 새 실제 방문 추가 → 저장 → 방문·영수증·지출 결과 확인으로 이어집니다.

위 자동 추출은 회원의 서버 OCR 경로입니다. 현재 게스트는 사진을 기기에 보관하고 내용을 직접 입력합니다. 두 모드를 별도 분기로 그려 주세요. 원본 보관 선택도 함께 보여줍니다.

다음 정보를 한 번에 읽을 수 있는 확인 화면이 필요합니다. 길어지면 요약과 펼치기를 활용하되 저장 대상 여행·DAY와 금액·통화는 확인하기 쉬운 위치에 둡니다.

| 확인 정보             | 사용자 행동                             | 결과 또는 예외                                              |
| --------------------- | --------------------------------------- | ----------------------------------------------------------- |
| 대상 여행·DAY         | 기록할 여행과 일차를 확인한다           | 다른 여행에 저장하는 실수를 줄인다                          |
| 상호·주소·지도 후보   | 잘못 읽힌 이름과 위치를 고친다          | 위치를 못 찾은 경우 주소 텍스트와 지도 좌표의 차이를 알린다 |
| 결제 일시·현지 시간대 | 실제 결제 시점을 확인한다               | 업로드 시각과 결제 시각을 혼동하지 않는다                   |
| 총액·통화             | 숫자와 통화를 확인한다                  | 통화별 금액을 구분하며 환산 총액을 임의로 만들지 않는다     |
| 음식·상품 품목        | 읽힌 품목을 확인·수정한다               | 일부만 읽힌 상태와 빈 상태를 표시한다                       |
| 연결할 방문           | 기존 방문을 고르거나 새 방문을 추가한다 | 기존 계획을 자동으로 완료 처리하거나 교체하지 않는다        |

이미지 계약은 JPEG/PNG, 최대 4MB이고 OCR 제한 시간은 75초입니다. 분석 중에는 진행 중임을 알리되 근거 없는 완료율을 표시하지 않습니다. 시간 초과 시 다시 시도하거나 이미지를 다시 선택할 수 있어야 합니다. 직접 입력으로 이어갈 수 있는 항목은 실제 지원 범위에 맞춰 구분합니다.

카메라 권한 거절에는 앨범 선택 등 가능한 대체 행동을 표시합니다. 분석이 일부만 성공했다면 사용자가 누락 내용을 고칠 수 있어야 합니다. **분석이 끝난 상태와 저장이 끝난 상태는 별개입니다.** 저장 실패 시 입력을 보존하고 중복 저장 없이 재시도하는 흐름을 요청합니다.

현재 품목 편집은 최대 50개이며 품목 없이도 저장합니다. 수량·단가·품목 금액을 모르면 비워 둘 수 있습니다. 품목 합계와 결제 총액이 다를 때는 사용자가 차이를 확인하고, 실제 지출에는 결제 총액을 한 번만 반영하는 구조로 설명합니다.

현재 저장 가능한 통화는 KRW·JPY·USD입니다. 미지원 통화를 읽었을 때는 실제 통화를 다른 통화로 바꾸도록 유도하지 않습니다. 원본 보관과 장소 직접 기록으로 이어가는 대안을 표시하고, 영수증 지출 저장이 완료된 것으로 표현하지 마세요.

### F05 여행 후 영수증 모아 정리

내 여행에서 완료 여행 선택 → 영수증 등록 → 결제 일시와 여행 DAY 확인 → 방문 연결 → 저장 → 같은 여행에 다음 영수증 등록으로 이어집니다.

여행 후 등록해도 업로드일이 아닌 실제 결제일을 확인합니다. 현재 날짜가 없거나 여행 기간 밖이면 결제 날짜 수정 또는 여행 기간 확인으로 돌아간 뒤 일치하는 DAY를 확인해야 합니다. DAY만 선택하면 저장되는 것으로 그리지 마세요. 날짜 미정 여행의 영수증 저장은 미정 여행 지원과 함께 검토할 항목입니다. 여러 장을 한 번에 분석하는 기능은 확정하지 않습니다. 우선 한 장씩 연속 등록하는 흐름을 그립니다.

같은 방문에 여러 영수증을 연결하는 경우와 같은 영수증을 다시 올리는 경우를 구분해야 합니다. 현재 코드는 같은 원본을 새 결제로 다시 등록하는 것을 막고, 유사 결제는 기존 기록 확인 후 별도 결제인지 선택하게 합니다. 취소 영수증의 합산 정책과 재시도 경계는 10절의 확인 항목으로 남깁니다.

### F06 동행자 초대와 공동 편집

여행 소유자 → 동행자 관리 → 편집/열람 권한 선택 → 초대 링크 생성·공유 → 수신자의 초대 확인 → 필요하면 로그인·프로필 → 수락 → 해당 여행으로 이동합니다. 기획상 편집자 권한이 초대 기본값입니다.

앱 설치 여부, 링크 만료·철회·이미 사용함, 다른 계정으로 로그인함, 오프라인 수락 실패를 분기로 표시합니다. 설치나 로그인 후 원래 초대로 돌아오는 흐름을 포함하되, 설치 후 자동 복귀가 검증된 기능이라고 표현하지 마세요. 링크를 다시 열어 이어가는 복구 경로도 제시합니다.

공동 편집 중 다른 사람이 먼저 저장했다면 내 입력을 보존한 채 최신 내용을 확인하고 다시 반영하도록 설계합니다. 실제 공유 채널의 지원 여부를 확인하기 전에는 모든 채널이 동일하게 동작한다고 전제하지 않습니다.

### F07 여행 선택 공개와 공개 철회

소유자의 여행 → 공개할 일정·사진·총액 요약 선택 → 공개 미리보기 → 공개 확인 → 발자국에서 결과 확인으로 이어집니다. 여행 기록과 원본 영수증은 기본 비공개입니다.

공개 미리보기에는 다른 사람이 보게 되는 정보만 표시합니다. 원본 영수증, 세부 구매 품목, 비공개 메모, 동행자 정보는 공개 상세에 포함하지 않습니다. 철회 후 앱 내 공개 목록·상세에서 어떻게 보이는지 표시하고, 이미 전달된 정보까지 회수된다고 보장하지 않습니다.

### F08 공개 일정을 내 여행으로 담기

발자국 검색·필터 → 공개 여행 상세 → `내 여행으로 담기` → 내 여행의 시작일 선택 → 새 여행 생성 → 내 여행 일정에서 확인합니다.

가져오는 것은 공개된 장소·일정 구조입니다. 다른 사람의 실제 지출·영수증·방문 증빙·멤버를 자신의 기록으로 복제하지 않습니다. 담기 실패 시 원래 공개 여행을 계속 볼 수 있어야 합니다. 원본 수정·삭제가 내가 담은 여행에 미치는 영향은 확인할 정책으로 표시합니다.

### F09 내 정보와 언어 설정

내 정보 → 프로필 편집 또는 설정 → 한국어·영어·일본어 선택 / 글자 크기 변경 → 이전 화면으로 복귀합니다. 긴 번역문과 큰 글자에서도 버튼·제목·탭이 잘리지 않아야 합니다. 언어 설정이 영수증 원문이나 여행 현지 시간대를 바꾸는 것처럼 표현하지 않습니다.

로그아웃과 탈퇴에는 계정 기록·기기 기록의 처리 차이를 실제 정책에 맞춰 설명할 자리를 두고, 최종 문구와 삭제 범위는 별도로 확인합니다.

## 8 공통 디자인과 접근성

기존 `HomeHeader`, `ScreenHeader`, `HeaderAction`, `GlobalNavigation`, `AppPopup`의 역할을 재사용합니다. 화면별로 새 헤더나 GNB를 만들지 마세요. 로고·하루 캐릭터·기존 아이콘 체계를 바꾸지 않습니다.

1차 결과물은 구조 검토용 와이어프레임으로 요청합니다. 회색조에서도 계획/실제, 선택/비선택, 오류/성공을 글자와 아이콘으로 구분합니다. 색을 넣을 경우 첨부한 토큰과 아래 확인 사항을 함께 적용합니다.

## 9 화면 문구와 예시 데이터

버튼과 안내는 여행자의 다음 행동을 설명해 주세요. 예를 들어 `영수증 내용을 확인해 주세요`, `저장하지 못했어요. 입력한 내용을 유지했어요. 다시 시도해 주세요`처럼 작성합니다. 개발 상태, 서버 구성, API·DB·세션 설명은 사용자 화면에 넣지 않습니다.

예시 여행은 `일본 · 오사카`, `2박 3일`, `DAY 2`, `도톤보리 식당`, `JPY 1,480`, `라멘 1개`처럼 서로 연결되게 사용해 주세요. 모든 예시는 와이어프레임 주석에서 가상 데이터로 표시하고, 실제 저장·공개·인증을 마친 서비스 화면으로 소개하지 않습니다. 실명, 이메일, 실제 초대 토큰, 결제 카드번호, 실제 영수증 원본은 사용하지 않습니다.

## 11 Manyfast에 요청할 산출물과 수용 기준

1. **전체 정보구조도**: 네 루트 탭, 여행 내부 탐색, 모달·시트·상세의 관계를 표시합니다.
2. **유저 플로우 F01~F09**: 게스트/회원, 소유자/편집자/열람자의 차이와 성공·취소·실패·재시도·복귀를 표시합니다.
3. **화면 S01~S24의 와이어프레임**: 핵심 화면을 먼저 만들고 지원 화면을 연결합니다. 빈 상태·로딩·오류는 상태 변형으로 제공합니다.
4. **화면별 설명표**: 화면 ID, 목적, 진입점, 정보, 필드, 주 행동, 보조 행동, 권한, 저장 결과, 오류, 뒤로가기 목적지, 연결 흐름 ID를 적습니다.
5. **확인할 정책 목록**: 10절의 쟁점마다 선택지, 사용자 영향, 결정이 필요한 이유를 정리합니다.

다음 기준으로 검토할 수 있어야 합니다.

- 새 사용자가 날짜 미정 상태에서도 목적지를 정하고 빈 DAY 일정까지 도달한다.
- 영수증 확인 화면에서 저장 대상 여행·DAY·결제 일시·통화·금액을 파악할 수 있다.
- 계획과 실제 기록이 구분되며, 기존 계획이 자동으로 교체되지 않는다.
- 저장 완료 후 방문·영수증·지출의 연결을 확인하고, 나갔다 돌아와 다시 조회하는 검증 절차가 명시된다.
- 여러 통화를 근거 없이 합치거나 같은 결제를 이중 합산하지 않는다.
- 미지원 통화를 지원 통화로 바꾸도록 유도하지 않고 원본 보관·장소 직접 기록으로 안내한다.
- 게스트가 로그인·초대·공개 중단 후 원래 작업을 이어갈 수 있다.
- 공개 미리보기와 공개 상세에 원본 영수증·품목·비공개 메모·동행자 정보가 포함되지 않는다.
- 열람자는 편집할 수 없고 소유자 전용 관리 행동이 구분된다.
- 모든 실패 상태에 다시 시도, 수정, 이전 화면 복귀 중 가능한 행동이 있다.
- 네 탭의 순서·개수·노출 정책, 안전 영역, 최소 터치 영역을 지킨다.
- 360·390·430 폭, 큰 글자, 긴 한국어·영어·일본어 제목에 대응한다.
- 구조도·와이어프레임·동작하는 프로토타입·실제 서비스 화면의 상태를 구분해 전달한다.
