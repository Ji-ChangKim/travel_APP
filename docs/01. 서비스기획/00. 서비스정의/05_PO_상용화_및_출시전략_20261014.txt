TripPrint 상용화 및 서비스 출시 전략 보고서
작성 기준일: 2026-10-14 / Asia/Seoul
검토 관점: 13년차 PO의 제품·사업·출시 의사결정

1. 의사결정 요약

TripPrint는 제한된 고객을 대상으로 베타 검증을 준비할 단계다. 현재 자료만으로 대중 공개 출시나 수익성 검증이 끝났다고 판단하기는 어렵다. 일정 작성·편집, 비용 기록, 영수증 확인, 권한과 저장 복구에 쌓아온 구현은 활용 가치가 있다. 다음 투자 우선순위는 기능 확대보다 실제 여행에서의 사용 검증과 운영 준비다.

권고하는 첫 고객은 출발을 2~6주 앞두고 일본으로 2~4명이 함께 여행하는 팀의 일정 담당자다. 도쿄·오사카를 모집과 콘텐츠의 첫 범위로 삼는다. 기존에 지원하는 다른 도시를 앱에서 막을 필요는 없다. 일본 여행이 가장 유리하다는 결론은 아직 고객 조사로 검증하지 않았으며, 짧은 여행 주기와 동행 공유를 함께 관찰하려고 선택한 가설이다.

첫 출시의 약속은 다음 문장으로 좁힌다.
“함께 가는 여행의 일정과 지출을 한곳에 정리하고, 여행 뒤에도 사진과 기록을 찾아보세요.”

처음 90일의 목표는 다운로드 수가 아니라 실제 여행팀의 사용과 첫 유료 구매를 확인하는 것이다. 일정표로 채택되는지, 동행이 함께 보는지, 여행 중 다시 여는지, 여행 후 결과물에 돈을 내는지를 순서대로 검증한다. 포토북·금융 제휴·관광 데이터 판매를 동시에 추진하지 않는다.

2. 검토 범위와 근거의 한계

프로젝트의 PRD, 기존 전략기획서 4종, 출시·QA·게스트 저장 정책, 최신 일정 v5 준비 보고서와 관련 소스를 읽었다. 일정 화면의 저장된 검수 이미지도 확인했다. 주요 확인 파일은 보고서 끝에 정리했다.

이번 분석에서는 코드를 수정하거나 새 빌드를 설치하지 않았고, 실기기·운영 계정·Play Console·실제 고객 데이터·제휴 계약·회계 자료를 확인하지 않았다. 기존 문서의 테스트 결과는 과거 실행 기록으로 인용한다. 현재 작업 트리 전체를 다시 검사한 결과로 표현하지 않는다. 투자 여력과 팀 구성을 알 수 없어 일정은 주 단위 실행안이며 출시일 확약이 아니다.

문서보다 현재 연결된 소스와 최신 릴리스 기록을 우선했다. 오래된 Supabase 중심 문서와 현행 D1/R2 구현, v4와 v5 자료가 함께 존재하므로 출시 기준 문서를 하나로 정리해야 한다.

3. 제품 준비 수준

영역 / 확인 내용 / 출시 판단

여행·일정
- 여행 생성, DAY, 일정 추가·편집·삽입·순서 이동, 체류 시간, 예상 비용 계약이 있다.
- 최신 일정 검토 문서는 브라우저 49/49, 모델·인증 74/74, API 70/70, 로컬 Workers·D1·R2 11/11, 릴리스 39/39 통과를 기록한다.
- 이는 내부 검증 근거다. 새 서명 앱의 실기기 인수와 실제 여행 사용은 별도다.

게스트
- 여행·사진·영수증은 기기에 저장하고, 회원 전환 때 자동 업로드하지 않는다.
- 최초 게스트 시작에는 서버 계정·세션 발급을 위한 인터넷이 필요하다. 이후 같은 기기의 로컬 편집과 첫 실행을 구분해야 한다.
- 앱 삭제·저장 공간 초기화 때 기록을 잃을 수 있으며 Android 자동 백업을 꺼두었다.
- 게스트에서 만든 계획을 회원 공유로 옮기는 연결이 성장 과정의 우선 검증 대상이다.

초대·협업
- 회원 초대와 역할 검사가 있지만, InviteScreen은 게스트에게 로그인을 요구한다. 게스트 저장 모델도 초대·멤버·공개 게시 명령을 차단한다.
- 따라서 ‘가입 없이 동행 참여’는 현재 출시 문구로 사용할 수 없다.
- 상세 조회는 Query 기반이며 확인한 경로에서 실시간 구독을 찾지 못했다. 충돌 보호가 있다는 사실만으로 실시간 공동 편집을 보장하지 않는다.

지도·항공
- 지도는 실제 좌표의 핀·방문 순서 연결을 사용한다. 웹은 상대 위치 도식이며 도로 경로와 구분한다.
- 항공 정보 직접 입력과 외부 검색을 실제 운항 조회·예약 인증으로 표현하지 않는다.
- 앱 내부 장소 추천·평점·영업시간, 자동 이동 시간·대중교통 경로는 최신 일정 준비 문서의 구현 범위에 없다.

비용·영수증
- 통화별 비용 합계와 회원 영수증 인식·검토 흐름이 있다. 게스트 영수증은 직접 입력하는 정책이다.
- 자동 환율 변환은 없으며, 확인한 WorkspaceExpense에는 개인별 결제자·분담금·채무 정산 구조가 없다.
- ‘여행 가계부’와 ‘동행 간 정산’을 구분해야 한다. 현재 단계에서 완성된 1/N 정산을 홍보하지 않는다.

기록·커뮤니티
- 여행 기록과 선택한 항목의 공개 게시, 신고·차단 경로가 있다.
- 포토북 주문·결제·인쇄·배송 완료 근거는 확인하지 못했다.
- 공개 커뮤니티는 신고 접수 이후 실제 처리할 운영 담당자와 절차가 있어야 한다.

운영·출시
- 최신 v5 문서는 배포 준비 상태이며 원격 배포, 서명 APK/AAB 생성, Play 업로드, 실기기 설치 인수를 완료로 기록하지 않는다.
- production 설정에는 운영 인증 주소·Origin 등의 빈 값이 있고, D1/R2/AI 바인딩과 비밀 값은 현행 배포 방식에 맞춰 확인해야 한다. 설정 파일만으로 원격 운영 상태를 단정하지 않는다.
- 계정 삭제, 백업 복구, 개인정보 고지, 고객지원은 기존 배포 문서에도 출시 전 과제로 남아 있다.
- 확인한 앱 코드·의존성에서 제품 행동 분석과 모바일 크래시 수집 전용 도구를 찾지 못했다. Worker 관측 설정은 있지만 가입·활성화·여행 사용을 측정하는 체계와는 다르다.

4. 기존 사업계획에서 바로잡을 내용

시장 규모
기존 시장 문서의 산식은 850만 명 × 28,500원 × 7.5%다. 결과는 18,168,750,000원, 약 181.7억 원이다. 문서의 1,800억 원과 약 10배 차이가 난다. 이 산식도 국내 전체 출국자, 실제 유효 고객, 유료 고객을 구분하지 않아 사업계획의 근거로 바로 사용할 수 없다.

온라인 여행 거래액과 일정 관리 서비스의 매출은 별도로 추정한다. 초기 시장은 ‘모집 가능한 여행팀 수 × 실제 사용 비율 × 구매 비율 × 순매출’로 계산하고, 각 입력값을 실험으로 채운다. 출처와 산식이 확인되지 않은 시장 비중·성장률은 외부 제안서에서 제외한다.

LTV와 CAC
기존 BM 문서의 연간 28,500원은 매출 가정이며 고객 생애가치가 아니다. 제조·배송·결제·환불·AI·스토리지·고객지원 원가와 재구매 기간을 반영해야 한다. LTV는 관측 가능한 고객 유지 기간의 누적 공헌이익으로 추정한다.

제휴 계약을 확인하지 않은 수수료, 포토북 전환율 25~28%, 제조원가와 마진은 미검증 가정으로 표시한다. 카드 제휴 수익이나 B2B 계약액을 확정 매출처럼 더하지 않는다. K-Factor를 적용해 CAC가 7,000원에서 2,800원으로 줄어든다는 계산도 실제 유입 집계로 대체한다.

사업 제안서에는 초기 18개월 8.5억 원의 예산안이 있지만 승인·조달 여부는 확인하지 못했다. 이를 실제 집행 가능 예산으로 간주하지 않는다. 첫 90일 비용은 인건비, 사용자 조사, 출시·개인정보 검토, 인프라, 제한된 채널 실험으로 다시 산정하고 검증 결과에 따라 다음 예산을 배정한다.

성장과 품질 목표
여행당 초대 수락자 수는 K-Factor와 다르다. 새로 들어온 동행자가 다음 여행을 생성하는 비율과 전파 주기까지 관찰해야 성장 지속성을 판단할 수 있다.

0.00% 데이터 유실, 50ms 미만 응답, 1초 자동 기록과 같은 보장은 검증 조건과 측정 범위가 없으면 삭제한다. ‘관측 기간에 확인된 유실 사고 0건’처럼 실제 증거의 범위로 기록한다.

5. 경쟁과 차별화 방향

Wanderlog 공식 사이트는 일정·지도·실시간 협업·예산·오프라인 기능을 안내한다. 공식 도움말은 기본 여행 계획과 동행 협업을 무료로 제공한다고 설명한다. 트리플 공식 사용 설명서도 여행 계획, 여행 중 활용, 오프라인 가이드, 여행 후 리뷰·일정 공유를 안내한다. 트리플의 해당 글은 오래된 안내이므로 최신 요금·세부 기능을 비교하려면 실제 앱을 추가 확인해야 한다.

자료만으로도 ‘계획부터 기록까지 한곳에’라는 넓은 주장이 독점적 차별점이라고 보기 어렵다. 주요 경쟁은 다른 여행 앱과 함께 카카오톡·구글 지도·기존 일정표 조합이다. 사용자가 이미 만든 계획을 다시 입력해야 한다면 새 앱 도입 비용이 커진다.

초기 차별화 가설은 다음과 같다.
- 일정 담당자가 장소 링크와 예약 정보를 정리하는 수고를 줄인다.
- 동행자가 최신 일정을 빠르게 확인하고, 변경 때 입력을 잃지 않는다.
- 기록을 별도로 다시 쓰는 부담을 줄여 여행 후 간단한 결과물을 남긴다.

승부를 판단할 질문은 ‘기능이 더 많은가’보다 ‘지금 쓰는 방식보다 편해서 실제 여행에 채택하는가’다. 기존 방식과 동일 과제를 수행하게 하고 첫 일정 작성 시간, 동행 확인 시간, 재입력 횟수를 비교한다. 효과를 측정하기 전에는 경쟁 우위를 확정하지 않는다.

6. 첫 출시 범위

필수 범위
- 여행 생성, DAY별 일정 편집·순서 이동, 외부 지도 연결, 입력한 항공 정보 정리.
- 통화별 지출 기록, 예상 비용과 실제 지출 구분, 수동 입력과 오류 재시도.
- 회원 초대, 동행 읽기·편집 권한, 다른 계정과 사진 접근 분리.
- 기기 저장 범위 안내, 계정 삭제 신청 경로, 지원 문의, 기본 행동·오류 측정.

베타에서 먼저 해결할 두 과제

첫째, 게스트 계획을 공유 가능한 회원 여행으로 옮기는 흐름이다. 현재 자동 업로드를 하지 않는 정책은 존중하되, 사용자가 범위와 목적을 확인한 뒤 선택적으로 옮기는 안을 검토한다. 일정·비용·사진의 실패 복구와 중복 방지를 포함해야 한다. 개발 전에는 별도의 여행으로 다시 만들게 되는 불편을 인터뷰와 관찰로 측정한다. 이를 숨긴 채 ‘만든 여행을 바로 공유’라고 안내하지 않는다.

둘째, 동행의 읽기 진입 부담이다. 링크로 일정 일부만 열람하는 웹 화면을 후보로 삼는다. 초대 수락·편집은 인증을 유지하고, 공개 범위·만료·철회·민감 정보 제외를 먼저 정한다. 읽기 링크도 보유자에게 내용이 노출되므로 기본 공개로 바꾸지 않는다. 이 기능은 신규 제안이며 현재 구현으로 간주하지 않는다.

여행 중 사용에 필요한 최소 범위
회원 일정의 오프라인 읽기 수요를 베타에서 확인한다. 필요하다면 마지막으로 저장한 일정의 기기 보관, 마지막 갱신 시각, 권한 철회·로그아웃 때의 정리부터 구현한다. 자동 쓰기 동기화까지 첫 버전에 넣을 필요는 없다. 오프라인 읽기를 내세워 고객을 모집하려면 해당 기능의 실기기 검증을 선행한다.

후순위
실시간 다자 편집, 자동 동선 최적화, 실시간 항공·환율, 완성형 개인별 정산, AI 대화형 코치, 글로벌 도시 콘텐츠 확대, 소셜 피드 성장 기능, 포토북 자동 생산, 금융·B2B 데이터 사업. 현재 기능은 유지하되 신규 개발과 광고의 중심에서 제외한다. 공개 게시를 유지하면 관련 운영 의무도 유지한다.

7. 출시 승인 조건

안전한 베타를 시작하기 전
- 검증할 소스·API·앱 버전을 고정하고 `npm run check`와 대상 빌드를 실행한다.
- 현행 계약의 API를 먼저 배포하고, 일정을 작성·재조회한 뒤 대응 앱을 배포한다. 최신 v5와 이전 API 혼용을 막는다.
- 기존 업로드 키로 서명한 앱에서 신규 설치와 업데이트 후 데이터 보존을 확인한다. dry-run·Hermes 번들은 설치 인수의 대체 근거가 아니다.
- 최소 두 실제 기기·두 계정에서 로그인 복귀, 초대 수락, 저장 응답 유실, 충돌, 권한 철회, 사진 거부·재시도, 앱 재실행을 확인한다.
- 오류 알림과 담당자, 지원 접수 창구, 데이터 보관·삭제 안내를 운영한다.
- 개인정보처리방침·약관·계정 삭제 요청을 실제 서비스 흐름에 연결한다. 계정 삭제 시 공유 여행 소유권과 다른 동행 기록의 처리를 정한다.
- DB와 사진의 복구 범위·보관 기간을 정하고 복구를 실제로 연습한다. 제안하는 초기 목표는 RPO 24시간 이내, RTO 8시간 이내이며, 제품 약속으로 쓰기 전에 실측한다.
- OCR 사용자별 한도·전체 비용 상한, 이미지 용량과 저장 한도, 실패 시 수동 입력을 정한다. 외부 호출이 끝없이 늘지 않게 한다.

대중 공개 전 추가 조건
- 핵심 일정·저장·초대 흐름에 미해결 차단 결함이 없어야 한다.
- 개인정보 노출·중복 비용·데이터 유실 사고는 해결 후 재검증한다. 사고가 확인되면 신규 모집을 멈추고 복구와 원인 제거를 우선한다.
- 계정 삭제 신청을 앱과 웹에서 실제로 접수하고 처리할 수 있어야 한다. 단순 로그아웃이나 여행 삭제로 대체하지 않는다.
- 공개 게시를 유지한다면 신고·차단 UI뿐 아니라 신고 검토, 게시 중단, 사용자 통지, 처리 기록의 담당과 절차를 확인한다.
- 최신 릴리스 문서가 기록한 의존성 감사의 높음 24건·보통 12건은 노출 조건과 대응을 검토한다. 건수만으로 실제 취약 앱이라고 단정하거나 반대로 통과 처리하지 않는다.
- production의 인증·저장소·Origin·비밀 값·도메인과 staging 분리를 점검한다. DB·사진·구버전 앱의 호환성을 포함한 되돌리기 절차를 기록한다.

스토어·개인정보 정책
Google Play 공식 안내상 2023-11-13 이후 생성된 개인 개발자 계정에는 신청 직전 14일 연속 참여한 최소 12명의 비공개 테스트가 요구된다. 현재 계정의 유형·생성일·Console 표시를 확인해야 적용 여부를 확정할 수 있다. 내부 테스트 수행만으로 이 요건을 충족했다고 보지 않는다.

계정 생성 기능이 있는 앱에는 앱 내 계정 삭제 경로와 앱 밖에서 요청할 웹 경로가 필요하다. 공개 UGC에는 신고·차단 및 지속적인 관리 요건이 있다. 외부 클라우드 처리에는 실제 이전 국가·수탁자·항목을 확인하고 개인정보 보호법 제28조의8에 맞는 근거와 고지를 정한다. 이 보고서로 개별 서비스의 법적 충족 여부를 확정하지 않는다.

8. 고객 검증과 시장 진입

인터뷰 15명
다음 2~6주 안에 출국하는 일정 담당자 10명과 동행자 5명을 모집한다. 사용 의향보다 지금 작성 중인 일정표, 공유 방식, 최근 변경 사례를 보여 달라고 요청한다. 일본 2~4인 팀이라는 가설과 다른 유형도 일부 비교한다. 긍정 답변만으로 기능을 추가하지 않는다.

관찰형 사용성 검사 5팀
현재 계획에 실제 장소 3개와 예약 1개를 입력하고 동행에게 공유하게 한다. 설명 없이 완료하는지, 게스트에서 회원으로 바뀌는 과정에서 멈추는지, 동행이 원하는 DAY를 찾는지 관찰한다. 기존 자료를 다시 입력하는 시간을 포함한다. 개발자가 옆에서 문제를 해결한 완료는 자력 완료와 따로 집계한다.

여행팀 베타 20~30팀
출발일이 가까운 순서로 나누어 모집한다. 출발 전, 여행 중, 귀국 후까지 한 여행 주기를 추적한다. 서비스가 도움 된 사례와 사용을 중단한 이유를 모두 기록한다. 사례 공개에는 별도 동의를 받고 실제 후기만 사용한다.

모집 채널
- 일본 자유여행 커뮤니티에서 운영 규칙에 맞춰 일정 담당자를 모집한다.
- 소규모 여행 콘텐츠 제작자와 ‘실제 일정 정리 과정’ 콘텐츠를 시험한다.
- 도쿄·오사카의 특정 고민을 다루는 검색 콘텐츠로 유입시킨다. 실제 제공하는 기능과 편집 정보만 설명한다.
- 친구 초대는 초기 고객이 채택한 뒤 측정한다. 초대 수락을 강요하거나 리뷰 보상과 연결하지 않는다.

스토어 메시지와 첫 화면
광고의 약속, 스토어 설명, 첫 일정 작성의 행동을 일치시킨다. 로그인 전에는 여행의 가치를 먼저 이해하도록 하고, 동행 공유처럼 계정이 필요한 행동에서 이유를 설명한다. 성별·생년월일 입력은 실제 서비스 목적과 필수성을 재검토하고 꼭 필요하지 않은 항목은 첫 사용 뒤로 미룬다.

유료 광고
첫 베타가 실제 여행에서 쓰였다는 증거가 생긴 뒤 소액 상한을 정해 시험한다. 클릭당·설치당 비용보다 활성 여행팀 1팀을 얻는 비용을 비교한다. 행동 측정과 랜딩→작성→저장 경로가 없으면 집행하지 않는다. 목표가 미달이면 광고비를 늘리기 전에 유입 고객의 적합성과 작성 과정을 수정한다.

9. 지표와 확장 기준

초기 핵심 지표는 ‘여행 중 실제로 사용한 팀 수’다. 제품 효용을 확인하는 활성 여행은 생성 7일 안에 일정 3개 이상을 저장하고 다른 날 다시 조회·편집한 여행으로 정의한다. 공유 가설은 이 중 동행 1명 이상이 실제로 일정을 조회한 팀을 따로 본다. 초대 수락과 실제 조회는 분리한다.

다음 수치는 업계 평균이 아니라 첫 90일의 내부 판단 기준 초안이다. 모집 특성과 표본에 맞춰 조정하며, 비율과 함께 분자·분모를 기록한다.

지표 / 정의 / 초기 기준안
- 여행 생성 완료율: 생성 화면에 진입한 신규 일정 담당자 중 여행 저장 완료 / 60% 이상.
- 활성 여행 전환율: 저장 완료 여행 중 위의 활성 여행 조건 충족 / 40% 이상.
- 동행 실사용률: 실제 초대한 활성 여행 중 동행 1명 이상 조회 / 50% 이상.
- 현장 사용률: 여행 기간이 종료된 활성 여행 중 여행 기간 내 서로 다른 2일 이상 조회·기록 / 50% 이상. 당일 여행은 따로 집계.
- 귀국 후 기록률: 종료한 활성 여행 중 귀국 후 7일 안에 사진·메모 추가 또는 기록 조회 / 30% 이상.
- 첫 유료 검증: 해당 결과물을 제안받은 유효 고객 중 실제 비환불 구매 / 최소 10건을 확보해 이유와 원가 확인. 지인 구매·보상 구매는 따로 표시.
- 품질: 확인된 개인정보 노출·데이터 유실 미해결 사고 0건. 핵심 저장 성공률과 충돌·재시도 회복률도 별도로 관찰.

주간 지표에는 아직 출발하지 않은 팀을 현장 이탈로 계산하지 않는다. 출발 전·여행 중·여행 후를 나누고 각 관측 기간이 끝난 팀끼리 비교한다. 여행 서비스의 전체 D7 재방문율 하나로 제품 성공을 판정하지 않는다. 첫 20~30팀은 방향을 찾는 표본이며 PMF나 장기 유지율의 증거로 확대 해석하지 않는다.

측정 이벤트 제안
trip_create_started, trip_created, schedule_saved, invite_opened, invite_accepted, companion_trip_viewed, trip_viewed, expense_saved, receipt_confirmed, record_viewed, purchase_completed, account_deletion_requested.

이 이벤트는 신규 도입 제안이다. 서버가 확정한 저장·수락·결제 성공을 기준으로 중복을 제거한다. 게스트 기기 이벤트와 서버 회원 이벤트를 구분하며, 사용자 선택 없이 개인 기록을 자동 연결하지 않는다. 장소명·영수증 원문·항공 예약 정보·정확한 위치는 분석 이벤트에 담지 않는다.

확대·수정·중단
- 두 차례의 연속 모집에서 생성·활성·동행·현장 사용 기준을 충족하고 치명 사고가 없으면 모집을 확대한다. 각 차수 최소 20개 활성 여행과 관측 기간 종료를 제안한다.
- 생성은 잘하지만 동행이 안 보면 초대·인증·조회 흐름을 우선 수정한다.
- 출발 전에는 쓰지만 현지에서 안 쓰면 읽기 속도·연결 불안정·지도 복귀를 확인한다.
- 여행 후 기록만 사용한다면 사진·기록 정리 제품을 별도 가설로 검증한다.
- 두 번의 개선 후에도 실제 여행에 채택되지 않으면 신규 기능과 광고 확대를 멈추고 타깃·문제를 재설정한다.
- 사용은 유지되지만 구매가 없으면 무료 효용과 유료 결과물의 차이, 구매 시점, 가격을 검증한다. 설치 수를 수익성으로 해석하지 않는다.

10. 수익화 순서와 경제성

첫 수익 실험은 한 번에 하나만 진행한다. 여행 주기가 길고 반복 사용이 아직 확인되지 않았으므로 월 구독보다 여행 단위 또는 결과물 단위의 일회성 구매를 우선 시험한다.

후보는 여행 기록의 PDF 결과물이나 여행별 고급 정리 기능이다. 현재 구현된 결제·내보내기 기능으로 간주하지 않는다. 4,900~9,900원은 가격 실험 후보일 뿐 고객 지불 의사나 매출 전망이 아니다. 인터뷰에서 원하는 결과물을 확인하고, 검수 가능한 샘플과 실제 제공 가능한 구매 흐름을 준비한 뒤 비용을 받는다.

디지털 기능·콘텐츠의 앱 내 판매에는 Google Play 결제 정책과 적용 가능한 예외·프로그램을 확인한다. 실물 포토북은 별도 상품이며 제조·배송·교환·개인 사진 처리·소비자 안내를 포함해 운영해야 한다. 결제 경로를 임의로 동일하게 설계하지 않는다.

그다음 단계
- 제휴 수익은 승인된 파트너 프로그램, 실제 정산 조건과 추적 경로가 생긴 뒤 반영한다. 외부 예약과 서비스의 책임 범위를 설명한다.
- 포토북은 주문·자동 제작 개발 전에 소수 고객의 디자인 샘플 평가와 인쇄 견적, 동의받은 수동 제작을 시험한다. 판매가에서 인쇄·배송·결제·환불·재제작·편집 인건비를 빼고 판단한다.
- 금융 제휴와 관광 데이터 판매는 초기 매출 계획에서 제외한다. 파트너 접근성, 별도 규제 검토, 데이터의 재식별 위험을 먼저 해결해야 한다.

손익 민감도 예시
구매 1건의 변동비 차감 공헌이익을 3,500원이라고 가정하면, 활성 여행의 구매 전환율이 5%/10%/20%일 때 활성 여행 1건당 기대 공헌이익은 각각 175원/350원/700원이다. 공급자 견적이나 실제 가격을 뜻하는 수치가 아니다. 여기에는 무료 고객에게 발생하는 OCR·저장·지원 원가와 고정 인건비가 빠져 있어 실제 이익은 더 작다.

이 상황에서 활성 여행 1건을 광고로 얻는 데 3,000원을 쓴다면 첫 여행만으로 비용을 회수하지 못한다. 재구매·제휴 이익이 관측되기 전에는 낮은 획득 비용의 채널과 초대 활용이 필요하다. 포토북 객단가가 높다는 사실만으로 전체 고객의 수익성을 보장할 수 없다.

활성 여행 CAC = 해당 채널의 모집·광고 비용 ÷ 신규 활성 여행 수.
여행 공헌이익 = 순매출 − 결제·환불·제작·배송·API·AI·저장·변동 지원 비용.
손익분기 유료 주문 수 = 월 고정비 ÷ 유료 주문 1건의 공헌이익. 무료 고객 비용도 별도 반영한다.

11. 90일 실행안과 담당

1~2주 / 출시 기준 고정
PO: 첫 고객·출시 약속·제외 범위·지표 정의, 일정 담당자와 동행 인터뷰 15명.
개발: 최신 API·앱 버전 정리, 서명 빌드, 오류·행동 측정, 계정·데이터 삭제와 복구 계획.
QA·디자인: 5팀 사용 관찰, 실제 기기 핵심 흐름과 입력 부담 검증.
완료 조건: 베타 핵심 흐름, 운영 담당, 개인정보와 지원 경로를 확인한다. 차단 결함이 있으면 모집 일정을 늦춘다.

3~4주 / 제한 베타
PO: 20~30팀을 출발일별 모집하고 직접 관찰한다.
개발: 가입 전후 기록 연결과 초대 이탈 중 영향이 큰 한 과제부터 개선한다.
운영: 문의·사고·신고 처리 기록, 실제 복구 연습과 API 비용 관찰.
완료 조건: 여행 생성과 동행 조회에서 반복되는 실패 원인을 설명할 수 있고 해결을 확인한다.

5~8주 / 여행 사용 검증
PO: 현장 사용과 귀국 후 기록을 추적하고 이탈 고객도 인터뷰한다.
개발·디자인: 현지 조회·저장 복구·지도 복귀, 필요성이 확인된 오프라인 읽기를 개선한다.
QA: 업데이트 후 기록 보존과 구버전 호환을 재검증한다.
완료 조건: 관측 기간이 끝난 팀의 현장 사용 기준을 확인한다. 첫 그룹이 아직 여행을 끝내지 않았으면 관측을 연장한다.

9~12주 / 제한 공개와 유료 실험
PO: 기준을 충족한 경우 한국 대상 Android 공개 범위를 늘리고 한 가지 가격 실험을 진행한다.
개발·운영: 결제·환불·지원과 원가를 기록한다. 미완성 기능을 결제 대상으로 표시하지 않는다.
그로스: 검색 콘텐츠와 소규모 제작자 채널을 비교하고 활성 여행 CAC를 측정한다.
완료 조건: 첫 비환불 구매 10건과 공헌이익, 획득 비용을 확인하고 확대 여부를 결정한다.

Android를 첫 네이티브 출시 대상으로 권고하되, 모집한 팀의 동행 기기 구성을 확인한다. iPhone 동행이 많아 참여가 끊기면 웹 조회·참여를 먼저 보완하거나 iOS 인수 계획을 앞당긴다. iOS 동시 출시를 전제한 일정으로 홍보하지 않는다.

역할은 한 사람이 겸할 수 있다. 다만 출시 승인, 장애 대응, 개인정보 요청, 신고 처리의 책임자는 명확해야 한다. 주 1회 제품 판단 회의에서 여행팀별 퍼널, 실패 3건, 다음 실험 1개, 비용을 검토한다. 예산과 인력 확인 뒤 주차별 작업량을 다시 산정한다.

12. 지금 결정할 우선순위

P0: 서명 앱 실기기 인수, 계정 삭제·개인정보·지원·복구, 운영 환경과 비용 제한, 출시 기능 문구 정합성.
P1: 고객·행동 측정, 게스트 계획의 회원 공유 연결, 동행 조회 진입, 여행 중 읽기와 저장 복구.
P2: 여행 후 결과물과 유료 구매 한 가지, 채널별 활성 여행 CAC.
보류: 포토북 생산 자동화, 금융·관광 데이터 사업, 광범위한 AI·콘텐츠·커뮤니티 확장.

첫 2주에는 출시 약속과 실제 동작의 차이를 없애고, 실제 여행팀이 계획을 맡길 수 있는 상태를 만든다. 그다음 고객의 여행 한 번을 끝까지 관찰해 개발과 마케팅 투자 근거를 얻는다.
