# 핵심 정책 구현 대조와 선택안

검토일: 2026-10-27 / 버전: v0.1 / 상태: 네 항목의 권장 A안 사용자 승인 완료(2026-10-27)

범위: [상위 기획안](서비스_상위기획_및_핵심흐름_검토안.md)의 POL-01·02·05·06을 현재 작업 트리의 코드와 대조했습니다. 아래 내용은 배포 서버나 앱의 실제 동작 검증 결과가 아닙니다. 세부 화면·코드는 변경하지 않았습니다.

## 먼저 선택할 내용

| 항목         | 권장 선택                                                                              | 사용자가 경험하는 차이                                                                      |
| ------------ | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 가입 전 입력 | 기본 정보 입력까지 허용, 서버 저장·협업·공개 전에 정식 로그인                          | 여행 준비를 먼저 시작하고 저장할 때 계정을 연결합니다.                                      |
| 날짜 미정    | 초안으로 저장, 출발일·도착일을 정한 뒤 정식 여행 생성                                  | 날짜를 억지로 넣지 않고 준비를 이어갑니다.                                                  |
| 동행 초대    | 7일 동안 유효, 링크당 새 참여자 1명, 소유자 철회 가능                                  | 친구가 바로 확인하지 못해도 참여할 여유가 있습니다. 여러 친구에게는 각각 링크를 발급합니다. |
| 공개         | 소유자만 발행, 계획은 여행 전부터·기록은 완료 후, 여행당 공개글 1개, 직접 확인 후 갱신 | 계획을 소개할 수 있고 변경 사항이 모르는 사이 공개되지 않습니다.                            |

네 항목 모두 권장 A안으로 확정했습니다. 현행 기준은 [핵심 정책 확정 사항](<../01. 기능정의/핵심정책_확정사항.md>)입니다. 아래 대안과 코드 대조는 결정 당시 이력이며 구현 완료를 뜻하지 않습니다.

## 1. 가입하기 전에 어디까지 쓸 수 있게 할까요?

‘아무 계정도 없는 상태’, ‘게스트로 시작해 익명 계정을 받은 상태’, ‘이메일·소셜 계정으로 로그인한 상태’를 구분해야 합니다. 현재 코드는 이 세 상태를 단순히 로그인 여부 하나로 처리하지 않습니다.

### 코드에서 확인한 내용

- 로그인 화면은 게스트 기록이 기기에만 저장된다고 안내합니다(E01).
- 앱의 여행 요청은 게스트일 때 기기 저장으로 보내며 기기 여행 생성 경로도 있습니다(E02). 단순한 입력 체험보다 넓은 기능입니다.
- 게스트 시작 시 서버에서 익명 계정과 세션을 발급받습니다(E03). D1 인증 경로는 유효 세션을 확인하지만 익명 계정을 별도로 차단하지 않습니다. 다른 Supabase 인증 경로는 익명 계정을 거부합니다(E04). 따라서 ‘회원 저장만 서버에서 허용한다’고 일괄 단정할 수 없습니다.
- 서버 초안은 현재 세션 사용자 ID로 저장합니다(E05). 앱에서 로컬로 보낸다는 사실만으로 서버의 회원 제한을 대신할 수 없습니다.

### 선택지

| 선택                                         | 장점                                                         | 부담·주의                                                                                                      |
| -------------------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| A. 기본 정보 입력 후 저장할 때 로그인 — 권장 | 처음부터 가입을 요구하지 않으면서 서버 중심 정책을 지킵니다. | 로그인 왕복 때 입력을 보존해야 합니다. 앱을 종료한 뒤 복구까지 보장하려면 별도 임시 보관 정책이 필요합니다.    |
| B. 입력 시작 전 로그인                       | 흐름과 저장 위치가 단순합니다.                               | 사용자가 앱의 가치를 느끼기 전에 가입해야 합니다.                                                              |
| C. 게스트가 기기에 여행·일정을 저장          | 가입 없이 충분히 체험할 수 있고 기존 로컬 기능을 활용합니다. | 기기 변경·삭제·회원 전환 시 복구와 이전 범위가 복잡해집니다. 서버 데이터 중심 지시와 구분된 예외가 필요합니다. |

권장 A의 입력 범위는 여행 이름·목적지·날짜 등 기본 정보입니다. 새 영수증·사진 업로드, 동행 수락·발급, 공개 발행은 정식 로그인 이후로 둡니다. 입력 중에는 저장 완료라고 안내하지 않습니다. 기존 게스트 기록은 삭제하거나 자동 이전하지 않고 별도 복구·명시적 가져오기 경로를 보존합니다.

추가 개발: 익명 계정과 정식 회원을 서버에서 구분하고 저장·초대·공개 제한을 일치시켜야 합니다. 로그인 복귀 시 기본 정보가 유지되는지 확인해야 합니다. 기존 게스트 기능을 제한하는 변경이므로 사용자 승인에 따라 후속 개발 대상이며 이번에는 적용하지 않습니다.

## 2. 날짜가 없어도 여행을 만들까요?

현재 정식 여행 입력은 나라, 출발일·도착일, 시간대 등을 요구하고 기간은 시작일 포함 1~90일입니다. 도시·제목·항공편은 필수가 아닙니다(E06). 초안 입력은 별도의 날짜 필수 조건 없이 기본 정보·항공편 단계의 입력값을 저장합니다. 서버 초안은 계정당 최대 5개입니다(E05).

| 선택                        | 사용 방식                                                           | 구현 영향                                                                             |
| --------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| A. 날짜 미정은 초안 — 권장  | ‘언젠가 일본 여행’을 보관하고 날짜를 정하면 정식 여행으로 만듭니다. | 기존 초안·생성 계약과 맞습니다. 초안 저장·복원·생성 후 재조회 연결을 검증해야 합니다. |
| B. 날짜 없는 정식 여행 허용 | 날짜 없이도 일정을 순서대로 넣고 동행을 초대합니다.                 | 날짜별 일정, D-day, 항공편, 영수증 날짜 연결 등 여러 계약을 바꿔야 합니다.            |
| C. 날짜 입력 전 저장 금지   | 날짜를 정한 여행만 보관합니다.                                      | 출발일 없는 계획도 준비한다는 기존 방향과 맞지 않습니다.                              |

권장 A에서는 출발일이 없으면 작성 중으로 분류합니다. 출발일만 있고 도착일이 없을 때도 정식 생성은 하지 않으며 초안으로 유지합니다. 이 경우 홈의 세부 표시 분류는 다음 단계에서 정합니다. 날짜 미정 초안에 장소 수집·동행 협업까지 제공하는 것은 이번 권장안에 포함하지 않습니다.

## 3. 초대 링크는 얼마나 오래, 몇 명이 사용할까요?

현재 코드는 소유자가 읽기 또는 편집 역할의 링크를 발급하며 유효기간은 **24시간**, 사용은 **1회**입니다(E07). 기존 문서의 ‘7일’은 구현값과 다릅니다. 링크는 특정 이메일에 묶여 있지 않으므로 전달받은 사람 중 조건을 만족한 첫 수락자가 사용할 수 있는 구조입니다.

또한 이미 참여한 사용자가 유효 링크를 수락하면 역할은 유지하지만 링크는 소비하는 경로입니다(E08). 기존 문서의 ‘기존 멤버는 미소비’ 권장안과 다릅니다. 같은 수락 요청의 재시도와 새 수락 요청도 구분합니다.

| 선택                        | 장점                                                                              | 부담·주의                                                        |
| --------------------------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| A. 7일·새 참여자 1명 — 권장 | 친구가 며칠 뒤 확인해도 사용할 수 있고 재전달로 여러 명이 들어오는 것을 막습니다. | 친구마다 링크가 필요합니다. 현재 24시간을 7일로 변경해야 합니다. |
| B. 24시간·1회 유지          | 현재 구현을 유지하며 링크가 노출되는 시간을 줄입니다.                             | 늦게 확인한 친구에게 링크를 다시 보내야 합니다.                  |
| C. 7일·여러 명              | 단체 대화방에 한 링크만 보낼 수 있습니다.                                         | 의도하지 않은 재전달, 인원 한도, 동시 수락 처리 범위가 커집니다. |

권장 A는 ‘기존 멤버가 열어도 역할을 바꾸거나 링크를 소비하지 않음’을 함께 포함합니다. 소유자는 수락 전에 철회할 수 있어야 합니다. 수락 후에는 링크 철회로 멤버가 자동 탈퇴하지 않으며 멤버 관리는 별도입니다.

추가 개발·검증: 7일 경계, 기존 멤버 미소비, 두 계정의 동시 수락에서 한 명만 참여, 재시도, 철회, 이미 제거된 멤버의 재진입 방지를 확인합니다. 링크당 1명은 지정한 친구의 신원까지 보장하는 정책이 아닙니다.

## 4. 누가 무엇을 공개하고, 어떻게 바꿀까요?

### 현재 구현

- 소유자만 발행·갱신·중단합니다. 편집 동행자는 공개할 수 없고 보관된 여행은 변경이 차단됩니다(E09).
- 계획 공유는 일정이 1개 이상이고 보관 상태가 아니면 가능합니다. 기록 공유는 COMPLETED 상태여야 합니다. 따라서 상위 기획안의 ‘종료 여행만 공개’는 기존 계획 공유를 제한하는 제안이었습니다(E09).
- 공개 자료는 별도 사본입니다. 여행당 하나의 공개글을 유지하며 재발행은 같은 글을 갱신합니다. 원본의 일반 수정은 자동 반영하지 않습니다(E10).
- 일정의 주소·시각·여행 날짜·장소 식별정보가 공개될 수 있습니다. ‘위치가 전혀 공개되지 않는다’고 설명하면 안 됩니다. 비용 선택 시 선택 일정만이 아니라 여행 전체 실제 지출을 통화별로 합산합니다(E11).
- 사진 삭제 명령은 공개에 쓰인 사진인지와 무관하게 공개글 전체를 내리는 처리가 있습니다(E12). ‘원본 변경은 공개글에 아무 영향이 없다’는 설명도 정확하지 않습니다.

### 선택지

| 선택                                             | 사용 방식                                                                                            | 구현 영향                                                                       |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| A. 소유자 공개·직접 갱신 — 권장                  | 계획은 여행 전부터, 기록은 완료 후 공유합니다. 여행당 공개글 하나를 유지하고 다시 확인해 갱신합니다. | 대부분 기존 구조와 맞습니다. 사진 삭제 영향과 공개 항목 안내를 보완해야 합니다. |
| B. 종료 여행 기록만 공개                         | 여행을 다녀온 뒤에만 공개합니다.                                                                     | 기존 계획 공유를 제한합니다. 친구에게 미리 일정을 소개하는 활용이 줄어듭니다.   |
| C. 동행 편집자도 공개, 계획글·기록글을 따로 유지 | 여러 사람이 편리하게 발행합니다.                                                                     | 공개 동의·권한·게시물 관리 정책과 구현 범위가 커집니다.                         |

권장 A의 세부 의미는 다음과 같습니다.

1. 공개 권한은 소유자에게만 둡니다. 공개 링크 열람은 원본 편집 권한을 주지 않습니다.
2. 선택한 일정·일반 사진과 공개될 장소·날짜 정보를 확인한 뒤 발행합니다. 비용은 여행 전체 실제 비용 합계임을 명확히 알리고 선택 공개합니다. 영수증 원본·품목·개인 메모·동행 개인정보는 자동 공개하지 않습니다.
3. 원본을 바꾸면 공개글을 자동 갱신하지 않습니다. 사용자가 다시 확인해 발행할 때 반영합니다. 계획글을 기록글로 바꾸면 기존 글을 대체하며 두 글이 동시에 남지 않습니다.
4. 공개에 쓰이지 않은 사진 삭제는 공개글에 영향을 주지 않도록 권장합니다. 공개에 쓰인 사진은 영향 확인 후 공개를 중단하거나 새 사본을 발행하도록 정합니다. 현재의 모든 사진 삭제 시 중단 처리와 달라 추가 개발이 필요합니다.
5. 공개 중단 후 새 열람은 차단합니다. 이미 외부에 내려받거나 캡처한 자료를 회수한다고 보장하지 않습니다.

## 5. 결정 후 진행할 일

선택한 정책을 확정 기록에 남긴 뒤 기존 문서의 서로 다른 설명을 정리합니다. 다음으로 필요한 개발 범위와 검증 시나리오를 정하고, 그 뒤 세부 화면을 설계합니다. 이번 조사만으로 기존 기능을 제거하거나 정책을 코드에 적용하지 않습니다.

이번 대조에서 실서버·웹·실기기 동작 검사는 실행하지 않았습니다. 로그인 복귀·계정 전환, 초안 재조회, 초대 동시 수락·재시도, 권한별 발행, 공개 중단·캐시, 사진 삭제 영향은 구현 단계에서 검증해야 합니다.

검토 이력: TOP-PLAN-01의 기존 상위 검토 이력을 유지합니다. POL-01·02·05·06은 코드 근거를 추가한 재검토 1회입니다. 주 에이전트가 통합했고 분석 담당이 POL-06의 읽기 전용 코드 조사를 맡았습니다. 동일 쟁점의 다음 재검토는 2회이며 파일명이나 담당자 변경으로 초기화하지 않습니다.
