# 영수증 기반 여행 기록 MVP 검토안

- 버전: v0.1 / 작성·검토일: 2026-10-26
- 상태: 정책 RCP-D01~D14는 2026-10-26 사용자 승인 완료. 화면 상세·개발 인계·수치 목표는 검토 중이며 구현 완료가 아님.
- 적용 범위: 여행 중·여행 후 영수증으로 일정·메뉴·실제 지출을 남기는 기능
- 작성 역할: PD·기획 / 근거 검토: 읽기 전용 분석·검토 담당
- 사용자 확정 방향: 영수증 기반 일정·메뉴 추가, 모바일 우선, 국제 접근성 기준을 고려한 UI/UX. 이번 작업은 문서만 작성.
- 연결: [P0 개발 인계](영수증_P0_개발인계_검토안.md), [모바일·접근성 규격](영수증_모바일접근성_검토안.md)

## 1. 사용자 문제와 제품 가설

여행 중에는 식당 이름·먹은 메뉴·금액을 따로 적기 어렵고, 여행 후에는 사진과 영수증이 어느 날의 방문인지 다시 맞춰야 한다. 영수증 한 장의 내용을 확인하면 방문한 날의 일정·메뉴·지출이 함께 남도록 한다.

첫 검증 대상은 국내·일본 자유여행의 음식점·카페 이용자다. 메뉴는 앱 탐색 메뉴가 아니라 음식·상품 품목이다. 기존 KRW·JPY·USD 지원은 유지하되 첫 품질 검증은 KRW·JPY 중심으로 진행한다. USD 품질을 검증하지 않았다면 검증 완료로 표시하지 않는다. 타깃 비율·시장 규모·매출 가정은 이번 MVP의 근거로 사용하지 않는다.

차별화 가설은 별도 일정·가계부·메모 입력에 비해 기록 시간이 줄고, 여행 후에도 메뉴까지 포함한 기록을 완성할 수 있다는 것이다. 영수증 진위나 본인 방문을 증명한다는 주장은 포함하지 않는다.

## 2. 현재 구현과 근거의 한계

| 구분      | 확인한 내용                                               | MVP 대응                                             |
| --------- | --------------------------------------------------------- | ---------------------------------------------------- |
| 사진·OCR  | 실제 공급자 분석과 사용자 확인 초안 존재                  | 공급자 교체보다 다양한 실물 영수증 검증 우선         |
| 일정      | 새 장소 기록 생성과 기존 일정 연결 존재. 기존 계획은 보존 | 기존 경로 재사용                                     |
| 메뉴      | 인식된 행의 수정 가능. 행 추가·삭제 UI는 확인되지 않음    | 품목 0개에서도 직접 보완 가능하게 함                 |
| 여행 후   | 결제일 DAY 연결, COMPLETED 변경 허용 코드 경로 존재       | 완료 여행 진입부터 재조회까지 실기기 검증            |
| 날짜 수정 | 저장된 영수증 수정에서 새 장소 생성 선택 제한             | 해당 날짜에 기존 일정이 없어도 수정 완료 가능하게 함 |
| 지출      | 영수증과 같은 ID의 실제 지출 동시 생성                    | 재시도·충돌·삭제 정합성 검증                         |
| 중복      | 동일 mediaId/영수증 ID 방지 존재                          | 재업로드와 수동 지출의 유사 중복 안내 보완           |

코드 근거: [ReceiptReview](../../../apps/mobile/src/features/workspace/ReceiptReview.tsx), [PlanEditorView](../../../apps/mobile/src/features/workspace/PlanEditorView.tsx), [receiptFlow](../../../apps/mobile/src/features/workspace/receiptFlow.ts), [workspaceModel](../../../packages/validation/src/workspaceModel.ts).

위 상대 경로는 문서 검사에서 확인한다. [과거 P0 인수 기록](<../../05. 검수/02. 검수보고/Stitch_P0인수검수.txt>)에는 합성 영수증의 실제 OCR·기존 일정 확정·재로그인 복원 기록이 있다. 이번 기획에서는 앱 실행·실제 영수증·카메라·현재 배포본을 재검증하지 않았다. 오래된 기기 초안 문서와 현재 코드가 다르면 문서만으로 미구현을 단정하지 않는다.

## 3. 경쟁 비교

확인일: 2026-10-26. 공식 소개·도움말 조사이며 서비스별 실기기 조작 비교는 미실행이다. 미확인은 미지원이 아니다.

| 서비스           | 공식 자료에서 확인                                                                 | 이번 MVP의 비교 질문                                                        |
| ---------------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 트리플           | 모바일 앱의 일정·가계부·정산·리뷰·여행기                                           | 영수증에서 일정·메뉴·금액을 함께 남기면 입력 부담이 줄어드는가?             |
| Wanderlog        | 웹·앱 일정·경비·예산·정산 및 외화 처리                                             | 금액뿐 아니라 실제 먹은 메뉴를 방문별로 남기는 것이 재조회에 도움이 되는가? |
| NAVER MY플레이스 | 모바일 영수증 방문 인증·리뷰, 중복 제출 제한. 해외 결제 영수증은 공식 인증 범위 밖 | 개인 여행 기록에 해외 영수증을 연결하는 가치가 있는가?                      |

- [트리플 공식 가이드](https://triple.guide/articles/8e26647d-9e7b-4346-8517-4945ced97bb8): 2023년 게시 자료이므로 최신 화면 차이는 추가 확인 대상.
- [Wanderlog 경비 기능](https://wanderlog.com/travel-budget-expense-splitting-app), [경비 추가 도움말](https://help.wanderlog.com/hc/en-us/articles/5159532161819-Add-an-expense).
- [NAVER 영수증 제출 기준](https://help.naver.com/service/19485/contents/9766?lang=ko&osType=MOBILE), [중복 제출](https://help.naver.com/service/19485/contents/11540?lang=ko&osType=MOBILE).

열람 자료에서 경쟁 서비스의 영수증 품목 OCR→여행 일정 생성 전체 흐름은 확인하지 못했다. 이를 독점 기능의 근거로 사용하지 않는다. 기존 경쟁 분석 문서의 단정적 비판은 이 검토안에 승계하지 않는다.

## 4. MVP 범위와 우선순위

| ID        | 우선순위 | 범위                                                | 선행 조건                       |
| --------- | -------- | --------------------------------------------------- | ------------------------------- |
| RCP-P0-01 | P0       | 메뉴 행 추가·수정·삭제, OCR 실패 수동 보완          | 메뉴 필수/선택과 품목 한도 결정 |
| RCP-P0-02 | P0       | 여행 후 등록, 결제일 변경, 새 일정·기존 일정 재연결 | 실제 기록·계획 보존 정책        |
| RCP-P0-03 | P0       | 요청 중복 방지, 유사 결제 안내, 실패·충돌 복구      | 중복 후보 규칙·기존 지출 처리   |
| RCP-P0-04 | P0       | 인증 표현·원본 보관·공개·권한·삭제 정책             | 오너의 정책 선택                |
| RCP-P0-05 | P0       | 실제 영수증·모바일 접근성·저장 정합성 인수          | 앞선 P0 구현과 검증 환경        |
| RCP-P1-01 | P1       | 여러 장 선택·처리 현황·실패건 재개                  | 단건 흐름과 호출 한도 검증      |
| RCP-P1-02 | P1       | 장소 추천·기존 지출 연결·이미지 유사 중복 탐지      | 오탐·권한·성능 기준             |
| RCP-P2-01 | P2       | 메뉴 번역·추천·검색 확장·선택 공개·여행책 활용      | 사용 가치와 데이터 품질 검증    |

MVP에서는 한 번에 영수증 한 장만 처리한다. 자동 일괄 확정, 오프라인 자동 전송 큐, 통화 확대·자동 환산, 진위 보장 배지, 메뉴 자동 번역은 추가하지 않는다. 기존 기능의 지원 범위를 임의로 삭제하지 않는다.

## 5. 사용자 흐름과 권장 정책

여행 중: 여행 선택 → 촬영/앨범 → 상호·결제일·통화·총액·메뉴 확인 → 기존 일정 연결 또는 새 장소 기록 → 저장 결과 확인.

여행 후: 완료 여행 선택 → 앨범에서 한 장 선택 → 과거 현지 결제일 확인 → 방문 연결·메뉴 보완 → 저장 → 다음 영수증 등록. COMPLETED와 읽기 전용 ARCHIVED를 구분한다.

정책 RCP-D01~D08의 상세 권장안을 [정책 결정표·통합 화면 흐름](영수증_정책결정_화면흐름_검토안.md)으로 옮기고 D09~D14를 추가했다. 해당 문서에서 선택 이유·대안·영향·검증 연결을 함께 관리한다. 이 문서는 MVP 범위와 우선순위를 관리하며, 화면 승인이나 구현 완료를 뜻하지 않는다. 정책 확정 이력은 연결된 결정표를 따른다.

## 6. 성공 지표와 개발 순서

| 지표           | 정의                                                       | 분리해서 볼 조건                    |
| -------------- | ---------------------------------------------------------- | ----------------------------------- |
| 등록 완료율    | 저장 성공한 등록 세션 / 영수증 선택 후 등록을 시작한 세션  | 여행 중/후, OCR/수동, 통화·플랫폼   |
| 기록 시간      | 영수증 선택부터 저장 성공까지 중앙값·상위 90백분위         | OCR 대기와 사용자 수정 시간을 분리  |
| 메뉴 보완 부담 | 메뉴 편집 건수·소요 시간 / 메뉴를 기록한 세션              | 0개 인식, 일부 인식, 전체 인식      |
| 중복 발생      | 재시도로 추가 생성된 레코드 수 및 사용자 신고 중복 건수    | 시스템 중복과 실제 별도 결제를 구분 |
| 재조회 정합성  | 재접속 후 기대한 날짜·메뉴·금액이 일치한 검수 건 / 검수 건 | 원본 보관 여부·수정·삭제            |

사용 지표의 목표치는 초기 실험 후 정한다. 검수에서 데이터 유실·중복 생성·권한 우회는 0건이어야 한다. 분석 이벤트에 원본 이미지, OCR 원문, 메뉴명, 상호, 결제 식별자를 보내지 않는다. 수집 항목과 동의 정책은 별도 검토한다.

순서: 정책·수용 기준 정리 → 메뉴 보완 → 날짜·연결 수정 → 중복·실패 처리 → 통합·모바일 인수. P0-04 정책과 모바일 규격은 모든 구현 작업의 공통 조건이다. 기간 추정은 코드 영향·검증 데이터·기기 확보 후 한다.

개발 시 [기획 진행 절차](<../01. 기능정의/기획_진행절차.md>)를 따르고, 데이터 계약을 실제로 변경할 때 DB 객체사전·API 계약을 함께 갱신한다. 이번 문서는 확정 스키마가 아니다.
