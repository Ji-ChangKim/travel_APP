- 버전: v0.1 / 작성·검토일: 2026-10-26 / 상태: 개발 착수 전 검토안
- 정책 상태: RCP-D01~D14는 2026-10-26 사용자 승인. 후속 개발 요청에 따라 로컬 구현과 자동 검수를 진행했다. [개발·검수 기록](<../../05. 검수/02. 검수보고/2026-10-26_영수증P0_개발검수.txt>)에서 결과와 미실행 범위를 확인한다.
- 적용 범위: RCP-P0-01~05. 아래 완료 기준은 유지하며 실기기·실물 영수증 인수 전에는 P0 전체 완료로 판단하지 않는다.
- 상위 기준: [MVP 범위·정책](영수증_MVP_검토안.md), [모바일·접근성 인수 기준](영수증_모바일접근성_검토안.md)
- 역할: PD는 범위·정책·인수 기준, 개발은 구현·계약·자동 검사, QA는 실제 흐름·기기·접근성 증거를 담당. 사람·개발 일정은 미정.

## 1. 공통 개발 계약

- 현재 OCR·영수증 확인·일정 연결·실제 지출·원본 보관·권한 처리를 재사용한다. 과거 검수 성공을 이번 수정의 통과 증거로 대체하지 않는다.
- 영수증 입력은 상호, 현지 결제일, 선택 시각, 통화, 총액, 메뉴 목록, 여행/DAY/일정 연결, 원본 보관 선택을 다룬다. 미확인 값은 추정해 채우지 않는다.
- 메뉴는 이름·선택 수량·선택 단가·선택 금액을 보관한다. 현행 `receiptItemSchema`는 이름 1~120자, 수량은 null 또는 1~10000 정수, 단가·금액은 빈 문자열 또는 정수부 최대 12자리·소수부 최대 2자리 문자열이며, 품목 목록은 최대 50개다. 현재 계약을 재사용하고 51번째 행은 설명과 함께 추가를 막는다. 품목 금액의 통화별 자릿수와 최종 결제 총액 검증이 일치하는지는 별도로 대조한다. 값이나 초과 행을 조용히 잘라 저장하지 않는다.
- 영수증과 실제 지출은 같은 ID를 유지한다. 생성·수정·삭제 시 관련 자료가 일부만 반영되지 않게 한다. DB 저장 성공과 원본 파일 삭제 성공은 분리해 재시도 상태를 설계한다.
- 새 실제 기록을 만들거나 연결을 바꿔도 기존 계획·메모·사진·다른 영수증을 임의로 이동·삭제하지 않는다. 원래 장소를 자동 삭제하지 않는다.
- 뷰어·보관 여행·다른 여행의 원본에 대한 제한은 서버에서도 유지한다. 앱의 버튼 숨김만으로 권한 검증을 대신하지 않는다.
- 변경 후 `npm run check`와 해당 업무 회귀 검사를 실행한다. 헤더·GNB·이동 영향이 있으면 `npm run test:headers:web` 및 뒤로가기·이탈 보호 검사를 포함한다. 새 핵심 동작은 의미 있는 모델/API/UI 검사로 검증한다.
- 실패는 입력 보존·재시도·돌아가기 중 가능한 행동을 제공한다. 화면 밖 종료 이후의 영속 초안/오프라인 큐는 이번 신규 범위가 아니며 저장됐다고 안내하지 않는다.
- 계약 변경이 확정되면 [DB 객체사전](<../../03. 개발/02. 데이터정의/DB_객체사전.txt>)과 [API 기본 계약](<../../03. 개발/01. API계약/API_기본계약.md>)을 함께 갱신한다. 이번 문서의 필드 설명만으로 스키마를 확정하지 않는다.

## 2. RCP-P0-01 메뉴 입력 완결

### 작업 범위

`ReceiptReview.tsx`, `ReceiptReviewView.tsx`, `receiptChecks.ts`와 관련 공통 입력 검증을 우선 확인한다. OCR 0개/일부 추출/수동 입력/기존 기록 수정 모두에서 메뉴 추가·수정·삭제를 제공한다. 배열 행 수정에만 의존하는 현 흐름을 보완하고, 추가·삭제 중 입력 포커스가 다른 행으로 바뀌지 않게 한다.

행 추가는 빈 이름 입력으로 시작한다. 사용자가 만든 빈 행이 남으면 해당 행의 입력 또는 삭제를 안내한다. 메뉴를 하나도 등록하지 않는 것은 허용하되 ‘메뉴 없이 저장’ 상태를 확인할 수 있게 한다. 알 수 없는 수량을 1로, 금액을 0으로 채우지 않는다. 메뉴 합계와 결제 총액의 차이는 세금·할인 가능성을 안내하고 현행 확인 절차를 유지한다.

### 완료 기준

- 품목 0개에서 한 행을 직접 만들고 저장·재조회할 수 있다.
- 중간 행 추가/삭제 후 다른 행의 이름·수량·금액과 포커스가 뒤섞이지 않는다.
- 메뉴 이름 오류는 행과 연결해 알리고 스크린리더도 이해할 수 있다.
- 원본 보관 선택과 지출 총액은 메뉴 편집만으로 임의 변경되지 않는다.

## 3. RCP-P0-02 여행 후 날짜·방문 연결

### 작업 범위

`PlanEditorView.tsx`, `receiptFlow.ts`, `formCommands.ts`, `workspaceModel.ts`와 연결 응답을 확인한다. COMPLETED 여행에서 단건 등록을 마칠 수 있게 하고, 저장한 영수증의 결제일을 변경했을 때 해당 DAY의 기존 일정 연결 또는 새 장소 기록 생성이 가능하게 한다. 기존 영수증 ID·실제 지출 ID는 유지한다.

결제일은 영수증의 현지 날짜로 입력하고 기기 시간대나 업로드일로 바꾸지 않는다. 시각이 없으면 빈 상태를 유지한다. 여행 기간 밖이면 날짜 수정·여행 재선택·권한 있는 여행 기간 변경으로 안내한다. 기존 영수증의 다른 여행 이전은 범위 밖이다. 일반 여행 종료와 ARCHIVED를 구분하고, 보관 해제는 기존 권한 있는 동작으로 안내한다.

기존 계획과 실제 결제일이 다르면 새 실제 방문에 연결하도록 하며, 계획 날짜를 자동 수정하지 않는다. 재연결할 때 보관 원본의 연결과 지출 DAY는 함께 갱신하되 이전 일정의 다른 자료는 유지한다. 장소 출처 표시는 RCP-P0-04와 협의한다.

### 완료 기준

- 완료 여행에서 등록을 시작해 과거 DAY에 저장·재조회할 수 있다.
- 저장 후 결제일을 바꾸고 빈 DAY에 새 장소를 생성해도 영수증·지출이 중복되지 않는다.
- 날짜·연결 검증이 앱과 서버에서 일치하며 원래 계획을 보존한다.
- ARCHIVED와 뷰어는 우회 저장할 수 없다.

### 검증 시나리오

| ID  | 준비·행동                                            | 기대 결과                                                   |
| --- | ---------------------------------------------------- | ----------------------------------------------------------- |
| D01 | 완료 여행에 과거 영수증 등록 → 새 장소 선택          | 결제일 DAY에 실제 기록 생성, 업로드일 미사용                |
| D02 | 기존 계획 선택 → 다른 결제시각의 영수증 저장         | 원래 계획 보존, 실제 시각은 영수증에 보존                   |
| D03 | 저장된 영수증 날짜를 일정 없는 DAY로 변경 → 새 장소  | 기존 영수증·지출 ID 유지, 새 연결, 이전 계획·다른 기록 보존 |
| D04 | 기간 밖·존재하지 않는 날짜 입력                      | 오류와 수정 행동 제공, 첫날 대체·자동 기간 연장 없음        |

| D06 | ARCHIVED/뷰어/다른 여행 원본으로 저장 시도           | 서버 차단, 기존 기록 불변                                   |

## 4. RCP-P0-03 중복·실패·충돌 복구

### 작업 범위

현재 요청키·버전 충돌·원자 저장을 유지하고 수정 경로에도 적용한다. 같은 원본 ID·영수증 ID와 같은 요청 재시도로 추가 레코드가 생기지 않게 한다. 조회 성공 전 새로운 요청으로 다시 생성하지 않는다.

동일 여행 안에서 상호(공백·대소문자 정규화), 통화, 총액, 결제일이 같은 영수증을 중복 후보로 제안한다. 양쪽 시각이 있으면 같은 시각을 강한 후보로, 시각이 없으면 ‘같은 날 비슷한 결제’로 구분한다. 정규화 방식·비교 범위는 공통 함수와 검증 사례로 확정하며 원문은 보존한다. 후보 일치만으로 자동 거부하지 않는다.

수동 지출은 제목이 상호와 다를 수 있으므로 같은 DAY·통화·총액을 약한 후보로 제시한다. 후보에서 기존 기록 열기, 등록 취소, 별도 결제로 계속을 제공한다. 자동 병합·기존 지출 자동 삭제는 P1이다. 사용자가 기존 수동 지출을 정리하려면 기존 편집 권한과 삭제 확인을 사용한다.

OCR 실패 시 재스캔·다른 사진·직접 입력, 제한 초과 시 나중에 재시도·직접 입력을 제공한다. 네트워크 오류와 권한/입력 오류를 구분한다. 원본 업로드 후 취소된 파일의 보존·정리 책임과 정리 실패 재시도는 개발 전 운영 정책과 대조한다.

통화 미인식은 원본 확인 후 KRW·JPY·USD 중 실제 통화를 선택하도록 한다. 실제로 미지원 통화라면 임의 환산·지원 통화로의 바꿔치기 없이 확정 저장을 제한하고, 원본을 보관한 뒤 지원 범위를 확인하도록 안내한다. 실제 지원 통화를 OCR이 잘못 읽은 경우에는 사용자가 원본을 확인해 정정할 수 있게 하는 안을 권장한다. 이는 미지원 통화 지원 확대가 아니며 확정 전 사용자 확인을 다시 받는다.

### 완료 기준

- 확정 응답 유실 후 재시도해도 일정·영수증·지출이 한 번만 생성된다.
- 유사 후보는 근거를 설명하고 다른 실제 결제를 저장할 수 있게 한다.
- 충돌 시 입력을 보존하고 최신 기록을 확인한 뒤 재시도할 수 있다.
- 확정 실패를 성공으로 표시하거나 원본을 먼저 지우지 않는다.
- 통화 미인식·오인식은 원본 확인 후 수정할 수 있고, 실제 미지원 통화에는 저장 제한과 다음 행동이 명확하다.

## 5. RCP-P0-04 표현·공개·권한·삭제

### 작업 범위

영수증 등록/확인/원본/일정 표시와 공개 투영을 검토한다. ‘영수증으로 기록’, ‘내용 확인’으로 안내하며 OCR 성공을 ‘방문 인증 완료’로 표시하지 않는다. 원본을 보관하지 않거나 사용자가 수정한 데이터에도 진위 보장 배지를 붙이지 않는다.

영수증 기반 신규 장소는 실제 기록의 출처를 구분한다. 기존 계획에 영수증을 연결한 경우에는 계획 자체를 실제 방문으로 변환하지 않는다. 출처를 기존 관계로 표시할지 별도 필드가 필요한지는 개발 계약에서 결정한다.

원본과 메뉴의 여행 멤버 조회 범위는 현행 권한을 따른다. ‘나만 보기’로 오해하게 하지 않으며 외부 공개 사본에는 원본·품목을 자동 포함하지 않는다. 로그·분석 지표에는 이미지·OCR 원문·결제 식별자를 기록하지 않는다.

기록 삭제는 연결 실제 지출을 함께 제거하고 일정은 남긴다. 보관 사진은 영수증 기록을 삭제해 참조를 해제한 뒤 기존 사진 삭제 흐름에서 별도로 삭제할 수 있음을 안내한다. 사진 미보관 선택 시 DB 확정 뒤 파일 삭제가 실패한 경우의 재처리·사용자 안내를 검증한다.

### 완료 기준

- 화면·스크린리더·공유 결과에서 확인 사실보다 강한 인증 표현이 없다.
- 비참여자·공개 링크·뷰어의 읽기/쓰기 범위가 현행 정책과 일치한다.
- 삭제·원본 미보관 처리에서 금액·메뉴·사진의 상태가 설명과 일치한다.

## 6. RCP-P0-05 통합·모바일 인수

### 작업 범위와 검증 데이터

앞선 P0의 자동 검사와 실기기 인수를 통합한다. 합성 데이터는 회귀 검사용으로 분리하고, 실제 영수증은 제공·사용 권한이 있는 자료로 준비한다. 결제 식별자·개인정보를 검수 보고에 노출하지 않는다.

권장 표본은 실제 KRW·JPY 영수증 총 30장 이상이며 통화별 최소 10장을 포함한다. 이는 초기 검수 표본 제안이며 통계적 정확도 보장이 아니다. 정상·긴 영수증·흐림/접힘·복수 세율·할인·일시 누락·메뉴 축약·품목 0개/다수·중복 후보를 표본에 태깅한다. USD도 최소 정상·소수점·팁/합계 차이 회귀 사례를 포함하되 검증 수준을 별도로 보고한다.

### 완료 기준

- M01~M06, D01~D06, F01~F08, P01~P05 및 아래 Q01~Q05의 필수 시나리오를 모두 통과한다.
- [모바일 규격의 A01~A10](영수증_모바일접근성_검토안.md) 통과 증거가 있다. Android는 실제 기기를 필수로 하고 iOS를 출시 대상으로 포함하면 iOS 실기기 검수도 필수다. 미실행 플랫폼은 출시 검증 완료로 표시하지 않는다.
- 데이터 유실·중복 생성·권한 우회 결함이 없고, 인식 실패도 사용자가 수동으로 복구할 수 있다. OCR 정확도 수치는 표본·분모·필드별 결과와 함께 별도로 보고한다.
- 자동 검사 성공만으로 시각 검수나 WCAG 전체 적합성을 선언하지 않는다.

## 7. 검수 기록과 인계 형식

모든 사례의 초기 상태는 **미실행**이다. 기록 열은 `사례 ID / 빌드·커밋 / 환경·기기·OS / 표본 ID / 절차 / 기대 / 실제 / 통과·실패·미실행 / 증거 / 결함·재검토 횟수`로 한다. 로컬 증거는 `outputs/` 아래에 두고 문서에는 결과 요약을 남긴다. 이미지·영상에 개인정보가 있으면 공유용 증거를 별도로 비식별 처리한다.

완료 보고에는 변경 파일·계약, 검사 결과, 실제 화면 대조, 플랫폼별 미검증 범위, 남은 정책 결정을 포함한다. 현재 문서는 테스트 실행 결과가 아니다. 재검토는 AGENTS.md의 최초 검토 이후 최대 2회 규칙을 따른다.
