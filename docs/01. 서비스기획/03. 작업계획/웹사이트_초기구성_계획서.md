# TripPoint 앱 연동 웹사이트 초기 구성 계획서

웹은 넓은 화면에서 여행 계획을 편집하고 다른 여행자의 공개 일정을 내 여행에 활용하는 공간으로 구성한다. 앱에서는 같은 계정과 같은 여행을 열어 현장에서 확인하고 영수증으로 실제 방문·구매 내역을 남긴다. 웹에서 모아 올린 영수증도 같은 기록에 저장한다.

사용자가 정한 필수 조건은 **앱·웹의 핵심 DB 공유**, **웹 게스트 계정 금지**, **장소명·실제 주소·지도 URL로 장소를 찾아 일정에 추가**, **공개한 일정을 앱과 웹의 커뮤니티에 함께 노출**하는 것이다. 아래의 단계 구분·페이지 배치·운영 수치는 초기 제안이며 구현 완료를 뜻하지 않는다.

첫 정식 1.0.0의 대상은 사용자가 선택한 **Android 앱·WEB**이며 iOS 앱은 후속이다. 최종 범위와 단계별 통과 조건은 [정식 출시 계획](앱웹_정식출시_계획서.md)을 단일 기준으로 사용한다.

요청 명칭인 TripPoint를 사용한다. 저장소의 브랜드명은 TripPrint이며 패키지·인증·배포 식별자에도 기존 이름이 남아 있다. 이번 계획만으로 로고·하루 캐릭터·패키지·도메인을 변경하지 않는다. 실제 웹 공개 전 표시 이름과 인증 동의 화면의 명칭을 함께 확정한다.

사용자의 후속 지시로 소개 랜딩 `/`과 서비스 홈 `/home`을 분리한다. 이번 구현 범위는 [랜딩](<../../02. 디자인/01. 화면설계/웹랜딩_화면규격.md>)·[웹 공통 모듈](<../../03. 개발/00. 구조설계/웹공통모듈_구조.md>)까지다. 홈은 화면·기능 설계 단계이며 계정·개인 여행 연동은 후속이다. 아래 서비스 기능은 전체 목표로 읽는다.

## 1. 서비스의 목적과 범위

### 해결할 사용자 문제

여행 준비 중에는 지도와 여러 탭에서 찾은 장소를 작은 화면에 옮기기 어렵다. 일차별 순서를 바꾸면서 동선을 비교하기도 번거롭다. 여행이 끝난 뒤에는 영수증이 쌓이고 방문 기록과 지출이 서로 떨어져 남는다.

웹에서는 검색·지도·일정을 함께 보며 계획을 정리한다. 앱에서는 같은 계획을 확인하고 실제 기록을 보탠다. 다른 여행자가 공개한 일정은 장소와 일차 구조를 가져와 내 일정으로 수정한다. 개인 여행이 커뮤니티에 자동 공개되지는 않는다.

| 이용 시점 | 웹의 역할                               | 앱의 역할                                | 같은 자료로 이어지는 결과      |
| --------- | --------------------------------------- | ---------------------------------------- | ------------------------------ |
| 여행 전   | 장소 비교, URL 붙여넣기, 일차·순서 편집 | 이동 중 계획 확인·간단 수정              | 같은 여행의 최신 계획          |
| 여행 중   | 필요할 때 일정 수정·영수증 파일 등록    | 일정 확인, 길찾기 열기, 영수증 촬영·등록 | 계획과 구분한 실제 방문·지출   |
| 여행 후   | 영수증 정리, 품목 확인, 공개 내용 편집  | 기록 확인·추가                           | 같은 방문·영수증·비용과 공개본 |

## 3. 홈페이지 컨셉

홈의 목적은 사용자가 지금 작업할 여행을 열거나 새 여행을 시작하게 하는 것이다. 첫 화면은 실제 일정 편집 화면을 이해할 수 있는 정적인 소개와 명확한 행동으로 구성한다. 대형 영상·복잡한 스크롤 효과·예약 상품 광고는 초기 범위에서 제외한다.

홈의 영역별 문구·버튼·이동·빈 상태·인증 복귀는 [웹 홈페이지 화면 계획](<../../02. 디자인/01. 화면설계/웹홈페이지_화면계획.md>)에서 구체화한다. 웹 홈 본문에만 적용하며 기존 앱 홈과 공통 헤더·GNB는 변경하지 않는다.

### 로그인 전 홈

공통 브랜드 헤더 아래에 **“넓은 화면에서 여행을 계획하세요”**라는 안내를 둔다. 주 행동은 **“여행 계획 만들기”**, 보조 행동은 **“공개 일정 둘러보기”**다. 계획 만들기는 Google 로그인 후 생성 입력 화면으로 연결하고, 기존 회원의 **“로그인”** 링크는 로그인 후 회원 홈으로 연결한다. 본문에서 장소 찾기 → 일차에 추가 → 앱에서 확인하는 과정을 짧게 설명한다.

공개 일정 영역에는 실제 공개 게시물만 표시한다. 게시물이 없으면 일정 둘러보기의 빈 상태와 계획 시작 방법을 안내한다. 예시 여행·임의 이용자 수·가짜 후기를 실제 자료처럼 넣지 않는다. 푸터에는 이용약관·개인정보처리방침·운영정책·문의·앱 안내를 둔다.

### 로그인 후 홈

작성 중 서버 초안을 우선하고, 초안이 없으면 진행 중·예정·날짜 미정·완료 여행 순서로 이어갈 작업을 고른다. 확인할 수 없는 최근 편집 시각을 표시하지 않는다. 초안은 **“이어서 만들기”**, 편집 가능한 저장 여행은 **“이어서 계획하기”**, 열람 전용은 **“여행 보기”**로 구분한다. 초안과 여행이 모두 없으면 **“새 여행 만들기”**가 주 행동이 된다. 이어서 내 여행, 빠른 작업, 공개 일정 탐색을 배치한다. 영수증 정리는 여행을 선택한 뒤 해당 여행의 사진·영수증 화면으로 연결한다.

대표 후보에서는 보관 여행을 제외하고 날짜 미정과 서버의 명시적 완료 상태를 구분한다. 저장 여행은 있지만 대표 후보가 없으면 첫 여행 안내 대신 내 여행 전체 보기로 연결한다. 세부 제외·정렬 기준은 홈페이지 화면 계획을 따른다.

홈의 공개 일정은 사용자의 여행과 구분한다. 추천 근거가 없는 개인화 문구를 사용하지 않는다. 초기에는 최근 공개 일정과 사용자가 고른 지역 조건을 사용하며 빈 결과·조회 실패를 구분한다.

## 4. 앱과 계정 연동

### 같은 계정을 확인하는 방법

앱과 웹은 같은 인증 서버와 내부 회원 ID를 사용한다. Google 인증 결과는 서버가 검증하고, 같은 Google 계정 식별자 `sub`에 연결된 기존 회원을 찾는다. 이메일·이름·프로필 사진이 같다는 이유로 계정을 자동 합치지 않는다. 서로 다른 플랫폼의 OAuth 클라이언트를 허용할 때는 각각의 대상·복귀 주소를 검증한다. [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)

로그인 성공 뒤에는 추가 가입 폼 없이 원래 작업으로 복귀한다. 닉네임·사진 변경은 MY에서 선택적으로 제공하고 현행 중복·30일 제한을 그대로 따른다. Google 로그인을 했다고 개인 Google 지도 저장 목록이나 위치 이력에 접근할 수 있는 것은 아니다. 이번 범위에서는 관련 권한을 요청하지 않는다.

웹에서 새 계정을 따로 만드는 절차나 앱과 연결하는 별도 가입 절차는 두지 않는다. 앱 사용자가 다른 Google 계정으로 로그인했다면 다른 회원의 자료가 보이는 것이 정상이다. 본인 계정 화면에서 사용 중인 계정을 확인하고 다시 로그인할 수 있게 한다.

### 웹 게스트 금지의 의미

로그인하지 않은 방문자는 소개·공개 일정·정책을 읽는 방문자다. 서버 익명 회원, 게스트 UUID, 비회원 여행·영수증·초안을 생성하지 않는다. 공개 일정의 **“내 여행으로 담기”**, **“계획 만들기”**, 초대 참여를 누르면 로그인 후 해당 작업으로 복귀한다. 공개 자료 열람까지 로그인을 요구하는 방식은 별도 선택 사항이다.

앱의 기존 기기 게스트 기록은 웹에서 자동으로 보이지 않는다. 앱에서 로그인하고 가져올 여행을 명시적으로 선택해 서버 저장을 마친 뒤 웹에서 조회한다. 웹 로그인만으로 앱의 기기 자료를 읽거나 자동 전송하지 않는다. 웹의 인증 실패·로그아웃·만료를 게스트 시작으로 바꾸지 않는다.

Android 게스트의 서버 저장·재조회는 기존 확정 필수 과제로 유지한다. 현재 기기 전용 정책과 목표 서버 자격·자료 수명·회원 전환의 정합은 정식 출시 계획의 0.1에서 맞추고 0.3에서 검증한다. 웹 게스트 금지와 별개이며, 현행 기능이 이미 서버에 저장된다는 뜻은 아니다.

### 로그인 유지와 종료

브라우저 로그인은 JavaScript로 읽을 수 없는 `HttpOnly`, HTTPS용 `Secure` 쿠키를 사용하는 방향을 권장한다. 현재 웹의 localStorage Bearer 방식에서 바꾸려면 인증뿐 아니라 업무 API의 세션 판정도 함께 연결해야 한다. 같은 웹 주소 아래 API를 연결하는 방식을 우선 검토한다. 별도 중계 서버를 두면 쿠키 세션을 확인하고 서버에 보관한 자격으로 인증된 업무 요청을 전달한다. 여행 권한·저장 규칙은 공통 API에서 계속 판정하고, 중계 서버에 별도 회원 DB나 여행 업무 규칙을 만들지 않는다. [OWASP 브라우저 저장 지침](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html)

개발 인계에는 쿠키 범위·SameSite 정책·인증 복귀·요청 위조 방지·허용 출처·리다이렉트 제한을 포함한다. 앱 세션과 웹 세션은 각각 발급하며 토큰을 URL·QR에 넣지 않는다. 앱에서 열기 링크나 QR에는 여행 식별자와 허용된 이동 경로만 담고, 수신한 앱도 로그인·접근 권한을 다시 확인한다. 앱이 없으면 웹 열람이나 앱 안내로 연결한다. 설치 여부와 상관없이 비공개 여행의 접근 검사를 생략하지 않는다.

웹 로그아웃은 해당 브라우저 세션과 비공개 캐시를 정리한다. 앱의 다른 세션까지 끝내는 **“모든 기기에서 로그아웃”**은 별도 구현 전 표시하지 않는다. 계정 삭제는 앱·웹 공통 계정 전체에 영향을 주며, 사전 조회·소유권 이전·최근 인증·명시 확인을 거친다. 삭제 접수와 실제 정리 완료를 구분한다.

## 5. 같은 DB와 동기화 원칙

앱·웹은 **동일 환경의 공통 API → 동일 D1 업무 DB·비공개 R2**를 사용한다. 웹에서 DB에 직접 연결하지 않는다. 개발·검수·운영 환경은 각각 격리하고 한 검수 환경 안에서 앱·웹의 같은 여행을 대조한다.

| 자료             | 공통 기준                       | 허용하는 별도 표현                 |
| ---------------- | ------------------------------- | ---------------------------------- |
| 계정·권한        | 같은 회원 ID, 여행 참여·역할    | 앱과 웹의 세션                     |
| 여행·일차·장소   | 같은 여행 ID·일정 ID·서버 버전  | 화면 폭에 따른 배치                |
| 영수증·품목·비용 | 같은 확정 기록과 연결 관계      | 앱 촬영·웹 파일 업로드 방식        |
| 공개 일정        | 같은 게시물 ID와 공개 버전      | 앱 카드·웹 목록 표현               |
| 초안·임시 표시   | 회원 소유 서버 초안이 저장 기준 | 저장 전 화면 입력·검색어·열린 패널 |

브라우저에만 있는 입력은 **저장 전**이다. 서버가 확인한 뒤에만 **“저장됨”**을 표시한다. 응답을 받지 못했으면 같은 요청 키로 결과를 조회·재시도하고 새 여행이나 비용을 중복 생성하지 않는다. 기존 `Idempotency-Key`와 `If-Match` 계약을 재사용한다.

동시에 고친 내용은 조용히 덮어쓰지 않는다. 버전 충돌 시 최신 기록을 다시 읽고 내 입력과 비교해 다시 적용하도록 한다. 웹 첫 출시에서는 서버 변경을 감지해 **“다른 곳에서 수정한 내용이 있어요”**를 보여주는 수준을 목표로 한다. 화면 복귀·초점 재진입·내 저장 직후에는 재조회하고, 편집 중에는 최대 15초 간격의 가벼운 버전 확인을 후보로 둔다. 실시간 공동 커서·자동 병합은 후속 범위다.

오프라인에서는 이미 읽은 화면과 저장 전 입력 상태를 구분한다. 웹 첫 출시에는 오프라인 새 저장 성공이나 무제한 자동 업로드를 약속하지 않는다. 전송 중·실패 상태에서 새로고침·창 닫기를 시도하면 가능한 범위에서 이탈을 안내한다. 브라우저 종료 안내만으로 입력 보존을 보장하지 않으며, 정상 인증 상태의 서버 초안 저장을 사용한다. 계정 전환 후 이전 응답·초안·사진 미리보기가 새 계정에 섞이지 않아야 한다.

## 6. 계획 만들기 페이지

### 여행 생성

홈 또는 내 여행에서 새 여행을 시작한다. 목적지 선택 → 기간 또는 날짜 미정 선택 → 세부 일정 만들기 순서와 기존 초안 계약을 재사용한다. 현재 지원하는 날짜·일수 상한을 유지하고 웹만 다른 범위를 허용하지 않는다. 다른 여행자의 공개본을 가져올 때는 현행 계약에 맞춰 내 출발일을 선택한다. 가져오기에도 날짜 미정을 제공하려면 시작일을 필수로 받는 공통 계약부터 확장해야 하므로 첫 출시의 기본 범위에서는 제외한다.

현재 앱은 일정·가계부를 중심으로 탐색한다. 웹도 같은 구분을 유지한다. 지도·사진·영수증·준비물·동행·공개 설정은 기존 여행 더보기에서 접근한다. 웹 본문에는 계획 작업을 돕는 장소 검색과 지도를 함께 배치하되, 상단·하단 공통 탐색을 새 메뉴로 바꾸지 않는다.

### 넓은 화면의 편집 본문

| 영역        | 사용자가 하는 일                                        | 화면에 보이는 결과              |
| ----------- | ------------------------------------------------------- | ------------------------------- |
| 장소 찾기   | 장소명·주소 검색 또는 지도 URL 붙여넣기                 | 출처·상호·주소가 있는 후보 목록 |
| 일차별 계획 | DAY 선택, 장소 추가, 위·아래·다른 DAY로 이동, 메모 편집 | 방문 순서가 있는 일정           |
| 지도        | 후보·일정 장소 위치 확인, 목록과 핀 선택                | 선택한 DAY의 번호 핀과 위치     |

넓은 화면에서는 일정과 지도를 함께 보여주고 검색은 접을 수 있는 작업 패널로 연다. 검색 패널까지 펼쳐 세 영역을 보여줄 때도 지도나 일정 글자를 임의로 줄이지 않는다. 기존 최대 폭에서 세 영역의 가독성이 부족하면 검색을 겹침 패널로 전환한다. 좁은 화면에서는 목록·지도를 전환하고 검색·상세를 별도 목적 화면으로 연다.

일정은 **일차·순서·장소·메모**를 기본으로 편집한다. 방문 시각·체류시간을 필수로 요구하거나 자동 경로 최적화로 일정을 다시 배치하지 않는다. 영수증의 결제 시각은 실제 기록의 정보이며 계획 시간 입력과 구분한다. 날짜 축소로 사라질 일차에 장소가 있으면 이동·유지 방법을 먼저 확인하고 삭제하지 않는다.

### 장소 검색과 지도 URL 처리

사용자는 입력 후 후보의 상호·도로명/현지 주소·지도 위치를 확인하고 DAY를 골라 추가한다. 같은 이름의 지점은 주소로 구분한다. 주소가 없는 장소나 좌표가 확인되지 않은 장소도 사용자가 직접 기록할 수 있지만 지도 위치를 확인한 것처럼 핀을 만들지 않는다. 재방문은 허용하되 같은 DAY의 같은 장소를 추가할 때 기존 일정을 안내한다.

| 입력                           | 첫 출시 지원안                                                       | 찾지 못했을 때                       |
| ------------------------------ | -------------------------------------------------------------------- | ------------------------------------ |
| 장소명                         | 여행 지역을 함께 사용해 후보 검색                                    | 지역·지점명 수정 또는 직접 입력      |
| 실제 주소                      | 도로명·지번·현지 주소 검색과 위치 확인                               | 상세 주소 수정, 위치 미지정 기록     |
| Google 정식 지도 URL           | 검증한 형식의 장소 식별자·검색어를 읽고 공식 조회로 후보 확인        | 장소명·주소를 붙여넣어 다시 검색     |
| Google 짧은 공유 URL           | 허용한 Google 호스트로 끝나는 안전한 이동만 제한적으로 확인          | 원래 링크 열기, 정식 URL·장소명 입력 |
| Naver 지도·장소 URL            | 검증한 형식에서 검색어·식별 힌트를 얻고 허용된 검색 경로로 후보 확인 | 링크를 열어 상호·주소를 복사해 검색  |
| Naver 단축 URL                 | 허용 도메인과 이동 경로가 확인된 경우만 처리                         | 정식 URL 또는 주소 입력              |
| 지도 목록·경로·블로그·기타 URL | 여러 장소 자동 가져오기는 후속                                       | 단일 장소 링크나 실제 주소 입력      |

Google의 공식 Maps URLs는 지도를 여는 규격이다. 모든 공유 URL을 역으로 읽어 장소 정보를 가져오는 API를 보장하지 않는다. 지원하는 URL 예시와 지원하지 않는 예시는 구현 때 합성·공개 장소 자료로 고정해 회귀 검사한다. [Google Maps URLs](https://developers.google.com/maps/documentation/urls/get-started)

Naver 지역 검색은 업체·기관 찾기, Naver Cloud Geocoding은 주소 찾기 서비스다. 이를 같은 기능으로 취급하지 않는다. Naver 식별자를 Google Place ID로 그대로 변환하지 않는다. 공급자 간 재검색 결과도 사용자가 같은 지점인지 확인해야 한다. Naver 검색 결과·좌표를 Google 지도 위에 표시하거나 영구 보관할 수 있는지는 별도 이용 조건 확인이 필요하며, 확인 전에는 원문 링크·주소 입력의 복구 경로만 제공한다. [Naver 지역 검색](https://developers.naver.com/docs/serviceapi/search/local/local.md), [Naver Cloud 주소 검색](https://api.ncloud-docs.com/docs/ai-naver-mapsgeocoding-geocode)

URL 자동 해석은 부가 편의 기능이다. 실패하면 입력을 보존하고 주소 검색으로 이어간다. 임의 사이트 HTML에서 장소·후기·사진을 긁어오지 않는다. 서버가 링크를 따라갈 때는 HTTPS·허용 호스트·이동 횟수·시간·응답 크기를 제한하고 매 이동마다 목적지를 재검사한다. 내부 네트워크 주소로 연결하거나 개인정보가 든 URL을 로그에 남기지 않는다.

## 7. 영수증 처리

### 목적과 기본 흐름

영수증은 실제 방문에 구매한 음식·상품 품목과 지출을 연결하는 기록이다. 앱 촬영과 웹 업로드는 같은 처리 경로를 사용한다. 여행 중 즉시 등록과 여행 후 모아 정리를 모두 지원하되, 첫 출시에서는 한 장씩 확인·저장하는 방식을 완성한다.

**여행 선택 → 사진 등록 → 상호·결제 시각·통화·총액·품목 확인 → 기존 방문에 연결 또는 새 실제 방문 추가 → 비용 반영 방법 확인 → 저장 → 재조회** 순서다. 웹에서는 원본 미리보기와 확인 폼을 나란히 보여주고 좁은 화면에서는 전환해서 본다. 인식 결과는 확인 전 초안이며 자동으로 확정하지 않는다.

### 확인할 정보

| 정보             | 확인 기준                                       | 예외 처리                                            |
| ---------------- | ----------------------------------------------- | ---------------------------------------------------- |
| 상호·주소        | 실제 방문 지점을 사용자가 확인                  | 읽지 못하면 직접 입력·장소 검색                      |
| 결제일·결제 시각 | 영수증 현지 시각, 시간대, 업로드일 구분         | 시각·시간대 미상은 미상으로 유지                     |
| 여행 연결        | 결제일에 해당하는 DAY를 제안                    | 기간 밖 결제·숙박 선결제는 강제 배정하지 않음        |
| 통화·총액        | 소수 자릿수·통화별 금액 형식 준수               | 임의 환율로 합치지 않고 통화별 합계                  |
| 음식·상품 품목   | 이름·수량·단가·금액, 읽은 값과 사용자 수정 구분 | 모르는 수량·단가는 비움. 합계로 품목을 창작하지 않음 |
| 방문 연결        | 기존 실제 방문·계획 장소를 참고해 선택          | 계획 원본을 자동 덮어쓰지 않음                       |
| 비용 처리        | 기존 비용과 연결, 새 지출로 추가, 장소만 기록   | 한 결제를 두 번 합산하지 않음                        |

같은 상점의 여러 결제가 같은 방문에 연결될 수 있다. 반대로 같은 상점을 다른 날 방문했다면 별도 방문으로 남길 수 있다. 영수증 하나를 다시 올리거나 확정 요청을 재시도해도 비용을 두 번 만들지 않는다. 이미지 지문과 상호·결제일·통화·총액은 중복 **후보**를 찾는 수단이며, 일치만으로 다른 결제를 삭제하지 않는다.

수동 지출을 먼저 적은 뒤 영수증을 등록했다면 기존 지출에 연결할지 확인한다. 세금·봉사료·할인 때문에 품목 합계와 결제 총액이 다를 수 있으므로 차이를 안내하고 사용자가 확인한다. 취소·환불은 원 결제와 연결하고 기존 지출을 어떻게 정정할지 명시한다. 부분 환불·분할 결제는 상세 계약 검증 전 자동 정산하지 않는다.

### 계획과 실제 기록의 분리

계획된 장소가 있으면 그 계획에 실제 방문 기록을 연결한다. 계획에 없던 방문은 실제 기록으로 추가한다. 기존 장소·순서·계획 메모는 유지한다. 현재 저장 모델과 명령으로 두 상태를 독립적으로 표현할 수 있는지 먼저 검증하고, 부족하면 공통 도메인·API·앱 읽기 계약을 함께 확장한다. 웹 화면의 배지 하나만으로 분리했다고 판단하지 않는다.

### 웹 연결 전 보완해야 하는 현행 제약

현재 확정 명령은 결제일과 선택 DAY 날짜의 일치·여행 기간 안의 날짜를 요구한다. 확인 화면에서 DAY를 바꾸면 결제일도 바뀌는 경로가 있다. 실제 결제일을 보존한 채 방문 일차를 선택하는 계약을 먼저 정리해야 한다. 결제 시각·방문 시각·선결제의 의미가 다른 경우를 화면 값 변경으로 맞추지 않는다.

현재 ‘장소만 남기기’는 금액을 0으로 보내는 반면 확정 명령은 양수를 요구해 충돌한다. 비용을 생성하지 않는 명시적 선택과 저장 계약을 보완한 뒤 웹에 연결한다. 같은 미디어의 재확정 방지는 존재하지만, 다른 파일로 다시 올린 같은 영수증·기존 수동 비용의 중복까지 해결한 것으로 간주하지 않는다. [핵심 사용자 사이클 검수](<../../03. 개발/04. 검증/핵심_사용자사이클_검수.md>)

첫 출시의 저장 통화는 현행 KRW·JPY·USD를 기본으로 하고 품목 최대 50개를 유지한다. 다른 통화·품목 상한 초과는 원문을 보존하고 지원 범위를 안내한다. EUR 등 추가 통화는 도메인·검증·합계·앱 표시까지 확장한 뒤 지원한다. 글자를 읽은 통화와 실제로 저장 가능한 통화를 혼동하지 않는다.

### 실패 복구

인식 실패는 다시 촬영·다른 사진 선택·직접 입력으로 복구한다. 일부만 읽혔으면 누락 항목을 표시한다. 업로드 성공·인식 성공·확정 저장 성공을 각각 구분하고, 인식 대기 중 화면을 벗어나도 확정 기록처럼 표시하지 않는다. 응답 유실 때 같은 작업을 확인해 재시도하며, 확정 전 취소한 임시 파일은 정리 대상으로 남긴다.

### 영수증의 공개와 개인정보

원본 영수증은 커뮤니티에 공개하지 않는다. 여행 안의 원본·품목 접근 권한은 현행 멤버 권한을 먼저 따른다. 업로더 전용 보관을 약속하려면 개인/공동 기록의 별도 데이터 계약이 필요하므로 이번 계획에서 있다고 가정하지 않는다. 공동 여행에서 누구에게 보이는지 업로드 전에 쉬운 말로 안내한다.

공개용 사진에는 영수증을 선택하지 못하게 하고, 공개 응답·미리보기·미디어 주소에도 원본과 품목을 넣지 않는다. 카드 번호·전화번호·주소 등은 로그와 측정 이벤트로 복제하지 않는다. 이미지 형식·실제 파일 내용·용량·메타데이터를 검사하고, 원본 보관 여부와 삭제 범위는 현행 정책과 함께 표시한다.

**사진에서 글자를 읽음**, **사용자가 내용을 확인함**, **구매 증빙을 확인함**, **본인 방문·원본 진위를 검증함**은 서로 다르다. 첫 출시에서는 **“영수증 기록”**, **“내용 확인 완료”**처럼 확인 가능한 상태만 사용한다. 영수증만으로 ‘실제 방문 인증’, ‘진짜 후기’, ‘위조 없음’을 보장하지 않는다.

여러 장 끌어넣기·일괄 검수는 후속 단계다. 도입할 때 파일별 진행·실패·재시도를 보여주고 성공한 파일만 남긴다. 일부 실패를 전체 성공으로 처리하지 않는다.

## 8. 커뮤니티 구성

### 여행 일정 중심의 커뮤니티

초기 커뮤니티의 게시 단위는 사용자가 고른 여행 일정이다. 일반 자유게시판을 먼저 만들지 않는다. 공개본에는 지역·일수·일차별 장소·공유용 설명·선택한 사진·선택한 통화별 비용 요약을 담는다. **여행 계획**과 **여행 기록**은 구분하며, 계획 게시물을 다녀온 기록으로 표시하지 않는다.

현행의 **여행당 공개본 1개**를 유지한다. 계획과 기록을 동시에 별도 게시물로 만들지 않는다. 계획 공개에는 일정이 필요하고 기록 공개에는 완료된 여행이 필요하다. 계획에서 기록으로 바꿀 때도 같은 공개본을 미리 확인해 갱신한다. 영수증의 세부 음식·상품 품목 공개는 현행 공개 범위에 없으므로 첫 출시에서 제외한다.

공개 피드에서 지역·여행 일수·계획/기록·검색어로 찾고 상세에서 일차별 장소를 읽는다. 초기 정렬은 최신 공개순을 기본으로 한다. 인기순·개인화 추천은 집계 기준과 악용 방지가 마련된 뒤 추가한다. 영수증 개수를 검증 점수나 방문 신뢰도 순위로 쓰지 않는다.

### 공개와 앱 노출

여행 소유자가 여행 더보기에서 공개를 선택한다. 공개할 일차·장소·설명·사진·비용 요약을 고르고 **로그아웃 방문자에게 보일 화면**을 미리 확인한 뒤 게시한다. 공동 여행 편집자가 소유자 동의 없이 전체 여행을 공개할 수 없게 한다. 동행자의 사진·정보는 공개 권한을 확인하며, 이름·연락처·동행 목록은 기본 제외한다.

공개본은 같은 서비스의 `CommunityPost`로 저장한다. 앱과 웹은 같은 게시물 ID와 같은 공개 데이터를 조회한다. 별도 웹 게시판 DB를 만든 뒤 앱에 다시 수입하지 않는다. 원본 여행 수정은 공개본에 자동으로 반영하지 않는다. **“공개 내용 업데이트”**로 다시 확인한 버전만 반영한다.

비용 공개의 기본값은 **공개하지 않음**을 권장한다. 현행 비용 요약은 선택한 일정만의 합계가 아니라 **여행 전체 실제 지출의 통화별 합계**다. 공개를 선택하면 ‘여행 전체 지출 공개’라고 표시하고 비공개 일정의 비용도 합계에 포함된다고 미리 안내한다. 선택한 일정의 비용만 공개하는 방식은 공통 집계·공개 계약을 확장한 뒤 제공한다. 일부 장소를 골랐다는 이유로 비용도 그 장소만 집계된다고 설명하지 않는다.

공개 저장 성공 후 앱 피드를 새로 조회하면 같은 게시물이 보여야 한다. 공개 철회·운영 숨김은 앱·웹의 상세·목록·사진 배포에도 함께 적용한다. 캐시된 목록이 잠시 남더라도 상세·미디어 접근 시 공개 상태를 확인해 차단한다. 공개 검색 노출의 지연과 외부에서 이미 복사한 내용의 회수 한계는 숨기지 않는다.

### 내 여행으로 담기

로그인 → 내 출발일 선택 → 가져올 일차 확인 → 새 비공개 여행 생성 → 편집 순서로 진행한다. 장소·공유용 설명·일차 구조만 가져오며 영수증·실제 지출·원본 사진·개인 메모·동행자·방문 인증 상태는 복제하지 않는다. 같은 API를 사용하는 앱의 가져오기도 같은 제외 규칙을 따라야 한다. 날짜 미정 가져오기는 공통 계약 확장 후 검토한다.

가져온 여행은 새 소유자의 독립 계획이다. 원작자가 수정해도 자동으로 덮어쓰지 않는다. 원 게시물 출처는 보관하되 철회·탈퇴 시 표시를 줄일 범위를 정한다. 이미 허용된 계획 복사본과 공개 게시물의 철회는 다르며, 공개 사진을 복사본에 배포하는 권한은 부여하지 않는다.

### 운영에 필요한 기능

신고·차단은 공개와 함께 준비한다. 신고 접수·운영 검토·숨김·복구·이의 문의를 구분하고 운영 변경 이력을 남긴다. 운영자는 공개본과 신고 내용을 필요한 범위에서 확인하며 비공개 영수증을 기본 열람하지 않는다. 무단 사진·광고·사칭·개인정보 노출을 처리할 기준과 담당자를 공개 전에 정한다.

북마크·좋아요·댓글·작성자 구독은 후속이다. 특히 댓글은 신고·차단·삭제·운영 처리까지 갖출 때 추가한다. 쪽지·실시간 채팅·결제·광고 보상·인증 배지 판매는 초기 범위에서 제외한다. 댓글을 나중에 추가하더라도 일정 기반 커뮤니티라는 게시 구조는 유지한다.

## 9. Google 지도 사용 방식

### 지도 표시와 길찾기의 분리

웹 편집기는 실제 Google 지도에서 선택한 DAY의 번호 핀과 선택 장소를 표시하는 것을 목표로 한다. 목록 선택과 지도 선택은 서로 연결한다. 핀이 없는 일정은 위치 미지정 상태로 목록에 남긴다. 지도 로딩에 실패해도 일정 열람·편집·주소 복사는 계속 가능해야 한다.

번호 핀을 잇는 단순 선은 **방문 순서**를 뜻한다. 실제 도로·교통편 경로·소요시간으로 표시하지 않는다. 초기 길찾기는 사용자가 선택한 구간을 외부 지도에서 여는 방식으로 시작한다. Google Maps URLs는 API 키 없이 지도를 열 수 있지만, 웹 내부 지도와 장소 검색은 별도 API·과금·약관 검토 대상이다. [Google Maps URLs](https://developers.google.com/maps/documentation/urls/get-started)

한국·일본·동남아·유럽 등 초기 대상 지역의 주소 검색·지점 구분·지도 위치·외부 길찾기를 실제 표본으로 확인한다. 국가나 이동 수단별 결과를 동일하게 보장하지 않는다. 국내 대체 지도는 사용자 입력과 공급자 이용 조건을 확인한 뒤 원문 링크로 여는 경로부터 제공한다. 웹 내부의 지도 공급자 전환은 후속 검토다.

### 장소 데이터 보관과 출처

Google Place ID와 자체 일정 ID를 구분한다. 공급자가 반환한 이름·주소·좌표·사진·후기를 사용자 기록이라는 이유로 무제한 보관하거나 커뮤니티·가져오기에서 재배포하지 않는다. 사용자가 직접 적은 메모와 외부 조회 자료는 출처를 구분하되, 검색 결과를 확인·수정했다고 공급자 제한이 사라지는 것으로 해석하지 않는다.

현행 공개본에는 위치 좌표가 없으므로 개인 여행 지도와 공개 일정 지도를 같은 계약으로 가정하지 않는다. 첫 출시의 공개 상세는 장소 목록·외부 지도 열기를 기본으로 하고, 내부 지도가 필요하면 공개 허용 위치·출처·보관 조건의 계약을 먼저 확장한다.

Google Places에는 저장 예외와 표시·출처 조건이 있다. Place ID는 저장 제한의 예외지만 다른 정보는 해당 서비스 조건을 따라야 한다. 지도 밖의 결과 목록에도 필요한 출처 표시를 적용한다. 지도·상세·공개본·앱·오프라인 저장·복사 기능을 포함한 필드별 보관/갱신/삭제 기준을 개발 전에 정한다. 현행 앱이 저장하는 자료도 같은 기준으로 점검한다. [Google Places 정책](https://developers.google.com/maps/documentation/places/web-service/policies)

### 사용량과 비용

장소 검색은 입력마다 호출하지 않고 검색 확정·지연 실행·이전 요청 취소로 중복을 줄인다. 지도는 사용하는 화면에서만 불러온다. 상세 조회는 필요한 필드만 요청한다. 지도를 다시 그리는 일과 새 지도를 불러오는 일을 구분하고, 모든 구간의 경로를 자동으로 재계산하지 않는다.

브라우저 지도 키는 웹 출처와 허용 API를 제한한다. 서버 조회용 키와 Naver 비밀 키는 서버에만 둔다. Google 로그인 자격과 지도 서비스 자격도 구분한다. [Google 지도 보안 지침](https://developers.google.com/maps/api-security-best-practices)

월 비용은 **지도 로드·장소 검색·상세 조회·주소 조회·경로 계산의 각 과금 단위 × 해당 구간 단가**, 영수증 인식 건수, 파일 보관·전송 비용을 합산해 추정한다. 실제 가격표·무료 범위·통화·세금·SKU를 예산 확정 때 다시 확인한다. 과거의 정액 무료 크레딧을 전제로 계산하지 않는다.

예산 알림만으로 지출이 멈추는 것은 아니다. API별 지원 쿼터·회원별 제한·서비스 차단 기준을 함께 정한다. 제안 알림 단계는 예산의 50%·80%·100%이며 최종 월 한도와 담당자는 출시 전 확정한다. 제한에 도달하면 검색 재시도 안내·직접 입력·외부 지도 열기를 제공하고 기존 여행 저장을 불필요하게 막지 않는다. [Google 비용 관리](https://developers.google.com/maps/billing-and-pricing/manage-costs)

여행에 참여하지 않은 로그인 회원은 여행 ID를 알아도 비공개 자료에 접근하지 못한다. 원본 파일·영수증·품목의 조회는 서버가 여행 권한을 확인한다. 초대 링크를 갖고 있다는 사실을 공개 열람 권한으로 바꾸지 않는다. 만료·철회·이미 사용한 링크는 현재 상태를 안내하고 소유자에게 새 초대를 요청하는 방법을 보여준다.

비공개 페이지에는 공개 검색용 메타데이터를 만들지 않고 공유 캐시를 사용하지 않는다. 공개 페이지의 대표 이미지도 공개 허용된 사진만 사용한다. 비공개 R2 주소를 페이지 소스·미리보기·오류 보고에 넣지 않는다. 관리자 경로의 숨김만으로 권한을 보호했다고 판단하지 않는다.

## 12. 화면과 디자인의 적용 범위

참조 기준은 [디자인 시스템](<../../02. 디자인/00. 공통규격/디자인시스템.md>), [토큰](<../../02. 디자인/00. 공통규격/design-tokens.json>), [헤더·GNB](<../../02. 디자인/00. 공통규격/헤더GNB_규격.md>), [홈](<../../02. 디자인/01. 화면설계/홈온보딩_화면규격.md>), [로그인](<../../02. 디자인/01. 화면설계/로그인_프로필생성_규격.md>), [여행 일정](<../../02. 디자인/01. 화면설계/여행일정_화면규격.md>), [공개 일정](<../../02. 디자인/01. 화면설계/공개여행계획_화면규격.md>), [커뮤니티 목록](<../../02. 디자인/01. 화면설계/발자국목록_화면규격.md>)이다.

기존 네이비·코럴·배경색과 LINE Seed 글꼴을 유지한다. 본문 16/26, 보조 14/22, 최소 조작 영역 48, 넓은 화면 분기 1024와 본문 최대 폭 1200 등은 현행 토큰을 따른다. 큰 글자에서도 대비는 토큰의 더 엄격한 4.5:1 기준을 적용하고 브라우저 확대를 막지 않는다.

웹에서 새로 필요한 차이는 **로그인 전 홈**, **게스트 없는 로그인**, **편집 본문의 실제 지도 병렬 배치**, **원본과 영수증 확인 폼 병렬 배치**다. 이는 웹의 본문·진입 정책에만 적용한다. 앱의 게스트 선택이나 다른 화면의 공통 헤더·GNB를 바꾸는 근거로 사용하지 않는다.

초기 웹도 `HomeHeader`, `ScreenHeader`, `HeaderAction`, `GlobalNavigation`을 재사용하는 방향을 우선한다. 루트의 홈 → 내 여행 → 커뮤니티 → MY 4탭과 하위 작업 화면의 GNB 숨김을 유지한다. 독립 웹에서 공통 구성요소를 공유할 구조는 UI 분리 시 검증한다. 임의로 같은 모양을 복제하지 않는다. 데스크톱 전용 상단 탐색으로 대체하려면 별도 공통 규격 변경으로 분리한다.

키보드만으로 검색·후보 선택·추가·순서 이동·저장·모달 닫기가 가능해야 한다. 드래그 순서 변경에는 위/아래 이동·다른 DAY로 이동의 대안을 둔다. 지도 핀의 정보는 목록에서도 읽을 수 있게 한다. 한글 조합 중 Enter·Escape를 제출·이탈로 오인하지 않고, 오류는 해당 입력 옆에서 수정 방법을 안내한다.

이번 산출물은 구성 계획이며 완성 UI 시안이 아니다. 화면별 설계 단계에서 제목 위치·글꼴·행간·색상·여백·터치 영역·이미지 비율을 대조한다. 구현 후 360·390·430 폭, 넓은 화면, 320 CSS 폭 재배치와 200% 확대, 긴 제목·빈 목록·오류 상태의 실제 캡처가 필요하다. 현재는 실제 화면 대조와 캡처가 미검증이다.

| 장소의 출처      | 자체 일정 ID와 공급자별 식별자, 입력·조회 경로    | 현재 `googlePlaceId`만으로 Naver를 표현하지 않음 |
| 위치·주소        | 확인한 위치, 확인하지 못한 위치, 공급자 보관 조건 | 무작위 좌표나 중심 좌표로 대체하지 않음          |
| 계획과 실제 방문 | 계획을 유지하며 실제 방문을 별도로 연결           | 기존 일정의 상태 변경만으로 원본이 사라지지 않음 |
| 영수증 연결      | 한 방문에 여러 영수증, 한 결제의 비용 중복 방지   | 기존 `scheduleId`·비용 관계의 표현 가능성 확인   |
| 결제 시각        | 현지 결제 시각·시간대·불확실성·업로드 시각        | 기존 문자열 필드로 시간대를 추측하지 않음        |
| 공개 버전        | 원본 여행 버전과 승인한 공개본 버전               | 비공개 수정의 자동 누출 차단                     |
| 가져오기 출처    | 원 게시물과 독립 복사본의 관계                    | 철회 후 사진·개인정보 재배포 방지                |
| 임시 처리        | 업로드·인식·확정·취소·정리 상태                   | 실패 재개와 고아 파일 정리                       |

현재 스냅샷 저장 구조를 무조건 정규화하거나 전면 교체하지 않는다. 새 관계·제약이 필요하면 공통 도메인 → 검증 스키마 → API → 저장소 → 앱·웹 순서로 적용한다. 실제 DB·도메인 변경 때 [DB·객체 사전](<../../03. 개발/02. 데이터정의/DB_객체사전.txt>)에 DB명·테이블·컬럼·타입·제약·설명을 함께 갱신한다.

### 웹 구현 구조의 권장 방향

페이지별 개발 폴더·공통 코드·브랜치·검사·검수·배포의 도입안은 [웹 개발과 Git 운영 계획](<../../03. 개발/00. 구조설계/웹개발_Git운영_계획.md>)을 따른다. 기존 저장소의 `apps/web`에서 Next.js App Router를 우선 검증하는 후보이며, 이번 계획만으로 프레임워크·공통 UI 추출·CI·배포 설정을 적용하지 않는다.

초기 검증은 기존 Expo 웹에서 계정·여행·공개 흐름을 확인한다. 정식 웹 작업 공간은 준비된 `apps/web` 영역을 쓰는 방향을 권장하되, 현재 확정되지 않은 프레임워크를 계획서만으로 설치하지 않는다. 공개 일정 검색 노출, 실제 지도, 키보드 편집, 공통 UI 재사용과 배포 운영성을 짧은 기술 검증으로 비교한 뒤 결정한다.

별도 웹 UI를 선택해도 서버·DB·도메인·검증·API 클라이언트는 공유한다. 공개 페이지 렌더링 방식과 비공개 편집 화면은 구분하고, 비공개 일정·이메일·영수증이 공개 HTML이나 검색 메타데이터에 섞이지 않게 한다. 기존 코드 폴더를 이번 기획 단계에서 이동하지 않는다.

## 14. 출시 단계와 제외 범위

세부 단계는 [정식 출시 계획](앱웹_정식출시_계획서.md)의 **0.1.0 기반 → 0.2.0 홈·회원 → 0.3.0 계획·지도 → 0.4.0 영수증 → 0.5.0 공개 → 0.9.0 베타 → 1.0.0 출시 후보 → 정식 출시**를 따른다. 아래 M0는 0.1 기반 묶음, M1은 0.2~정식 1.0 범위, M2는 정식 이후 개선 묶음이다. 서로 다른 출시 일정으로 관리하지 않는다.

| 단계           | 목표                            | 포함할 작업                                                                                                   | 다음 단계 진입 조건                                 |
| -------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| M0 기반 준비   | 같은 계정·저장 계약 검증        | 공통 인증, 웹 게스트 차단, 쿠키/API 연결, 지도 약관·비용, 모델 부족 확인, 정책 페이지                         | 같은 회원·권한·여행 조회 증거와 지도 사용 조건 확보 |
| M1 첫 공개     | 계획 편집 → 앱 확인 → 선택 공개 | 홈·내 여행·생성·편집·실제 지도·검증한 URL, 단일 영수증, 가계부·초대·준비물 연결, 공개·철회·가져오기·신고·운영 | 핵심 사이클·개인정보·실제 외부 연동·화면 검수 통과  |
| M2 사용성 확장 | 반복 작업 줄이기                | 장소 보관함, 다중 URL, 여러 영수증 검수, 북마크, 운영 준비 후 댓글                                            | 초기 사용 지표와 실패 사례로 우선순위 결정          |
| 후속 검토      | 규모와 수요에 맞춘 확대         | 공동 커서, 경로 계산·최적화, 공개 프로필·구독, 일정 인쇄·내보내기                                             | 별도 비용·권한·운영 계약 확정                       |

M1은 지도·영수증의 실제 공급자 검증 전에는 출시 완료로 판단하지 않는다. 외부 지도 표시나 인식 기능이 막힌 상태라면 내부 검수 범위로 제한하거나 실제 가능한 기능만 안내하는 축소안을 별도로 결정한다. 필수 검증을 예시 데이터로 대신하지 않는다.

작업 기간은 개발 인원·정식 웹 구현 방식·앱 공통 계약 확장량·운영 예산이 정해진 뒤 산정한다. 지금은 주차별 납기를 확정하지 않는다. 착수 순서는 계정·공통 계약 → 장소·실제 지도 → 계획 편집 → 영수증 → 공개·가져오기 → 운영·회귀 검수다. 독립적인 정책 페이지 작성과 공개 페이지 설계는 기반 작업과 함께 진행할 수 있다.

코드 변경 후 `npm run check`를 통과한다. 인증은 `npm run test:auth`, API·도메인은 `npm run test:foundation`, 헤더·GNB·이동은 `npm run test:headers:web`와 이탈·뒤로가기 검사, 배포 설정은 `npm run test:release`를 추가한다. 문서 변경은 `npm run check:docs`와 서식 검사를 한다. 검사를 통과하려고 공통 규격이나 실패 조건을 낮추지 않는다.

각 실제 검증에는 대상 버전·환경·사전 조건·조작·기대 결과·실제 결과·판정·증거 위치를 남긴다. 이번 기획 단계에서는 위 실제 동작 검증을 수행하지 않았다. 로컬 증거는 `outputs/`에 보관하고 다른 담당자에게 필요한 결과는 작업 보고에도 요약한다.

## 19. 비교 서비스와 외부 근거

확인일은 **2026-11-10, 한국 시간**이다. 공식 안내에서 확인한 범위만 비교했다. 직접 제품을 조작한 검증과 다르며, 영수증·품목 기록을 소개에서 찾지 못했다고 해당 서비스에 없다고 단정하지 않는다.

| 서비스                                                                                               | 확인한 플랫폼·기능                                                 | 이번 계획에 참고한 점                             | 확인하지 못한 범위                                 |
| ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------- | -------------------------------------------------- |
| [Wanderlog](https://wanderlog.com/)                                                                  | 웹·앱 안내, 일정과 지도 병렬, 협업·사용자 가이드                   | 큰 화면의 지도·일정 연계, 계획과 공개 콘텐츠 연결 | 영수증의 실제 방문·품목 연결 정책과 내부 저장 구조 |
| [Tripadvisor Trips](https://www.tripadvisor.com/Trips)                                               | 확인한 웹 페이지에서 저장한 장소·친구 협업·여행 아이디어 정리 안내 | 장소 수집에서 일정 정리로 연결하는 흐름           | 앱별 세부 편집·영수증·계정 내부 정책               |

일정·지도 결합은 비교 서비스에서도 확인된다. TripPoint의 차별화 가설은 **앱·웹에서 같은 여행을 이어 쓰면서 실제 방문에 영수증의 음식·상품 품목과 지출을 연결하고, 사용자가 고른 일정만 다시 활용하게 하는 것**이다. 우월성이 입증된 것으로 쓰지 않으며 실제 등록 완료·재조회·공개 일정 가져오기 지표로 검증한다.

외부 API의 기능·표시·저장 조건은 4·6·9절의 공식 출처를 따른다. Naver 결과를 Google 지도에 섞는 이용 조건, 공급자별 데이터 보관, 실제 예산은 출시 전 재확인이 필요하다. 이 계획서는 법률 검토나 지도 공급자의 사용 승인을 대신하지 않는다.
