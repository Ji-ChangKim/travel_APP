# TripPoint Android APP WEB 1.0.0 출시 계획

1.0.0의 목표는 사용자가 웹에서 여행을 계획하고 Android 앱에서 같은 여행을 확인·기록한 뒤, 영수증의 음식·상품 품목과 지출을 실제 방문에 연결하고 선택한 일정만 공개하는 것이다. 다른 사용자는 공개 일정을 자신의 비공개 계획으로 가져와 수정한다.

사용자가 확정한 첫 출시 대상은 **Android 앱과 WEB**이다. **iOS 앱은 정식 출시 이후 별도 단계**로 진행한다. 회원의 핵심 데이터는 같은 환경의 공통 DB·API를 사용하고 웹에는 게스트 계정을 만들지 않는다.

이 문서는 목표 제품과 단계별 통과 조건을 정의하는 검토안이다. 현재 기능이 모두 구현·검증됐다는 뜻이 아니다. 단계의 버전 표기는 개발 목표를 구분하는 이름이다. 별도 웹 패키지는 개발 준비를 나타내는 `0.0.1`을 사용하며 기존 앱·루트 패키지·Android 빌드 번호는 바꾸지 않는다. 기존 [웹 전체 계획](웹사이트_초기구성_계획서.md), [홈페이지 상세 계획](<../../02. 디자인/01. 화면설계/웹홈페이지_화면계획.md>), [개발·Git 운영 계획](<../../03. 개발/00. 구조설계/웹개발_Git운영_계획.md>)을 실행 자료로 사용한다.

## 1. 1.0.0을 이용하는 전체 흐름

사용자는 PC에서 Google 계정으로 로그인하고 여행지·기간·일차를 정한다. 장소명·실제 주소·지원하는 지도 URL로 후보를 찾고 위치를 확인해 일정을 만든다. 저장한 여행을 Android 앱에서 다시 열면 같은 장소·일차·순서를 볼 수 있다.

여행 중에는 앱에서 일정을 확인하고 외부 지도의 길찾기를 연다. 영수증을 촬영하거나 여행 후 웹에서 사진을 올린다. 상호·결제일·현지 시각·통화·총액·품목을 확인한 뒤 기존 방문에 연결하거나 새 실제 방문을 남긴다. 원래 계획과 실제 기록을 구분하고 비용을 중복 합산하지 않는다.

정리한 여행은 기본 비공개다. 소유자가 공개할 일정·공유용 설명·사진과 전체 지출 공개 여부를 확인해 게시한다. 앱과 웹에는 같은 공개본이 나타난다. 다른 회원은 출발일을 정해 공개 일정을 자신의 새 계획으로 가져온다. 원본 영수증·세부 품목·실제 지출·동행자·개인 메모는 복제하지 않는다.

1.0.0 완료는 이 흐름을 실제 Google 계정·지도·영수증 인식·서버 저장·Android 설치본·운영 웹에서 확인한 상태다. 화면 수나 코드 존재만으로 완료를 판단하지 않는다.

권장 조합은 **단일 저장소 + 독립 웹 화면 + 공통 데이터·업무 규칙 + 최소 공통 UI**다. 초기 기반 작업량이 늘어나는 비용을 감수하는 대신 앱·웹 데이터와 규칙의 불일치를 줄이는 선택이다. 개발 기간이 얼마나 줄거나 늘지는 실제 기반 검증 전 수치로 단정하지 않는다.

0.1에서 독립 웹의 이점보다 유지 비용이 크거나 실행 호환을 확보하지 못하면 기존 Expo 웹 확장안과 비교해 구현 방식을 다시 결정한다. 핵심 DB·계정·웹 게스트 금지 조건을 바꾸거나 두 웹 구현을 동시에 제품으로 키우지 않는다. 프레임워크를 바꾸는 결정을 이미 확정한 것으로 설명하지 않는다.

## 5. 먼저 해결할 정책·데이터 기준

### Android 게스트와 웹 비회원의 구분

세 조건을 별도로 유지한다. **웹은 게스트 계정 없음**, **Android 게스트의 서버 저장·재조회는 기존 확정 필수 과제**, **같은 Google 회원은 앱·웹에서 공통 데이터 사용**이다.

현재는 앱 기기 게스트가 기준인 계정 문서와 게스트 서버 기록을 요구하는 기능·검수 문서가 함께 있다. 0.1에서 게스트 자격·소유권·유효기간·복원·사용량·삭제·회원 가져오기를 맞춘다. 앱이 보낸 UUID만으로 서버 권한을 주거나 웹에 익명 회원을 자동 생성하지 않는다. 서버 게스트를 Google 회원과 같은 `user/account` 생성 방식으로 구현한다고 미리 확정하지 않는다.

사진·영수증·품목·비용의 게스트 이용 범위, 검색·인식 요청의 권한·사용량, 회원 전환 후 원본 소유권도 0.1에 정한다. 기기 사진이 서버에 저장됐다고 안내하거나 여행 텍스트의 전환만 확인하고 사진까지 가져왔다고 처리하지 않는다. 기존 제공 범위를 줄이는 제안이 필요하면 영향과 대안을 별도로 기록한다.

0.3에서 Android 게스트의 실제 여행 저장·서버 재조회·재실행을 검증한다. 기기 기록을 서버 기록으로 가져온 뒤 로그인해 회원 기록으로 전환할 때는 선택한 여행과 성공 결과를 확인한다. 재시도로 복사본이 늘지 않고 실패 시 원본을 보존해야 한다. 이 과제를 기기 저장 성공만으로 완료하거나 1.0 필수 범위에서 조용히 제외하지 않는다. [기본 구조 기능 정의](<../01. 기능정의/앱기본구조_페이지별기능정의서.md>), [핵심 사이클 검수](<../../03. 개발/04. 검증/핵심_사용자사이클_검수.md>)

### 계획·영수증·실제 기록

계획과 실제 방문을 구분할 관계, 결제일과 방문 일차의 차이, 금액 없이 장소만 남기는 명령은 0.1에 설계하고 0.4에서 실제 검증한다. 현재 결제일을 DAY 변경으로 바꾸는 경로와 0원 확정 실패를 그대로 웹에 복제하지 않는다.

영수증의 사용자 확인은 본인 방문·원본 진위 인증을 뜻하지 않는다. 원본·품목은 현행 여행 참여자 열람 범위에 포함되므로 ‘업로더만 보는 비공개’라고 안내하지 않는다. 업로드 전에 공동 여행에서 보이는 범위를 설명한다. 공개본에는 원본·세부 품목을 넣지 않는다.

### 공개·비용·가져오기

비용 공개는 기본 끔을 권장하며, 공개 시 선택 장소만의 비용이 아니라 여행 전체 실제 지출 합계임을 표시한다. 공개본 수정은 미리보기와 명시 확인을 거친다. 원본 여행 수정이 공개본을 자동 변경하지 않는다. 공개 철회와 다른 회원이 이미 만든 독립 계획의 삭제를 구분한다. 가져오기는 현행 출발일 필수 계약을 사용한다.

Android의 상태 보존·뒤로가기·권한·기기별 동작은 [Android 기본 품질 가이드](https://developer.android.com/docs/quality-guidelines/core-app-quality)를 참고해 프로젝트 검사와 연결한다. 내부 테스트·심사·실제 제공 상태는 [Google Play 게시 안내](https://support.google.com/googleplay/android-developer/answer/9859751?hl=ko)에 따라 구분한다. 확인일은 2026-11-10이며 실제 등록 직전 대상 계정의 요구사항을 다시 확인한다. 심사 완료 날짜는 개발 일정과 별도로 다룬다.

## 8. 저장·오프라인·삭제·업데이트 기준

같은 환경의 앱·웹은 같은 서버 데이터를 사용한다. 로컬·검수·운영은 분리한다. 웹은 브라우저 쿠키, Android는 보호된 앱 자격을 사용하는 공통 인증 연결을 검증한다. 로그인 자격·Google 공급자 정보·여행 소유권을 각각 구분한다.

Android의 1.0 오프라인 목표는 이 기기에 저장을 마친 기본 여행 일정의 조회와 마지막 갱신 상태 안내다. 지도 타일·외부 장소 콘텐츠를 임의로 오프라인 수집하지 않는다. 회원의 서버 변경은 재연결·권한 확인 뒤 처리하고, 확인하지 못한 쓰기를 저장 완료로 표시하지 않는다. 전체 오프라인 편집·자동 충돌 병합은 후속이다.

비공개 캐시는 계정별로 분리하고 로그아웃·계정 전환·삭제 요청 시 정리한다. 오프라인 동안 원격에서 철회한 권한을 즉시 확인할 수 없다는 한계와 저장 범위는 0.1에서 정한다. 연결 후 서버 권한을 다시 확인한다. 다른 회원에게 이전 캐시가 보이지 않는지 검사한다.

앱 업데이트를 사용자가 즉시 설치한다고 가정하지 않는다. 필드·명령을 호환 가능하게 확장하고 구버전 저장이 새 기록·품목·공개 정보를 지우지 않는지 확인한다. 서버 호환 확장→새 웹·Android 배포→사용 중 버전 확인→필요한 구 계약 정리 순서를 따른다. API의 `/api/v1`, 서비스 출시 버전, 앱 표시 버전, Android 빌드 번호, Git 커밋은 별도 기록한다.

계정 삭제는 접수·파일/DB 정리·완료를 구분하고 공유 소유권·동행 기록·원본·OCR·공개 사본 영향을 검증한다. 게스트 자격 만료·기기 분실·회원 전환의 서버 자료 수명도 0.1에서 결정한다. 마이그레이션과 삭제의 실제 복구·백업 범위를 운영 준비에서 검수한다.

## 9. Git과 검증에서 단계 관리

단일 저장소와 `codex/` 기능 브랜치를 유지한다. 버전별로 오래 유지하는 브랜치를 추가하지 않고 단계는 작업 목록·PR·검증 기록·배포 기록에 연결한다. 핵심 공통 계약을 먼저 합친 뒤 의존하는 페이지를 구현한다.

| 실제 배포   | 대상·시각·제공 상태·배포 후 조작·실제 결과·후속 조치        |

코드 변경 뒤 `npm run check`와 변경 범위에 맞는 인증·API·헤더·배포 검사를 통과한다. 새 웹의 타입·빌드·경계 검사와 Android 설치본 검수는 별도로 연결한다. 문서·코드·자동 검사·실제 화면·실제 서버 저장·운영 배포의 상태를 각각 관리한다. 기존 작업 기록으로 이번 후보를 검증했다고 설명하지 않는다.

현재 기준은 `bbb3833`과 기획·0.0.1 웹 준비 변경이다. 독립 웹은 실행·검사 기반이며 실제 공급자·전체 여행 사이클·운영 전환의 검증이 남아 있다. 0.1을 달성했다고 표시하지 않으며 화면 수로 임의 진행률을 만들지 않는다. 기존 구현은 기능별로 인수해 재사용하고 새 문제·변경이 없는 검증을 반복하지 않는다.

## 10. 출시 후 순서와 지금 결정할 항목

정식 출시 직후에는 저장·로그인·공개·인식 실패와 문의를 살펴 수정한다. Android·WEB 1.0이 안정화되면 iOS를 별도 인수 트랙으로 진행한다. 같은 서버 계약을 사용하되 Apple 기기의 실제 인증·사진/카메라·링크·지도·권한·스토어 절차를 별도로 검증한다. 코드가 공통이라는 이유로 iOS 출시 완료로 처리하지 않는다.

영수증 여러 장 검수·장소 보관함·북마크·일정 내보내기는 사용 자료와 비용을 보고 다음 기능 후보로 정한다. 댓글·구독·채팅·예약·결제는 운영 여력과 정책을 갖춘 뒤 별도 우선순위를 정한다. iOS 출시와 이 기능들을 반드시 한 버전에 묶지 않는다.
