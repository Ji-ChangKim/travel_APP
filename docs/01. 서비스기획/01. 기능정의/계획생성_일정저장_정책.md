# 계획 생성부터 일정 저장까지

상태: 사용자 요청에 따른 기존 확정 정책의 적용 기준 / 적용일: 2026-11-02 / 범위: 기본 입력·로그인 복귀·초안·정식 생성·세부 일정 저장·재진입

여행을 만든 뒤 날짜별 일정을 추가하고, 저장한 내용을 다시 열어 볼 수 있어야 합니다. 이 문서는 [핵심 정책 확정 사항](핵심정책_확정사항.md)을 화면과 저장 처리에 같은 기준으로 적용합니다. 여러 일정을 작성한 뒤 전체를 한 번에 확정하는 별도 저장 방식은 추가하지 않습니다.

## 단계별 결과

기본 정보의 ‘바로 여행 만들기’는 항공편 단계를 거치지 않고 생성합니다. 상단 ‘다음’과 ‘항공편 추가 및 확인 (선택)’은 항공편을 확인하는 단계로 갑니다. 세 행동은 같은 기본 입력 검증과 정식 회원 확인을 사용합니다. 로그인 후에는 입력으로 돌아와 사용자가 다시 생성 행동을 선택합니다. 저장·재조회 중에는 이동 버튼도 잠그며, 브라우저 뒤로가기를 취소하면 확인창을 닫고 같은 내용을 계속 작성합니다.

날짜 미정 또는 출발일만 정한 입력은 초안으로 저장합니다. 정식 생성은 출발일·도착일을 모두 갖춘 뒤 진행합니다. 정식 전환이 끝나면 서버 초안을 제거하고, 홈의 남은 조회 결과에서도 같은 ID를 두 여행처럼 표시하지 않습니다.

## 화면에서 유지할 규격

[디자인 시스템](<../../02. 디자인/00. 공통규격/디자인시스템.md>), [헤더·GNB](<../../02. 디자인/00. 공통규격/헤더GNB_규격.md>), [여행 일정 화면](<../../02. 디자인/01. 화면설계/여행일정_화면규격.md>)을 따릅니다. 공통 헤더·하단 메뉴의 배치는 변경하지 않습니다. 일정 작성의 DAY·유형은 선택 여부를 화면 읽기 도구에 전달하고, 터치 높이는 공통 토큰의 48 이상을 보장합니다.

## 개발 계약

- 정식 생성 입력은 `packages/validation/src/foundation.ts`의 `persistedTripCreateSchema`를 기준으로 합니다. `tripCreationInput`으로 같은 입력을 변환하며, 기본 정보의 다음에서는 선택 항공편을 제외하고 검사합니다. 화면 버튼이 도시를 별도 필수로 만들지 않습니다.
- 서버 초안과 정식 여행의 구분은 날짜 유무만으로 결정하지 않습니다. `plan_drafts`의 작성 정보는 정식 생성 전까지 초안입니다. `homeTravelGroups`가 이를 예정·여행 중 분류에서 제외합니다.
- 일정 명령은 실제 여행 ID·DAY ID·여행 버전과 함께 전송합니다. 기존 회원 권한·버전 충돌·같은 요청의 중복 방지 검사를 유지합니다.
- 저장 성공 콜백에서만 폼의 DAY와 일정 ID를 목록 선택에 반영합니다. 실패 후 다시 저장해 성공한 경우에도 같은 복귀 처리를 실행합니다.
- API·DB·도메인 객체의 필드와 제약은 이번 화면 연결 수정으로 변경하지 않습니다. 서버의 기존 원자 저장과 초안 버전 검사를 유지합니다.

## 인수 기준

도시·제목·항공편 없이 나라와 3일 기간을 입력합니다. 위·아래 다음과 로그인 취소·복귀를 확인합니다. 실제 여행을 생성한 뒤 DAY 1에서 일정 작성을 열어 DAY 2로 바꿔 저장합니다. DAY를 다시 누르지 않고 DAY 2와 저장한 행이 보이는지 확인합니다.

그다음 다른 화면 왕복·새로고침·새 브라우저 로그인 후 같은 여행을 엽니다. 인증된 HTTP 재조회와 DB 직접 조회에서 일정 ID·DAY·내용이 같고 한 건만 남아야 합니다. 서버가 저장한 뒤 응답만 끊은 경우에도 같은 요청을 다시 보내 중복 없이 복구해야 합니다.

실제 로컬 API·D1을 쓴 검사와 응답을 통제한 자동 검사는 구분합니다. 로컬 검사 통과를 운영 배포·실기기 저장 인수로 표현하지 않습니다.
