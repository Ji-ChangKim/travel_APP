# 일정 화면 구현과 배포 준비

## 서비스 결정

Stitch의 `005_전체 일정`과 `일정 추가 및 정리`를 실제 앱의 일정 조회·작성 흐름에 반영했다. UI TOOL KIT와 아이콘 모음에서 추출한 색상·간격·모서리·SVG를 사용한다. 초기 차이는 화면 원본 대신 파생 명세를 기준으로 구현한 구조, 큰 공통 허브 헤더, 일정 전용 입력 화면과 저장 계약의 부재에서 발생했다. 원인과 비교 근거는 `docs/00. 문서안내/개발검수_현재상태.txt`에 정리했다.

사용자는 전체 또는 DAY를 선택해 방문 순서와 시각을 보고, 장소를 추가할 위치를 고른 뒤 시간·체류 시간·메모·예상 비용을 함께 저장한다. 이미 제공하던 항공편 상세, 사진, 영수증, 실제 지출과 여행 권한은 유지한다.

## 기획 재검토에 따른 수정

초기 기획 검토에서 승인을 보류하고 `../../../02. 디자인/00. 공통규격/일정화면_기획검토.md`의 기준을 고정한 뒤 수정·재검토를 반복했다. 최종적으로 일정 계획 MVP의 승인 기준 8개를 통과했다. 상세 판정과 근거는 해당 문서에 기록했다.

- 변경한 일정을 닫거나 전역 메뉴·영수증 작성으로 전환할 때 계속 작성과 명시적 버리기를 선택한다. 새 여행에 갔다 돌아와도 버린 폼은 다시 나타나지 않는다. 저장 응답을 기다리는 동안 전역 이동을 막는다.
- 방문 시각 역전과 체류 시간 겹침을 요약해 알리고 상세는 펼쳐서 확인한다. 입력한 예약·항공 시각을 자동으로 바꾸지 않는다.
- 일정 삭제 시 해당 일정에서 자동 생성한 예상 비용만 제거한다. 실제 지출·수동 예산·사진은 보존한다. 일정의 DAY를 바꾸면 연결 비용의 DAY도 함께 바꾸고 영수증 거래 날짜 보호는 유지한다.
- 직접 제목 입력을 기본으로 하고 Google 지도 검색·링크는 선택해 펼친다. 메모·할 일에는 장소 지도 입력을 숨긴다.
- 삽입 위치를 선택하면 후보 목록을 접고 작성 중인 일정과 앞뒤 방문을 먼저 보여준다. 전체 목록은 필요할 때 펼친다. 작성 중인 장소에 좌표가 없으면 그 사실을 안내한다.
- 중앙 버튼은 비행기 아이콘과 ‘새 여행’ 문구로 일정 추가와 구분한다. 전역 메뉴는 유지한다.

추가 코드: `scheduleExitGuard.tsx`, `scheduleConflicts.tsx`, `scheduleTimeConflicts.ts`. 경로는 `apps/mobile/src/features/workspace/`다.

원본 전체 기능을 구현한 것으로 표현하지 않는다. 앱 내부 장소 추천·평점·영업시간, 자동 이동 시간·대중교통 경로, 드래그 정렬, 자동 환율 변환은 이번 버전에 없다. 장소 사진은 실제 등록한 사진만 표시한다. 이런 기능에는 공급자 계약·응답 명세·비용 정책과 별도 상호작용 구현이 필요하다.

## 저장 계약과 호환성

- `WorkspaceSchedule.durationMinutes`: 1~1440분 또는 null. 생략한 과거 요청은 기존 값을 보존한다.
- `schedule.save.afterScheduleId`: 같은 DAY의 이전 일정 ID 또는 null. null은 맨 앞, ID는 해당 일정 뒤에 삽입한다. 화면의 마지막 선택은 저장 직전에 실제 ID로 바꾼다.
- `schedule.save.estimatedCost`: 금액·통화 객체 또는 null. 별도 예상 비용을 같은 저장 요청에서 변경한다. 생략하면 기존 기록을 보존한다.
- `schedule-plan` 출처의 예상 비용만 수정·해제한다. 실제 지출, 영수증, 수동으로 추가한 다른 비용은 지우지 않는다.
- 일정 자체를 삭제할 때도 자동 예상 비용만 제거한다. 다른 비용은 일정 연결을 해제해 독립 기록으로 보존한다. 일정 날짜 이동 시 연결 비용의 날짜를 함께 맞춘다.
- `schedule.reorder`: 같은 DAY의 전체 일정 ID를 중복 없이 전달한다. 다른 DAY나 누락된 목록은 거부한다. 방문 순서는 `sortOrder`로 읽으며 API 배열의 물리 위치에 의존하지 않는다.
- 현행 D1 `trips.snapshot` JSON과 기기 게스트 문서에 저장한다. 물리 SQL 컬럼 변경은 없다. 레거시 Supabase SQL 구현은 이번 배포 대상이 아니다.
- 기존 버전 검사·멱등 요청·권한 검사를 사용한다. 영수증의 거래 날짜와 다른 DAY로 부모 일정을 옮기는 요청은 거부한다.
- 상세 타입·제약조건·보존 및 해제 규칙은 `docs/03. 개발/02. 데이터정의/DB_객체사전.txt`에 추가했다.

## 검증과 산출물

검증 결과와 번들 해시는 `.release/schedule-v5/manifest.json`에 기록한다. 테스트 화면의 장소·사진·금액은 격리된 검사 데이터이며 실제 사용자 여행에 넣지 않았다.

- `npm run check`: TypeScript 엄격 검사·ESLint·Prettier 통과. 문서 정리 뒤 최종 검사도 실행한다.
- 인증·기기 모델 74/74, API 70/70, SVG 네이티브 연결을 포함한 최종 릴리스 39/39, 로컬 Workers·D1·R2 11/11, 전체 브라우저 49/49 통과. 마지막 웹 위치 버튼 문구 수정 뒤 관련 브라우저 3/3과 전체 `npm run check`도 추가 통과했다.
- 최초 브라우저 46/47에서 이전 통합 문구를 찾던 게스트 검사 선택자를 고친 뒤 전체 47개를 재실행했다. D1 순서 검사는 배열 위치 대신 `sortOrder`를 비교하도록 바로잡았다. 기존 릴리스의 자동 연결 제한 시간 초과는 순차 재실행으로 해소했다.
- 실제 자동 연결 검사에서 루트 EAS의 SVG 누락을 발견해 루트와 모바일 양쪽에 Expo SDK 호환 의존성을 선언했다. 두 경로 모두 네이티브 연결을 확인했다.
- staging 웹 29개 경로, Worker dry-run, staging Android Hermes 번들 생성 통과. Gradle APK·AAB 작업 연결은 오프라인 dry-run에서 통과했고 실제 패키징·서명은 실행하지 않았다.
- 360·390·430px 일정 화면에서 가로 넘침을 검사하고 실제 렌더링을 캡처했다.
- `.release/schedule-v5/release-notes-ko-KR.txt`: 내부 테스트 변경 안내.
- `apps/mobile/dist/`: staging 웹 준비본. `release:artifacts`로 진입 경로·rewrite·테스트 설정 미포함 확인.
- `apps/mobile/.release/schedule-v5-android/`: staging Android Hermes 번들과 자산. 설치용 APK/AAB는 아니다.
- `apps/api/.release/.release/schedule-v5/`: API dry-run 번들. 원격 업로드 없이 생성한다.
- `outputs/schedule/`: 일정·작성·삽입 미리보기 검수 캡처.

이 문서와 manifest는 배포 준비 결과다. 실제 원격 배포, Play 업로드, 서명 APK/AAB 생성, 실기기 설치 검증은 완료한 것으로 기록하지 않는다. 현재 로컬 Gradle release 기본 설정은 디버그 키이므로 그대로 Play 제출용으로 사용하지 않는다.

브라우저 검수는 `npm run test:schedule:web`로 재현한다. 이 명령은 검수 번들을 캐시 없이 생성하고 주소를 확인한 뒤 Playwright를 실행한다. 검수용·배포용 Expo export는 같은 캐시를 사용하므로 동시에 실행하지 않고 환경을 바꿀 때마다 산출물의 API 주소를 확인한다.

### 의존성 감사

기존 `shell-quote` 1.10.0에서 보고된 치명 항목은 호환 범위의 1.12.0으로 갱신해 해소했다. 현재 전체 workspace 감사 결과는 치명 0, 높음 24, 보통 12다. 높음 항목의 주요 원인은 기존 Expo 빌드 도구의 `braces`·`node-forge`와 Miniflare의 고정 `sharp` 의존성이다. 허용 범위 안의 갱신을 시도했지만 이 세 패키지는 보고된 취약 버전을 유지했다. 자동 감사가 제안하는 Expo 44·React Native 0.72 등의 주요 버전 변경은 적용하지 않았다.

이 감사 건수는 앱의 실제 공격 가능성을 판정한 결과가 아니며 빌드 도구를 포함한 의존성 트리의 결과다. 배포 전 해당 공급자의 수정판과 노출 조건을 검토해야 한다. 원본 결과는 `scratch/schedule-dependency-audit-final.json`, 잠금 파일과 결과 요약은 manifest에 보관한다. 잔여 보안 검토가 있는 상태를 무조건적인 배포 승인으로 표현하지 않는다.

## 배포와 인수 순서

1. 검증한 v5 API를 staging에 먼저 배포한다. 이전 strict API는 새 일정 필드와 정렬 명령을 거부한다. SQL 마이그레이션 추가는 필요하지 않다.
2. `/health`와 `/public/startup`을 확인하고 테스트 계정에서 일정 삽입·체류·예상 비용·정렬 후 재조회한다.
3. `apps/mobile/dist/`를 기존 staging Pages 프로젝트에 배포하고 DAY·영수증·항공편·권한·게스트 저장을 확인한다.
4. Play의 최고 versionCode를 확인한다. 이번 준비 번호는 5이며 미사용 여부는 업로드 직전에 확인해야 한다.
5. 기존 preview APK 또는 play-internal AAB 빌드 흐름으로 새 네이티브 패키지를 만든다. SVG 모듈이 추가됐으므로 이전 설치본에 JavaScript만 교체하는 방식으로 배포하지 않는다.
6. AAB에는 기존 업로드 키를 적용하고 서명·패키지 `com.tripprint.app`·versionCode를 확인한다. CI 서명 경로는 `scripts/android-ci.gradle`을 사용한다. 새 키를 임의로 만들지 않는다.
7. 실기기에서 이전 버전 업데이트 후 여행 보존, 지도·SVG·폰트, 키보드와 하단 저장 버튼, 시스템 글자 확대, 사진·영수증 권한 및 외부 지도 복귀를 확인한다.
8. 인수 통과 후 Play 내부 테스트 트랙에 제출한다. Git 커밋·푸시와 원격 게시는 이 준비 작업에서 실행하지 않았다.

## 롤백 기준

웹 문제는 이전 웹 배포로 되돌리고 v5 API는 유지한다. v5 API는 과거 앱의 생략 요청을 호환 처리한다. v5 앱 사용자가 남아 있는 동안 API만 v4로 되돌리면 일정 저장이 실패할 수 있다. 서버를 되돌려야 할 때는 새 계약을 수용하는 수정 버전을 먼저 준비한다. 저장된 JSON·비용 기록이나 사용자 사진을 롤백 명목으로 삭제하지 않는다.
