# 공개 추천 일정 데이터 작성·등록 가이드

기준일: 2026-10-20. 대상은 홈의 공개 일정 카드와 발자국의 공개 목록·상세에 보여줄 여행계획이다. 현재 Cloudflare D1 경로와 실제 저장·공개 스키마를 기준으로 작성했다. 이 문서와 양식은 자료 준비용이며 자동 가져오기 기능이나 등록 실행 스크립트가 아니다. 가이드 작성 단계에서는 DB 저장·공개 게시·배포를 하지 않았다. 이후 사용자 승인으로 등록한 북큐슈 일정의 자료·수정 내역·DB 결과는 `../00. 공개여행계획/02. kyushu-onsen-yatai-4d-v1/README.md`에서 확인한다.

## 1. 작성자가 준비할 자료

추천 일정 하나를 **여행 기본 정보 → DAY별 주제 → 방문 항목 → 출처 → 공개 사진**으로 나눈다. 한 장소의 설명을 별도 항목으로 관리해야 수정·정렬·공개 선택이 가능하다.

| 자료      | 작성 단위                       | 우선 준비할 내용                                              | 양식                                                       |
| --------- | ------------------------------- | ------------------------------------------------------------- | ---------------------------------------------------------- |
| 여행      | 추천 계획 한 개당 한 행         | 제목, 국가·대표 도시, 기준 날짜, 시간대, 통화, 짧은 공개 소개 | [trips.csv](<00. 양식/00. 공개여행계획/trips.csv>)         |
| DAY       | 날짜마다 한 행                  | DAY 번호, 실제 날짜, 하루 제목, 하루 컨셉                     | [days.csv](<00. 양식/00. 공개여행계획/days.csv>)           |
| 방문 항목 | 장소·이동·숙소 등 한 건당 한 행 | DAY, 순서, 유형, 이름, 시각, 주소, 공개 설명                  | [schedules.csv](<00. 양식/00. 공개여행계획/schedules.csv>) |
| 출처      | 검증 근거마다 한 행             | 원문 주소, 확인일, 확인자, 검증 상태                          | [sources.csv](<00. 양식/00. 공개여행계획/sources.csv>)     |
| 사진      | 사용할 파일마다 한 행           | 원본 파일 위치, 권리 근거, 연결 항목, 공개 여부               | [photos.csv](<00. 양식/00. 공개여행계획/photos.csv>)       |

처음에는 여행·DAY·방문 항목을 작성하고, 게시 전 출처와 공개 사진을 확인한다. 사진 없이도 계획은 공개할 수 있다. 확인하지 못한 시간·가격·좌표를 만들어 채우지 않는다.

같은 폴더의 [example.commands.json](<00. 양식/00. 공개여행계획/example.commands.json>)은 **형식 확인용 가상 예시**다. 실제 추천 장소·운영 계정·실제 DB ID가 아니며 게시하면 안 된다. JSON 전체를 하나의 API 요청으로 보내는 방식도 지원하지 않는다.

## 2. 여행 기본 정보

| 준비 항목 / API 필드                  | 필수 구분      | 현재 규격과 작성 방법                                                                                                                                              |
| ------------------------------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 관리 키 `planKey`                     | 양식 필수      | 예: `osaka-walk-2d-v1`. 여러 CSV를 연결하는 작성용 키이며 DB UUID가 아니다                                                                                         |
| 제목 `title`                          | 편집 필수      | 생성 API는 생략 가능·최대50. 공개 추천은 무엇을 하는 여행인지 구체적으로 작성한다. 계획 공개 제목은 이 여행 제목을 사용한다                                        |
| 국가 `country`                        | API 필수       | 공백 제거 후1~50. 대륙 대신 국가 이름을 통일한다                                                                                                                   |
| 대표 도시 `city`                      | 편집 권장      | API는 빈 문자열 허용·최대50. 공개 검색과 홈 도시 필터에 쓰이므로 가능한 한 작성한다. 여러 도시라면 대표 도시를 정하고 DAY 설명·각 장소 주소에 나머지 도시를 적는다 |
| 시작·종료일 `startDate`, `endDate`    | API 필수       | `YYYY-MM-DD`. 실제 달력 날짜, 시작일≤종료일, 양끝 포함1~90일                                                                                                       |
| 시간대 `timezone`                     | API 필수       | 유효한 IANA 이름·최대100. 예: 일본 일정은 `Asia/Tokyo`. `GMT+9`처럼 임의 표기하지 않는다                                                                           |
| 기본 통화 `defaultCurrency`           | 편집 필수      | 현재 지원값 `KRW`, `JPY`, `USD`. API 기본값은KRW이므로 해외 일정은 명시한다                                                                                        |
| 공개 소개 `publicBody` → `input.body` | 편집 필수      | 공개 명령에서 문자열 필수·최대2000. 대상 여행자·여행 주제·주요 제약을 짧게 설명한다                                                                                |
| 비용 공개 `includeCosts`              | 공개 요청 필수 | 추천 계획은 원칙적으로 `false`. 현재 공개 비용 합계는 실제 지출이며 예상 여행 예산이 아니다                                                                        |
| 검수 상태·담당자·검수일               | 양식 필수      | `editorialStatus`, `reviewer`, `reviewedAt`은 작성 관리용이다. 여행 상태나 서버 명령에 넣지 않는다                                                                 |

기간만 있는 상시 추천도 현행 저장에는 실제 시작·종료일이 필요하다. 내부 기준 날짜와 이용 가능한 시기·요일·계절 조건을 구분해 공개 소개에 명시한다. 미래 항공편·영업일이 확인됐다는 뜻으로 기준 날짜를 사용하지 않는다. 상시 템플릿 전용 기간 필드는 현재 없다.

항공편은 추천 계획의 필수 자료가 아니다. 특정 예약·운항 정보를 추천 일정으로 가장해 만들지 않는다. 실제 항공편을 연결할 때만 기존 항공 검증 계약을 별도로 따른다.

## 3. DAY별 주제

| 준비 항목 | 저장 필드 / 명령             | 규격                                                   |
| --------- | ---------------------------- | ------------------------------------------------------ |
| DAY 번호  | `days[].dayNumber`           | 여행 첫날부터1, 2, 3 순서. 기간의 모든 날짜와 일치     |
| DAY 날짜  | `days[].tripDate`            | `YYYY-MM-DD`. 시작일에서 DAY 번호−1일을 더한 실제 날짜 |
| 하루 제목 | `day.plan.input.planTitle`   | 최대200. 예: 도착 후 숙소 주변을 천천히 걷는 날        |
| 하루 컨셉 | `day.plan.input.planConcept` | 최대2000. 하루 목표·이동 범위·선택 기준·주의점을 설명  |

여행 생성 시 DAY UUID는 서버가 만든다. 작성자는 DAY 번호와 날짜만 준비하고, 등록 담당자가 저장 응답의 DAY UUID로 연결한다. API의 `day.plan`에는 `dayId`, `planTitle`, `planConcept`을 보낸다. 제목·컨셉의 빈 문자열은 기존 값을 해제한다.

공개본에는 **공개 선택한 일정이 있는 DAY만** 포함된다. 하루 제목만 작성하고 그날의 장소를 하나도 공개 선택하지 않으면 그 DAY 설명이 공개되지 않는다.

## 4. 방문 항목 한 건의 작성 규격

| ------------------------------------------ | ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `itemKey`                                  | 등록 시 일정 `id`와 연결                  | 양식 필수. 계획 안에서 중복 없는 관리 키. 예: `d1-stop-01`                                                                              |
| `dayNumber`                                | 해당 DAY의 `dayId`                        | 양식 필수. 날짜 자체를 일정 객체에 따로 넣지 않는다                                                                                     |
| `sortOrder`                                | `input.sortOrder`                         | API 필수. 양의 정수1~10000. 작성 규칙은 DAY마다1부터 연속 번호, 중복 없음                                                               |

| `title`                                    | `input.title`                             | API 필수. 공백 제거 후1~100. 장소는 실제 지점 이름까지 구분                                                                             |

| `googlePlaceId`                            | `input.googlePlaceId`                     | 선택. 검증된 Google 장소 ID. 영문·숫자·`_`·`-`, 최대200. 지도 URL이나 상호 이름을 넣지 않는다                                           |

| `STAY`        | 숙박                                                       |
| `RESERVATION` | 예약·입장 일정. 공개 설명에는 개인 예약번호를 넣지 않음    |
| `TODO`        | 여행 중 해야 할 일                                         |
| `MEMO`        | 특정 장소와 무관한 일정 안내                               |

### 공개 설명은 이렇게 나눈다

장소마다 “어떤 곳인지 → 왜 이 코스에 넣었는지 → 어떻게 이용하면 좋은지 → 확인할 조건” 순으로 쓴다. 줄바꿈과 원문 공백은 보존한다. 휴무·운영시간·요금·예약 조건처럼 바뀌는 내용은 출처와 확인일을 함께 관리하고, 확실하지 않으면 확정된 정보처럼 쓰지 않는다.

`memo`는 개인 여행 원본에 남는 **비공개 메모**다. 공개 설명을 여기에 넣으면 공개 상세에서 보이지 않는다. 공개할 글은 `planContent.description`에 넣고, 개인정보·동행 정보·예약번호를 처음부터 포함하지 않는다. DAY 제목·컨셉과 공개 소개도 같은 공개 검토 대상이다.

`location`과 항공 상세는 개인 여행 원본에 저장할 수 있지만 현재 공개 일정에는 투영되지 않는다. 공개 장소에는 `googlePlaceId`, 이름·주소·시각·계획 설명이 포함된다. 좌표를 준비했다는 이유만으로 공개 지도·사진의 연결까지 완료됐다고 판정하지 않는다.

### 순서와 시간은 별개다

방문 순서는 `sortOrder`, 시작 시각은 `timeSlot`이다. 작성 검수에서는 시각이 앞뒤로 뒤집히지 않는지, 이동·식사·휴식 시간이 빠지지 않았는지 확인한다. 이동 시간을 조사하지 못했다면 임의 숫자를 넣지 않는다. 최적 동선이나 정확한 소요시간을 자동 보장하는 입력 구조는 아니다.

DAY마다 순서를 정리한 뒤 `schedule.reorder`를 쓴다면 그 DAY의 **전체 일정 UUID**를 중복 없이 보내야 한다. 일부 UUID만 보내는 순서 변경은 허용되지 않는다.

### 선택 코스와 대체 코스

같은 구간에서 하나를 고르는 항목들은 동일한 `choiceGroup`을 사용한다.

| 예시           | `choiceGroup`  | `choiceKind` | `choiceLabel`   |
| -------------- | -------------- | ------------ | --------------- |
| 기본 야외 코스 | `day2-weather` | `choice`     | 맑은 날 선택    |
| 우천 대체 코스 | `day2-weather` | `backup`     | 비 오는 날 대체 |

그룹은1~80, 라벨은최대200. `choiceKind`는 `choice` 또는 `backup`이며, 라벨이나 종류를 쓰면 그룹이 있어야 한다. 편집 규칙으로 그룹·라벨·종류를 함께 작성하고 같은 DAY의 대안끼리 묶는다. 그룹은 선택 관계를 표시할 뿐 모든 대안을 실제 방문으로 확정하거나 자동 예약하지 않는다.

### 비용을 모를 때

공란은 미확인, 명시한0은 무료라는 뜻으로 작성 자료에서 구분한다. 현행 예상 비용 API는 **양수만** 받으므로 무료 항목은 금액 객체를 만들지 않고 공개 설명에 “무료·확인일”을 적는다. 알 수 없는 금액을0으로 저장하지 않는다.

예상 비용은 별도 `expenses` 항목으로 저장되며 `isActual:false`다. 공개의 `includeCosts:true`는 **선택한 일정에 한정하지 않고 여행 전체의 실제 지출**을 통화별로 합산한다. 추천 예산을 표시하기 위한 우회 수단으로 쓰지 않는다. 가격을 공개할 필요가 있으면 확인한 예상 요금·기준일·포함 범위를 공개 설명에 적는다.

EUR·VND 등 현재 지원하지 않는 통화는 확인한 원문과 출처를 작성 자료에 남기고 API 금액 객체 등록을 보류한다. 임의 환율로 KRW·JPY·USD로 바꾸거나 다른 통화인 것처럼 저장하지 않는다.

## 5. 출처와 사진

출처 양식에는 원문 URL, 확인일, 확인자, 검증 상태, 확인한 내용을 남긴다. 상호·주소·운영 조건은 공식 안내 등 확인 가능한 자료로 점검한다. 타인의 원문을 그대로 복사하는 대신 필요한 정보를 확인해 직접 설명을 작성한다.

사진은 사용 권리를 확인한 파일만 준비한다. 권리자·허용 조건·증빙과 연결할 `itemKey`를 사진 양식에 적는다. `altText`는 편집 자료이며 현행 공개 저장 명령의 별도 필드가 아니다. 로컬 파일 경로나 외부 이미지 URL을 `photoIds` 또는 `photoPaths`에 직접 넣지 않는다.

실제 업로드 → 해당 여행의 일반 사진으로 등록 → 반환된 media UUID를 `photoIds`에 선택하는 기존 절차를 따른다. 현행 업로드는 JPG/PNG·파일당 최대4MiB이며 영수증 사진은 공개 사진으로 선택할 수 없다. 사진 저장소는 R2, 접근·등록 메타데이터는 DB가 관리하며 짧게 발급되는 조회 URL을 원본 데이터로 보관하지 않는다.

공개 상세의 장소 사진 조회와 홈 카드 표지는 별개다. Google 장소 사진이 상세에서 조회되더라도 자동으로 `photoPaths[0]`가 되지 않는다. 홈 카드는 공개 선택한 일반 사진 중 첫 번째를 표지로 쓰고, 없으면 지도 아이콘을 표시한다. 홈 배경용 일러스트를 개별 장소의 실제 사진으로 등록하지 않는다.

## 6. 현재 DB에 어떻게 연결되는가

```text
작성용 CSV와 출처 자료
  → 실제 운영 계정으로 여행 생성
  → trips.snapshot에 DAY·일정·계획 설명 저장
  → 소유자가 공개할 일정·사진을 선택
  → community.publish(kind="plan")
  → posts.snapshot에 공개 허용 필드만 복사
  → 공개 목록·단건 상세·홈에서 조회
```

| 실제 저장 위치              | 역할                                                                              |
| --------------------------- | --------------------------------------------------------------------------------- |
| `trips.snapshot` JSON       | `trip`, `days`, `itinerary`, `expenses`, `media` 등 개인 여행 원본                |
| `trips.version`, `last_key` | 변경 충돌과 요청 일치 관리                                                        |
| `trip_members`              | 같은 여행의 실제 소유자·편집자·열람자 인덱스                                      |
| `posts.snapshot` JSON       | 현재 공개된 `CommunityPost` 사본. `trip_id`는유일하므로 여행 하나당 공개 글 한 개 |
| `uploads`와 R2 파일         | 실제 업로드된 사진의 메타데이터·원본                                              |
| `mutation_requests`         | 계정별 요청 키·입력 해시·확정 결과                                                |

이전 DB 사전 앞부분의 PostgreSQL `trip_days`·`itinerary_items` 테이블에 행을 추가하는 SQL을 현행 D1에 그대로 적용하지 않는다. D1의 날짜·일정은 위 JSON 배열이다. 배포 대상이 D1인지 실제 설정을 확인하고 등록한다.

등록은 기존 API를 사용한다. DB에 JSON만 직접 쓰면 소유자 인덱스·버전·중복 요청 기록·공개 선택 검사를 건너뛸 수 있다. 공개본만 만들거나 개인 원본만 수정하면 양쪽 내용도 달라진다. 운영용 직접 SQL 등록문은 이 가이드에 포함하지 않는다.

`planKey`, `itemKey`, 출처·검수·사진 권리 항목은 **작성용 관리 정보**다. 새 DB 컬럼이나 새 도메인 객체를 만든 것이 아니다. API는 strict 입력이므로 CSV 열을 그대로 JSON에 붙여 보내면 검증에 실패한다. 실제 요청에는 이 문서에서 매핑한 기존 필드만 넣는다.

## 7. 등록 담당자의 처리 순서

1. 실제 게시를 담당할 계정과 대상 API 환경을 확인한다. 공식 추천처럼 보이게 운영할 경우 작성자 이름도 실제 운영 계정의 닉네임으로 관리한다. 계정·토큰을 양식에 넣지 않는다.
2. CSV를 검토하고 ID 연결표를 준비한다. `planKey→tripId`, `(planKey, dayNumber)→dayId`, `(planKey, itemKey)→scheduleId`, `assetKey→mediaId`를 등록 결과로 보관한다.
3. `POST /api/v1/trips`로 여행을 만든다. 등록된 여행 ID를 받고 `GET /api/v1/trips/{tripId}/workspace`로 DAY UUID와 현재 버전을 읽는다. 예시 JSON의 가상 UUID를 운영에 재사용하지 않는다.
4. 각 DAY를 `day.plan`, 각 항목을 `schedule.save`로 순차 저장한다. 날짜·주소·장소 ID·공개 설명·선택 관계를 원본과 대조한다. 하나의 쓰기 요청 안에서의 저장은 원자적이지만 여러 요청으로 만든 계획 전체가 하나의 트랜잭션인 것은 아니다. 중단 시 마지막 확정 지점부터 복구한다.
5. 사진을 사용할 경우 실제 업로드·등록을 마친다. 기존 일정이나 사진을 가리키는 선택 ID만 사용한다.
6. 개인 여행 원본을 다시 읽어 전체 기간·DAY 수·정렬·공개 설명·누락을 검수한다. 이 단계에서는 공개하지 않는다.
7. 소유자 계정으로 `community.publish`를 보낸다. `kind:"plan"`을 명시하고 `scheduleIds`를최소1개 선택한다. `title`, `body`, `photoIds`, `includeCosts`도 넣는다. 계획 공개 제목은 서버가 여행 제목으로 확정하므로 `title`에도 같은 제목을 보낸다.
8. 갱신된 workspace의 `postId`를 읽고 `GET /public/community/{postId}`로 공개 내용을 대조한다. 현재 웹의 `/community/{postId}`도 열어 DAY·설명·대체 코스·표지와 개인정보 제외를 확인한다.
9. 공개 목록과 홈에서 노출 조건을 확인한 뒤 등록 ID·버전·공개 URL·입력 자료 버전·검수 결과를 보관한다. 부분 성공이나 미확인을 게시 완료로 기록하지 않는다.

계획은 `DRAFT`, `PLANNED`, `IN_PROGRESS`, `COMPLETED`에서 공개 가능하며 공개 때문에 여행을 완료 상태로 바꿀 필요가 없다. `kind` 생략은 기존 기록 공개로 취급되며 완료 여행 조건이 적용된다. `ARCHIVED` 여행은 수정·공개할 수 없다. 공개 명령은 소유자만 실행할 수 있고, 편집 권한이 있다고 게시 권한까지 있는 것은 아니다.

### 요청 형태

여행 생성은 `Content-Type: application/json`, 실제 계정의 인증, UUID `Idempotency-Key`가 필요하다. 이후 변경은 아래 형식을 쓴다. 중괄호 자리표시는 실제 값으로 치환한다.

```http
POST /api/v1/trips/{tripId}/commands
Authorization: Bearer {실제 세션 토큰}
Content-Type: application/json
Idempotency-Key: {이번 명령의 UUID}
If-Match: "trip:{tripId}:{현재 version}"
```

```json
{
  "operation": "community.publish",
  "input": {
    "title": "여행 원본과 같은 제목",
    "body": "검수한 짧은 공개 소개",
    "kind": "plan",
    "scheduleIds": ["00000000-0000-4000-8000-000000005001"],
    "photoIds": [],
    "includeCosts": false
  }
}
```

위 일정 ID 역시 형식 예시다. 실제 원본에 존재하는 UUID로 바꾼다. 실제 토큰·비밀번호·키를 문서·CSV·검수 로그에 저장하지 않는다.

변경 성공마다 응답의 최신 `tripVersion`을 사용한다. 각기 다른 쓰기에는 새 요청 키를 쓰고, 응답 유실 등으로 **같은 입력을 재시도할 때는 같은 키**를 유지한다. 같은 키로 다른 내용을 보내지 않는다. 버전 충돌409는 최신 원본을 읽고 차이를 확인해 병합한다. `If-Match` 누락은428, 입력 검증 실패는422다.

각 요청은 UTF-8 JSON 전체16KiB 이하이어야 한다. 한국어·이모지의 표시 글자 수와 요청 바이트 수는 다르다. 문자열 길이 상한은 JavaScript UTF-16 단위 기준이며 이모지는 여러 단위일 수 있다. 공개 선택은 최대 일정300개·사진30개지만, 각 상한을 모두 채운 요청이16KiB에 들어간다는 뜻은 아니다. 전체 일정을 긴 `body` 하나에 넣지 말고 DAY·장소별 명령으로 나눈다.

### 이미 공개한 계획 수정

`posts.snapshot`은 개인 여행 원본의 실시간 참조가 아니다. 장소 설명이나 DAY를 수정한 뒤 공개 미리보기를 다시 검수하고, 같은 여행에서 공개 명령을 다시 실행해야 공개본에 반영된다. 같은 여행의 공개는 기존 `postId`를 유지하며 갱신된다. 여행을 새로 만들어 중복 공개하지 않는다.

`schedule.save` 수정 시에는 원본을 읽어 필요한 기존 필드와 합성한다. `memo`, `address`, `timeSlot`은 생략 시 빈 값 기본값이 적용될 수 있고, `googlePlaceId`도 생략 시 해제될 수 있다. 공개 설명만 고치려고 나머지 값을 비우지 않는다. `planContent`, `location`, `durationMinutes`의 생략은 기존 값 보존, 명시적null은 해제다. 예상 비용 생략은 보존, null은 해당 일정에서 만든 예상 비용 해제다.

계획 전체 교체가 아니라 일부 수정이라면 일정 UUID를 유지해 기존 사진·비용 연결을 보존한다. 잘못 공개했을 때는 `community.withdraw`로 공개를 철회할 수 있으며 개인 여행 원본은 유지된다.

## 8. 홈·공개 목록에 보이는 조건

| 화면                          | 현재 연결                                               | 등록 후 확인                                                                             |
| ----------------------------- | ------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 홈 “어디로 떠나볼까요?”       | 공개 피드 첫 페이지를 읽고 선택 도시에서 최대3개 표시   | 게시 성공이 홈 상단 고정을 뜻하지 않음. 최신 글·계정 차단·도시 필터·캐시·API 환경을 확인 |
| 공개 목록                     | `/public/community` 또는 인증된 `/api/v1/community`     | 최신 순20개 페이지. `kind`, 검색·여행 기간 필터가 대상과 일치하는지 확인                 |
| 공개 상세                     | `/public/community/{postId}` → 웹 `/community/{postId}` | 목록 첫20개 밖으로 밀려도 단건 ID로 조회할 수 있음                                       |
| 홈 “N월의 여행지”·도시 가이드 | 별도 `/public/discovery` 데이터                         | 공개 추천 계획을 게시하는 것만으로 여기에 새 도시 가이드가 생기지 않음                   |

현재 게시 명령에는 홈 고정·추천 점수·인기 저장 수를 지정하는 필드가 없다. 홈에는 계획과 기록이 함께 섞일 수 있다. 작성용 태그·대상 여행자·난이도·예산 등의 관리 열을 추가하더라도 현재 자동 검색 필터나 화면 배지로 연결되는 것은 아니다.

## 9. 공개 전 확인표

- [ ] 여행 제목·대표 도시·시간대·기준 기간을 확인했고 DAY 번호와 실제 날짜가 일치한다.
- [ ] 모든 공개 장소에 읽을 수 있는 공개 설명을 작성했다. 개인 `memo`에만 설명을 넣지 않았다.
- [ ] 실제 지점·주소·장소 ID를 확인했으며 운영시간·요금·예약 조건의 출처와 확인일을 남겼다.
- [ ] 이동·체류·식사·휴식이 가능한지 검토했다. 미확인 시간·좌표·금액을 채워 넣지 않았다.
- [ ] 선택·우천 대체 코스를 같은 그룹으로 묶었고 모두 방문해야 하는 순서로 오해되지 않는다.
- [ ] 사진 권리·등록 완료·공개 선택을 확인했다. 영수증·개인 예약·동행 개인정보를 제외했다.
- [ ] 추천 예산을 실제 지출로 만들지 않았다. `includeCosts`의 공개 범위를 확인했다.
- [ ] 운영 계정·환경·원본 UUID·최신 버전·요청 키를 확인했고 중복 여행·공개 글이 없다.
- [ ] 비공개 원본과 공개 JSON·실제 상세 화면을 대조했다. 선택한 모든 장소의 설명과 DAY가 나온다.
- [ ] 홈·목록·단건 상세 노출을 구분해 확인하고 등록·검수 결과를 남겼다.

작성 양식은 UTF-8 CSV이며 한 행이 한 단위다. 날짜·시각·금액·관리 키는 스프레드시트에서 텍스트로 다뤄 자동 변환을 피한다. 여러 줄 설명은 인용부호로 감싼 CSV 셀 또는 JSON의 `\n`으로 보존한다. 비워 둔 선택값을 실제 API의 공백·생략·null 중 무엇으로 보낼지는 위 매핑에 맞춰 등록 담당자가 결정한다.

권장 작성 상태는 `draft`(작성 중) → `review`(검수 중) → `approved`(게시 검토 통과)다. 이는 CSV의 `editorialStatus`이며 여행의 DB 상태와 별개다. 출처의 `verificationStatus`는 `pending`, `verified`, `rejected`로 구분하고 게시 자료에는 검증한 근거를 연결한다. `publish`, `includeCosts`는 `true`·`false`만 작성하고 등록 때 JSON 불리언으로 변환한다. 빈 값이나 문자열 `"false"`를 임의로true로 처리하지 않는다.

## 10. 구현 근거와 이번 산출물 범위

실제 계약은 `packages/validation/src/foundation.ts`, `workspace.ts`, `workspaceModel.ts`, `packages/domain/src/workspace.ts`를 우선한다. D1 물리 구조는 `apps/api/migrations/0001_cloud_storage.sql` 이후 마이그레이션, 변경·공개 처리는 `apps/api/src/cloudStore.ts`, `cloudRpc.ts`, HTTP 경로는 `workspace.ts`와 `app.ts`를 확인했다. 홈·표지는 `HomeExplore.tsx`, 별도 도시 안내는 `discoveryService.ts` 기준이다.

이 문서는 기존 필드를 설명하는 운영 작성 기준이다. DB 테이블·컬럼·런타임 도메인 객체·API·화면을 추가하지 않았으며 자동 CSV 변환기·관리자 게시 도구도 구현하지 않았다. 실제 자료 작성과 계정·환경 확인 뒤 등록 작업은 별도로 진행한다.
