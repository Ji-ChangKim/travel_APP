TripPrint 고객 여행 기록 완주 점검·개선 요청
기준일: 2026-10-16 / 고객 요구: 항공권·일정·여행 계획·영수증·경비 요약·커뮤니티·개인 여행기록
상태: 로컬 보완·기획 독립 재검수 통과. 후속 실제 staging 검사19개 중14개 통과·5개 실패로 빌드 HOLD. 최신 API·DB·R2·AI 결과: STAGING_CUSTOMER_JOURNEY.txt. 아래 로컬 결과와 구분한다.

1. 고객이 끝내려는 일

이미 다녀온 여행 하나에 항공권, 다녀온 장소·시간·메모, 사진·영수증과 실제 지출을 모은다. 경비를 확인한 뒤 원하는 내용만 커뮤니티에 공개하고, 전체 원본은 내 여행기록에서 다시 읽고 수정한다.
고객이 나열한 일곱 항목은 기능의 완주 범위다. 입력 순서를 강제하지 않는다. 저장할 여행지·기간을 한 번 정한 뒤 항공권·일정·영수증을 원하는 순서로 추가한다.
커뮤니티 공개는 선택이며 공개하지 않아도 개인 기록은 완성된다. 원본 보존과 공개 선택을 분리하고, 공개를 철회해도 개인 기록을 지우지 않는다.
검수 시나리오: 고객이 앱에 접속해 여행을 만들고 일곱 기능을 사용하는 흐름. 사용자에게 실제 여행 정보를 추가 요청하지 않는다. 새 계획과 다녀온 여행 기록을 격리된 검수용 데이터로 확인하며 고객의 실제 자료와 구분한다.

2. 현재 흐름과 확인한 문제

① 항공권 입력 / P0 / 클라이언트 우선, 서버 계약 함께 확인
근거: FlightTicketEditor.tsx의 완료는 selected가 있을 때만 활성화된다. selected는 조회 후보 선택으로만 생성하며 조회 실패·0건에 직접 입력 동작이 없다. 같은 앱의 FlightLookup.tsx에는 수동 입력이 있어 두 화면이 다르다.
고객 영향: 지난 여행·해외 출발편·항공사 미검색·공급자 실패·조회0건에서 가지고 있는 항공권을 입력할 수 없다. 여행을 먼저 건너뛰고 일정 안에서 다시 항공편을 입력해야 한다.
추가 근거: 기존 항공권 브라우저 테스트가 직접 입력 버튼0개를 기대한다. 과거 테스트 기대도 고객 요구에 맞게 바꿔야 한다.
요청 CJ-01: 항공권 입력 화면에도 ‘항공권 직접 입력’을 제공한다. 조회 실패·0건에서도 선택 가능하며 항공편 번호·출도착 공항·현지 출도착 날짜/시각을 기존 검증으로 확인한다. 알 수 없는 정보는 만들지 않는다. 조회→수동 전환·뒤로·목록 수정 시 입력과 다른 항공편을 보존하고 중복 등록하지 않는다.
서버: 기존 flights 배열·DAY 연결·자정 넘는 도착일·중복/멱등·권한 계약을 사용한다. 현재 공급자의 과거·해외 조회 범위는 실제 응답으로 확인하고 지원 범위를 UI에 정확히 연결한다. 과거 조회가 항상 불가능하다고 단정하지 않는다.
완료 조건: 조회가0건/503인 지난 여행에서도 수동 왕복 항공권을 입력·저장·재실행 후 같은 여행의 날짜에 확인한다.

② 일정 입력 / P0 운영 조건·P1 UX / 클라이언트·서버
현재: DAY별 직접 제목·메모·주소·지도 위치, 추천 코스와 수동 검색 경로가 있다. 저장·이탈·중복 보호는 유지한다.
확인: 직전 지도 검수에서 staging Places 키 미등록을 확인했다. 화면 연결·빈 지도 생성은 로컬에서 보완했으나 실제 Google 검색·타일 동작은 미확인.
요청 CJ-02: 기록할 DAY에서 장소를 직접 입력하거나 검색해 저장하고, 지도 서비스 실패에도 제목·메모·사진 기록을 계속한다. 여행 완료 날짜라는 이유로 기록 추가를 막지 않는다. 지도 키와 Places 서버 키의 실제 설정을 확인한다.
완료 조건: DAY2에 기록한 일정이 DAY1로 옮겨지지 않고 앱 재실행·직접 링크에서도 유지된다. 잘못된 장소나 좌표를 자동 생성하지 않는다.

③ 여행 계획 추가·연결 / P1 / 클라이언트
현재: 새 여행 생성은 여행지·기간→항공편의 두 단계이며 과거 날짜를 스키마에서 거부하지 않는다. UI는 ‘여행 계획 만들기’, ‘어디로, 언제 떠날까요?’ 등 출발 전 표현을 사용한다.
확인: 발자국 빈 화면은 ‘여행 계획하러 가기’만 제공한다. 이미 다녀온 여행을 추가하려는 고객에게 기록 시작 경로가 불명확하다.
요청 CJ-03: 발자국/내 여행에서 ‘다녀온 여행 기록하기’를 찾을 수 있게 하고 동일 여행 생성·편집 계약으로 연결한다. 지난 날짜를 입력하면 기록에 맞는 문구와 추가 행동을 보여준다. 별도 여행 복제나 날짜에 따른 공개 자동 실행은 금지한다.
완료 조건: 과거 기간 여행을 생성하고 같은 여행 ID·DAY를 유지한 채 항공권·일정·영수증을 순서와 무관하게 추가한다.

④ 영수증 촬영 / P0 실제 공급자 확인·P1 연결 UX / 클라이언트·서버
현재: 시스템 카메라/앨범→업로드·인식→확인/수정→일정과 실제 지출 연결. 인식 실패 시 직접 입력, 합계 차이·미지원 통화 확인과 사진 보관 선택이 있다.
서버 인식: receiptAnalysis.ts의 AI 바인딩이 우선, ocr.ts의 Vision은 호환 경로다. Vision 키가 반드시 필요한 구조라고 해석하지 않는다. 실제 staging 인식·R2 업로드·권한은 별도 확인해야 한다.
요청 CJ-04: 실제 일본어 영수증에서 결제일이 DAY2/3으로 연결되는지 확인한다. 기존 일정에 연결하면 일정이 중복되지 않고 영수증 한 장은 실제 지출 하나만 만든다. 취소·재시도·응답 유실·사진 미보관에서 원본과 금액을 잃지 않는다.
완료 조건: 회원의 실제 인식 성공 증거와 수동 복구 증거를 구분한다. 사진과 후보만으로 지출을 확정하지 않는다.

⑤ 여행 경비 요약 / P1 / 클라이언트·서버
현재: 비용 허브와 다이어리에서 실제/예상·통화별 합계를 제공한다. 원화·엔화·달러를 환율 없이 분리한다.
요청 CJ-05: 여행 전체 실제 지출을 먼저 보여 주고 통화·날짜별 상세로 이어지게 한다. 영수증 수정/삭제 후 요약·다이어리·공개 미리보기를 같은 원본으로 갱신한다. 예상 지출과 실제 지출을 이중 합산하지 않는다. 원화 환산은 별도 환율 계약 없이 추가하지 않는다.
완료 조건: 직접 지출1000 KRW+영수증2500 JPY+예상500 JPY에서 실제는1000 KRW/2500 JPY, 예상은500 JPY. 재시도에도 합계가 늘지 않는다.

⑥ 커뮤니티 노출 / P0 완료 상태 연결·P1 발견성 / 클라이언트·서버
확인: 날짜상 완료 여행도 저장 status가 PLANNED면 WorkspaceScreen.tsx의 공개 버튼이 비활성이고 publication.ts가 거부한다. 기록 정리 완료는 여행 더보기→정보/기록 정리 안에 있어 공개 화면만으로 다음 행동을 찾기 어렵다.
요청 CJ-06: ‘기록 정리 마치기’의 명시적 행동과 공개 선택 화면을 연결한다. 날짜 상태와 공개 준비 조건의 차이를 고객이 추측하지 않게 한다. 기록 정리 완료는 고객 확인으로만 저장하고 날짜로 자동 게시하지 않는다. 소유자만 일정·일반 사진·비용 공개 여부를 선택하고 미리보기→게시→공개 피드 재조회로 이어진다.
완료 조건: 지난 여행을 처음 만든 고객이 설정 메뉴를 헤매지 않고 정리 완료·선택 공개를 끝낸다. 영수증 원본·카드/예약 정보·비공개 메모는 공개 응답에서 제외한다. 공개 실패 시 개인 기록은 유지한다.

⑦ 내 여행기록 남기기 / P0 보존·P1 동선 / 클라이언트·서버
현재: 날짜가 지난 여행을 발자국/다이어리에서 읽을 수 있고 ‘여행 기록 관리’로 상세에 돌아가 수정한다. 원본 status=COMPLETED만 공개 선택에 연결한다.
요청 CJ-07: 저장 후 ‘내 기록 보기’와 ‘기록 더 추가’를 제공한다. 공개 여부와 관계없이 항공권·일정·사진·영수증·실제 지출이 같은 여행에서 보존되는지 확인한다. 다시 로그인/앱 재실행/공개 철회 후에도 남아 있어야 한다. 게스트의 기기 보관과 회원 보관 차이는 쉽게 안내한다.
완료 조건: 게시 없이 종료한 경우와 게시/철회한 경우 모두 비공개 원본이 유지되고 타인 계정은 원본을 읽을 수 없다.

3. 우선순위와 담당

P0 먼저: CJ-01 수동 항공권 막힘 → CJ-02 실제 지도/검색 설정·직접 입력 복구 → CJ-04 실제 OCR·중복 지출 검증 → CJ-06 공개 전 정리 완료 연결 → CJ-07 보존·공개 경계 확인.
P1 이어서: CJ-03 과거 기록 시작 경로 → CJ-05 실제 경비 요약·수정 반영 → 나머지 입력·복귀·문구·큰 글꼴.
클라이언트/서버 채팅이 기능·API 보완을 맡고, UI/UX 채팅의 공통 헤더 작업은 보존한다. 이 기획 채팅은 고객 시나리오·화면 증거·인수 조건과 요청/응답을 관리한다.

수동 항공권·영수증 수정/삭제·선택 공개/철회의 신규 공통 모델3/3을 기획에서 독립 실행했다(outputs/customer-journey/customer-model-review.log). 사진 미보관 영수증의 수정 오류는 담당이 보완했고, 수정 시 원본 보관 선택·영수증/지출 ID 유지와 기존 일정 명시 선택으로 중복 장소 생성을 막고 있다.
빌드 입력 정적 확인: 현재8/0.1.0, Play 프로필 AAB·배포store·공개staging 주소, Android 지도 키 형식·release:check 통과. 로그 outputs/customer-journey/release-config-check.log. 현재 수정 중 소스500개를 preparation-source.json으로 기록했으며 승인/고정 후보가 아닌 임시 준비 스냅샷이다.
범위 구분: 코드·계약·설정·검수표까지 빌드 전 준비하고, 새 Play 설치본의 실제 카메라·지도 타일·OS 동작은 이후 내부 테스트에서 별도 인수한다. USB 연결을 이번 준비 조건으로 요구하지 않는다. 실제 공급자 미검수와 키 미등록·배포 API 미대응은 각각 구분한다.

[담당의 배포 환경 확인]
클라이언트/서버 담당의 읽기 전용 확인 결과: staging은 새 receipt.update 미배포, 항공 조회 키·조회 제한 바인딩·Places 키 미등록. 해당 상세 증거는 담당 구현 기록에서 확인한다. 원격 기능 동작을 로컬 테스트로 대신 승인하지 않는다.
항공권은 직접 입력으로 기록할 수 있게 보완하되 실조회 지원과 구분한다. 새 영수증 수정은 API 반영이 필요하다. 실제 카메라·지도 타일·OCR·기기/계정 보존은 이후 Play 내부 테스트에서 별도 확인한다.

6. 최종 고객 관점 재검수 / 로컬 코드 인수

항공권: 조회0건/503에서도 직접 입력. 왕복·추가편과 슬롯별 초안·현지 도착일을 저장·재조회했다.
일정: 같은 여행/DAY에 제목·시간·메모를 추가하고 저장 실패 후 재시도해도 중복되지 않았다.
여행 생성·계획: 고객이 여행지·기간을 지정한 원본을 항공권·일정·영수증·기록에서 그대로 사용했다. 다녀온 여행의 기록 진입을 추가했다.
영수증: 확인 전 지출 없음, 확인 후 일정/지출 연결. 사진 보관/미보관 모두 같은 영수증·지출 ID로 수정·삭제를 검증했다. 미보관 원본을 재조회하지 않는 복구와 기존 일정 명시 연결을 확인했다.
경비: 사용한 통화의 실제 지출을 먼저 표시하고 예상 비용은 선택해 펼친다. 수정/삭제가 요약·다이어리에 반영되며 서로 다른 통화는 합산하지 않는다.
커뮤니티: 명시적 기록 정리 완료→공개 항목 선택→게시→피드 재조회. 영수증 원본과 비공개 메모는 제외했다. 날짜만으로 상태 변경/자동 게시하지 않았다.
내 기록: 같은 여행의 항공권·일정·영수증·지출을 기록에서 재조회. 기록 추가/경비 복귀를 제공하고 공개 철회가 비공개 원본을 지우지 않는 계약을 확인했다.

담당 최종 검사 로그 직접 확인: npm run check 전체 통과(scratch/customer-journey-check-final.log), 모델/인증203/203(scratch/customer-journey-model-final.log), 고객 관련 Chrome22/22(scratch/customer-journey-browser-final.log), 격리 D1/R2 통합17/17(scratch/customer-journey-cloud.log), 릴리스48/48(scratch/customer-journey-release.log). 중간 회귀4건의 낡은 문구/날짜/이동 기대는 현행 계약으로 보완한 뒤 통과했다.
기획 독립 재검수: 한 여행의 일곱 기능 완주+수동 항공권+영수증 수정 true/false+지도 검색10/10 통과(outputs/customer-journey/customer-final-browser.log). 담당22개와 겹치는 범위이므로 합쳐32개라고 집계하지 않는다.
앱·공유 모델·자산·빌드 입력500개 파일의 검사 전후 SHA-256 일치. sourceSha256=cbb78cc7fd368b850c982417aea5e8a1d6d8e141ee55e339fa34b6531af5a10f. 근거: review-source-before.json/review-source-after.json/final-source-changes.json. 전체 서버 배포본이 같은 해시라는 뜻은 아니다.
390px 최종 비용 화면을 직접 확인했다. 사용 통화 JPY와 실제 금액을 먼저 보여 주고 영수증 삭제 뒤 남은 직접 지출1500.00이 한 카드로 표시됐다. 초기0원 통화·예상 비용 카드가 실제 내역을 밀던 문제는 개선됐다.

7. 빌드 인계와 남은 조건

판정: 로컬 고객 흐름 코드 인수 통과 / 운영 조건 HOLD. ‘기획 채팅 완료’는 빌드·배포 승인과 같지 않다. 클라이언트/서버 담당에도 이 판단을 전달했다.
현재8/0.1.0을 유지한다. Android 공개 프로필은 staging 주소이며 고객 검수용8816/fixture 값이 들어 있지 않음을 확인했다. 검수 출력·scratch·환경 파일·서명 키는 기존 EAS 제외 규칙으로 보호한다.
필수 운영 보완: staging의 receipt.update 지원 반영, KAC_FLIGHT_SERVICE_KEY·FLIGHT_LOOKUP_LIMITER·GOOGLE_PLACES_API_KEY 등록, Android 키의 Play 앱 서명/API 제한 확인, Play 최대 versionCode·서명·앱/API 후보 대응 확인. 실제 공급자와 Play 설치본 인수는 별도로 미검수 상태를 유지한다.
준비 기록: outputs/customer-journey/build-preparation.json. 로컬 설정·소스·검수·미충족 조건을 분리했다. AAB/APK 생성·업로드·원격 배포·커밋·푸시는 이 기획 채팅에서 실행하지 않았다.

이번 기획 채팅의 변경 파일
- docs/qa/CUSTOMER_JOURNEY_REVIEW.txt: 고객 목표·일곱 기능의 문제/인수 조건·CJ 요청/응답·검수 근거·판정.
- docs/qa/DEVICE_ACCEPTANCE.txt: 일곱 기능 완주, 비공개 보관, 공개 철회, 항공 조회 실패 복구, 영수증 수정/집계의 실제 내부 테스트 항목. 현재 버전8 반영.
- docs/PLAY_INTERNAL_PREBUILD.txt: 준비 완료로 오해하던 제목/상태와 현재 버전을 정리하고 고객 게이트·운영 조건/기기 인수 시점 분리.
- docs/CURRENT_STATUS.txt: 현재 고객 흐름 우선순위·담당 보완·로컬 인수와 운영 보류 구분.
- docs/README.md: 현행 고객 점검 문서 연결.
- outputs/customer-journey/*: 격리 웹 검수 설정·로그·스크린샷·소스 해시·빌드 준비 JSON. Git/EAS 제외 경로이며 배포 입력이 아니다.
앱/API/모델 수정 파일과 상세 구현은 클라이언트/서버 담당의 CUSTOMER_JOURNEY_IMPLEMENTATION.txt 및 DB_DICTIONARY.txt에서 관리한다.

추가 빌드 입력 확인: design-tokens.json·루트/모바일 eas.json·.easignore·GitHub 내부 테스트 workflow5개는 별도 SHA-256을 기록했다(supplemental-build-inputs.json). 각 파일의 수정 시각은 최종 검수 시작 이전이며 500개 소스 대조와 구분한다. 실제 빌드 승인 시에는 이 입력과 배포 API를 함께 다시 고정한다.
담당은 기획 인수 결과와 운영 HOLD를 수용했고, 채팅 종료만으로 AAB 생성에 진입하지 않도록 기존 후속 자동화 조건도 보완했다. 이 기획 채팅은 원격 배포나 빌드를 실행하지 않았다.
