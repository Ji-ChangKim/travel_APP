TripPrint 실제 staging QA 로그인·등록 계약 확인
기준일: 2026-10-16 / Asia/Seoul
범위: 기획 담당의 실제 서버 검증을 위한 기존 로그인 도구·가입·정리 계약 확인. 이 확인 작업에서는 계정 생성·원격 데이터 쓰기·배포·키 변경·Android 빌드를 실행하지 않음.

1. 기존 QA 로그인 정보·도구
확인한 scripts와 .env.release/.env.mvp/apps/api/.dev.vars에는 QA 로그인 설정이 없음. 환경 파일은 설정 이름만 검사했고 값은 출력하지 않음. 기존 검수 계정 비밀번호·토큰은 확인하거나 재사용하지 않음.
앱의 실제 로그인 구현: apps/mobile/src/services/cloudAuth.ts. emailSession은 /api/auth/sign-up/email 또는 /api/auth/sign-in/email에 요청하고, 응답의 set-auth-token 헤더를 사용함. JSON body.token을 대체 토큰으로 사용하지 않음.
tests/cloud/runtime.test.mjs의 request/signup은 로컬 Miniflare 검사 도구임. 실제 staging 검증기로 그대로 실행하거나 fixture-signed-session/고정 테스트 비밀번호를 실제 환경에 재사용하지 않음.

2. 정상 가입 계약
기획 채팅의 최신 사용자 요청은 실제 서버 통신·데이터 등록·저장 검사임. 필요한 격리 QA 계정의 정상 가입은 이 검증 경로에 해당함. 현재 담당이 생성하므로 다른 채팅에서 중복 생성하지 않음.
대상 API: https://tripprint-api-staging.gametps.workers.dev
Origin: https://tripprint-staging.pages.dev
POST /api/auth/sign-up/email, Content-Type: application/json, body: {name,email,password}.
새 QA 전용 고유 이메일과 2~20byte 고유 닉네임 사용. 비밀번호는 실행 프로세스에서 보안 난수로 생성해 메모리에만 보관하고 명령 인수·출력·리포트에 넣지 않음.
현재 로컬 cloudAuth 설정은 이메일/비밀번호 인증을 활성화하고 최소8자를 요구하며, 이메일 확인 필수/발송 함수는 설정하지 않음. 실제 배포본의 가입 성공 여부는 HTTP 응답과 후속 세션 조회로 판단. 설정을 읽었다는 이유로 원격 가입 성공으로 기록하지 않음.
가입 성공 시 user.id와 set-auth-token 헤더의 존재를 확인. 토큰 원문은 기록하지 않고 Authorization: Bearer 헤더로만 사용.
POST /api/auth/sign-in/email로 재로그인, GET /api/auth/get-session 및 /api/v1/profile로 계정 일치 확인. 재로그인 검증을 해야 하므로 같은 프로세스가 비밀번호를 메모리에 유지.

3. 실제 저장 확인
POST /api/v1/trips: 논리 요청당 UUID Idempotency-Key 사용.
POST /api/v1/trips/{QA_TRIP_ID}/commands: 동일 요청 키와 If-Match: "trip:{QA_TRIP_ID}:{현재 version}" 사용. 응답 유실 재시도는 같은 본문·키·버전을 유지.
생성/수정 응답만으로 저장 완료를 판단하지 말고 새 HTTP GET으로 workspace를 재조회. 로그아웃/재로그인 뒤 동일 여행 ID·DAY·일정·영수증·실제 지출을 확인.
기록 가능한 증거: HTTP 상태, 공개 오류 코드, requestId, 이번 실행의 QA user/trip/media/receipt ID, 버전, 건수, 금액, 동일 ID 재조회 판정. 비밀번호·토큰·전체 세션/요청 헤더·원본 개인 데이터는 기록하지 않음.
실제 receipt.update·항공/Places/OCR/R2 지원 여부는 해당 배포본의 응답으로 분리. 미지원이면 기존 고객 원본이나 임의 DB 수정으로 성공시킨 것으로 기록하지 않음.

4. 정리 범위와 제한
현재 공개 명령에는 community.withdraw, receipt.delete, expense.delete, schedule.delete, media.delete가 있음. 삭제 순서와 참조 제약을 지켜 이번 QA ID만 정리. 원본 파일 삭제는 별도 파일 API 결과도 확인.
영수증 삭제는 지출을 함께 제거하지만 장소 일정과 보관 사진은 남음. 별도 항목 정리가 필요함. 미보관 원본의 경우 확정 단계에서 이미 제거되었을 수 있으므로 실제 잔존 여부를 구분.
POST /api/auth/sign-out으로 이번 세션을 철회하되, 재로그인 보존 검사 뒤에 실행.
공개 API에는 여행 전체 삭제 경로가 없고 현재 cloudAuth에 user.deleteUser 활성화 설정도 없음. 따라서 항목 정리·로그아웃만으로 QA 계정/빈 여행/멱등·업로드 메타데이터까지 삭제 완료라고 쓰지 않음.
전체 정리가 필요하면 생성 시 기록한 정확한 QA ID와 소유권을 대조해 별도 관리 작업 범위를 정함. 기존 계정·다른 여행을 이름 접두사나 전체 테이블 조건으로 정리하지 않음. 미정리 QA 계정/여행 ID와 사유를 인수 기록에 남김.

6. staging 갱신 준비 항목 — 실행 전 단계
현재 판정: 실제 기본 저장·R2·AI 연결은 일부 확인했지만 고객의 일곱 기능 전체 완주는 실패. 빌드/배포 준비 HOLD 유지. 자동 확인을 재개하지 않음.
① 승인 소스의 API·공유 검증/모델·Worker 설정·필수 DB 열/마이그레이션 대응을 고정. 모바일500파일 해시만으로 서버 전체 배포 입력 일치를 주장하지 않음.
② onboardingCompleted/선택 birthDate, schedule.save.flight, receipt.update, flights/lookup, 공개 app-config를 포함하는 현행 계약을 staging 갱신 후보에 포함. 계약을 맞추려고 앱 필드를 버리거나 영수증 수정을 새 지출로 바꾸지 않음.
③ KAC_FLIGHT_SERVICE_KEY·FLIGHT_LOOKUP_LIMITER·GOOGLE_PLACES_API_KEY의 현재 원격 등록 상태와 필요한 API 활성화를 확인. AI/DB/MEDIA는 이번 실제 성공 근거가 있으나 새로운 배포 후보에서도 바인딩을 유지해야 함. 키 원문은 공유·로그에 넣지 않음.
④ API 후보의 로컬 품질/HTTP/D1-R2 검사, 실제 배포 차이와 롤백 대상을 검토. 원격 배포·키 등록은 승인된 실행 범위에서 별도 진행. 이번 요청으로는 실행하지 않음.
⑤ 갱신 후 동일 고객 조건으로 실패 항목5개와 세분화 복원·중복/권한·공개 철회/개인 보존을 다시 검사. 온보딩이나 항공권 저장을 우회한 REST 성공을 전체 앱 완주로 판정하지 않음.
⑥ 기존 Play 지도 키 제한·실제 설치본 카메라/지도/OS 인수 조건은 별도로 유지. 실제 서비스 성공과 Android 빌드/기기 검수는 다른 단계임.
이 추가 기록은 실제 결과 반영과 갱신 준비 목록이다. 서버 코드·DB·키·Android 빌드·배포 상태를 변경하지 않음.
