## 착수 근거와 범위

‘기획’ 채팅 `01a13a9d-44d9-7733-b519-4b02c7f99b4b`의 여행 생성·편집·공유 작업이 completed/idle인 것을 확인했다. 해당 보고의 275건 통과는 인계 자료이며 이번 검수 결과와 합산하지 않는다. 현재 작업 폴더에는 여러 작업의 미커밋 변경이 있다. 이를 보존하고 현재 소스를 검사한다.

`ver.text`는 versionCode=11, versionName=0.1.0이다. 과거 Ver09 문서보다 현재 설정을 우선한다. Play에서 11번 사용 여부와 배포 여부는 확인하지 않았다. Android 빌드·서명·업로드·원격 배포·커밋·푸시는 실행하지 않는다.

완성 기준은 영수증 등록 → 인식 결과 확인·수정 → 일정·실제 지출 연결 → 저장·새 조회 → 필요한 항목만 공개하는 흐름이다. 부가 기능은 후속 업데이트로 분리한다.

## 소스 대조

### 영수증·DB·서버

- `receiptFlow.ts`는 결제 날짜와 일치하는 DAY만 선택한다. 날짜를 읽지 못하면 첫날을 임의로 넣지 않는다.
- `ReceiptConfirmation.tsx`는 정보 확인, 합계 차이 동의, 원본 보관 선택을 분리한다.
- `workspaceModel.ts`의 receipt.confirm은 같은 원본 또는 같은 영수증 ID의 재등록을 막고, 일정·영수증·실제 지출 변경을 함께 구성한다. 기존 일정 연결 시 일정 내용을 덮어쓰지 않는다.
- receipt.update는 기존 영수증 ID·원본 보관 선택을 유지한다. 날짜를 바꾸면 그 날짜의 일정 재선택이 필요하다.
- `cloudStore.ts`는 여행 버전 조건과 요청 키를 사용해 D1에 변경을 저장한다. 사진 미보관 시 업로드 참조와 OCR 캐시를 정리한다. `cloudRpc.ts`는 DB 확정 뒤 원본을 지우고 같은 요청 키 재시도에서도 삭제를 이어간다.
- `ocr.ts`는 여행 권한·원본 목적을 검사한 뒤 캐시 또는 공급자를 호출한다. 조회 전용 동행은 인식 요청을 실행할 수 없다. 인식 실패는 수동 입력 또는 재시도로 복구한다.
- `receiptAnalysis.ts`는 인식 후보를 스키마로 검증하고 사용자가 확인하기 전 지출로 확정하지 않는다. 인식 성능·실제 공급자 성공률은 로컬 모델 검사로 입증되지 않는다.
- `docs/DB_DICTIONARY.txt`에는 과거 Supabase 테이블과 현재 D1 스냅샷 모델이 함께 있다. 실제 저장 경로는 `docs/planning/V11_DATA_FLOW.md`의 D1 경로와 대조해야 한다. 이번 단계에서 DB나 객체 구조는 변경하지 않았다.

### UI/UX

참조 문서: `docs/design/DESIGN.md`, `design-tokens.json`, `SCREEN_HEADER_SPEC.md`, `PAGE_FUNCTION_SPEC.txt`, `docs/1.uiux/ITINERARY_SCHEDULE_SCREEN_SPEC.md`.

공통 제목 26/36, 좌우 20, 최소 터치 48, 큰 글꼴에서 자연스러운 확장 규칙을 기준으로 검사했다. 21건의 헤더·GNB 검사와 새 캡처를 확인했다. `outputs/header-standard/receipt-capture-390-100.png`와 `receipt-capture-320-200.png`는 이번 실행에서 생성한 파일이다. 390에서는 촬영·앨범 선택과 사진 전송 안내가 보이며, 320·200%에서는 제목과 본문이 줄바꿈되고 긴 내용은 스크롤로 이어진다. 영수증 화면의 색상은 DESIGN.md에 명시된 범위 예외인 `ledger-tokens.json`을 따른다. 공통 헤더·GNB는 수정하지 않았다. 영수증 확인·원본 보기의 모든 시각 상태와 Android 시스템 글꼴·카메라 인수까지 완료한 것은 아니다.

### 운영 준비

현재 `apps/api/wrangler.jsonc`의 staging은 D1/R2/AI 바인딩을 명시하지만 production에는 해당 연결과 인증 주소·허용 출처가 준비돼 있지 않다. 운영 리소스와 도메인을 정하지 않고 staging 값을 복사하지 않는다. 이는 저장소 설정의 확인 결과이며 원격 환경의 실제 상태를 조회한 결과는 아니다.

실제 OCR, Google 로그인·지도·카메라 권한 복귀, 새 Play 설치본, 개인정보처리방침·삭제 요청 경로, 운영 비용 한도는 별도 출시 인수가 필요하다. 기존 기능 문서의 G11·G12 미확정 항목도 유지한다.

## 출시 후 30일 1만 다운로드 계획

목표 기준은 Google Play 공개 출시일부터 30일간 신규 설치 10,000건이다. 30일 단순 평균은 하루 약 334건이며 확보된 유입 예측이 아니다. 재설치·업데이트를 신규 설치와 섞지 않는다.

1. 출시 전: 영수증 한 장이 일정·지출로 남는 실제 화면 시연과 스토어 이미지·설명을 준비한다. 지원 통화와 사진 공개 범위를 실제 기능대로 알린다.
2. 출시 1주차: 유입 경로별 스토어 방문·설치·첫 여행·첫 영수증 확정 비율을 측정해 가장 많이 이탈하는 단계를 보완한다.
3. 2주차: 사용자 동의를 받은 사례로 영수증 등록 과정을 설명하고, 측정 결과에 따라 소개 문구와 온보딩을 조정한다.
4. 3~4주차: 첫 기록 성공과 재사용이 확인된 유입 경로에 집중한다. 광고 예산과 외부 게시·발송은 별도 결정하며 자동 집행하지 않는다.

측정 설계는 첫 실행 → 여행 생성 → 영수증 업로드 → 인식 성공/실패 → 확인 저장 → 7일 내 재사용이다. 이벤트에 원본 사진·상호·품목·주소·금액·인증값을 넣지 않는다. 이벤트 수집 구현 여부와 동의 정책은 아직 검수하지 않았으므로 수집 완료로 표현하지 않는다. 스토어 전환율을 가정하면 필요한 방문 수는 10,000 ÷ 전환율이며, 예산·실제 전환율 없이 유입 달성을 보장하지 않는다.
