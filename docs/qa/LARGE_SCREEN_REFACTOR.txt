TripPrint 큰 화면 역할 분리·회원 저장 검수
기준일:2026-10-19 / 기존 UI·UX 유지 / Android 빌드 없음

1. 작업 범위
프로필·발견·항공권·기록 상세/편집·일정 작성·위치 선택·여행 생성·타임라인·영수증 확인·공개 선택·여행 상세·시작 점검의 큰 화면 함수를 역할별로 나눴다.
DB 구조·API 입력·인증 운영값·공개 사본·기존 여행 ID·DAY ID·동행 권한은 바꾸지 않는다. 회원 검수에는 기존 전용 QA 계정과 이번 검수 여행만 사용한다.

2. 역할과 파일
표현:*View.tsx, WorkspaceSections.tsx, WorkspaceDialogs.tsx. 영역별 입력·상태·행동을 같은 배치로 표시한다.
상태:useMyAccountController/useDiscoveryController/useFlightTicketController/useScheduleLocationController/useRecordEditorController와 기존 useWorkspaceController.
요청 수명:workspaceSaveSession/Commands/FormActions/MediaActions/ChecklistActions, recordPersistence, profileEditorActions/LogoutActions. 렌더 수명에 묶인 행동 훅으로 구성한다.
시작:useStartupController와 useStartupLifecycle. 공통 데이터 캐시·스토어 복귀·최종 목적지 이동의 순서와 구독 해제를 유지한다.
명령:workspaceScreenActions. 화면에 있던20개 이벤트의 명령 본문·초안 생성·금액 정리·삭제 후 파일 정리를 기능 계층으로 옮겼다.
기록 투영:recordDetails. 해당 일정의 일반 사진과 지출을 같은 원본에서 계산한다.
스타일:myAccountStyles.ts와 tripTimelineStyles.ts. 기존 값을 그대로 옮겼다. 기존 공통/Ledger 토큰은 유지한다.
기록의 저장·삭제는 여전히 기존 명령과 잠금·버전·요청 키로 실행한다. 파일로 나눴다는 이유로 새 저장 경로나 자동 저장을 추가하지 않았다.

3. 분리하면서 보완한 계약
일정/추천 코스 초안은 클릭할 때 한 번 생성해 같은 UUID와 DAY를 사용한다. 렌더링과 미리보기 선택 자체는 저장이 아니다.
편집 화면의 충돌 복구 버튼은 error.includes('동행') 대신 실제 충돌 상태를 받는다. 화면 표시 값은 state로 관리하고 요청 잠금·재시도 참조와 구분한다.
이미 확정된 사진 등록 삭제 이후에만 기존 후속 콜백으로 원본 파일을 정리한다. 저장 후 재조회 실패와 저장 실패를 구분하는 기존 경계를 유지한다.
사용자·여행·계정 정보는 모듈 전역에 캐시하지 않는다. 기존 계정/화면 종료 후 늦은 결과 보호와 조회 취소 정책을 유지한다.

4. UI 기준과 비교
DESIGN.md, design-tokens.json, SCREEN_HEADER_SPEC.md, ledger-tokens.json, STITCH_CURRENT_INTEGRATION.txt를 읽고 대조했다.
코드의 화면 태그·문구·고정 라벨·스타일 표현1452개는 분리 전후 차이0건이다. 이것만으로 실제 화면 인수를 완료했다고 판단하지 않는다.
실제 회원 화면의 분리 전 MY·프로필 캡처를 보존했다. 최신 웹의 캡처·저장·재조회·공개 확인 결과는 아래에 확정한다.

주소: https://tripprint-staging.pages.dev

회원 실검수: 기존 이메일 검수 회원으로 화면을 조작하고, 별도 로그인 세션으로 서버 원본을 재조회했다. 인증 값과 서명된 파일 URL은 보고서·증거 파일에 남기지 않았다.

- 오사카 2026-10-01~04 여행을 생성했다. 항공권 KE721 / ICN→KIX / 09:00→11:00을 수동 등록했고, DAY 4개와 완료 상태를 확인했다. 항공편 공급자 조회 성공을 검증한 것은 아니다.
