## 운영 원칙과 역할

기존 PRD를 제품 의도의 기준으로 유지하고 세부 문서를 요구사항 ID로 연결한다. 코드와 다르면 결정 목록에 기록하며, 구현되어 있다는 이유로 제품 정책을 확정하지 않는다.

| 역할      | 책임                                           |
| --------- | ---------------------------------------------- |
| 제품 오너 | 대상 사용자·MVP·우선순위·정책 결정, 인수 승인  |
| 기획      | 요구사항 ID·흐름·예외·완료 기준·결정 이력 관리 |
| 디자인    | 화면 상태·흐름·접근성·디자인 시스템 관리       |
| 개발      | 기술 타당성·DB/API 계약·구현·검사·영향 기록    |
| QA        | 기능·권한·재접속·실기기 검증과 증거 관리       |

한 사람이 여러 역할을 수행할 수 있다. 실제 담당자와 일정은 미정이다.

## 문서 형식과 변경 관리

상세 명세는 버전·날짜·상태(초안/확정)·담당 역할·관련 요구사항 ID를 둔다.

- 화면: ID/라우트 → 목표 → 데이터 → 액션 → 저장 결과 → 상태/오류/권한 → 인수 기준.
- 결정: ID → 질문/대안 → 채택안/이유 → 확정자/날짜 → 영향 ID/문서 → 재검토 조건.
- API: ID → method/path → 인증/권한 → 검증 → 응답/에러 → 저장 결과 → 재시도/중복 처리.
- QA: ID → 환경/빌드/계정 → 사전 조건 → 절차 → 기대/실제 결과 → 증거 → 판정/결함.

요구사항 상태는 `초안 → 확정 → 구현 중 → 검증 대기 → 인수 완료`다. 목업·메모리 동작은 구현 메모이며 인수 증거가 아니다.

변경 시 ID·이유·화면/DB/API/검증 영향·범위 변경 여부를 기록하고, 오너 결정 후 관련 문서를 함께 갱신한다. DB/도메인 수정에는 DB 사전 갱신을 포함한다. 착수 시 요구사항·정책·의존성을 확인하고 종료 시 검사·인수 증거·잔여 문제를 기록한다.

총 진행률은 확정 요구사항의 분모와 인수 증거를 확보한 뒤 산출한다. 화면 개수로 추정하지 않는다.
