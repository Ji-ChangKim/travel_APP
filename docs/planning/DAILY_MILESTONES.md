## 1. 일정 산정 전제

2026-10-02 추가 요청인 [발자취 콘텐츠](TRAIL_CONTENT_SPEC.md)는 기기 초안 기능으로 선행 구현했다. 영수증 OCR·자동 항공 조회·서버 동기화는 기존 40일 계획의 완료로 간주하지 않으며 공급자/접근 준비와 별도 작업량 산정이 필요하다.

| 항목         | 가정                                                                                                  |
| ------------ | ----------------------------------------------------------------------------------------------------- |
| 투입         | 개발자 1인 전일제, 하루 8시간, 개발/검증 6시간 + 설계/문서/조정 2시간                                 |
| 제품·QA 역할 | 개발자가 기획 보완·QA를 겸임. 제품 오너는 결정/인수 때 참여하며 가용 여부 확인 필요                   |
| 착수         | 10/02는 현재 기획 준비일. 개발 업무 Day01은 10/06부터                                                 |
| 작업일       | 월~금, 주말·대한민국 공휴일 제외. 개인 휴가·회사 휴무는 아직 미반영                                   |
| 공휴일       | 10/05 개천절 대체공휴일, 10/09 한글날 제외                                                            |
| 대상         | Android/iOS 앱·초대용 웹은 Day01에 실제 지원 범위 확정. 웹 플래너·공개 여행은 별도                    |
| 범위         | MVP-01~10 및 기본 프로필/직접 장소 등록. Realtime·GPS·OCR·사진/후기·Today는 P1                        |
| 외부 준비    | Auth 제공자 콘솔/콜백·Supabase 테스트 환경·지도 공급자/키·실기기/EAS 접근 준비를 Day01~03에 요청·확인 |

| 추정 신뢰도  | 실제 DB·OAuth·실기기 연결이 아직 검증되지 않아 초기 추정. Day03/08/13에 재산정                        |

공휴일 근거는 [한국천문연구원 2026년 월력요항 발표](https://www.kasi.re.kr/kor/post/newsMaterial/32031)다. 10/06~12/08 사이의 평일에서 10/09를 제외해 45영업일을 계산했다. 10/05는 착수 전 공휴일이라 업무일에 포함하지 않았다.

40일은 약 320시간(개발/검증 240시간 + 설계/기록 80시간), 예비는 40시간이다. 주말 작업·야근을 전제로 압축하지 않는다. 하루 4시간만 투입되면 시간 기준 80+10영업일 수준으로 재산정하며 날짜를 그대로 유지하지 않는다.

## 2. 매일 반복하는 업무 프로세스

| 시간 예시   | 업무                                                             | 종료 산출물                           |
| ----------- | ---------------------------------------------------------------- | ------------------------------------- |
| 09:00~10:00 | 전일 결과·차단 항목 확인, 당일 요구사항/정책/설계·인수 기준 확인 | 오늘의 작업 카드와 완료 목표          |
| 10:00~12:00 | 서버/DB 또는 앱의 선행 작업, 작은 단위로 구현                    | 하나의 검토 가능한 변경               |
| 13:00~16:00 | 화면→API→DB→다시 조회 흐름 연결                                  | 당일 사용자 시나리오 실행 가능한 상태 |
| 16:00~17:00 | 변경 관련 QA·타입/lint/format·재접속·실패 확인                   | 실제 검사 결과·증거·결함              |
| 17:00~18:00 | DB 사전/명세·상태 기록, 다음날 의존성·잔여 문제 정리             | 일일 기록과 다음 작업                 |

시간은 운영 예시다. 당일 목표는 화면 개수보다 재현 가능한 사용자 결과 1개를 우선한다. 선행 결정이 없으면 의존 작업을 완료로 처리하지 않고 독립적인 검증/문서/테스트 환경 준비를 진행한다.

코드 변경일에는 `npm run check`를 통과시킨다. 실제 스키마/객체 변경은 같은 작업에서 DB 사전과 계약을 갱신한다. 커밋을 수행할 때는 `타이틀 : 설명` 규칙을 따른다.

## 5. 의존성과 외부 준비 기한

핵심 경로는 **정책/접근 → DB·Auth·권한/원자 쓰기 → 여행 보존 → 일정 → 장소/지도 → 비용/체크 → 초대·동행 → QA → 인수**다. 지도 키·OAuth·실기기는 코드보다 늦게 준비되면 해당 단계의 일정을 직접 지연시킨다.

| 준비/결정                             | 요청·확인 목표                    | 실제 사용 전 기한            | 미준비 영향                                                  |
| ------------------------------------- | --------------------------------- | ---------------------------- | ------------------------------------------------------------ |
| 제품 범위·핵심 D-01~15                | Day01~03                          | 해당 DB/API 구현 전          | 계약/스키마 재작업, M0 이후 날짜 재산정                      |
| Supabase 테스트 환경·테스트 계정 권한 | Day01 요청, Day03 확인            | Day04                        | M1 및 이후 핵심 경로 차단                                    |
| 로그인 제공자 설정·콜백/앱 식별       | Day01 요청, Day03 상태 확인       | Day09                        | M2 차단. 실제 제공자 성공 검증을 임의 계정으로 대체하지 않음 |

담당자는 제품 오너/개발 역할로 기재하며 실제 계정 권한 보유자의 이름·응답일은 착수 때 기록한다. 외부 준비 대기는 개발 공수가 줄어드는 것이 아니라 달력상 지연 요인이다.

## 6. 지연·범위 변경 대응

1. 매일 차단 사유·영향 요구사항·필요한 결정/외부 준비·예상 해소일을 기록한다.
2. 당일 목표가 하루 이상 밀리면 다음 단계 중 독립 가능한 QA/문서/환경 작업을 앞당기되 선행 기능 완료로 가장하지 않는다.
3. 마일스톤 검토 시 남은 작업을 실제 가용시간으로 재추정하고 M8/R 날짜를 다시 계산한다. 예비 사용량을 따로 누적한다.
4. 추가 제공자·게스트 생성/이전·오프라인 쓰기·Realtime·공개 웹이 요청되면 신규 공수와 영향 문서를 기록한 뒤 기준선을 변경한다.
5. 일정 단축이 필요하면 제품 오너와 실제 제공자/지원 플랫폼 등의 명시적 범위를 조정한다. 권한·원자 저장·재접속·핵심 QA를 생략해 날짜를 맞추지 않는다.
6. 외부 계정/키 지연·스토어 심사 기간은 고정 5일로 해결된다고 가정하지 않는다. Day45에도 차단이면 새 일정을 제시한다.

**재산정 시점:** Day03(정책/접근), Day08(DB/API 실측), Day13(인증 실측), 이후 매 마일스톤. 1인 개발에서 별도 병렬 개발 인력을 가정하지 않는다. 인력이 늘면 독립 API/UI 작업을 분리하되 공통 계약·통합 QA 시간은 유지한다.

## 7. 실제 진행 기록 양식

날짜 표는 계획 기준선이다. 모든 행은 아직 미착수이며 실제 시작/완료로 자동 전환하지 않는다. 다음 형식을 일일 기록에 사용한다.

## 8. 이번 계획 작성 범위

45개 업무일의 날짜·업무·산출물·검증, 9개 마일스톤과 예비, 일일 프로세스·외부 의존·지연 대응·기록 양식을 작성했다. 기존 상세 기획 문서 안내·프로세스와 진행 보고서에 이 계획을 연결한다. 기능 구현·배포·정책 승인 결과는 이 일정 작성으로 변경되지 않는다.
