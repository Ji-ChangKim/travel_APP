TripPrint 1차 MVP 후보 — 메인 자동 슬라이드·배포 준비·성능 확인
기준일: 2026-10-12 (한국 시간)
후보 버전: 0.1.0 / mvp-0.1.0-internal-candidate-20261012
대상: Google Play 내부 테스트. 원격 배포·AAB 업로드·실기기 인수 완료와 구분한다.

1. 이번 마무리 범위

- 메인의 이달 추천을 한 장씩 자동으로 넘기는 사진 슬라이드로 변경했다.
  기본 간격은 4.5초이며 세 번째 카드 다음에는 첫 카드로 순환한다.
  현재 위치 표시, 일시정지/재생, 이전/다음 버튼, 직접 가로 넘김을 제공한다.
- 사진·소개·출처·월별 편집 선정과 실제 문서 조회 통계는 앞선 공개 API 구현을 유지한다.
  광고·가짜 게시물·가짜 여행객 순위·새 유료 공급자를 추가하지 않았다.
- 터치 중에는 멈추고 터치가 끝난 뒤 최소 8초의 유예를 둔다.
  마우스가 카드 위에 있으면 멈추며 키보드로 카드·이전/다음에 초점을 두면 명시적 재생 전까지 멈춘다.
- 도시 상세·다른 경로·앱 백그라운드에서는 자동 예약을 취소한다.
  동작 줄이기 또는 네이티브 화면 읽기 기능이 켜져 있으면 자동 이동을 하지 않는다.
  웹은 화면 읽기 활성 여부를 감지할 수 없어 동작 줄이기·초점 정지·명시적 조작을 사용한다.
- 카드 세 장을 재사용하고 자동 이동 때문에 API를 다시 호출하지 않는다.
  크기 변경은 선택한 카드를 유지하며 새 너비가 적용된 뒤 스크롤을 맞춘다.
- 탐색 → 도시 상세 → 같은 목적지 여행 계획 → 로그인/기기 게스트 흐름을 유지한다.

4. 성능 검사 방법 및 결과

실행: 먼저 일반 릴리스 웹을 빌드하고 실제 공개 응답을 읽은 뒤
node scripts/measure-mvp-performance.mjs

측정 도구는 프로젝트의 기존 Playwright·Chrome 및 Chrome DevTools Protocol이다.
새 계정·원격 여행·게시물은 만들지 않는다. 공개 도시 응답은 실제로 읽어 저장한 파일을 재현한다.
따라서 홈 준비 시간은 원격 여행지 API의 최초 공급자 조회 시간을 포함하지 않는다.
사진은 실제 Wikimedia 호스트에서 읽는다. 공개 피드도 배포된 staging에서 실제 응답을 읽어 재현한다.
public-community-capture.json에 조회 시각과 공개 응답을 보관한다. 계정·세션은 만들지 않는다.
첫 실험에서는 localhost 출처의 원격 피드 요청이 CORS 정책에 막혀 오류 화면이 나타났다.
해당 결과를 error-fallback-baseline.json으로 별도 보존했고, 최종 측정에서는 정상 공개 피드 재현을 확인한다.

일반 PC와 CPU 4배 지연·왕복 150ms·다운로드 1.6Mbps/업로드 750Kbps 조건을 각각 세 번 측정한다.
공개 커뮤니티 첫 진입의 FCP/LCP와 이후 홈 탭 준비 시간을 분리한다.
자동 이동 15초의 프레임 간격, 12회 수동 전환·상세 열기/닫기의 메모리와 입력 응답을 기록한다.
입력 지연은 실험 표본이며 실사용 INP가 아니다. 전체 관찰 구간 긴 작업 합계는 Lighthouse TBT가 아니다.
정적 로컬 서버는 압축 없이 제공하므로 실제 CDN 압축·캐시 결과와도 구분한다.

판정:
- 세 장의 자동 순환과 사진을 준비한 이후의 프레임 간격은 안정적이었다.
  반복 이동에 따른 여행지 API 추가 호출은 없었다. 짧은 구간의 힙 증가가 약 0.5~0.6MiB였으며
  이 수치만으로 장시간 메모리 누수가 없다고 판정하지 않는다.
- 제한 환경의 첫 로드·사진 준비·입력 응답은 개선 대상이다. 전체 앱 성능 합격으로 처리하지 않는다.
  같은 출처의 큰 자산으로 웹 JS 2,263,332바이트, 로딩 안내 PNG 1,163,240바이트,
  빈 상태 PNG 1,793,767바이트, Ionicons 폰트 389,724바이트가 관측되었다.
  제한 환경 첫 실행에서 JS 다운로드 약 11.7초, 두 안내 PNG 약 18.1/21.2초가 관측되었다.
  큰 초기 자산과 CPU 처리 지연은 후속 최적화 후보이며, 이 자료만으로 각 자산의 절감 효과를 단정하지 않는다.
- 로컬 서버는 압축 없는 웹을 제공한다. 실제 Pages CDN의 압축·캐시 및 Android의 기기 내 번들과 구분한다.
  원격 배포 후 캐시 없는/있는 상태의 초기 로드, 공개 API 캐시 미스/히트, 사진 준비를 재측정한다.
- 첫 진입의 LCP 기록에는 이후 홈 사진 전체 준비가 포함되지 않는다. LCP·실험 입력 수치로
  서비스 전체 Web Vitals 또는 실사용 INP 합격을 선언하지 않는다.
- Android 콜드 시작·프레임·메모리·배터리·장시간 동작 및 서버 동시 사용자 부하는 이번 측정 범위 밖이다.

desktop-home.png와 mobile-emulation-home.png는 실제 공개 응답과 Wikimedia 사진을 사용한 메인 화면이다.
정상 공개 데이터 재현으로 측정한 최종 결과와 오류 화면 기준 error-fallback-baseline.json을 혼합하지 않는다.

5. Play 내부 테스트 배포 순서

1) 앞선 0006_unique_nicknames.sql과 새 API를 staging에 적용한다.
   공개 /public/discovery가 실제 도시 소개를 반환하는지 확인한 뒤 같은 후보의 웹을 배포한다.
   Worker는 release:prepare로 생성한 apps/api/.release/wrangler.json의 검증된 공개 설정을 사용한다.
   원본 기본 staging 템플릿의 빈 Google 식별값으로 기존 로그인 설정을 덮어쓰지 않는다.
2) 이번 작업을 포함한 소스로 GitHub Android Play Internal의 AAB를 빌드한다.
   artifact_type=aab, submit_play=false로 다운로드 후 Play Console에 직접 올릴 수 있다.
   자동 제출은 별도 서비스 계정 자격이 있는 경우에만 사용한다.
3) 기존 Play 업로드 키와 같은 서명을 사용하고 현재 최고값보다 큰 versionCode를 확인한다.
   업로드 서명 Secrets 4개와 Play 권한은 이 로컬 검사로 확인하지 않았다.
4) 내부 테스트에 AAB를 등록하고 테스터 Google 계정·참여 링크로 새 설치/업데이트를 확인한다.
5) 실제 Google 동의→앱 복귀→회원 설정·재로그인, 기기 게스트 오프라인 저장,
   여행 생성/수정·영수증·커뮤니티 게시/철회·다른 계정 비공개 접근 거부를 실기기에서 인수한다.
6) 동일한 설치 빌드로 아래 성능 인수를 수행하고 문제가 없을 때 내부 테스트 후보를 확정한다.

현재 로컬 환경에서 adb/Android SDK 경로를 확인하지 못했다. Android Studio JBR 25는 있으나 JDK 17 구성은 미확인이다.
Hermes export는 설치 가능한 AAB가 아니며 실기기 시작·프레임·메모리 합격으로 판정하지 않는다.
실기기 인수: 보급형/주 사용 기기 각각 콜드 시작 10회, 홈 3분 자동 순환,
20회 수동 넘김·상세 왕복, 탭 이동·백그라운드 왕복 10회, 오프라인 로컬 저장 및 재실행.
adb shell am start -W 또는 Perfetto로 시작/프레임을 측정하고 메모리 추이를 기록한다.
출발 목표는 콜드 시작 5초 미만·700ms 이상 멈춤 없음이며 실제 수치를 기록해 인수한다.
브라우저의 프레임 간격 측정을 Android 네이티브 프레임 렌더링 수치로 옮기지 않는다.

계정 복구·탈퇴/삭제와 Google 저장 목록 직접 동기화 등 기존 미완료 범위는
PLAY_INTERNAL_READINESS_20261012.txt에 남아 있으며 이번 변경으로 완료 처리하지 않는다.
실제 한국인 방문객 순위 API는 인증키/활용 승인 후 별도 범위다.
