## 2. 앱 기본 구조와 계정 관리

로그인 직후에는 생일·성별·소개·여행 스타일을 입력받지 않는다. 기본 이름은 ‘여행자’이며 실제 확인한 이용 방식만 표시한다. 과거 `/profile-setup` 주소도 추가 입력 없이 허용된 원래 목적지로 돌아간다. Google 회원이 나중에 MY에서 닉네임·사진을 고르는 행동은 시작 과정의 필수 입력과 구분한다.

홈은 TripPrint 브랜드 헤더, 내 여행·커뮤니티·MY는 공통 제목 헤더를 사용한다. `/footprints`와 `/community`는 같은 커뮤니티 화면과 검색 구성을 사용한다. 하단 GNB는 홈 → 내 여행 → 커뮤니티 → MY의 기존 4탭을 유지한다.

계정 관리는 본인 정보 → 삭제 사전 확인 → 필요한 소유권 이전 → 삭제 내용 확인 → 명시적 요청 순서다. 조회 실패 때 삭제 버튼을 열지 않고 재시도를 제공한다. 신규 삭제는 90일 복구 유예를 안내하지 않는다. 늦게 도착한 이전 계정의 응답을 새 계정에 적용하지 않으며, 게스트 자료는 로그인만으로 자동 전송하지 않는다.

기본 화면의 상세 구현·로컬 실제 서버 검수는 [앱 기본 구조 구현 검수](<../../03. 개발/04. 검증/앱기본구조_구현검수.md>)에 있다. 실제 약관·개인정보 페이지와 게시 주소는 후속 작업으로 남았다.

## 3. MY 닉네임·프로필 사진

Google 회원은 MY에서 닉네임 변경 → 입력 → 중복 확인 → 저장 순서로 바꾼다. 저장 후 홈·MY와 서버 재조회에서 같은 값을 확인한다. 게스트에는 Google 로그인 안내를 제공하고 변경 API도 서버에서 권한을 검사한다.

| 닉네임 항목    | 확정 기준                                                                                                     |
| -------------- | ------------------------------------------------------------------------------------------------------------- |
| 문자           | 영어·숫자·한글·일본어 히라가나·가타카나와 일본어 장음 `ー`. 한자·이모지·특수문자 거부                         |
| 길이           | NFC 정규화 후 1~10자. 중간 공백도 글자 수에 포함                                                              |
| 공백           | 앞뒤 공백·공백만·탭·줄바꿈 거부. 문자 사이 ASCII 공백은 총 2개까지 허용. 자동으로 잘라 저장하지 않음          |
| 중복           | NFC + 소문자 비교. `A가나다`와 `a가나다`는 동일. 중간 공백 수는 보존                                          |
| 변경 간격      | 마지막 성공 저장 후 정확히 30일, 2,592,000,000ms. 달력 월 기준이 아님                                         |
| 최초·같은 값   | 최초 선택은 즉시 가능. 완전히 같은 값은 변경 시각·기회를 갱신하지 않음                                        |
| 기본 이름      | 미설정 ‘여행자’는 공용 표시이며 예약이 아님. 직접 선택한 이름만 고유 예약                                     |
| 동시 요청·실패 | 사전 중복 확인은 예약이 아님. 저장 시 고유 제약·30일 조건 재검사. 실패를 성공 처리하거나 기회를 차감하지 않음 |

`"a b c"`와 `"a  b"`는 허용한다. `" asd"`, `"asd "`, `" asd "`, `"a b c d"`는 거부한다. 예시의 따옴표는 공백 위치를 구분하기 위한 표시다. 아직 30일이 지나지 않으면 변경 버튼을 잠그고 다음 변경 시각을 보여준다. 통신 실패·응답 유실은 현재 프로필을 다시 조회해 확인하도록 안내한다.

| 개선 전                                                                       | 개선 후                                                                                    |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| MY의 기본 프로필은 읽기 전용이어서 회원이 표시 이름과 사진을 선택할 수 없었음 | Google 회원이 MY에서 선택적으로 닉네임·사진 변경. 시작할 때는 추가 입력 없이 이용          |
| 사용자가 바꾼 닉네임이 인증 정보 갱신 때 기본 ‘여행자’로 덮어써질 수 있었음   | 공급자 이름 갱신을 제외하고 사용자가 선택한 이름을 보존. 같은 조건에서 저장·재조회 검사    |
| 닉네임 변경 간격과 중복을 화면 안내만으로 처리할 수 없었음                    | 서버에서 마지막 변경 후 30일과 대소문자 무시 고유 예약을 함께 확인하고 다음 변경 시각 표시 |

사진은 앨범 선택 또는 촬영으로 언제든 교체하며 닉네임의 30일 제한을 적용하지 않는다. 앱에서 긴 변 최대 1,024px의 실제 PNG로 변환하고 서버가 PNG·10MiB 상한을 검사해 불필요한 메타데이터를 제거한다. 취소하면 기존 사진을 유지한다.

- 버킷: `tripprint-staging-private`, Worker 바인딩 `MEDIA`.
- 객체 키: `User/profile/pfImg_{유저ID}.png`. 같은 회원이면 같은 키를 덮어써 현재 객체 한 개를 유지한다.
- 조회: 인증한 본인의 현재 사진만 제공하며 `no-store`와 ETag 버전을 사용한다. 공개 R2 주소를 만들지 않는다.
- 상태: R2 현재 객체가 사진의 기준이다. 과거 `profile_photos`에 새 파일 행을 만들지 않는다. 회원 전환 뒤 늦은 응답·미리보기를 새 회원 화면에 적용하지 않는다.
- 정리: 과거 개인정보 정리에서 새 선택 닉네임·사진은 보존하며 계정 삭제·고아 파일 정리는 새 경로도 처리한다.

닉네임은 `0016_member_profile_names.sql`의 고유 예약 테이블에 저장한다. 예약·`user.name`·기존 게시물 작성자·참여 여행 표시 이름 갱신은 D1 배치 한 트랜잭션으로 확정한다. 인증 정보 갱신이 선택 이름을 ‘여행자’로 덮어쓰던 문제도 재현·수정했다. 공급자 이름·사진을 새로 수집하는 기능은 추가하지 않았다.

세부 계약은 [MY 프로필 변경 규격](<../../02. 디자인/01. 화면설계/MY_프로필변경_규격.md>), [앱·서버 API 계약](<../../03. 개발/01. API계약/앱서버_API계약.md>), [DB·객체 사전](<../../03. 개발/02. 데이터정의/DB_객체사전.txt>)을 따른다.

## 4. 여행 일정 화면

현재 여행 상세는 공통 헤더의 여행 제목·더보기 → 여행 요약 → 일정/가계부 → DAY 선택 → 항공권 추가·동선 지도 → 일차별 타임라인 → 하단 중앙 장소 추가 순서다. 지도·사진·영수증·준비물·동행·여행 공유는 더보기에서 연다.

| 영역      | 반영한 동작                                                                                                                                        |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 여행 요약 | 여행 제목, 여행 기간과 박수, 동행 정보. 동일 연도는 `11.27~11.30 (3박 4일)`, 연도 변경은 `26.12.30~27.01.02 (3박 4일)`, 날짜 미정은 예정 일수 표시 |
| DAY 선택  | 날짜를 반복 표시하지 않고 DAY 번호로 선택                                                                                                          |
| 항공권    | DAY 아래 ‘항공권 추가’와 빈 일정의 항공편 입력 진입. 장소 추가 → 이동 → 항공편 등록 경로도 유지                                                    |
| 지도·거리 | 선택 DAY의 번호 핀·연결선. 네이티브 지도와 웹 SVG 동선 도식을 구분. 인접 좌표의 거리는 직선 거리이며 실제 길찾기 거리로 표시하지 않음              |
| 타임라인  | 장소 상세·접기/펼치기·관리·길찾기, 일차 제목·소개, 기록 배지 연결                                                                                  |
| 순서 편집 | 일차의 편집/완료 모드에서 삭제·위/아래 이동. 변경 순서와 동선 표시 연결                                                                            |
| 중앙 추가 | 원형 `+`의 접근성 이름은 ‘장소 추가’. 눌림·잠금 색상과 아이콘 전경을 공통 토큰으로 보완                                                            |

장소 검색·상세와 항공편 조회·수동 입력, `schedule.save` 등 저장 명령의 연결을 정리했다. 영수증 진입은 사진·영수증 영역과 지원하는 작성 경로에서 확인한다. 코드 연결·검수 자료를 쓴 회귀 통과를 실제 Google 검색·실제 항공 공급자·카메라·OCR·서버 등록 전체의 통과로 확대하지 않는다.

당일 개별 보고서의 초기 ‘지출’ 표기는 최종 ‘가계부’로 맞췄다. 초기에는 없던 직접 항공권 추가 진입이 후속 작업에 포함됐으므로 최종 구조를 기준으로 합쳤다. 화면 규격은 [여행 일정 화면 규격](<../../02. 디자인/01. 화면설계/여행일정_화면규격.md>)에서 관리한다.

## 8. Git 반영 결과

사용자가 반영 범위를 ‘Git 커밋·푸시까지’로 선택했다. 커밋 메시지는 `타이틀 : 설명` 규칙을 따랐으며 기존 사용자 수정·흐름 이미지 3개도 보존했다. 환경 변수·키·로컬 `outputs/`는 커밋에서 제외했다.

- 커밋: `c470064e128c0735814fe5f7798b3e6b7c96ebd6`, 109개 파일 변경.
- 메시지: `feat: 앱 기본 구조·MY 프로필 변경·여행 일정 개편 통합 : 추가 입력 없는 시작과 계정 관리, 닉네임 중복·30일 제한과 고정 PNG 교체, 일정·가계부 및 헤더 회귀 22개와 기능·검수 문서 반영`.
- 원격: `origin/main`에 푸시 후 같은 SHA를 확인했다. 당시 로컬·원격 차이 0/0, 작업 폴더 변경 없음.
- [GitHub CI 실행](https://github.com/Ji-ChangKim/travel_APP/actions/runs/42572759823)은 푸시 직후 확인 당시 진행 중이었다. 이번 문서 통합에서 CI 결과를 새로 조회하거나 통과로 판정하지 않았다.
- 웹·API 배포와 Play 내부 배포는 별도 수동 작업이다. Git 반영을 서버 배포·원격 DB 적용으로 표시하지 않는다.

이전 개별 보고서의 ‘커밋·푸시 미실행’은 Git 요청 전의 기록이다. 이 절은 뒤에 완료한 Git 반영 결과이며, 이번 보고서 통합 편집 자체의 재커밋·재푸시를 의미하지 않는다.

## 9. 홈 정보 구성 검토안

홈은 여행을 시작하고 기존 여행·기록을 이어가는 화면으로 제안했다. 레퍼런스의 인사말·원형 도시·빠른 실행 구성을 참고하되 TripPrint 공통 헤더·하단 4탭은 유지한다. 아래 내용은 검토안이며 새 홈 레이아웃 구현 완료가 아니다.

| 순서 | 정보·행동                                            | 필요한 데이터                                              |
| ---- | ---------------------------------------------------- | ---------------------------------------------------------- |
| 1    | 닉네임 인사·D-Day·여행 일차                          | 프로필 이름, 여행 날짜·상태                                |
| 2    | 진행 중 또는 가장 가까운 예정 여행 한 개·이어서 열기 | 여행 ID·도시·제목·기간·작성 상태                           |
| 3    | 검색·도시 원형 바로가기                              | 도시 ID·이름·국가·대표 이미지                              |
| 4    | 새 여행·영수증 등록·가계부·준비물                    | 대상 여행·실제 연결 화면. 저장·재조회 검수된 기능부터 노출 |
| 5    | 다른 여행자의 공개 일정·방문 기록                    | 공개 게시물 ID·유형·도시·기간·대표 이미지                  |

여행이 없으면 도시 탐색·새 여행, 여행 전에는 계획 이어보기, 여행 중에는 오늘 일정·영수증 등록, 여행 후에는 기록 정리·공유를 우선하는 안이다. 기존 도시·여행·공개 목록 자료를 활용할 수 있으나 오늘 일정·영수증 상태의 홈 연결은 별도 검수가 필요하다. ‘인기’·‘NEW’는 집계·등록일 근거를 갖춘 뒤 사용한다. 실시간 날씨·환율은 이번 기본안에 추가하지 않는다.

| 영수증           | 촬영·업로드 → OCR → 사용자 확인 → 기존 방문 연결/새 실제 방문 → 저장·재조회 | 실기기·실제 OCR·전체 저장 흐름 미검증         |
| 프로필 원격 반영 | 대상 DB·백업 확인 → 0016 마이그레이션 → API → 앱 → 실제 R2 교체·재조회      | 원격 미적용                                   |
| 설치본           | Android·iOS 로그인·카메라 권한·촬영·안전 영역·큰 글꼴·재실행                | 미실행                                        |
| 홈               | 구성안 확정 → 데이터·이동 연결 → 실제 화면 대조                             | 제안 단계                                     |

복구 시 새 닉네임 테이블·R2 객체를 즉시 삭제하지 않는다. 자료를 보존한 채 이전 개인정보 정리 코드가 새 선택 자료를 지우지 않는지 확인한다. 운영 변경·삭제는 해당 대상과 승인 범위에서 별도로 실행한다.

모든 버튼·API의 정상·빈 상태·오류·처리 중 조건을 나누고, 저장 직후 표시뿐 아니라 재진입·재조회까지 확인한다. 게스트·보기 전용·다른 계정·오프라인·중복 요청·버전 충돌도 기능에 필요한 범위로 선정한다. 전체 과거 여행 편집 웹 검사 묶음은 이번 보고서 통합에서 실행하지 않았다. 전체 수용 기준은 [핵심 사용자 사이클 검수](<../../03. 개발/04. 검증/핵심_사용자사이클_검수.md>)에 있다.

## 12. 일일 보고서 문서 사이트

사용자의 추가 지시에 따라 날짜·요일별 작업과 개선 결과를 읽고 일지를 작성하는 [HTML 문서 사이트](../index.html)를 제작했다. 진입 파일은 같은 보고서 루트의 `index.html`이다. 기존 여행 앱 화면과 분리했으며 앱의 헤더·GNB·API·DB는 변경하지 않았다.

| 개선 전                                                                                    | 개선 후                                                                                            |
| ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| Markdown 보고서를 파일별로 열어야 해서 날짜·요일별 작업과 개선 내용을 한눈에 보기 어려웠음 | 주간 달력·등록 일지 목록에서 날짜를 선택하고 작업 요약·개선 전후·전체 문서·검증·후속 작업으로 탐색 |
| 문서 파일을 직접 편집해야 새 작업을 남길 수 있었음                                         | 일지 등록 창과 브라우저 보관, 수정·삭제, Markdown 내려받기·JSON 백업/가져오기·인쇄 제공            |

원본이 있는 2026-11-09 월요일만 초기 등록 자료로 사용한다. 다른 날짜는 기록 없음으로 표시한다. 직접 작성한 일지는 이 브라우저에만 저장하고, 다른 기기로 옮기려면 백업·가져오기를 사용한다. 서버 저장·자동 저장소 반영으로 표시하지 않는다. 원본 문서에서 온 일지는 화면에서 덮어쓰지 않는다.

`npm run reports:build`는 날짜별 원본 Markdown과 공통 토큰·템플릿으로 HTML 한 파일을 생성한다. `npm run reports:preview`는 보고서·필요한 글꼴만 허용한 로컬 미리보기를 연다. 원본이 바뀌면 다시 생성하며 생성 HTML은 직접 편집하지 않는다. 화면 규격은 [일일 보고서 사이트 규격](<../../02. 디자인/01. 화면설계/일일보고서_사이트규격.md>)을 따른다.

생성·미리보기 도구는 `scripts/design/build-daily-reports.mjs`, `daily-report-markdown.mjs`, `preview-daily-reports.mjs`다. 템플릿·스타일·동작은 `docs/02. 디자인/02. 리소스/00. 일일보고서사이트/`에, 브라우저 검수 도구는 `scripts/qa/verify-daily-reports.mjs`에 있다. HTML·가져온 내용은 실행하지 않도록 이스케이프하고 파일 형식·날짜·문자열·크기를 검사한다. 잘못된 가져오기와 저장 실패는 기존 기록을 유지한다.

`npm run test:reports:web`로 파일 직접 열기·월요일/주간 이동·검색과 빈 결과·등록 후 새로고침·수정/삭제·백업/가져오기·HTML 실행 차단·320/390/768/1440px·글자 200%·인쇄를 확인했다. 저장이 실패할 때는 성공으로 처리하지 않고 입력·기존 기록을 보존하는 것도 확인했다. 브라우저 오류는 0개다. 최종 검수 결과는 `outputs/daily-report-site/results.json`과 `browser-final3.log`, 실제 캡처는 같은 폴더에 있다.

공통 토큰·LINE Seed를 기준으로 데스크톱 요약·개선 전후·전체 원문, 작은 화면과 큰 글꼴의 메뉴·작성 창을 실제 캡처와 대조했다. 브라우저의 기본 대화창 최대 폭이 큰 글꼴에서 더 좁아지는 부분은 뷰포트 기준 최대 폭으로 보완했다. 숨김이나 글자 축소로 넘침을 피하지 않았다. 최종 폭 보완 후 브라우저 검수와 전체 필수 검사 `npm run check`가 모두 통과했다(`outputs/daily-report-site/check-final3.log`, 종료 코드 0). 외부 서비스 게시·운영 배포·추가 커밋·푸시는 이번 사이트 제작 범위에 포함하지 않는다.

## 13. 작업 완료 후 누적 기록과 저장 위치

사용자가 작업이 끝날 때마다 날짜·요일별 작업 내용, 개선 전후, 검수 결과와 남은 작업을 이 사이트에 누적하도록 요청했다. `AGENTS.md`와 문서 관리 규칙에 완료 절차를 기록했다. 같은 날에는 원본 한 개에 이어 쓰며, 새 날짜에는 그날 파일을 만들고 HTML을 다시 생성한다. 생성본만 직접 편집하거나 브라우저의 임시 보관 기록으로 공식 파일 기록을 대신하지 않는다.

| 개선 전                                                                   | 개선 후                                                                                                               |
| ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 사이트 제작 후 작업 기록을 언제·어디에 누적할지 고정된 완료 절차가 없었음 | 한국 시간 날짜별 원본 누적 → HTML 생성 → 날짜·요일·작업·개선·검수·후속 반영 확인 → 완료 보고를 프로젝트 규칙으로 관리 |

사이트 파일은 `docs/998. 일일 업무 보고서/index.html`, 날짜별 공식 원본은 `docs/998. 일일 업무 보고서/YY.MM.DD/일일_통합_작업보고서.md`다. 화면의 등록 창으로 직접 작성한 일지는 이와 별개로 현재 브라우저의 `tripprint.daily-journal.v1`에 보관된다. `file://` 페이지와 로컬 미리보기 주소도 서로 다른 브라우저 저장 공간을 사용한다. 브라우저 기록을 파일로 보관하려면 백업 버튼으로 JSON을 내려받는다.

일지가 늘어도 브라우저 검수가 특정 항목 수·이미 등록된 날짜 때문에 실패하지 않도록 검수 자료의 개수와 미등록 날짜를 현재 자료에서 정한다. 이번 변경은 기록 관리·검수 도구에 한정하며 여행 앱 기능은 변경하지 않는다. 실제 새 세션에서 규칙을 읽는 동작까지 검증한 것으로 보고하지 않는다.

누적 기록 갱신 후 `npm run test:reports:web`는 날짜 탐색·저장/재조회·수정/삭제·백업/가져오기·큰 글꼴·인쇄를 통과했다(`outputs/daily-report-site/accumulation-browser.log`). 이번 검수 도구의 ESLint는 오류·경고 0건, 문서 검사는 7개 검사와 문서 45개·링크 205개 오류 없음으로 통과했다. 변경 문서·HTML·검수 도구의 서식도 통과했다. 이전에 보고됐던 `WorkspaceExpenseView.tsx`의 `TripIcon` import 경로와 `runningIndex` 재할당 오류 2건도 이어진 가계부 개편 작업에서 모두 해결해 전체 `npm run check`가 오류 0건으로 통과한다.

## 16. 페이지별 TC 체크 차트 추가

- 기록일: 2026-11-09 월요일, 한국 시간 기준.
- 목적: 앱 페이지마다 무엇을 검사할지 정하고, 개발 완료·Android Studio 에뮬레이터·내부 빌드 실기기의 결과를 따로 남긴다.
- 범위: 일일 보고서 사이트의 ‘페이지별 TC’, TC 정의·결과 파일, 생성 도구와 웹 검수 도구. 앱 화면·공통 헤더·GNB·DB·API와 운영 배포는 이번 변경 대상에 포함하지 않는다.

| 개선 전                                                                               | 개선 후                                                                                                         |
| ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 검사 결과가 보고서 본문에 흩어져 페이지별 확인과 실기기 검수 여부를 구분하기 어려웠다 | 18개 페이지·64개 TC를 한 차트로 모으고 개발·에뮬레이터·실기기의 성공·실패·미검증을 각각 집계한다                |

앱 실행, 로그인, 기본 프로필, 홈, 내 여행, 커뮤니티, 공개 여행 상세, MY, 설정, 계정 관리, 여행 만들기, 여행 일정, 장소 추가, 영수증 등록, 가계부, 준비물, 동행, 공유를 다룬다. 게스트 서버 저장·재조회는 미구현 후속 과제로 명시하고 기기 저장으로 통과를 대신하지 않는다. 장소 검색과 영수증 OCR은 실제 공급자·저장·재조회 검수를 요구한다.

한 단계에서 성공과 실패를 동시에 체크할 수 없다. 선택한 체크를 해제하면 미검증으로 돌아간다. 개발 성공을 체크해도 나머지 두 단계는 바뀌지 않는다. 세 단계 모두 성공일 때만 해당 TC를 전체 성공으로 집계한다. 체크는 검수자의 수동 기록이며 앱 테스트를 자동 실행하지 않는다. 최초 파일에는 판정을 넣지 않았다.

페이지별 진행 현황을 펼쳐 영역별 수치를 확인하고, 페이지·TC 검색·결과 상태로 항목을 좁힌다. ‘기준·메모’에서 사전 조건 → 조작 순서 → 기대 결과를 읽고 실제 검사 후 결과와 증거를 남긴다. 저장 실패 때는 안내를 읽고 저장 공간을 확인한 뒤 다시 시도한다. 기존 파일 결과를 가져올 때는 같은 TC·단계가 바뀌는 범위를 확인하고 적용한다.

사용 순서는 ‘페이지별 TC’ → 페이지 선택 → ‘현재 디자인 추가’ → 이미지 종류·제목·파일·버전·메모 입력 → ‘디자인 저장’이다. 저장 뒤 같은 페이지를 다시 열어 이미지와 설명을 확인한다. 전체 페이지 선택 상태에서는 개별 페이지를 먼저 고르도록 안내한다. 이미지가 없으면 등록 안내를 보여준다. 디자인을 등록해도 TC 판정은 자동으로 바뀌지 않는다.

PNG·JPEG·WebP 한 장을 페이지마다 등록한다. 한 장은 2MB 이하이며 가로·세로 각 8,000px, 전체 1,200만 픽셀 이하다. 파일의 바이너리 헤더와 브라우저 해독을 확인한다. 확장자만 바꾼 HTML·SVG, 손상되거나 너무 큰 이미지는 저장하지 않는다. 원본 바이트를 보존하며 비율을 유지해 전체 이미지를 보여준다. 페이지를 빠르게 바꿔도 늦게 읽힌 이전 이미지를 새 페이지에 적용하지 않는다.

이미지는 현재 브라우저의 IndexedDB `tripprint.tc-designs.v1`에 보관한다. 같은 페이지의 디자인을 바꾸면 한 행만 교체한다. 브라우저 초기화나 기기 변경 전에 ‘디자인 백업’을 내려받는다. 가져오기는 모든 페이지·설명·이미지를 먼저 확인하고 교체할 페이지 수를 안내한 뒤 한 번에 적용한다. 실패하면 기존 자료를 유지하고, 저장 실패 시 입력을 보존해 다시 시도하도록 한다. 이 백업은 TC 판정 JSON과 별도이며 프로젝트 폴더나 서버에 자동 저장하지 않는다.

참조한 [일일 보고서 사이트 규격](<../../02. 디자인/01. 화면설계/일일보고서_사이트규격.md>)에 등록·보관·오류·검수 기준을 추가했다. 공통 디자인 토큰·LINE Seed·48px 컨트롤을 유지했다. 실제 1440px·390px·320px와 글꼴 200% 캡처를 대조해 등록 창·확대 보기·긴 제목·빈 상태의 문서 가로 넘침이 없음을 확인했다. 이번 기능에서 앱 공통 헤더·GNB를 변경하지 않아 앱 이동 회귀는 해당하지 않는다.
